# The pack, read through the command

A project's pack is the organization's skills and documents: a repository in the SkillCDN Format, served by SkillCDN at the project's skills address, or at the organization's when the project names none. The console reads it for the agent, a private pack with the pack token the project or the workspace holds ([ADR-0028](/docs/adr/0028-the-console-reads-a-projects-pack-through-the-deployments-rest-api-with-a-pack-token-for-a-private-one.md)) and a pack on the console's own machine from its directory ([ADR-0031](/docs/adr/0031-the-console-reads-a-pack-as-the-skillcdn-command-does-and-a-local-one-from-a-directory.md)), so that an agent needs nothing but the console's token and reads what it would read over MCP. A task or the rules name a skill to load; this page says how it is found and read.

| To | Command | What comes back |
|---|---|---|
| See the pack | `console skills` | Where the pack is, at a deployment or on the console's machine, and how the read went; what a client is told of it on connect; every skill with the path of its `SKILL.md` and every document; where the console's own skills are on this machine. |
| Look into a folder | `console skills <folder>` (`.` for the root) | What it holds, as `browse_repo` lays it out for a model: its skills, its folders with the README that introduces each, its files. |
| Find by words | `console skills --search <words> [<folder>]` | What the words find, as `search_repo` does: skills first, with the files of theirs that matched, then documents, each with the sections that matched and the offset and limit that read each; in the pack's language, and by meaning too where the deployment searches by it, which the result then says; ten unless `--limit` says otherwise, up to 25, and `--cursor` continues where more matched. |
| Read a skill | `console skill <path>` | The skill whole, as `load_skill` gives it to a model: the rules of the repository from its root to the nearest manifest, the instructions, the files it includes, then its supporting files and what it refers to. `<path>` is the `SKILL.md`'s path as `console skills` lists it, or the URI the pack names it by (`skill://<host>/<owner>/<name>/<path>`). |
| Read a file of it | `console skill --file <path>` | The file whole, as `read_repo_file` does, or what a folder holds. |
| Read one section | `console skills <file>`, then `console skill --file <file> --offset <n> --limit <n>` | The file's outline, every heading with the offset and limit that read its section; then that section alone, as a search or the outline named it, with where the file continues. |

`--json` on any of them answers with what the pack answered, in the shapes of the main repository's REST API.

What is refused: `status not_found`, the pack is not served to the console, a private one with no pack token on the project or the workspace, which an owner or an administrator connects with a code a person approves (planning-the-board, or the Settings page); `status token_invalid`, the token no longer works, and an owner sets a new one; `status failed` on a file, the pack will not carry it, too large or not text. A read the pack refused prints its status and the pack's own words, and exits with `0`.

How the pack is used. Load the skill the task names before anything is made, and with none named the one whose description fits the work; follow it to the end before applying it. A host that lists skills through a connection of its own to the address loads them by their URI, which means nothing elsewhere for a pack on the console's machine; either way a skill is never fetched another way. The rules those skills share arrive with each of them, from their repository's `SKILLCDN.md`, and hold within that work beside the board's rules, which come first where they differ. What is read of a private pack is the project's: it stays in the work, and is not copied into a report, a page or a comment beyond what the work needs.
