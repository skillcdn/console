# The pack, read through the command

A project's pack is the organization's skills and documents: a repository in the SkillCDN Format, served by SkillCDN at the project's skills address, or at the organization's when the project names none. The console reads it for the agent, a private pack with the pack token the project or the workspace holds ([ADR-0028](/docs/adr/0028-the-console-reads-a-projects-pack-through-the-deployments-rest-api-with-a-pack-token-for-a-private-one.md)) and a pack on the console's own machine from its directory ([ADR-0031](/docs/adr/0031-the-console-reads-a-pack-as-the-skillcdn-command-does-and-a-local-one-from-a-directory.md)), so that an agent needs nothing but the console's token and reads what it would read over MCP. A task or the rules name a skill to load; this page says how it is found and read. A skill is found by words and then loaded: the rows below stand in that order, and the listing of the whole pack, which is long, is for looking around.

Which pack a command reads follows the directory: where a project is named (`console whoami` says which, and what named it), the project's; where none is, in a desk or in a folder a repository is about to be made in, the organization's, and the first line of the answer says so. `--project <key>` reads a project's own from anywhere.

| To | Command | What comes back |
|---|---|---|
| Find a skill, or a page, by words | `console skills --search <words> --limit <n> [<folder>]` (or `--path <folder>`) | What the words find, as `search_repo` does: skills first, with the files of theirs that matched, then documents, each with the sections that matched and the offset and limit that read each; in the pack's language, and by meaning too where the deployment searches by it, which the result then says; ten unless `--limit` says otherwise, up to 25, and where more matched the last line is the command that reads the next page. A hit is some hundreds of characters and the skill a task needs is among the first: a `--limit` of three to five finds it. |
| Read a skill | `console skill <path>` | The skill, as `load_skill` gives it to a model: the rules of the repository from its root to the nearest manifest, the instructions, the files it includes, then its supporting files and what it refers to. A long skill comes in parts: a part whose last line is `console skill <path> --cursor <cursor>` is not the whole skill, so run that command, and the one the next part ends with, until a part ends with `Skill context is complete: this was its last part.` Where the pack counts them, a part says how many pages of the skill follow it. The command is printed so that bash and PowerShell both run it as it is; for a path no one spelling keeps whole in both, the line says to run the command you ran again with `--cursor <cursor>`, quoted for your shell. `<path>` is the `SKILL.md`'s path as `console skills` lists it, or the skill's folder, or the URI the pack names it by (`skill://<host>/<owner>/<name>/<path>`). |
| Look into a folder | `console skills <folder>` (`.` for the root) | A page of what it holds, as `browse_repo` lays it out for a model: its skills, its folders with the README that introduces each, its files; 50 entries unless `--limit` says otherwise, and a page that ends before the folder does ends with the command that reads the next (`Next page: console skills <folder> --cursor <cursor>`). |
| Look around the pack | `console skills` | Where the pack is, at a deployment or on the console's machine, and how the read went; what a client is told of it on connect; every skill with the path of its `SKILL.md`, and how many documents stand outside the skills, which a folder (`console skills <folder>`) and a search read; where the console's own skills are on this machine. A long listing comes in pages, each ending with the command that lists the rest (`console skills --cursor <cursor>`): for getting to know a pack, never for finding one skill. |
| Read a file of it | `console skill --file <path>` | A page of the file, as `read_repo_file` does, or what a folder holds: 24,000 characters, ended at a line, unless `--limit` says otherwise, and a page that ends before the file does says the offset the next begins at, which `--offset` reads. |
| Read one section | `console skills <file>`, then `console skill --file <file> --offset <n> --limit <n>` | The file's outline, every heading with the offset and limit that read its section; then that section alone, as a search or the outline named it, with where the file continues. |
| Take a table or code whole | `console skills --rows [<folder\|file>]`, `console skills --code [<folder\|file>]`, with `--out <path>` for a file | The tables of a document, or of every document under a folder, as one CSV: a header of `path`, `heading` and every column name, then a line per row in reading order. Or the fenced code blocks as written, each under a line that says where it stands. `--heading <words>` keeps what stands under a heading, `--format json` gives the rows as an array, and `--grep <pattern>` keeps the blocks whose text matches. A document's outline says how many it has and names these commands. |
| Read a plugin's skills | `console plugin <key> skills`, `console plugin <key> skill <path>` | The same reads, of the pack a plugin ships in its package, when the rules name the plugin. |

Each read is the `skillcdn` command's own, printed by the reads that command prints with, page for page and word for word, with the reads named as these commands ([ADR-0124](/docs/adr/0124-the-commands-reads-of-a-pack-are-the-skillcdn-commands-own.md)): a skill whole where a host shows it whole and in parts where it is longer, a folder and a file a page at a time, the tables and the code blocks whole as data. `--json` on any of them answers with what the pack answered, in the shapes of the main repository's REST API.

What is refused ends the command with exit `1` and says why on standard error, so that nothing printed is ever a refusal. Of one read, the pack's own code and words, as the `skillcdn` command prints them: `skill.not_found: No skill at "<path>". Use console skills <folder> or console skills --search for its exact SKILL.md path. Available: ...` names the skills there are, and `file.not_found` says that no file is at a path; the pack answered, so the path is what to mend. Of the pack as a whole, a first line that says where it is and how it stands: `not_found`, the pack is not served to the console, a private one with no pack token on the project or the workspace, which an owner or an administrator connects with a code a person approves (planning-the-board, or the Settings page), the workspace's being the one the organization's pack is read with; `token_invalid`, the token no longer works, and an owner or an administrator sets a new one; `unavailable` or `indexing`, ask again later.

A table a task needs whole, a list of codes to build into a program, a set of definitions to generate from, is taken with `--rows` into a file and read by a program: never copied out of a section row by row.

How the pack is used. Load the skill the task names before anything is made, and with none named the one whose description fits the work, found by the words of the work (`console skills --search <words> --limit 5`), not by listing the pack; read it to its end, every part of it, before applying it. Its questions and its checkpoints are kept, on the board as off it: what it asks before it begins is asked in chat where the person is in the conversation, and written on the task; what it has a person approve is a decision ([SKILL.md](../SKILL.md), "How the person is involved"). A host that lists skills through a connection of its own to the address loads them by their URI, which means nothing elsewhere for a pack on the console's machine; either way a skill is never fetched another way. The rules those skills share arrive with each of them, from their repository's `SKILLCDN.md`, and hold within that work beside the board's rules, which come first where they differ. What is read of a private pack is the project's: it stays in the work, and is not copied into a report, a page or a comment beyond what the work needs.
