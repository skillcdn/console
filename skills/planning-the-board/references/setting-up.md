# Setting up: the commands, and the standing each needs

Which command does what, and who may. What the person may not, the console refuses (`auth.forbidden`): that step goes back to them in the account, with who may do it, never worked around.

## The project, for an administrator to make and an owner to keep

- **Made:** `console project new <key> "<name>" [--description <markdown>] [--visibility workspace|private] [--skills <address>] [--color <name>] [--symbol <text>]`, by an administrator alone, who is then its owner. Private unless `--visibility workspace` says everyone of the workspace works in it. The key is lowercase letters, digits and hyphens and does not change once made: chosen with the person, and `project.key_taken` is not guessed around. The organization's skills are the project's unless `--skills` names an address of its own.
- **Changed:** `console project edit <key> [--name "<name>"] [the same flags; none clears]`, for an owner; its mark, `console project icon <key> <file>` (a PNG, JPEG, GIF or WebP) or `--remove`.
- **Read:** `console project <key>` in full; `console projects` lists those the person may work in, with what they are in each.

## A checkout bound to its project, for whoever works in it

`console use <key>` in a repository's root writes `.skillcdn-console.json` there: the project and the console's address, never a token, and an account only when `--account` names one, which is each person's own and is not committed. Every command of the board run in that directory or below it then works in that project at that console, whichever console is the machine's default. A private repository commits the file, so that every clone is bound from its first command; a public one leaves it out (`.gitignore`), since it names the organization's console, and each person binds their own checkout once. The command prints the sentence the repository's agreement carries, which sends every agent that reads the agreement to the board ([the-sentence.md](/skills/working-the-board/references/the-sentence.md)); the project's key named beside it lets an agent hold `console whoami` against something the binding did not write. One project may hold the work of several repositories: each task then names its repository in its body, and the project's rules list them under "Where the work lives". A repository set up whole, with its agreement, its documents and its check, is the work of a skill of the organization's pack where it has one (`console skills --search "set up a repository" --limit 5`); this page gives the board's side of it.

## A plugin's board project, for an administrator

A plugin the deployment installed ([building-a-plugin](/skills/building-a-plugin/SKILL.md) writes one; the deployment installs it) does nothing until an administrator enables it, consenting to what it requires and turning on what they choose of what it can go without (`console plugin <key> capabilities` says which, and turns them on or off later), and one that puts decisions, tasks and pages on a board names its project then: `console plugin <key> enable --consent <capability>,... --board new|<key> [--projects all|<key>,...] [--set <setting>=<value>]...`, `new` making a private project from the plugin's own defaults (its key, name and description, with the icon and the colour it names for it, which `console plugin <key>` shows beforehand, with what each capability opens), `<key>` binding a project that exists; several plugins may share one. `--consent` must name every capability the manifest asks, each read as the sentence it is: what the plugin may do and reach. The project's members are listed as any project's; the plugin's own roles are granted apart, `console plugin <key> grant <role> --person <login>|--project <key>|--everyone`, and taken back with `console plugin <key> revoke <grant>`; `console plugin <key> settings --set <setting>=<value>` fills its settings, and a secret is set by a person: typed unseen at the prompt of `console plugin <key> secret <name>` in their own terminal, or on the plugin's settings page; never an argument, which a shell keeps, and never through an agent, whose transcript would keep it (a script redirects a file into the command). From then on the rules an agent reads in that project carry a section `## Plugins` that names it ([working-the-board](/skills/working-the-board/SKILL.md)), and what the plugin writes there carries its name beside the person's. `console plugin <key> disable` stops it and keeps its data. A plugin that runs with something wrong in it says so: `console plugins` lists each plugin's problems beside its state, a job that failed twice running among them with since when (`the job <name> has failed since <moment>`), and `console plugin <key>` shows each job's last run and next time; `console plugin <key> events --kind plugin.failed` says why it failed, and the problem goes when the job's next run goes well. An owner who is not an administrator enables no plugin: the step goes back to the administrator, with the command.

## The members, for an owner

`console member add <login> [--role owner|member] [--project <key>[,<key>...]]`, `console member role <login> <owner|member>`, `console member remove <login>`; `console members` lists them. In a project open to the workspace everyone is a member already: `member add <login> --role owner` lists an owner, `member role <login> member` takes the listing back, and a plain `member add` is refused (`member.open_project`).

## The categories, for an administrator

`console category new <key> "<name>" [--color <name>]`, `console category edit <key> [--name "<name>"] [--color <name>]`, `console category remove <key>`; `console categories` lists them, the same in every project. A category tasks or goals are sorted into stays until they are moved (`category.in_use`: `console task edit <number> --category <other|none>` moves one).

## The people, for an administrator

- `console person role <login> <admin|member>`: what a person is in the workspace; the board keeps at least one administrator in (`person.last_admin`).
- `console person manager <login> <manager login|none>`: whom a person reports to, the reporting line of the directory, which `console people` shows beside each person and the plugins read as a default (the approver of their leave, say) in place of a line of their own; another active person who does not report to them, directly or through others (`person.invalid_manager`), or `none`.
- `console person add <login> [--host gh|google]` lets a login in: whoever signs in with that account at that host is a person from then on; the host is read off the login (an address is Google's, anything else GitHub's) unless `--host` says. `console person remove <login>` takes a login away that nobody has signed in with yet.
- `console person deactivate <login>` takes a person out: refused on every request at once, their agents with them, kept with everything they did, and listed nowhere; `console person reactivate <login>` takes them back in. A person the organization let in, through its domain or its organization at the git host, comes and goes with it (`person.of_organization`).
- `console person title <login> "<title>"|none`: what a member does, in a line (`Release engineer`), shown under their name and printed by `console people`; every member's, a person's as an agent account's, and of an agent account its supervisors write it too.
- `console people` lists the people the person sees, by login, with what each is, and the logins let in that nobody has signed in with yet.

## An agent account, for an administrator

An agent account is an agent that is a member of its own: it signs in as itself, is assigned tasks, is asked and answers, and reports to a manager, never as an administrator. It is not the person's own agent, which acts as them with a token: ask which is meant when "add an agent" could be either.

- Before one is made, read [the account and the invitation](/skills/running-an-agent/references/the-account-and-the-invitation.md) of running-an-agent: the account it signs in with has to be there first at a git host, and no password of it is ever written in a task, a comment or a command. Its invitation, its machine, its secrets and what a supervisor tells it are that skill's.
- `console agent new <handle> [--login <login>] [--name "<name>"] [--title "<title>"] [--manager <login|me>] [--project <key>]` makes one: the handle it is called by (`@mira`), which never changes; the account it will sign in with, a login at the git host or an address at Google, made of the workspace's short name, the handle and its domain where the workspace names its identity service and `--login` is left out; its manager, the person asking when none is said; and the project it starts in, the directory's unless `--project` says. The member's row is written at once, so that tasks are assigned to it before anyone signed in with it (`--worker @mira`). The pages make one from proposals instead: Agents, "Add an agent account".
- `console agents` lists the agent accounts, `console agent <handle>` reads one. Its role, its manager and whether it is in are a member's, said with `console person`, by its login or its handle: `console person manager @mira <login>`, `console person deactivate @mira`. An agent account is never made an administrator (`person.agent_admin`), and its manager is replaced, never taken away (`person.manager_required`).

## The workspace, for an administrator

`console workspace` says its settings; `console workspace edit` changes them: `--people-visibility <everyone|shared-projects>`, who sees whom on the People page and in the pickers; `--week-start <auto|monday|sunday>`, the day the calendars begin a week on; `--time-zone <zone|none>`, an IANA name such as `Asia/Seoul`, in which the command prints moments from then on. What the organization's agents work with is named there too: `--handle <name|none>`, the organization's short name (`acme`); `--domain <domain|none>`, its mail and web domain; and `--service <role>=<kind|none>[,<parameter>=<value>]...` for each of `identity`, `git` and `messenger`, as `--service identity=google-workspace --service git=github,organization=acme --service messenger=slack,workspace=acme.slack.com`. No secret goes there. With them named, an agent account's login is put together for it: `console agent new mira` signs in as `mira@acme.example`.

## The rules, for an owner or an administrator

`console rules` prints what holds, under a first line that says which parts follow: what the project adds, then what the organization adds, then the console's rules, which always hold and which nobody edits. Where they differ the earlier part holds, and none takes back what the console's rules say never happens. `console rules write --file <path>` writes what the project adds, for an owner: what differs in the project and nothing else, in the shape of [the example](project-rules.md). With `--workspace` it writes what the organization adds, for an administrator: what it asks besides the console's rules, and nothing they say already. `none` puts what was added away. Written only when a person asked for exactly that, and never to loosen what they ask of agents: every agent reads them.

## The goals, for an owner

`console goal new "<title>" [--body <markdown>] [--state <state>] [--category <key>] [--starts <day>] [--due <day>]` sets a goal on the roadmap; `console goal edit <id> [the same flags; none clears a category or a day]` changes one; `console goals` lists them, `--search <words>` by the words of a title; `console task archive --goal <id>` puts every done or dropped task of a goal away at once.

## A private pack, for an owner or an administrator

A project whose skills are a private repository holds a SkillCDN token the console reads them with: `console project pack-token <key> --connect`, for an owner; for the organization's pack, which every project reads that names no address and holds no token of its own, `console workspace pack-token --connect`, for an administrator. The command prints a page at SkillCDN and a code, which the agent relays; the person approves there, signed in as someone who may open the repository, and the console keeps the token, shown to nobody. `--stdin` reads a token a person made by hand at SkillCDN from standard input, never an argument: one for the pack's repository, or, for a pack a deployment serves from a directory of its own and lets nobody read without a token, the one its operator made, which no code connects since nobody signs in there; `--remove` takes it away. Until a token is set, `console skills` says the pack is not served to the console.
