# ADR-0025: The command names its version on every request, and the console holds it to the range it takes

- Status: Accepted; point 3 before 1.0 is amended by [ADR-0033](0033-the-package-has-a-version-of-its-own-and-says-which-skillcdn-it-is-built-on.md): a command of the console's minor, whatever the patch
- Date: 2026-10-13

## Context

The command and the console come from one package, versioned on the core line ([ADR-0007](0007-the-package-is-published-through-trusted-publishing-and-versioned-on-the-core-line.md)): before 1.0 any release may change the contract between them, and the changelog says so in words. The package is published on every version pull request, a deployment pins a release on a cadence of its own, and a person installs the command for the machine, in a project, or runs it once from a cache. Nothing told a command that it no longer went with the console it was talking to: it met `not_found` on a route the console did not have yet, or an answer its schema no longer parsed. The console did not know its own version either (`0.0.0`, sent to the git host as its user agent), and the access log could not tell the commands apart, since the platform's `fetch` names itself `node`. Open question 6 of the architecture asked whether the REST API should be versioned, given that custom consoles are built against it.

## Decision

1. **The command names itself on every request**, in the standard place: `user-agent: skillcdn-console/<version> (cli; node <v>; <platform>)`. The product token is what HTTP has for a client's name and version, and the access log keeps it already. A request without the token, a browser's, a script's, another client's, passes as it always did: nobody but the command is held to anything.
2. **The console says its version on every answer of the API**: `console-version`, and `console-client-range`, the range of command versions it takes as npm spells one (`>=0.1.18 <0.2.0`). `GET /api/v1/me` answers both as `console`, for a console built on the package to compare itself with. The version is the package's, read from its manifest when the process starts: the image is built from a commit, and the package at that commit is what the command is held to.
3. **The common rule.** Before 1.0, a command from the console's own version on and within the console's minor: `^<console version>`, since any release may change the contract until then. From 1.0, the console's major and a minor within one of the console's, either way, whatever the patch: a minor adds, a major breaks. Within the range the console answers: a command older than it is told once that a newer one exists; one newer is warned that what the console has not got yet is refused as not found. Outside the range the console refuses with `426` and a stable code, `client.outdated` or `client.too_new`, naming both versions and the range; the command exits with `4` and prints the command that updates it where it is installed: for the machine, in the project, or run again from the cache, with the package manager that put it there.
4. **The package narrows the rule and never widens it.** `CLIENT_POLICY` in the package's `compat` module raises the floor (`atLeast`) or refuses versions outright (`refused`), for a contract that moved within what the rule allows or a release whose command is wrong; changed with a changeset that says why. A floor below the rule's, or a range wider than the rule's, is ignored: what the rule promises stays predictable for whoever installs the command. The one module holds the rule, the policy and the parsing, and the console and the command read it alike, so that the command can tell before the console refuses. An operator's own narrowing is not built; it would sit behind the same policy.
5. **Said once, where it does not get in the way.** The command notices on stderr, once a day for one pair of versions (`notices.json` beside the credentials), so that an agent's many commands do not repeat it and `--json` stays the console's JSON; `whoami` says the versions, where the command is installed and what the console takes, every time. The token keeps the version of the command that last presented it, noted with its last use, and the Agents page shows it beside each agent with whether the console still takes it.
6. **The REST API stays at `/api/v1`.** Compatibility between the console and its clients is the package's version and this rule, not a version in the path; the path's number waits for a major. This answers open question 6 for the console's own clients; a custom console built on the package compares its version with `me.console` and is not refused.

## Consequences

- Before 1.0, every deployment of a new release makes every agent's command update once. The refusal names the exact command to run, and the skill `working-the-board` tells an agent to run it and go on, or to stop and tell its person where the machine refuses.
- A command newer than the console within the minor is answered, with a warning; a new minor is not. A person who works against two consoles of different minors installs the command in each project, beside the project's `package.json`, which the notice names as the place.
- No request is added anywhere: the judgement is a few comparisons on a header already read, the command reads two headers off the answers it gets anyway, and the notice file is touched only when there is something to say.
- A console of a person's own in the browser cannot set `user-agent` and is not held to the range; a later step may let it name itself with a header of its own and show a banner from `me.console`.
- `426` is used as APIs commonly use it for a client that must upgrade, not as the HTTP specification means it for protocol upgrades; the stable code is what clients branch on, and the status keeps the refusal apart from `4xx` that mean the request itself.
- Rejected: a floor the console declares with no common rule (it would drift from the contract, and whoever installs the command could not tell what goes with what); the command asking the registry for the latest version (a request, a cache, and a version the console may not take, when the console's own version is the one that matters); a version per route (nothing says which routes a command of a version uses); a policy that widens the rule (the rule would stop meaning anything).
