# ADR-0092: The image of a release is published, and the smallest install is made from a bundle

- Status: Accepted
- Date: 2026-11-12
- Amends [ADR-0002](0002-one-image-one-database-and-the-main-repositorys-toolchain.md) and [ADR-0007](0007-the-package-is-published-through-trusted-publishing-and-versioned-on-the-core-line.md), which left every image to whoever deploys the console: the repository stopped at an image that builds, and the image had no version. Builds on ADR-0007 (publishing with no stored secret), [ADR-0034](0034-the-package-is-versioned-on-skillcdns-line-one-line-at-a-time-with-a-patch-of-its-own.md) (the one version), [ADR-0031](0031-the-console-reads-a-pack-as-the-skillcdn-command-does-and-a-local-one-from-a-directory.md) (packs from a directory) and [ADR-0049](0049-a-plugin-is-an-npm-package-installed-into-the-image-and-enabled-by-an-administrator.md) (a plugin is built into the image). The contract is [deploy/README.md](../../deploy/README.md).

## Context

Whoever wanted to run the console cloned the repository, built the image, a toolchain and some minutes away from trying it, and wrote the settings by hand. A network that reaches nothing outside had a paragraph of the deploy guide: save the images where they were built, load them inside, pack the command. Nothing checked what arrived, and the command packed that way does not install there, since npm asks a registry for what the package depends on.

ADR-0002 kept publishing out of the repository because the pipeline that pushes an image belongs to one deployment's accounts. That holds for a deployment's own registry. It does not hold for the image everyone may run, which is given where the package is: beside the repository, by the workflow that publishes the package. The main repository publishes the image of each release from its 0.5.0 and installs from a bundle, and an organization that runs SkillCDN inside a closed network runs its console beside it.

## Decision

1. **The release workflow publishes the image of each release.** Once the package of a release is published, the same workflow builds the image from the same commit and pushes it to the container registry of the repository's own host, as `ghcr.io/skillcdn/console:<version>` and `latest`, for `linux/amd64` and `linux/arm64`, with the build's provenance and a list of what it contains attached. It signs in with the token of its own job: no stored secret, no cloud account, nothing of any deployment. A version the registry has is never built again.
2. **The image's version is the package's.** A release is one commit, and its package and its image are built from it, so the command and the console of one version go together as the floors have it ([ADR-0038](0038-the-command-and-the-console-go-together-within-a-line-and-a-release-that-changes-what-passes-between-them-raises-the-floors.md)). A deployment may still pin any commit of `main` and build the image itself, as the reference deployment does.
3. **The published image is the console as this repository has it:** the default pages and no plugin. Which plugins a console runs is an organization's choice, and their code is trusted by whoever builds them in (ADR-0049), so a console with plugins, or with pages of an organization's own, stays an image that organization builds, now from the published one.
4. **`install.sh` makes the smallest install on one host.** It checks for docker and its compose plugin, writes the settings file with a database password of its own making, readable by its owner alone, brings `compose.yaml` up on the image of the release its files are of, and waits until the console is ready. It takes no secret as an argument and prints none. Signing in is registered at an identity provider by a person, so the script cannot make it: it says what to put into the settings file, and, run again with a provider there, makes the secret that signing in is sealed with and turns it on. Run again, it keeps every setting.
5. **An installation without internet is made from a bundle.** `bundle.sh`, run where there is internet, puts into one directory the images, the release's and the database's, the files an installation runs, the command for the agents' machines, and the digest of every file. `install.sh --offline` checks every file against those digests, loads the images and never pulls. Nothing of an installation's own goes into a bundle: no settings, no secret, no pack.
6. **The command travels as a cache npm installs from.** The bundle holds the package of the release with everything it depends on, as npm keeps what it fetched, and `npm install -g --offline --cache <bundle>/command @skillcdn/console@<version>` installs the command on an agent's machine from that alone, on whatever system the machine runs. Node.js is the machine's own.

## Consequences

- Trying the console is one script on a host with docker. An installation without internet is one directory carried over, the same script, and one line of npm on each agent's machine.
- The repository's host holds a public package beside the repository. Making it public is set once, by a maintainer, as the npm publisher was ([deploy](../../deploy/README.md#repository-settings-checklist)).
- The image job runs only when a release is published: its first run is the first release after this record, and what that run shows is checked then.
- CI makes a bundle from the image it built and installs from it with nothing fetched, on every change: the two scripts are exercised as the image is.
- Signing in inside a closed network still needs an identity provider that network reaches, a git host of its own or Google where it is let through. A console for a network with neither stays an open question of [the architecture](../architecture.md#open-questions).
- A deployment's own registry, accounts and pipeline stay outside this repository, as ADR-0002 says. The registry named here is where the open image is given to everyone, as the package registry is for the package.
- Rejected: an image for every commit of `main` (one deployment's cadence; whoever installs wants releases); an installer fetched from a URL and piped into a shell (the script must travel with the files it runs, above all where there is no internet); a published image with plugins in it (point 3); the command as its tarball alone (it does not install without a registry); the provider's client secret as an argument of the script (it would stay in the shell's history).
