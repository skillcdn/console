# ADR-0050: Plugin code runs in a host process of its own and reaches the console only through the capabilities it declared

- Status: Accepted
- Date: 2026-11-01

## Context

A plugin is third-party code. Code loaded into the console's own process is the console: it reads `process.env` and so every secret, opens the database, writes files, spawns processes, and a loop in it stops every request. Trusting the install path alone ([ADR-0049](0049-a-plugin-is-an-npm-package-installed-into-the-image-and-enabled-by-an-administrator.md)) would make every plugin as trusted as the console, and an administrator's consent to what a plugin may do a promise nothing enforces. The console decides every request at the edge and fails closed ([ADR-0004](0004-people-and-agents-reach-the-board-only-through-the-api-with-a-credential-of-their-own.md)), and sends requests only to configured addresses; plugins must fit that model, not loosen it.

## Decision

1. **A host process.** The `api` and `worker` roles each start one child process, the plugin host, from the console's own code, with an empty environment, no database credentials and no configuration but what the parent sends over their channel. It runs under Node's permission model: reading the plugins directory and the host's own code, writing nothing, no child processes, no addons. The `migrate` role starts one to run the plugins' upgrades and stops it.
2. **A thread per plugin.** Within the host, each plugin's server module is loaded in a worker thread of its own with a memory limit, so that one plugin's crash, loop or appetite ends that thread alone, which the host starts again fresh. The thread is hardened before the module loads: the network, process, thread and code-generation built-ins are refused, the global `fetch` and `WebSocket` are gone, `process.env` is empty. The hardening is defence in depth over the process boundary, not a sandbox of its own; a host container without egress would complete it and is left for later.
3. **Capabilities are the only hands.** Everything a plugin does to the console is a call on `ctx`, and every call is a message to the parent: records, the board, people and projects, outbound requests, secrets, other plugins, the log. The parent holds the manifest's capabilities as the administrator consented to them and refuses what was not declared. The catalogue, with what each opens and how far a malicious plugin holding it reaches, is in the specification. No capability opens: a secret or a credential in the clear, the database, files beyond the plugin's own directory, another plugin's records or secrets, answering a decision or acting in a person's place, changing people, roles, memberships or the workspace's settings, or any request a person could not make themselves.
4. **Roles are the other layer.** A plugin declares roles for people; an administrator grants them to a person, to the members of a project, or to everyone, and holds every role; a default role, where the manifest names one, is every member's. A command, query, page or widget names the roles that may use it, and the parent enforces them before the plugin's code runs; what of the console a person sees through a plugin is decided by the person's own policy, as everywhere. A token acts with its person's roles ([ADR-0021](0021-a-token-configures-as-its-person-does.md)).
5. **Bounded.** A command has thirty seconds, a query or an endpoint ten, a hook thirty, a job five minutes; a message four mebibytes; a thread the memory the deployment allows; records, versions, files and events their quotas. Past a bound the call fails, as `plugin.timeout` or `plugin.too_many`, and the console answers on.
6. **Secrets are never handed to plugin code.** A setting of type `secret` is sealed with the deployment's secret and used where the plugin names it, by the parent: in the header or the query of an outbound request, or to sign or verify a payload.
7. **Everything is on the record.** Every command is an event, `plugin.command`: who, through which agent, which plugin and command, the arguments with the secret ones hidden, the outcome, the run. Every change a plugin makes on the board is the board's own event with the plugin's key beside the person. Enabling, disabling, configuring, granting, upgrading and failing are events of their own. Reads, queries, endpoint calls and jobs that succeed are lines of the operational log, with the plugin, the person, the name, the duration and the outcome.

## Consequences

- The SDK is a message protocol: arguments and results are JSON, files travel as handles, callbacks do not travel. A plugin written to it does not change when the boundary does.
- One child process per role and a thread per plugin; a plugin's module-level state does not survive a restart, so its state lives in records.
- The host is the console's code and ships in the image; a deployment adds a directory of packages and, where it wants them, two limits.
- A malicious plugin reaches what its consented capabilities say, and every act of it is attributed and reversible on the board; sending anything out needs an outbound host the administrator consented to.
- Rejected: loading plugins in the console's process with capability objects (nothing enforces an object in Node); a container per plugin (a network boundary with its own authentication between console and plugin, and a platform concern in every deployment); the web code in the console's own document ([ADR-0054](0054-a-plugins-pages-run-in-a-sandboxed-frame-and-speak-only-to-their-plugin.md) answers it).
