# ADR-0171: The smallest install registers its GitHub App from a manifest, with one press

- Status: Accepted
- Date: 2026-11-28
- Amends point 4 of [ADR-0092](0092-the-image-of-a-release-is-published-and-the-smallest-install-is-made-from-a-bundle.md), under which signing in is registered at an identity provider by a person and the install script cannot make it, and what [ADR-0017](0017-the-reference-deployment-is-the-image-on-aws-behind-cloudflare-written-as-a-skill.md)'s skill has the person do for a GitHub App. Builds on [ADR-0005](0005-people-sign-in-through-an-identity-provider-and-membership-and-roles-are-the-consoles-own.md) (people sign in through a provider, and the console keeps no password), [ADR-0022](0022-who-is-in-is-the-consoles-own-record-and-an-administrator-keeps-it.md) (the first administrators, and an organization that says who is in), [ADR-0126](0126-an-agent-account-at-a-git-host-is-bound-to-the-hosts-account-when-it-is-added.md), point 4 (a console that names no organization), and [ADR-0015](0015-the-consoles-skills-live-in-this-repository-in-the-skillcdn-format-and-the-package-carries-them.md) (the skills, and where they are carried). The contract is [deploy/README.md](../../deploy/README.md).

## Context

A developer who wanted to try the console on their own computer got as far as a console nobody can sign in to. `install.sh` brought it up in a minute and then said what a person had to do: register an app at an identity provider by hand, a form of some ten fields at GitHub, make a client secret there, copy both into a settings file, and run the script again. The reference deployment's skill had the person fill the same form and carry two secrets into a file. An agent asked "let me try the console on this computer" found no skill for it, put a plan together from three documents, and its plan ended at signing in: no first project, no agent connected, no task worked.

GitHub registers an app from a manifest: a page posts the app's settings to GitHub, a person signed in there confirms them with one press, and GitHub hands back the app's credentials in exchange for a code. Its documentation says ([Registering a GitHub App from a manifest](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest), read 2026-11-28):

- the form is posted to `/settings/apps/new`, or to `/organizations/<organization>/settings/apps/new`, with the manifest as a JSON string in a field `manifest` and a `state` that comes back;
- of the manifest only `url` is required; `hook_attributes` is optional, and its `url` is required where it is given; `redirect_url`, `callback_urls` (ten at the most), `public`, `default_permissions`, `default_events` and `request_oauth_on_install` are as this decision uses them;
- GitHub sends the browser to `redirect_url` with a `code`, which `POST /app-manifests/<code>/conversions` exchanges, with no credential, for the app's `id`, `client_id`, `client_secret`, `pem`, `html_url` and `owner`; the three steps are done within an hour.

What it does not say: whether `redirect_url` may be an address of the loopback over plain HTTP, and whether a manifest without `hook_attributes` registers an app with no webhook. For the first, programs that register an app this way from a developer's machine, the one GitHub's own page points to among them, send the browser back to `http://localhost:<port>/...`, and GitHub's documentation of signing in lists `http://127.0.0.1` and `http://localhost` as loopback callbacks. Neither was confirmed here: the press takes a browser signed in to GitHub.

## Decision

1. **A script registers the app, and the skill deploying-a-console carries it.** `skills/deploying-a-console/scripts/github-app.mjs`, plain Node with no dependency, serves one page on the loopback (`http://127.0.0.1:11196/`), which posts the manifest to GitHub; takes GitHub's redirect at `/callback`; holds it to the `state` it made, compared in constant time; exchanges the code once; and ends. A skill's folder is the one place carried by the pack, by the package and by the image, so one file serves the install script, which runs it from the image, and the deploying skill, which runs it on the person's machine.
2. **The manifest asks for the least.** The console's origin as the homepage, `<origin>/auth/gh/callback` as the one callback, not public, no webhook (no `hook_attributes`), no event, no permission; for an organization the one permission that reads who is a member (`members: read`). The browser is sent back to `http://localhost:<port>/callback`, the form the practice above has seen work, while the page is opened at `127.0.0.1`: nothing is kept in the browser between the two, so the names need not match, and the page answers only to this machine's own names.
3. **What GitHub hands back is never printed, an argument or a chat message.** By default the script writes lines of an env file to its standard output, for a program to take, and everything meant for a person to standard error. With `--secrets <file>` it merges the secrets into the deploying skill's secrets file, readable by its owner alone, and prints only what is no secret. The private key is written only where an organization is read, since nothing else uses it.
4. **GitHub's answer is untrusted.** It is bound to 64 KiB and held to the fields that are read, each in the form it must have to stand in a settings file: a client secret of letters, digits, `_` and `-` alone, a key that is a PEM key and nothing after it. Anything else is refused whole and nothing is written. The owner, the app's name and its page are kept only in a form that reads as itself in a shell, a page and a settings file.
5. **`install.sh --github-app` makes signing in on the smallest install.** Where the settings name no provider, it runs the script in a container of the console's image, port 11196 published on the loopback alone, so the host needs docker and nothing else; reads the answer from the container's standard output into the settings file; and writes `PUBLIC_URL` (`--url`, else `http://127.0.0.1:<port>`), `AUTH_SECRET` and `ADMINS`. The first administrator is whoever registered the app, where that is a person and nobody is named; `--admins <logins>` names others. `--org <login>` registers the app under an organization and writes what reads its members; an organization names no person, so `--admins` is then required before anything is registered. `--github-url <origin>` names a GitHub Enterprise Server. An installation that names a provider keeps it: run again, the script registers nothing.
6. **A key of several lines is one line of the settings file:** in double quotes, its line breaks written as `\n`, which is how compose reads an env file.
7. **A skill, `trying-a-console`, takes a trial from one sentence to a first task worked to its end, on one machine:** the release fetched by its tag, the script, the one press, the first administrator's sign-in, the command connected for the person's own agent, a first project, one task taken, reported on, asked about, handed in and finished, and how it is all taken down. `docs/start.md` sends "let me try the console" there, and the deploying skill points to it for one machine.
8. **A trial needs no organization and no domain.** A console that names no organization lets in whoever its administrators list, an agent account by its login alone until its first sign-in (ADR-0126, point 4): on a trial the first agent account signs in with any GitHub account of its own.

## Consequences

- **A trial is two runs of one script and one press**, and the settings file is never opened by hand. The reference deployment's GitHub App is the same press, with the secrets written to the secrets file by the script.
- **An app stays at GitHub after a trial**, among its owner's GitHub Apps, until it is deleted there. The script prints its page, and the skill says to delete it.
- **Whoever registers an app of their own is the console's first administrator.** That is who ran the install, on their own machine; a console for others names its administrators.
- **Port 11196 of the host has to be free** while the press is waited for, ten minutes at the most.
- **The image has to carry the script.** The script of a release runs the image of that release, which does; an image named with `--image` that does not is refused with what to do.
- **`install.sh` takes a few more options**, and still no secret as an argument: ADR-0092's point stands that a provider's client secret is never typed into it.
- **Seen against a stand-in, not against GitHub.** On 2026-11-28 the script was run from the image by `install.sh --github-app` on Windows under Git Bash, against a stand-in for GitHub that played the app's creation, the exchange and one sign-in: the console came up with signing in on, the first administrator signed in, and with `--org` the console read the organization with the key that was handed over. Not seen: the press at GitHub itself, and so the two things its documentation leaves unsaid (context). Where GitHub refuses the manifest, its page says why, and the form by hand, which the deploy guide and the deploying skill keep, is the way on.
- **Rejected:**
  - a first administrator let in without a provider on a console bound to the loopback: a request that came through a proxy or a tunnel on the same machine arrives from the loopback too, and an agent account signs in through the provider, so the exception would not stay where it was put;
  - one GitHub App of the project's own that every installation signs in through: every console anyone runs would depend on that one registration;
  - the registration served by the console itself, before a provider is set: whoever reached such a console first would name its provider, and the console's settings are its environment, which a container does not write;
  - a listener in the install script's shell: none that every host has;
  - a command of `console` for it: the command is the board's client, and the host of a console need not have Node.js;
  - the installation's files carried by the npm package or attached to a release: a shallow clone of the release's tag is one command, with the documents beside the script;
  - a webhook address in the manifest to be safe: the console takes no webhook, and an address of the loopback is none GitHub can reach.
- **Not decided here:** the same press for Google, which has no such registration; a first sign-in for a network that reaches no provider, which stays an open question of [the architecture](../architecture.md#open-questions).
