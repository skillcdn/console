# ADR-0032: The package's major and minor are SkillCDN's, its patch its own, and the packages it is built on are taken at one version

- Status: Superseded by [ADR-0033](0033-the-package-has-a-version-of-its-own-and-says-which-skillcdn-it-is-built-on.md), which gives the package a version of its own and keeps the packages taken at one version
- Date: 2026-10-18
- Amends [ADR-0007](0007-the-package-is-published-through-trusted-publishing-and-versioned-on-the-core-line.md), whose points 2 and 3 followed the line of `@skillcdn/core` alone; the rest of it stands. The rule is held by `scripts/check-version-line.mjs`; what a changeset says is in [AGENTS.md](../../AGENTS.md#workflow).

## Context

ADR-0007 gave `@skillcdn/console` the major and the minor of the `@skillcdn/core` it is built on, so that whoever installs the console sees at a glance which line of SkillCDN it goes with, and made every other change a patch. `core` was then the one package the console depended on. The console now depends on five, `core`, `indexer`, `reader`, `client` and `brand`, with the `cli` that the checks run beside them, and the main repository has since given its seven published packages one version ([its ADR-0058](https://github.com/skillcdn/skillcdn/blob/main/docs/adr/0058-the-published-packages-share-one-version.md)): "SkillCDN 0.3.0" names the set; a patch of it changes nothing that exists; a minor may, and says so first in its changelog as `Breaking:`; a consumer installs every package at one version and moves them together, and the ranges between the packages refuse a mix across minors. A line that `core` alone named, and a check that read `core` alone, said nothing of the other four: the console could declare `client` 0.3 next to `brand` 0.1 and pass.

## Decision

1. **The line is SkillCDN's.** The major and the minor of `@skillcdn/console` are those of the SkillCDN version the console is built on, the one version the main repository's packages share, as the workspaces declare them; the patch is the console's own, bumped by every release on the line. `@skillcdn/console` 0.3.x is a console for SkillCDN 0.3.
2. **The packages are taken at one version.** Every `@skillcdn` package this repository depends on, in every workspace and at the root, wherever a manifest declares it, is declared at a caret range on that version (`^0.3.0`), and the lockfile resolves all of them to one version. They move together, in one change: a patch of SkillCDN with `pnpm -r update "@skillcdn/*"`, the next line with `pnpm -r update --latest "@skillcdn/*"` and the version set beside it. One is never bumped alone.
3. **The bump, read as the main repository reads it.** Within a line every release is a `patch`: it fixes and adds, and where it must change or remove something that exists, an export of the package, a shape of the REST API, a command's arguments, output or exit codes, a variable of the image's configuration, the changelog entry says so first, as `Breaking:`, since the minor is spoken for and the words are what a reader has. Adopting the next line of SkillCDN is a `minor` changeset in the same change as the bump of the packages, `Breaking:` first where the console's own surface changes with it; never a `major` while the major is 0, and the console's 1.0.0 waits for SkillCDN's. A line the console skips is out of a changeset's reach, which bumps one minor: the version is set by hand to the line's `.0` in the same change, with a `patch` changeset, and the release publishes `.1`.
4. **A surface leaves in two steps where a release can afford it:** marked `@deprecated` with what replaces it, removed in a later release with a `Breaking:` entry. Before 1.0 a surface may leave in one release, said as `Breaking:`.
5. **The rule is checked.** `pnpm check` fails when the package's line differs from the line of any `@skillcdn` package a manifest declares, or when the lockfile resolves the packages to more than one version (`scripts/check-version-line.mjs`); `0.0.0`, the version before the first release, is not asked. The package itself, `workspace:*` in the app, declares no line.

## Consequences

- The check reads every manifest and the lockfile instead of `core` in two: adding one `@skillcdn` package at the newest version with the rest left behind fails it, and the failure names the command that moves them together.
- Whoever installs `@skillcdn/console` 0.3.x has a console for SkillCDN 0.3, and reads a release's entry before taking it where it starts with `Breaking:`; the command and the console keep to one minor between them, as [ADR-0025](0025-the-command-names-its-version-on-every-request-and-the-console-holds-it-to-the-range-it-takes.md) holds them.
- The console takes a new line of SkillCDN deliberately, by its version, never at once ([the main repository's ADR-0047](https://github.com/skillcdn/skillcdn/blob/main/docs/adr/0047-the-console-is-a-separate-repository-built-on-the-published-packages.md)); a patch of SkillCDN is taken with the lockfile and nothing else.
- Rejected: a version of the console's own, with the line in the changelog alone (what ADR-0007 rejected, for the reason that stands: a custom console would learn too late that it and its deployment disagree); a `minor` for a breaking change of the console's own (the minor would no longer name the line); the catalog of `pnpm-workspace.yaml` for the ranges (the published manifest must carry a range the registry reads, and what replaces `catalog:` at pack time is one more thing to trust, where a check that reads the manifests and the lockfile is enough); a pinned version with no caret (a patch of SkillCDN would need a change here to be taken, and the main repository's own ranges are carets).
