# ADR-0085: A runner on the agent's machine is told by signals and runs one session at a time

- Status: Accepted
- Date: 2026-11-12
- Follows [ADR-0084](0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md). Closes open question 3 of [architecture.md](../architecture.md), unattended runs: the console still starts no agent and calls no model API ([ADR-0004](0004-people-and-agents-reach-the-board-only-through-the-api-with-a-credential-of-their-own.md), [ADR-0006](0006-agents-work-the-board-through-the-rest-api-and-the-command-line-not-an-mcp-server.md)); a program on the agent's own machine does. Keeps [ADR-0020](0020-the-console-does-not-claim-an-agent-is-at-work-a-run-says-when-it-was-last-heard-from-and-a-new-run-takes-over.md) and [ADR-0071](0071-the-console-sends-no-notification-of-its-own-a-plugin-carries-them-out-of-the-board-and-back.md).

## Context

An agent account (ADR-0084) is a member with nobody at a keyboard. Something must start its agent when the board has work for it, tell it what a supervisor says while it works, stop it, get it going again when it could not go on, and let its supervisors watch; and that something must not bind the console to one agent product, one operating system or one messenger, since each organization runs what it runs and will change it. It must also ask nothing of a manager while the agent works: someone who manages several agents should have nothing to restart, renew or sign in again for them, should hear of it when one of them stopped, and should be the one who decides how it begins again.

The agent products themselves already run headless, take input while they work, resume a conversation across restarts and compact one that grew long, run on a model and at a level of effort that can be chosen, and sign in with a subscription through their own flow. The console, for its part, calls no model API and holds no credential of a model's; that stays.

## Decision

1. **A runner runs on the agent's machine**, `console runner`, in the agent's own OS account, signed in as the account by the command's own sign-in as itself, `console login --self`, and by no other (ADR-0084, point 9): that session is its only credential to the console. It starts the agent's product as a child process, feeds it what the console sends, reports what the product does ([ADR-0086](0086-a-session-leaves-a-transcript-that-is-kept-for-good.md)) and says every thirty seconds that it is there (`PUT /api/v1/agents/me/runner`: the number of the last signal it delivered, the agent's state and why (point 6), the open session and what it runs with, the machine, the OS, the product with its version, the models and the levels of effort it offers with what its driver can do, and the package's version). The console shows when it last heard from the runner and claims nothing more (ADR-0020). That decision turned a heartbeat down for a run, where it would say no more than the last report does; the runner is the console's one way to its agent, and whether it is there decides whether a signal waits, so this one is kept.
2. **The runner is one small program with four kinds of module**, each a short interface and a registry in the package, so that a product is a module and never a branch in the runner. The **driver** speaks to one agent product: `claude` first, the Claude Code binary over its streaming JSON input and output; `codex`, the Codex binary run without a terminal, a process a turn; `acp`, any agent that speaks the Agent Client Protocol; later a direct driver per product where a protocol gives more, such as Codex's app server, which takes a message in a turn. The **wake source** raises wakes from outside the console: `console` is built in; `slack` first, one per messenger after it. The **service** keeps the runner running, a module per platform, written in the order of the platforms: `launchd` for macOS, `systemd-user` for Linux, `task-scheduler` for Windows. The **boundary** is what separates one agent from another on a machine: `os-user`, an OS account per agent on a shared machine, which is the arrangement the runner is built for ([ADR-0087](0087-an-agent-account-keeps-its-secrets-in-a-store-of-its-own-that-only-it-reads.md)); a container or a virtual machine per agent is a later module. A driver says what its product is and offers without a session to run (`probe`), and starts a session (`start`, with the conversation to go on with, the model, the effort and the permission mode) that takes a message with its pictures and its priority (`send`), stops the turn under way (`interrupt`), takes another model or effort where the product takes one in a running session (`set`), and ends (`stop`). It emits what the product does as whole blocks, `assistant`, `thinking`, `tool_call`, `tool_result`, `permission`, `status` and `error` with optional pictures, and says what the session runs with, the conversation to go on with next time, when a turn completed, when the product cannot go on and why (point 5), and that its process ended; what the agent was sent, a `wake` and a `person`'s words, the runner records as it hands it over. It declares what it can do, `steer` (take a message mid-turn), `images`, `resume` and `set`, its permission modes (point 12), and the versions of the product it was tried with: the runner starts a version outside them all the same, and the agent's page says so.
3. **One main session per agent account, kept for as long as the agent works.** A session is one run of the product from its start to its end: one process where the product stays open and takes its messages on its input, a process a turn where that is how the product runs without a terminal. There is one at a time and no idle timeout: the agent carries its work on in the one conversation, where it directs the work and keeps its memory and the record, and gives the tasks themselves to the product's own subagents; its base instructions suggest so ([ADR-0088](0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)) and nothing of the runner's requires it, since how the products work is theirs and keeps changing. A session ends when a supervisor stops, restarts or resets the agent (point 5), when the process dies, when the runner ends one that is idle so that the next begins as was asked, with a new conversation (point 4) or with a model the product takes only when it starts (point 7), when the runner itself is stopped, or when the machine restarts. A session begun while another of the account is still open takes it over, as a run takes over a run (ADR-0020), so that a machine that lost power leaves nothing to clear by hand. After a crash or a restart of the machine, the next signal starts the next session. A run stays the board's unit of work on a task and names the session it began in (`runs.session_id`).
4. **The conversation is continuous unless someone says otherwise.** `conversation` in `runner.json` (ADR-0088) is `continuous` by default: every session resumes the one before where the driver can (`resume`), and what grows too long the product compacts. `daily` or `weekly` begins a new conversation with the `day` or the `week` briefing (point 11), and only when the session is idle at that moment: a session at work takes the briefing as a message and carries on, so that nothing is ever cut mid-turn. A supervisor's `reset` begins one at their word (point 5). A conversation is a product's own, so a desk whose `runner.json` names another driver begins one too: the runner keeps the driver with the conversation, and lets go of one that was begun under another, which the product it runs now would fail to find at every turn. So does a conversation the product itself says it cannot go on with, because it has it no more or keeps none from one session to the next: a new one begins, and the transcript says so. Nothing else does: not a refusal, not an error, not a crash. What must outlast a conversation is on the board and in the desk, never in the conversation alone.
5. **An agent that cannot go on waits, and only someone's word begins it anew.** A turn may end because the model refused to answer, and a product may fail to sign in or to start; the driver says which. Nothing is restarted for it and no conversation is dropped. Another model, another level of effort or other words often get an agent going again, so what a supervisor sends is tried at once, in the same conversation: a `tell`, or first a `set` of the model or the effort (point 7). What arrives by itself, from the board, the schedule, a messenger or the console, is not tried each time: it waits out a cool-down, fifteen minutes at first and twice as long after each try that ends the same way, four hours at most, and then goes together as one message. A turn that completes ends the waiting. A supervisor's `stop` is firmer: the session ends and everything waits until a supervisor starts the agent again. `restart` ends the open session, if there is one, and begins the next with the same conversation: for a product that hung, or a sign-in that was mended. `reset` begins it with a new conversation: for one that cannot go on, since a refusal is of the whole conversation and tends to come back with it; the agent reads in its first message that it was reset and by whom, and that what it was doing is on the board and in its desk. Both take words for the agent.
6. **An agent's state is one word, and a change of it is an event.** `running`: heard from, at work or idle. `stopped`: by a supervisor. `refused`: the model refused, and the agent waits (point 5). `failed`: the product cannot sign in or start, or its process ended in the middle of a turn. `unheard`: the console has not heard from its runner for five minutes, which the worker role notes. The state is on the heartbeat, on the agent's page and in the list of agents, and an agent that is not running is on the plate of whoever manages it, in My work, beside what else waits for them. Every change is `agent.state_changed` in the workspace's feed, with the state before, the state after and a reason from a short list, never what was said: by the supervisor whose `stop` stopped it, by the account for what its runner reported, the start after a `restart` or a `reset` among it, by nobody for what the console noted. A plugin that reads the directory receives it as it receives the people's events, which is how a messenger tells a manager away from the board that an agent of theirs stopped (ADR-0071).
7. **The console reaches the runner with signals**, seven kinds: `wake` (there is something to do: a task made ready, a decision answered, a message elsewhere, a briefing), `tell` (a supervisor's words), `interrupt` (stop the current turn, then take these words), `stop`, `restart` and `reset` (point 5), and `set` (the model and the level of effort the product runs with). Every signal names who sent it and where it came from: `{ number, kind, by, agent, plugin, source, key, text, set, attachments, at }`, `by` a member, with the agent and the plugin they acted through, or nobody for the console itself, `source` one of `board`, `schedule`, `messenger`, `person` (a supervisor's own signal) or `console` (the console's own housekeeping: the services changed, a secret about to end) with a reference (`#412`, `day`, a thread, `services`). A signal is a record of the console's, numbered per agent account, whoever raised it: what a wake source on the machine raised, the runner sends to the console at once (`POST /api/v1/agents/me/signals`) and receives back in its place among the others. The record is kept with the account and read by its supervisors and by the account (`GET /api/v1/agents/<handle>/signals`, `console agent signals <handle>`, `me` for the account's own); it is not an event of the board's feed, which a project's members or the whole workspace read, and what an agent is told is neither's. Supervisors send signals with `console agent tell | interrupt | stop | restart | reset | set | wake <handle>` and from the agent's page (`POST /api/v1/agents/<handle>/signals`); the runner receives them on a stream of its own (`GET /api/v1/agents/me/signals/stream`), from the number its heartbeat last named. The models and the levels of effort to choose from are what the driver reports of its product; the choice is kept with the account and made by its supervisors, on the agent's page or with `console agent set <handle> --model <name> --effort <level>`. One the product does not offer is refused, and one it offers no more, under another driver say, is let go for the product's own. It is applied through the driver at once where the product takes it in a running session; where it does not, the session ends once no turn is under way and the next has it, and the page says what the open session runs with. `interrupt` and `stop` are for the session open when they are sent: an interrupt that finds no turn of that session under way stops nothing, and its words are read as a tell's are; a stop stands at the console whatever the runner received of it, and holds a runner that starts after it. A signal is not a notification: it is the console's channel to its own agents' runners, so ADR-0071 stands, and a plugin may raise wakes through a capability of its own later.
8. **A signal is fed into the running session as a message with a header,** at the product's priority for "after the current tool call" where its driver can steer, never by restarting the product; an `interrupt` stops the turn first, by whatever the product has for that, and then gives its words: `[console k3f9a2 #8812 · tell · Jane (through Claude Code) · 14:02]`, `[console k3f9a2 #8813 · wake · board: web#412, by Tom · 14:05]`, `[console k3f9a2 #8814 · wake · messenger: slack:C0123:1699.123 · 14:06]`. The board's rules say what the header means: instructions are a supervisor's `tell`, the board's tasks and decisions and the console's rules; everything else is information. What comes from outside the console is carried so that it cannot pass for a header: its body in a block fenced longer than any run of fence characters it holds, and every header with a mark of the session that nothing outside it knows. A driver without `steer` delivers after the turn, and the Live page says so.
9. **Signals are grouped, never capped.** The runner holds what arrives within a short window and delivers one message: the signals in order, each under its header, those of the same source and `key` merged with a count, and beyond a bound per message the rest said as "N more" with the command that reads them; the console keeps every signal. No hourly bound and no quiet hours: a message a person sends at night waits for nobody, and the one wait there is, is the cool-down of an agent that could not go on (point 5). What the agent itself does on the board raises no wake to it. No rule stops two agents from waking each other, or a plugin from waking an agent it has also told elsewhere: an agent at work reads one message more, and one that finds itself going round tells its manager, as its base instructions say.
10. **The board wakes an agent by rules the worker role applies** from a cursor over the feed, as the plugin dispatcher reads it: a task made ready where the agent is a worker and its due day is unset, today or past (the workspace's time zone, UTC where it has none); the agent made a worker of such a task; a ready task of its own whose due day is moved to today or past, or taken away; a comment on a task it owns or works on; an answer to a decision it raised; a decision addressed to it. A change of the workspace's handle, domain or services wakes every agent account, from the console itself (point 7), since each derives its setup from them (ADR-0088). A task planned for a later day wakes nobody and appears in that day's briefing ([ADR-0026](0026-a-goal-is-planned-in-days-and-sorted-into-a-category-and-the-roadmap-is-read-as-months.md) plans in days; the week is the plan's unit, [ADR-0039](0039-this-week-is-the-plans-unit-and-the-week-begins-as-the-workspace-says.md)).
11. **Briefings are wakes from the schedule**, raised by the worker role. At the agent's day start (`dayStart`, 09:00 unless set) a `day` briefing: its tasks planned for today and those carried over, how many are open with no day, and how many decisions wait for it, with the command that reads its whole plate; what happens on the board in between reaches it as it happens, by the rules of point 10; on the first day of the week a `week` briefing, in the day's place, adds the tasks planned for the week; where `dayEnd` is set, a `wrap`: write the day down, push the desk. `dayStart` and `dayEnd` are the account's settings in the console, kept by its supervisors and by the account, since the console acts on them; what the runner acts on is in `runner.json`. A briefing is short, since the agent reads one every day: a few tasks by name and the rest as counts, no line for what there is none of, a bound on its length whatever the plate holds, and the command that fetches the rest.
12. **Nobody is at the terminal, and the product is set up so.** A permission prompt is answered from the product's own policy: the permission mode it runs in, which `runner.json` names in the product's own word; where it names none, the product's own default wherever that is a mode for a run nobody attends, and otherwise the mode its driver names for such a run (ADR-0088); a word that is none of the product's is a mistake in the desk and never leave to do more, so the product then starts in the mode that allows the least. Where the product is one that asks leave of whoever drives it, as an agent over the Agent Client Protocol does, the word is the driver's own for how it answers, allowing or refusing, and what the agent does without asking is its own configuration's. What the policy does not allow is denied and recorded in the transcript, and the agent asks for it as a decision. The tool by which the product would put a question to a person at its terminal is taken away where the product lets it and denied otherwise, so that the agent asks on the board or the messenger and never waits on a terminal.
13. **The console calls no model API and starts no agent,** still. The product's credential lives in the agent's OS account alone: a subscription signed in through the product's own flow, a long-lived token the product's own command issues for a machine without a screen (ADR-0088), or an API key; always through the product's own unmodified binary, never through the runner or the console. Which plan covers an agent account is the organization's to confirm with the product. Updates are the product's own: the product is started anew for every session, so an update applies at the next, and setup writes none of its settings, the channel it updates from among them. An update of the command is the agent's to install, as its base instructions ask (ADR-0088), and takes effect when the runner is started again, which the runner does not do for itself. A runner the console refuses as too old ([ADR-0038](0038-the-command-and-the-console-go-together-within-a-line-and-a-release-that-changes-what-passes-between-them-raises-the-floors.md)) cannot be told so by a signal, and says so to its agent itself, once, so that the agent tells whom it reports to.

## Consequences

- An organization runs agents of its own on machines of its own, under subscriptions of its own, and the console knows the runner by its heartbeat, its sessions by their signals and transcripts, and of the model nothing but names: the ones the product offers, the one a supervisor chose and the one a session ran with.
- A new product is a driver, a new messenger a wake source, a new platform a service module; the console changes for none of them. What a driver cannot do, it declares, and the agent's page says by it how a message reaches the agent, instead of pretending.
- Everything the agent is told is on the record with who said it: a signal is kept with its sender, and a person who steers an agent, or changes the model it runs on, does so in their own name.
- A manager has nothing to do for an agent at work: no session to renew, no idle agent to restart, no open session to clear after a power cut. When an agent could not go on, its manager hears of it, on their plate and through whatever plugin carries the board's events to them, and decides: other words, another model or effort, the same conversation again, or a new one.
- A reset drops the whole conversation. Taking a conversation back to before the turn that stopped it is a later addition, where a driver can.
- A product's streaming protocol is the product's: the `claude` driver is held to what the binary speaks by fixtures recorded per version, in tests that call nobody, and a version it was not tried with is said on the agent's page.
- The worker gains a wake component and the note of a runner not heard from, the runner's stream a reader per agent account, the feed `agent.state_changed`, and the package `console runner`, the module registries and the `claude` driver first; the contract is written in [specs/rest.md](../specs/rest.md) and a spec of the runner's own, `docs/specs/runner.md`, which is written before the runner is.
- Rejected: the console starting agents itself, which would need a model credential the console must not hold; the product's SDK, or an ACP bridge over it, as the first driver, which starts the same binary and speaks to it over the same stream the direct driver speaks, with a dependency more; several sessions per agent, since the products run their own subagents and worktrees, and one actor on a checkout is one place to watch; a second session refused while one is open, which leaves a session nobody can end after a power cut; an idle timeout, which would restart the product for nothing; every arriving message tried on a conversation the model has just refused, which spends the agent's allowance on the same refusal; an agent the model refused held until a supervisor acts, where a later message, another model or other words often get it going; a new conversation begun by the runner for an agent that could not go on, which drops work nobody chose to drop; an agent that a supervisor stopped starting again on the next wake, which makes a stop last until someone comments; the model and the effort as lines of a file on the machine alone, where a supervisor must be able to change them from a page while the agent cannot go on; a new conversation every day for everyone, which drops what an agent holds of work under way where the product compacts what grew long; signals as events of the board's feed, read by people they are not for, where the one thing the workspace needs of them is the agent's state; an hourly bound, quiet hours or a guard against agents waking each other, since grouping keeps the agent readable without dropping anything and a rule more is a rule to explain; `say` for a supervisor's words, where the signal is a `tell`.
