# ADR-0085: A runner on the agent's machine is told by signals and runs one session at a time

- Status: Proposed
- Date: 2026-11-10
- Follows [ADR-0084](0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md). Closes open question 3 of [architecture.md](../architecture.md), unattended runs: the console still starts no agent and calls no model API ([ADR-0004](0004-people-and-agents-reach-the-board-only-through-the-api-with-a-credential-of-their-own.md), [ADR-0006](0006-agents-work-the-board-through-the-rest-api-and-the-command-line-not-an-mcp-server.md)); a program on the agent's own machine does. Keeps [ADR-0020](0020-the-console-does-not-claim-an-agent-is-at-work-a-run-says-when-it-was-last-heard-from-and-a-new-run-takes-over.md) and [ADR-0071](0071-the-console-sends-no-notification-of-its-own-a-plugin-carries-them-out-of-the-board-and-back.md).

## Context

An agent account (ADR-0084) is a member with nobody at a keyboard. Something must start its agent when the board has work for it, tell it what a supervisor says while it works, stop it, and let its supervisors watch; and that something must not bind the console to one agent product, one operating system or one messenger, since each organization runs what it runs and will change it. The agent products themselves already run headless, take input while they work, resume a conversation across restarts, and sign in with an ordinary subscription through their own flow, which their terms allow for the unmodified binary and not for a program that holds the credential in their place. The console, for its part, calls no model API and holds no credential of a model's; that stays.

## Decision

1. **A runner runs on the agent's machine**, `console runner`, inside the agent's own OS account, with the agent account's token as its only credential to the console. It starts the agent's tool as a child process, feeds it what the console sends, reports what the tool does (ADR-0086) and says every thirty seconds that it is there (`PUT /api/v1/agents/me/runner`: the machine, the OS, the tools and their versions, the package's version). The console shows when it last heard from the runner and claims nothing more, as it claims nothing of a run (ADR-0020).
2. **The runner is one small program with four kinds of module**, each a short interface and a registry in the package, so that a product is a module and never a branch in the runner: the **driver**, which speaks to one agent product (`claude`, the Claude Code binary over its streaming JSON protocol; `acp`, any agent that speaks the Agent Client Protocol; later a direct driver per product where the protocol lacks something, such as `codex-app-server`); the **wake source**, which raises wakes from outside the console (`console` is built in; `slack` first, one per messenger after it); the **service**, which keeps the runner running (`launchd`, `systemd-user`; Windows later); and the **boundary**, what separates one agent from another on a machine (`os-user`, an OS account per agent; a container or a virtual machine are ideas written down, not modules planned). A driver implements `start(resume?)`, `send(text, images, priority)`, `interrupt()` and `stop()`, emits `wake`, `person`, `assistant`, `thinking`, `tool_call`, `tool_result`, `permission`, `status` and `error` with optional attachments, and declares what it can do: `steer` (take a message mid-turn), `images`, `resume`.
3. **One session per agent account, and no idle timeout.** A session is the lifetime of one tool process; the console refuses a second active session of the same account. It ends when a supervisor stops it, when the process dies, when the runner restarts to apply an update between turns, or when the machine restarts; the next signal starts the next session, which resumes the tool's previous conversation where the driver can (`resume`), so that an update lands between sessions and nothing is lost by a restart. `console agent wake <handle> --fresh` starts one that resumes nothing. A run stays the board's unit of work on a task and names the session it ran in (`runs.session_id`).
4. **The console reaches the runner with signals**, four kinds: `wake` (there is something to do: a task made ready, a decision answered, a message elsewhere, a briefing), `tell` (a supervisor's words), `interrupt` (stop the current turn, then take these words) and `stop` (end the session). Every signal names who sent it and where it came from: `{ id, kind, by, source, key, text, attachments, at }`, `by` a member with the agent and the plugin they acted through or nobody for the console itself, `source` one of `board`, `schedule`, `messenger`, `person` (a supervisor's own words) or `console` (the console's own housekeeping: the services changed, a token about to expire) with a reference (`#412`, `day`, a thread, `services`). A signal is a record of the console's, numbered per agent account, whoever raised it: the runner reports what a wake source on the machine raised as it delivers it, so that the transcript, the Live page and `console agent signals <handle> <from>..<to>` read every signal alike. Supervisors send them with `console agent tell | interrupt | stop | wake <handle>` and from the agent's page (`POST /api/v1/agents/<handle>/signals`); the runner receives them on a stream of its own (`GET /api/v1/agents/me/signals/stream`), as the pages receive the feed. A signal is not a notification: it is the console's channel to its own agents' runners, so ADR-0071 stands, and a plugin may raise wakes through a capability of its own later.
5. **A signal is fed into the running session as a message with a header,** at the tool's "after the current tool call" priority (`next`; `interrupt` alone uses `now`), never by restarting the tool: `[console #8812 · tell · Jane (through Claude Code) · 14:02]`, `[console #8813 · wake · board: #412 ready, by Tom]`, `[slack · #ops · Tom · thread 1699.123]`, the body of anything from outside the console in a fenced data block under the header. The board's rules say what the header means: instructions are a supervisor's `tell`, the board's tasks and decisions and the console's rules; everything else is information. A driver without `steer` delivers after the turn, and the Live page says so.
6. **Signals are grouped, never capped.** The runner holds what arrives within a short window and delivers one message: grouped by source (a thread, a task, a person), the same `key` merged with a count, and beyond a bound per message the rest said as "N more" with the range to fetch; the console keeps every signal. No hourly bound and no quiet hours: a message a person sends at night waits for nobody. What the agent itself does on the board raises no wake to it.
7. **The board wakes an agent by rules the worker role applies** from a cursor over the feed, as the plugin dispatcher reads it: a task made ready where the agent is a worker and its due day is unset or today or past (the workspace's time zone); a ready task whose due day is moved to today or past; a comment on its task; an answer to a decision it raised; a decision addressed to it. A task planned for a later day wakes nobody and appears in that day's briefing ([ADR-0026](0026-a-goal-is-planned-in-days-and-sorted-into-a-category-and-the-roadmap-is-read-as-months.md) plans in days; the week is the plan's unit, [ADR-0039](0039-this-week-is-the-plans-unit-and-the-week-begins-as-the-workspace-says.md)).
8. **Briefings are wakes from the schedule.** At the agent's day start (`dayStart`, 09:00 unless set, in the workspace's time zone) a `day` briefing: its tasks planned for today, those carried over, what is new in its projects since the last briefing, the decisions waiting for it and those answered, the comments since, the goals due this week; on the first day of the week a `week` briefing adds the week's tasks and goals; where `dayEnd` is set, a `wrap`: write the day down, push the desk (ADR-0088). A briefing is bounded in size and says the counts and the commands that fetch the rest.
9. **Prompts the tool raises are answered on the machine.** A permission prompt is answered from the tool's own policy, which setup writes as the tool's settings (ADR-0088), fail closed and recorded in the transcript; what is denied the agent asks for as a decision. A question the tool asks of a person is answered with one standing text, that nobody is at this terminal and a question goes to the board or the messenger, so that the agent never waits on a terminal.
10. **The console calls no model API and starts no agent,** still: the tool's credential lives in the agent's OS account alone, as a subscription signed in through the product's own flow (the recommended way), as a long-lived token the product's own command issues for a machine without a screen (ADR-0088), or as an API key; always through the product's own binary, never through the runner or the console. Updates are the product's own: the runner runs one process per session so that an update applies at the next, and exits with a code the service restarts it on once the agent has updated the package.

## Consequences

- An organization runs agents of its own on machines of its own, under subscriptions of its own, and the console knows the runner by its heartbeat, its sessions by their signals and transcripts, and nothing of the model.
- A new product is a driver, a new messenger a wake source, a new platform a service module; the console changes for none of them. What a driver cannot do, it declares, and the pages say what is missing instead of pretending.
- Everything the agent is told is on the record with who said it: a `tell` is an event (`agent.told`, with `agent.woken`, `agent.interrupted`, `agent.stopped`, `agent.session_started` and `agent.session_ended`) and a message with a header the agent reads; a person who steers an agent does so in their own name.
- The worker gains a wake component, the runner's stream a reader per agent account, and the package `console runner`, the module registries and the `claude` driver first; the contract is written in [specs/rest.md](../specs/rest.md) and a spec of the runner's own when it is built.
- Rejected: the console starting agents itself, which would need a model credential the console must not hold; the agent product's SDK or an ACP bridge over it as the first driver, since the products' terms tie a subscription to the unmodified binary and the SDK's own transport is that binary's streaming protocol, which the direct driver speaks; several sessions per agent, since the products run their own subagents and worktrees, and one actor on a checkout is one place to watch; an idle timeout, which would restart the tool for nothing; an hourly bound or quiet hours, since grouping keeps the agent readable without dropping anything; `say` for a supervisor's words, whose event is `told`.
