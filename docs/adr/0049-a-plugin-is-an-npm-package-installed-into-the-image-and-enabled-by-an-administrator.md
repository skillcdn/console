# ADR-0049: A plugin is an npm package installed into the image and enabled by an administrator

- Status: Accepted; point 3 amended by [ADR-0060](0060-what-a-plugin-asks-is-required-or-optional-and-the-optional-are-the-administrators-to-choose.md)
- Date: 2026-11-01

## Context

The console's own features are the board: tasks, runs, decisions, documents, people. The work an organization runs with agents reaches further (leave, customers, money, the figures of a campaign), and each of those is a feature of its own, wanted by some organizations and not others, best written by whoever needs it. Building them into the console would make every console carry every feature; leaving them to custom consoles would put logic into pages, where the console keeps none ([ADR-0006](0006-agents-work-the-board-through-the-rest-api-and-the-command-line-not-an-mcp-server.md)). The console needs a unit a third party writes, an operator installs, an administrator turns on, and an agent works, under the rule the board itself follows: people decide, agents work.

Node packages are the unit everyone already has: a registry, versions, a lockfile with integrity hashes, a minimum release age, provenance, and installation from a git host without publishing. The console's image is built by its operator from a lockfile, and runs as a non-root user under a policy that runs nothing inline and loads nothing from elsewhere; a console that installed code into itself at runtime would give those up.

## Decision

1. **A plugin is one npm package.** Its manifest, `console-plugin.json` at the package root, is data read without running anything: the plugin's `key`, which identifies it everywhere (paths, tables, addresses, the command); its name, description and a note for agents per language; the major of the plugin API it was written against (`pluginApi`); its server module, its web bundle, its skills and its migrations; the capabilities it asks of the console; the roles it offers people; whether it needs a board; its settings; its menu, pages and widgets; its data version. The package's `version` is the plugin's. The contract is [`docs/specs/plugins.md`](../specs/plugins.md).
2. **Installing is building the image.** A deployment lists its plugins in a `package.json` of its own, installs them with their lockfile and no install scripts into one directory, and the console reads that directory (`PLUGINS_DIR`) at boot: a package there with a manifest is a plugin, one without is a dependency of one. A plugin that fails to load is refused with its reasons, and the console boots without it. Nothing installs, downloads or updates a plugin at runtime; the directory may as well be a mounted volume, read the same way.
3. **Enabling is an administrator's doing, at runtime.** An installed plugin does nothing until an administrator enables it, on the console's own pages or through their agent: consenting to the capabilities the manifest names, making or choosing its board project where it needs one ([ADR-0052](0052-a-plugins-board-is-a-project-made-or-chosen-when-it-is-enabled-and-what-it-puts-there-carries-its-name.md)), naming the projects it is on where it has project pages, and filling its settings. Disabling stops it and keeps its data; a plugin whose package is gone stays as what was installed, with its data, until an administrator exports and purges it. A new version that asks more than was consented to waits, disabled, for consent again.
4. **The plugin API is versioned by a major of its own**, `pluginApi`; the console names the majors it serves and refuses a plugin written against another at load. Before 1.0 the major moves whenever the contract between console and plugin breaks, with no floor between them: a plugin is rebuilt against the console it runs on.
5. **This repository ships the contract, not the plugins:** the manifest schema and the SDK (`@skillcdn/console/plugin` for the server module, `@skillcdn/console/plugin/web` for the pages), the authoring command `console-plugin` (`init`, `check`), an example plugin that is also a test fixture, the specification and a skill. Plugins live in repositories of their own, one or many to a repository as their authors choose.

## Consequences

- Installing a plugin is a release of the deployment: planned, read and started by a person, under the deployment's lockfile, release age and review. A store, when there is one, is an index that tells an administrator what exists; its "install" writes a task for the deployment's agent.
- The pages the image serves need no rebuild for a plugin: its web bundle comes in the package and is served by the console in a frame of its own ([ADR-0054](0054-a-plugins-pages-run-in-a-sandboxed-frame-and-speak-only-to-their-plugin.md)). A deployment's own pages stay as they are.
- A plugin's key must be unique in a console and may not be one of the console's own words; two packages claiming one key are both refused.
- Rejected: installing at runtime from the pages, or fetching from a registry at runtime, or a writable directory the console manages (a running console writes no code into itself, and its policy loads none from elsewhere); plugins as part of a custom console's build (their web code would run with the person's whole authority, and every deployment would compose pages); the manifest inside `package.json` (a file of its own is read and checked by the authoring command and a store alike).
