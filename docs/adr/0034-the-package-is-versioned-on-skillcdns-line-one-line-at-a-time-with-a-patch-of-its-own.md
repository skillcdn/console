# ADR-0034: The package is versioned on SkillCDN's line, one line at a time, with a patch of its own

- Status: Accepted
- Date: 2026-10-18
- Supersedes [ADR-0033](0033-the-package-has-a-version-of-its-own-and-says-which-skillcdn-it-is-built-on.md), and through it [ADR-0032](0032-the-version-is-skillcdns-with-a-patch-of-its-own-and-the-packages-are-taken-at-one-version.md), whose rule it brings back with the procedure that was missing; amends [ADR-0007](0007-the-package-is-published-through-trusted-publishing-and-versioned-on-the-core-line.md) (points 2 and 3, the version on the line of `@skillcdn/core`). [ADR-0025](0025-the-command-names-its-version-on-every-request-and-the-console-holds-it-to-the-range-it-takes.md) stands as written: the amendment of its point 3 in ADR-0033 is withdrawn. The rule is held by `scripts/check-version-line.mjs`; what a changeset says is in [AGENTS.md](../../AGENTS.md#workflow).

## Context

Three decisions in one day. ADR-0007 gave `@skillcdn/console` the major and the minor of the `@skillcdn/core` it is built on, ADR-0032 those of the one version the main repository's packages share since [its ADR-0058](https://github.com/skillcdn/skillcdn/blob/main/docs/adr/0058-the-published-packages-share-one-version.md), and ADR-0033 gave the package a version of its own, because a mirrored version seemed to need setting where changesets only bump. It does not. Changesets bump one minor, and the lines of SkillCDN come one at a time: a console that adopts every line in order moves with one `minor` changeset per line and never writes a number. A skipped line is the one case that needs a hand, and even that lands on `.0` when the hand writes the previous line's `.0` beside the `minor` changeset; the `.1` of this morning came from writing the line's own `.0` beside a `patch`.

What ADR-0033 bought, a patch that never changes what exists, cost the one thing the number was for. `@skillcdn/console` would have been the one package under `@skillcdn` numbered apart from the set the main repository now releases at one number, and a console 0.2 on SkillCDN 0.3 reads as a mistake. The packages that mirror an upstream's version are the precedent the console follows: a component library carries the major and minor of the framework it is built for, the typings packages those of the library they type, each with a patch of its own.

## Decision

1. **The version is SkillCDN's line with a patch of the console's own.** The major and the minor of `@skillcdn/console` are those of the one version of the main repository's packages the console is built on, as every manifest declares it (`^0.3.0`) and the lockfile resolves it; the patch counts the console's releases on the line. `@skillcdn/console` 0.3.x is the console for SkillCDN 0.3.
2. **Lines are adopted in order, one `minor` each.** The next line of SkillCDN is a `minor` changeset in the same change as `pnpm -r update --latest "@skillcdn/*"`, and the version pull request lands on `<line>.0`. A line the console skipped is reached in one release too: in that change the version is set to the previous line's `.0`, which is never published, beside the `minor` changeset; this is the one number ever written by hand. Within a line every release is a `patch`. Never a `major` while the major is 0.
3. **A patch is read by its entry.** Semantic versioning promises nothing of a 0.x line; that a patch changes nothing that exists is the main repository's own convention for its packages. The console's convention: the minor is SkillCDN's line, and within a line a release that changes or removes a public surface, an export, a shape of the REST API, a command's arguments, output or exit codes, a variable of the image's configuration, says so first in its entry, as `Breaking:`, and whoever installs reads the entry before taking it. From 1.0, the console's own breaking changes ride SkillCDN's majors, as those of the main repository's packages do. ADR-0025 therefore stands as written: before 1.0 a console takes a command from its own version on, within its minor, since any release may change the contract between them.
4. **The rule is checked.** `pnpm check` fails when the `@skillcdn` ranges of the manifests name more than one line, when the lockfile resolves the packages to more than one version or to another line, or when the package's line is not the manifests' line; a package one line behind is allowed while a `minor` changeset is pending (one major behind, a `major`), which is how the next line is adopted and how a skipped one is reached. `0.0.0`, the version before the first release, is not asked.
5. **The number is the data.** The API answers the console's version as before and nothing else of SkillCDN; the README says that the major and the minor are SkillCDN's. A console built on the package compares its own major and minor with the deployment it reads.

## Consequences

- The console moves with SkillCDN: every line of SkillCDN is a release of the console, in order, and the number says at a glance which deployment a console, or a command, goes with. A console that falls behind by two lines catches up in one release, through the previous line's `.0`.
- A patch of the console may change what exists, said as `Breaking:`; a deployment of any release makes every agent's command update once, as ADR-0025 has it.
- Today the manifest reads `0.2.0`, the `.0` of the line before, never published, beside two `minor` changesets, and the release is `0.3.0`.
- The check reads the manifests, the lockfile and the pending changesets, and no network.
- Rejected: a version of the console's own (ADR-0033: the one package of the scope numbered apart from the set, and a number that says nothing of the deployment it goes with); joining the main repository's fixed group (the console in the monorepo, which both repositories' ADR-0047 keep apart); a computed version written by a publisher of our own (one `minor` per line is what the tooling does already, and the hand is needed for a skipped line only).
