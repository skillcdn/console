# ADR-0084: An agent account is a member of its own, with a manager above it

- Status: Proposed
- Date: 2026-11-10
- Extends [ADR-0004](0004-people-and-agents-reach-the-board-only-through-the-api-with-a-credential-of-their-own.md), [ADR-0021](0021-a-token-configures-as-its-person-does.md) and [ADR-0056](0056-a-record-that-names-the-person-who-did-a-thing-names-the-agent-they-did-it-through.md), under which an agent is a person's own process acting as that person; and [ADR-0068](0068-a-decision-reaches-whom-it-is-addressed-to-wherever-it-is-and-a-plugins-reaches-the-managers-above-them.md), whose reporting line it relies on. The first of six decisions on agent accounts, with [ADR-0085](0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md) (the runner and the signals), [ADR-0086](0086-a-session-leaves-a-transcript-that-is-kept-for-good.md) (the transcript), [ADR-0087](0087-an-agent-account-keeps-its-secrets-in-a-store-of-its-own-that-only-it-reads.md) (the secrets), [ADR-0088](0088-an-agent-account-has-a-desk-and-is-enrolled-with-an-invitation-code.md) (the desk and the enrollment) and [ADR-0089](0089-a-workspace-names-the-services-its-agents-work-with.md) (the workspace's services).

## Context

Every agent on the board so far is a person's: it holds a token one person made, acts as that person within their roles, and is named beside them on what it does. That is right for an agent a person runs for themselves, and it is the only shape there is. An organization that wants an agent to hold work of its own, to be assigned tasks, to be asked and to answer, to keep its own memory and to be told what to do by whoever manages it, has to lend it a person's identity, and then nothing on the board tells the agent's work from the person's, a decision cannot be addressed to the agent, and the agent's permissions are whatever its lender holds.

The organization's own tools already know the shape: a service account, a bot account, a machine user is a member of the directory of its own kind, with an owner responsible for it. The board needs the same, within the model it has: one directory, one policy, one reporting line.

## Decision

1. **A member is a person or an agent account.** The directory gains a `kind`: `person`, as every member has been, or `agent`. An agent account is a row of the same table, with the same memberships, teams, roles in projects, tokens, decisions and attribution; the pages mark it with a badge, "Agent", and everything that lists people lists it among them. Its `host` is `console` and its `hostAccountId` its handle: nobody signs in as it, since nothing vouches for it elsewhere.
2. **An agent account always has a manager.** `managerId` is required for an agent account and may name a person or another agent account; a person's stays optional. The line never loops ([ADR-0068](0068-a-decision-reaches-whom-it-is-addressed-to-wherever-it-is-and-a-plugins-reaches-the-managers-above-them.md)), so every chain of agents ends at a person, who is accountable for what they manage. An agent account cannot be made or kept without one, and a manager cannot be taken away from it, only replaced.
3. **Within what it holds, it is equal to a person.** It works in the projects it is a member of, owns tasks and projects, is a worker, raises decisions and answers the decisions addressed to it, writes documents, and may manage people or agents. It cannot be a workspace administrator, so that configuring the workspace, letting people in and granting what a plugin asks stay a person's. Its own decision is addressed to its manager unless another is named, and reaches the managers above as a plugin's does (ADR-0068, point 3), since its work waits as a plugin's does.
4. **Its supervisors are the administrators and the line above it.** Whoever manages it, directly or up the reporting line, and every administrator may watch its sessions, tell it, interrupt it, stop it, configure it and seed its secrets (ADR-0085 to ADR-0087). Nobody else: an owner of a project it works in sees its runs and reports as they see anyone's, not its transcript. The rule is one function of the policy, `supervises(asker, agent)`, with its row in the table test ([ADR-0035](0035-who-may-see-whom-is-decided-by-one-policy-and-the-workspace-keeps-its-settings.md)).
5. **It acts through tokens alone.** A token of an agent account is a row of the same table under the same rules: hashed, expiring, revocable, refused when the account is deactivated ([ADR-0044](0044-a-token-of-a-person-who-is-out-is-kept-and-refused-with-the-reason-until-they-are-back-in.md)), which is how an agent account is stopped for good. It is made by the claim of an invitation code or of a connection approved "as this agent account" by an administrator (ADR-0088), never on a page of the agent's own, since it has none. A record of what it did names the account as the actor and the token's name as the agent, so that ADR-0056 holds unchanged: "Mira (agent) through Claude Code".
6. **It has a persona.** A `name` in any language and a `handle` (`[a-z0-9-]`, 2 to 39 characters, unique among the workspace's logins and never a word the addresses use, `new`, `me`, `setup`, as a project key is never `new`; what the command and the pages call it by, `@mira`), a one-line `role`, and an avatar the console draws: `avatar: { seed, parts }`, a composition of flat parts (background, head, ears or none, eyes, mouth, marks, accessory, palette) decided by the seed, rendered as SVG by the console at `GET /api/v1/people/<id>/avatar.svg` from shapes alone, cached by the hash of the parts. Lists of names per language and the palette of parts ship in the package as suggestions a deployer replaces when building a console and an administrator edits in the workspace's settings; a suggestion never restricts a choice, and `GET /api/v1/agents/proposals?count=&lang=` answers seeds with their names, handles and a description of the parts for whoever makes an agent account by command. No picture is uploaded for an agent account in this decision; no SVG from outside is ever accepted.

## Consequences

- Work is assigned to an agent as to a colleague, asked of it, and read as its own; a person who ran an agent as themselves keeps doing so, since "your agent" changes nothing.
- The policy gains one kind of member and one relation; every listing, picker and guard that read "person" reads a member, and a table test says what an agent account may not do: administer, sign in, be without a manager.
- The directory's reporting line, kept for the plugins' approvals, becomes the line of command for agents as well; a plugin that reads the directory sees agent accounts among the people and reads their `kind`.
- The schema gains `kind`, `handle`, `role`, `avatar` and the manager rule on `people`; the REST API answers `kind` on every person (read as optional, `person` when absent) and the agents' routes under `/api/v1/agents`; the command gains `console agent new | ls | show` for an administrator or a supervisor. The contract is written in [specs/rest.md](../specs/rest.md) and [specs/cli.md](../specs/cli.md) when it is built.
- Rejected: a separate table for agents, which would duplicate memberships, teams, tokens and attribution and leave every query asking twice; an agent account as a workspace administrator, which would let an agent let people in and consent to plugins; several managers or a supervising team, a second permission structure beside the one the board has; a persona uploaded as SVG, which the pages could not show safely; an agent account without a manager, which would leave nobody accountable.
