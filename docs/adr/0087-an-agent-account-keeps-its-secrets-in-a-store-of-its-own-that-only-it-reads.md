# ADR-0087: An agent account keeps its secrets in a store of its own that only it reads

- Status: Proposed
- Date: 2026-11-10
- Follows [ADR-0084](0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md). Keeps the console's sealing as a plugin's secrets have it ([ADR-0070](0070-a-secret-is-sealed-by-the-console-from-an-answer-and-goes-where-its-setting-says.md), [ADR-0075](0075-a-secret-never-comes-back-to-a-plugin-and-sealing-fails-closed.md)), and the rule that no credential of another member's ever reaches an agent ([AGENTS.md](../../AGENTS.md), rules 3 and 4).

## Context

An agent account holds accounts elsewhere as a person does: a mailbox, a git-host account, a messenger membership, perhaps a long-lived token for its model, perhaps the password of its OS account. A person keeps theirs in a password manager; an agent's would be on a machine that may be lost, or in files a tool reads and may print. Its manager should not have to hold them, since a key held by a person is a key to rotate when the person leaves and a reason to hold the person answerable for what the agent did with it.

## Decision

1. **The console keeps a secret store per agent account:** named values, sealed with the console's server-side key as the pack tokens are. A name is `[a-z0-9._-]`, up to 64 characters (`git.token`, `mail.password`, `claude.oauth_token`, `os.password`); a value up to 8 KiB; up to 200 per account. A value that ends on a known day, a product's long-lived token say, may carry that day (`expiresAt`): a month before, the console wakes the account, which asks whoever can renew it.
2. **The owner reads, writes and removes; a supervisor seeds and removes, never reads.** The account, on its own session, has `console secrets` (the names), `console secret <name>` (the value), `console secret <name> --set` and `--remove` (`GET`, `PUT`, `DELETE /api/v1/agents/me/secrets/<name>`), a value typed unseen or read from a file, never given on the command line. A supervisor (ADR-0084, point 5) has `console agent secret <handle> <name>` (`PUT /api/v1/agents/<handle>/secrets/<name>`), write-only, so that a person or an agent above can hand the account a credential it cannot make for itself; `console agent secret <handle> <name> --remove`; and `console agent secrets <handle>` for the names. Every access is on the account's record, read by its supervisors, naming the secret and never its value: set, read or removed, by whom, and whether it was seeded. It is not an event of the board's feed.
3. **The runner hands secrets to a session and takes them back.** The runner's configuration ([ADR-0088](0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)) maps names to environment variables and files; at session start the runner reads them on the account's session and writes files with mode 600 in the agent's own account, and removes them at session end. It reads every value of the store besides, to take them out of the transcript before upload ([ADR-0086](0086-a-session-leaves-a-transcript-that-is-kept-for-good.md)).
4. **Whether the agent administers its machine is its operator's choice.** The console neither grants nor asks for an administrator's rights on a machine: setup and the runner need none, and whoever prepares the OS account decides whether it may use `sudo`. Where it may, the agent installs and updates what it needs without asking, keeps the account's password in its store and uses it through an askpass helper the runner writes, so that it never stands on a command line. Where it may not, what installs in the account's own space serves, and the rest is asked of whoever administers the machine. Safety and speed are had together by giving the agent a machine of its own, real or virtual, which it administers alone: OS accounts on one shared machine separate identities, sessions and credentials, and with an administrator's rights they do not separate one agent from another. The guide says so where the operator chooses.
5. **A lost machine is recovered by signing in again.** An administrator ends the account's sessions there; on the next machine the account signs in (ADR-0088) and its secrets come back from the store. The one thing the store cannot give back is the way in to itself: the account's sign-in at the identity provider is recovered there, by the provider's administrator resetting it, as a person's is.

## Consequences

- No manager holds a key for an agent, and nobody but the provider's administrator ever resets one; a secret is on a disk only while a session runs.
- The account's session reads all its secrets, so the session is the thing to protect: it lapses when unused, a supervisor ends it at once, and every read is on a record its supervisors see. The transcript carries no value of the store, and sealing (ADR-0086) covers what slips through by another way.
- What a secret is for is the agent's business: the console seals bytes under a name and never sends them anywhere itself, unlike a plugin's secret, which the console puts into a request. Whoever holds the deployment's key and its database can open them, as they can everything the console seals.
- On a shared machine where agents administer it, one agent can reach another's session and through it the other's secrets; the organization that does not accept this gives each agent a machine, or no administrator's rights.
- Rejected: a password manager of the agent's own on the machine, which is lost with the machine and read by nobody when the agent is gone; recovery codes and keys held by the manager, which the manager must rotate and be answerable for; secrets as files in the desk repository, which a tool would print and a push would publish; supervisors reading a secret, which no record could make safe; the console deciding whether an agent may use `sudo`, which is a setting of a machine the console does not run.
