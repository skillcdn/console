# Spec: the REST API of the board

- Status: **Draft.** Version 1 serves the default UI, the `console` command ([cli.md](cli.md)), and a custom console built from `@skillcdn/console`. It changes until 1.0; the package's changelog says when.
- The schemas live in `packages/console` (`@skillcdn/console/api`); the handlers in `apps/console/src/http/rest.ts`. The integration tests parse every answer with the package's schemas, which is what the pages and the command parse with.

The API is the board as its members see it: the people, the projects, and in each project the tasks, the runs, the decisions, the documents, and everything that happened. It is the one surface of the console ([ADR-0006](../adr/0006-agents-work-the-board-through-the-rest-api-and-the-command-line-not-an-mcp-server.md)): the pages, the command and a custom console are all its clients. Every route but `GET /api/v1/me` is for whoever is signed in, or for whoever presents a token a person made; nobody is answered with a refusal, never with less. The one workspace of the deployment is implied: there is no workspace in any path until a second one exists. The board is a project's ([ADR-0008](../adr/0008-a-workspace-holds-projects-and-what-a-person-may-see-and-change-is-decided-per-project.md)): what belongs to one is under `/api/v1/projects/<key>`, and a project the asker may not see is not found, whatever is asked under it.

## Conventions

- Base path `/api/v1`; UTF-8 JSON. Absent values are `null`, never missing keys. Instants are ISO 8601 strings.
- Every answer is `cache-control: no-store`: it is one person's, or it changes.
- A request that changes something (`POST`, `PATCH`, `DELETE`) on a session must carry the session cookie **and** come from the console's own pages: the browser's `origin` header must be `PUBLIC_URL`. The cookie is `SameSite=Lax`, so another site's request does not carry it in the first place; the origin is the second fence.
- A token ([`POST /api/v1/tokens`](#get-apiv1tokens-and-post-apiv1tokens)) is presented as `Authorization: Bearer <secret>` on any route, by an agent, a script or a console of a person's own. It is then the credential: a cookie beside it is not looked at, and no origin is needed, since nothing attaches a token but whoever holds it. A token that is nothing is refused, whatever cookie travels with it. What a token does is attributed to its person, and the event names the agent: the token's name, or what the agent called itself on its run.
- The command signed in as the account itself ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md), point 9) holds a session of its own in place of a token, and presents its secret (`cns_a_...`) the same way, as `Authorization: Bearer <secret>`. It is the account: what is done with it names no agent beside the member, since the member did it. Presented as a token is, it is held to what a token may ask, and whatever is said below of a token's request holds for it; where a rule names "a session", it means a browser's. Each kind is read only where it is presented: a command's secret in a cookie is nobody, and so is a browser's token in the header.
- A token configures as its person does ([ADR-0021](../adr/0021-a-token-configures-as-its-person-does.md)): every request a session may make, a token may make, within the same roles, except the tokens themselves, the sessions and the approval of a connection, which stay a person's own doing, signed in on the console's own pages; the one thing a token does about the tokens is give itself up (`DELETE /api/v1/me/token`).
- An agent connects without anyone copying a token ([ADR-0011](../adr/0011-an-agent-connects-with-a-short-code-a-person-approves-and-the-token-is-never-shown.md)): [`POST /api/v1/connect`](#connecting-an-agent) is nobody's, the approval is a person's own doing on the console's own pages, and the claim is the command's, with the secret it was given.
- The command names its version on every request, as the product token of its `user-agent` (`skillcdn-console/0.1.18 (cli; node 24.11.0; linux)`), and every answer under `/api` says the console's version (`console-version`) and the range of command versions it takes (`console-client-range`, as npm spells one: `>=0.1.18 <0.2.0`) ([ADR-0025](../adr/0025-the-command-names-its-version-on-every-request-and-the-console-holds-it-to-the-range-it-takes.md)). Before 1.0 the range is the console's line, every patch of its major.minor, from the floor the console names where a release raised one: the oldest command whose requests and answers still fit it, raised only by a release that changed what passes between them ([ADR-0038](../adr/0038-the-command-and-the-console-go-together-within-a-line-and-a-release-that-changes-what-passes-between-them-raises-the-floors.md)); from 1.0, the console's major and a minor within one, either way. A command outside the range is refused with `426` before anything else is asked of its request, `client.outdated` or `client.too_new`, the message naming both versions and the range. The command holds the console to a floor of its own the same way, and refuses a console below it itself, as `console.outdated`, in this same form. A request that names no command, a browser's, a script's, is held to nothing.
- Request bodies are JSON, at most 256 KiB, and parsed once with the package's input schema. Text is trimmed where it is a line, bounded everywhere (`MAX_TITLE_LENGTH` and the rest of `@skillcdn/console/api`), and refused when it carries control or invisible characters. Links are `https` URLs only.
- Errors have `{ "error": { "code": "...", "message": "..." } }`. The code is stable; the message is in English, for whoever reads the API by hand or through the command. The pages never show it: they read the code in the language pack, `errors`, and a test holds every code the server can answer to having words in every pack, so that a person meets a failure in their own language ([ADR-0012](../adr/0012-the-pages-speak-the-persons-language-from-packs-that-ship-with-the-package.md)).
- The plugins' routes, under `/api/v1/plugins`, are in [plugins.md](plugins.md) with their refusals; every event carries `plugin`, the key of the plugin that caused it, or `null` for the console's own doing.

### `GET /api/v1/people?login=`

`{ "items": [person, ...], "listed": [listing, ...] }`: the people the asker may see, those in first and by login, and the logins an administrator let in that nobody has signed in with yet ([ADR-0022](../adr/0022-who-is-in-is-the-consoles-own-record-and-an-administrator-keeps-it.md)). Who sees whom is the workspace's setting, decided by the one policy of the server on every request ([ADR-0035](../adr/0035-who-may-see-whom-is-decided-by-one-policy-and-the-workspace-keeps-its-settings.md)): with `everyone`, everyone who has signed in; with `shared_projects`, a member sees the active people who are in a project they are in, themselves, the administrators, and their own reporting line, whom they report to and whoever is below them, whatever the projects say ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md)), while an administrator sees everyone whatever the setting; a project open to the workspace has everyone in it, so a member of one sees everyone. The logins let in (`listed`) and the organization's reading (`organization`) go only to whom the policy shows everyone, `[]` and `null` otherwise. With `login`, one person by their exact login, compared without regard to case, or one agent account by its handle, written with its `@` (`?login=@mira`, [ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md)), or none: whom the asker sees, and, for an owner of a project, anyone active of the workspace, so that an owner lists someone the list does not show, learning that the login is one of the workspace and nothing more; `listed` is `[]` and `organization` `null` then; an empty or overlong login is `request.invalid`. A person carries their `role` in the workspace (`admin`, who configures it, or `member`, who works in the projects they are in), their `status` (`active`, or `deactivated`: kept with everything they did, refused on every request, and offered to no picker), their `source` (what let them in at their last sign-in: `organization`, the git host's organization the deployment names; `domain`, the Workspace domain it names; or `listed`, an administrator's listing), `deactivatedAt` (or `null`) and `managerId`, the id of the person they report to, the reporting line of the directory an administrator keeps, or `null` for nobody (answered from 0.4.4 and read as optional): what a plugin that reads people takes as the default where it needs someone's manager, the approver of their leave, say, in place of a line of its own. A person also carries `language`, the language they read in: the one they chose, else the one the pages first saw them in, or `null` until then (answered from 0.4.4 and read as optional): what a plugin or an agent writes for them in ([ADR-0065](../adr/0065-a-plugin-writes-one-text-and-a-persons-language-is-kept-from-the-first-time-the-pages-see-them.md)). To an administrator, and to each person for themselves, a person carries `email`, their work email, lowercase, or `null` until known ([ADR-0069](../adr/0069-the-directory-keeps-a-work-email-read-by-an-administrator-the-person-and-a-plugin-allowed-to.md)): the address they sign in with at Google, kept at every sign-in, else what an administrator wrote; everyone else reads a person without it, here and wherever a person is named (answered from 0.4.5 and read as optional). A listing carries its `id`, the `host` (`gh`, `google`), the `login` as the administrator spelled it, and `createdAt`. `organization` is the organization at the git host whose members are in, where the deployment names one (`host`, `name`, and `syncedAt`, when the worker last read it whole, or `null` until it has), or `null`. What a picker of workers and of members is made of, the active people. A token reads it as its person does: what the command's `--worker`, `member` and `person` take a login from, through `login`.

### `PATCH /api/v1/people/<id>`

Takes `role`, `status`, `managerId`, `email`, `title`, one or more, and answers the person, with their `email`. For an administrator, signed in or through their agent's token ([ADR-0021](../adr/0021-a-token-configures-as-its-person-does.md)). `title` says what the member does, in a line up to `MAX_PERSON_TITLE_LENGTH`, or `null` for none ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md)): every member's, a person's as an agent account's; a patch that names a title alone is taken from a supervisor of an agent account too, an administrator or whoever is above it in the reporting line, who is answered the person without an `email`. It writes `person.updated` with `login`, `fields: ["title"]`, and the `handle` of an agent account. The board keeps at least one administrator in (`person.last_admin`). ### `DELETE /api/v1/me/token`

The token the request is made with gives itself up, so that it is good for nothing from now on, and the answer is `204`: what `console logout` does, so that a token forgotten on a machine does not outlive it. The one thing a token does about the tokens; with a browser's session, which has none to give, it is `request.invalid`. A command signed in as the account itself gives its session up the same way, and that session is good for nothing from then on. A token whose person is out is refused here as everywhere ([ADR-0044](../adr/0044-a-token-of-a-person-who-is-out-is-kept-and-refused-with-the-reason-until-they-are-back-in.md)): the console keeps it for when they are back in, and the command forgets it on the machine.

### `GET /api/v1/sessions`, `DELETE /api/v1/sessions/<id>` and `DELETE /api/v1/sessions/others`

Where whoever is signed in is signed in: their browsers, and any command signed in as the account itself ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md)), each a session with its `kind`, `browser` or `command`, and for a command's its `name`, what the command called itself when it signed in (`null` for a browser's, as `browser` and `platform` are `null` for a command's). For a person signed in on the console's own pages, never with a token or a command's session (`auth.session_required`), so that a credential which leaks reaches no session of its member's. `GET` answers `{ "items": [session, ...], "idleDays": 30 }`, the current session first and then the last used first: `id`, `current` (whether it is the session this request was made on), `createdAt`, `lastSeenAt` (noted at most hourly), `expiresAt` (the idle limit from the last use; `idleDays` says it in days, the deployment's `SESSION_TTL_DAYS`), `browser` and `platform` (what the browser called itself when the session began, read as families, `Chrome` on `Windows`, or `null` for either the console does not know), `address` (where the browser last came from, as the server saw it behind a trusted proxy or not, noted with the last use, or `null`), and never the cookie's token. `DELETE .../<id>` ends one of the asker's sessions and answers `204`; the current one ends with its cookie, which the answer takes away; another person's, or one already ended, is `session.not_found`. `DELETE .../others` ends every session of the asker but the one the request is made on, and answers `204`. A session not used for `SESSION_TTL_DAYS` ends on its own, which is the one policy for a session left alone.

### `GET /api/v1/people/<id>/tokens` and `DELETE /api/v1/people/<id>/tokens/<token id>`

An administrator's sight of everyone's agents ([ADR-0011](../adr/0011-an-agent-connects-with-a-short-code-a-person-approves-and-the-token-is-never-shown.md)): the live tokens of any person, as `GET /api/v1/tokens` lists one's own, and the way to take one away, from the console's own pages; `auth.forbidden` for a member, `person.not_found` for an id that is nobody's, `token.not_found` for a token that is not that person's.

### `GET /api/v1/people/<id>/work`

`{ "tasks": [{ "project", "task" }, ...], "closed": [{ "project", "task" }, ...] }`: what is on another person's plate, for whoever oversees them: an administrator, or an owner of a project the person is in (everyone of the workspace is in a project open to it; a private one holds those listed), signed in or through their agent. The open tasks the person is at work on, the sooner due first and those with no day last, and as `closed` those of them done or dropped and not yet put away, both within the projects the asker may see and no other, each with its project; the decisions are left out, since they wait for anyone. `auth.forbidden` for anyone else; `person.not_found` for an id that is nobody's. `?brief=true` leaves the tasks' bodies out, as it does on the asker's own plate.

### `GET /api/v1/pictures?src=`

A picture from elsewhere, for a page that shows one ([ADR-0048](../adr/0048-a-picture-from-elsewhere-is-read-through-the-console-from-a-public-address-and-kept-a-while.md)): the console fetches it and hands it over, so that the person's browser reaches nobody's server. `src` is the https URL that names it, up to `MAX_URL_LENGTH`, on its default port and with no credentials in it; anything else is `request.invalid`. For whoever is signed in, with a session or a token. Fetched from a public address only, the host resolved first: an address of the console's own network, the loopback, a private or a link-local range, is `picture.refused` (`403`), and so is a redirect to one. What comes back must say it is a picture (`image/*`) and be at most `MAX_FILE_BYTES`; the origin's error, its silence or anything else is `picture.unavailable` (`502`). Answered with the picture's bytes and type, an `etag` of the bytes, `cache-control: private, max-age=86400`, so that a browser keeps it a day and asks with `if-none-match` after (`304`), and the headers a file is served with, under a policy that runs nothing. The console keeps what it fetched in memory, within a bounded room, for an hour before it asks the origin again with what the origin said the picture was; keeps serving it for a day when the origin cannot be reached; and keeps a refusal five minutes, so that a dead link costs one try in a while. The pages read every picture from elsewhere through here, a person's picture from the git host included, and load nothing from elsewhere themselves.

### Connecting an agent

`POST /api/v1/connect`, `GET /api/v1/connect/<code>`, `POST /api/v1/connect/<code>/approve`, `POST /api/v1/connect/<code>/deny` and `POST /api/v1/connect/claim`: how an agent gets its token without anyone copying one ([ADR-0011](../adr/0011-an-agent-connects-with-a-short-code-a-person-approves-and-the-token-is-never-shown.md)).

`POST /api/v1/connect` is nobody's: the command sends `{ "agent" }` (what the agent calls itself and where it runs, a line up to `MAX_TOKEN_NAME_LENGTH`) and is answered `201` with `{ "code", "url", "secret", "expiresAt", "interval" }`: a code of eight characters in two groups (`ABCD-EFGH`, from an alphabet without look-alikes) for a person to approve, the console's own page for it, a secret (`cns_c_...`) the command claims with and shows nowhere, when the request expires (thirty minutes after it began), and how many seconds the command waits between claims. A deployment holds a bounded number of requests at once (`connect.too_many`), and a bounded number from one address, as the trusted proxies resolve it: at that bound the oldest request of the address not yet approved makes way for the new one, and its claim is `connect.not_found`; an address whose requests are all approved is `connect.too_many` ([ADR-0047](../adr/0047-a-connection-request-is-bounded-per-address-and-the-oldest-not-yet-approved-makes-way.md)).

`GET /api/v1/connect/<code>`, for a person signed in, answers what asks: `{ "code", "agent", "createdAt", "expiresAt", "approved", "as" }`. A code is read as a person types it: any case, with or without the hyphen. `POST .../approve`, from the console's own pages, takes what `POST /api/v1/tokens` takes (`name`, `expiresInDays`) and answers the request, approved; `POST .../deny` takes the request away and answers `204`.

`POST /api/v1/connect/claim` takes `{ "secret" }` and answers `202` with `{ "status": "pending", "expiresAt" }` while nobody approved, or `200` with `{ "status": "connected", "token", "secret" }` once: the token is made then, for the approver, as any token of theirs is, and the request goes with it, so that a second claim is `connect.not_found`. Nothing secret rests in the database meanwhile: the hash of the command's secret, and never a token.

A connection may ask to be the account itself ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md), point 9): the command sends `as: "self"` beside `agent` (`"agent"`, or nothing, is an agent's connection as above), which is how an agent account's own command signs in, and a person's where they work at it themselves. `GET /api/v1/connect/<code>` then answers `as: "self"`, and the page asks whoever is signed in whether the command is them: `POST .../approve` takes no name and no days for it, and whoever approves says "this is me". The claim answers `200` with `{ "status": "signed_in", "session", "secret" }`: a session of the command's, begun then from where the claim comes, called what the command called itself, kept for as long as it is used and ended when left unused for `SESSION_TTL_DAYS`, as a browser's is; and its secret, this once, which the command presents as a token is presented. A request that is refused because the member is out is no use of the session: it is refused with the reason, as a token is ([ADR-0044](../adr/0044-a-token-of-a-person-who-is-out-is-kept-and-refused-with-the-reason-until-they-are-back-in.md)), and works again when they are back within the days it had left; out for longer, the account signs its command in again. The session is listed among the member's own ([`GET /api/v1/sessions`](#get-apiv1sessions-delete-apiv1sessionsid-and-delete-apiv1sessionsothers)) and ended there, or by a supervisor of an agent account ([`.../sign-ins`](#get-apiv1agentshandlesign-ins-and-delete-sign-insid)).

## A project

Everything below is under `/api/v1/projects/<key>`, for whoever may see the project; what changes it needs a member (with a session from the console's own pages, or a token), what configures it an owner signed in.

### `GET /api/v1/projects/<key>` and `PATCH /api/v1/projects/<key>`

The project, as the asker sees it. A patch, for an owner, signed in or with a token, takes any of `name`, `description`, `visibility`, `skillsAddress` (`null` for the organization's), `color` and `symbol` (`null` for none), and writes a `project.updated` event naming the `fields`; what is already so writes nothing. The key does not change.

### `POST /api/v1/projects/<key>/icon`, `DELETE .../icon` and `GET .../icon`

The project's own image for its mark, in place of the symbol on the colour. `POST`, for an owner, takes a form with a part called `file`: a PNG, a JPEG, a GIF or a WebP of at most `MAX_PROJECT_ICON_BYTES`, known by its first bytes and never by what the form says of it (`project.invalid_icon`; `request.too_large`). The bytes are kept by their hash, the project is answered with its `icon`, and the board hears `project.updated` with `fields: ["icon"]`; the same image again writes nothing. `DELETE` takes the image away and answers the project. `GET`, for whoever may see the project, answers the bytes with their type, the hash as `ETag` and `Cache-Control: private, max-age=86400, immutable`, since the address the pages read it at carries the hash, or `304` to a matching `If-None-Match`; a project without an image is `project.no_icon`. The pages read it at `projectIconPath(key, icon)`, which carries the hash as a version.

### `GET /api/v1/projects/<key>/members` and `POST /api/v1/projects/<key>/members`

`{ "items": [member, ...] }`: the members of the project, by login, each a `person`, their `role` in it (`owner`, `member`), `addedAt` and `listed` ([ADR-0035](../adr/0035-who-may-see-whom-is-decided-by-one-policy-and-the-workspace-keeps-its-settings.md)). In a private project, those listed. In a project open to the workspace everyone active of it is a member, so the list is everyone: an owner where a listing says so or the person is an administrator, a member otherwise; `listed` says whether a listing holds them, and `addedAt` is the listing's day or, for a member without one, the later of the project's making and their joining. An administrator is an owner of every project, listed or not. `POST`, for an owner, takes `personId` (a person of the workspace; `member.invalid_person`) and optionally `role` (default `member`), answers `201` with the member and writes `project.member_added` with `login` and `role`. A person listed already is `member.exists`; in a project open to the workspace everyone is a member already, so a `role` of `member` is `member.open_project` and only an owner is listed.

### `PATCH /api/v1/projects/<key>/members/<person id>` and `DELETE .../members/<person id>`

For an owner, signed in or with a token. The patch takes `role` and writes `project.member_changed`; in a private project the person must be listed (`member.not_found`). In a project open to the workspace anyone active of it may be made an `owner`, which lists them, and an owner made a `member` again loses the listing and stays the member everyone is, answered with `listed: false`; an administrator owns every project whatever is asked, and nothing is written for them. The removal takes a listing away, answers `204` and writes `project.member_removed`; a person not listed is `member.not_found`, and in a project open to the workspace the person stays a member. A project may be left without an owner listed; the administrators own it then.

### `GET /api/v1/projects/<key>/tasks?state=&open=&archived=&category=&goal=&worker=&unassigned=&dueBy=&q=&limit=&offset=`

`{ "items": [task, ...], "more": boolean }`: the project's board, newest first, a page at a time: `limit` (1 to `LIST_LIMIT`, the default) and `offset` (from 0) say which page, and `more` whether there is one after it; a `limit` or an `offset` that is not a number in range is `request.invalid`. `state` keeps one state of it; `open=true` the tasks not done or dropped, `open=false` the rest; `category=<key>` those sorted into a category; `goal=<id>` those that work towards a goal; `worker=<person id>` those one person is at work on, `unassigned=true` those nobody is at work on (with `worker`, nothing); `dueBy=<day>` (`2026-10-24`) those due on that day or before it; `q=<words>` (1 to `MAX_SEARCH_LENGTH` characters) those whose title holds every word, whatever the case and in any order, and the task of that number for a number (`12`, `#12`), which is how a picker or a command finds a task by its title ([ADR-0037](../adr/0037-a-task-has-one-owner-and-any-number-of-workers-and-a-parent-or-a-goal-is-found-by-search.md)). The tasks put away ([ADR-0029](../adr/0029-a-task-done-or-dropped-is-put-away-out-of-the-board-and-open-by-its-number.md)) are left out; `archived=true` answers them alone, newest first: the archive and the board are two listings, never one. A task carries its `number` (the one people say out loud, numbered per project), `title`, `body` (Markdown, to be shown as text or rendered to elements, never as HTML), `state`, `priority`, `owner` (one person, whoever wrote it), `agent` (the agent the task was written through, or `null` when a person wrote it themselves, the owner may have changed since; [ADR-0056](../adr/0056-a-record-that-names-the-person-who-did-a-thing-names-the-agent-they-did-it-through.md); from 0.4.4, read as optional), `workers` (the people at work on it, in the order they came to it, `[]` while nobody is; [ADR-0037](../adr/0037-a-task-has-one-owner-and-any-number-of-workers-and-a-parent-or-a-goal-is-found-by-search.md)), `parentId`, `category` (its `key`, `name` and `color` as the workspace keeps it, or `null`), `goalId` (or `null`), its plan ([ADR-0019](../adr/0019-a-task-is-planned-in-days-the-board-keeps-its-moments-and-goals-and-categories-give-the-work-its-shape.md)): `startsOn` and `dueOn`, each a day (`2026-10-24`) or `null`; its moments, which the board keeps itself: `startedAt`, when it was first moved past `ready`, and `doneAt`, when it was moved to `done`, each an instant or `null`; `archivedAt`, when it was put away, an instant or `null` while it is current; `links` (`url` and `label`), `openDecisions` (how many decisions about it wait for a person), `openRuns` (how many runs on it are open: begun and not ended, which says nothing of whether an agent is still at it, [ADR-0020](../adr/0020-the-console-does-not-claim-an-agent-is-at-work-a-run-says-when-it-was-last-heard-from-and-a-new-run-takes-over.md)), `createdAt` and `updatedAt`.

### `POST /api/v1/projects/<key>/tasks`

Takes `title`, and optionally `body`, `state` (default `idea`), `priority` (default `normal`), `workerIds` (the people to be at work on it, each one who may work in the project: everyone of the workspace for a project open to it, those listed for a private one, an administrator anywhere; each once however often named, up to `MAX_WORKERS`; `task.invalid_worker`), `parentId` (a task of the project), `category` (the key of a category of the workspace, or `null`; `task.invalid_category`), `goalId` (a goal of the project, or `null`; `task.invalid_goal`), `startsOn` and `dueOn` (days; the due day not before the start, `task.invalid_dates`) and `links`. The owner is whoever writes it. Answers `201` with the task, numbered after the project's last, and writes a `task.created` event. A task written past `ready` has its `startedAt`; one written `done` has its `doneAt` too.

### `GET /api/v1/projects/<key>/tasks/<id or number>` and `PATCH .../tasks/<id>`

One task, by its id or by its number in the project (`/tasks/7`): the pages hold ids, people and their agents say numbers. A patch takes the id and names only what changes, with the same fields as a creation; a field set to `null` clears it, and `workerIds` names the workers whole, in place of those there were, only the newcomers being checked, `[]` leaving nobody on it. A change of `state` is a `task.moved` event with `from` and `to`; any other change is one `task.updated` event naming the `fields` (`workers`, `category`, `goalId`, `startsOn` and `dueOn` among them, as the input names them), and, where the change put anyone to work on it, their ids (`workersAdded`). A patch that changes nothing writes nothing and answers the task as it is. The moments follow the moves: the first move past `ready` sets `startedAt`, a move to `done` sets `doneAt`, and a move back out of `done` clears it.

### `POST .../tasks/<id>/archive`, `POST .../tasks/<id>/restore` and `POST /api/v1/projects/<key>/tasks/archive`

Putting a task away, and bringing it back ([ADR-0029](../adr/0029-a-task-done-or-dropped-is-put-away-out-of-the-board-and-open-by-its-number.md), [ADR-0030](../adr/0030-a-task-is-put-away-from-any-state.md)). A task is put away, whatever its state, by whoever may work in the project, with a session or a token, and brought back the same way: putting away is a moment the board keeps (`archivedAt`), not a state, so the task keeps its state, counts toward its goal as before, and keeps its runs, decisions, comments and events; it is out of the listings, the board and the calendar, and open at its own address by id or by number still. Each answers the task and writes `task.archived` or `task.restored` with the task's `number` and `title`; what is so already answers the task and writes nothing. `POST .../tasks/archive`, for an owner, takes `{ "goalId" }` and puts every done or dropped task of that goal away at once, one event each, answering `{ "archived": n }`, how many went; a goal with nothing to put away, or that is not the project's, is `0`. The console puts away by itself what was done or dropped and not touched for `TASK_ARCHIVE_AFTER_DAYS` ([deploy/README.md](../../deploy/README.md#environment-contract)), each with a `task.archived` event that names no actor.

### `GET .../tasks/<id or number>/comments` and `POST .../tasks/<id or number>/comments`

The discussion on a task ([ADR-0024](../adr/0024-a-task-carries-a-discussion-of-comments-with-their-files-read-as-one-thread-with-the-runs-and-the-decisions.md)): `{ "items": [comment, ...] }`, oldest first and whole, for whoever may see the project. A comment is `id`, `taskId`, `author` (a person), `agent` (what the agent the author wrote through calls itself, or `null` for a person writing themselves), `body` (Markdown), `files` (each an `id` and the `file` as a run hands one in: `name`, `size`, `contentType`, `sha256`) and `createdAt`. A comment is never rewritten or deleted: a mistake is corrected in the next one.

Writing one, for whoever may work in the project, with a session or a token, is one request, one comment, one event: as JSON, `{ "body" }` (Markdown, `MAX_BODY_LENGTH`, not blank); or as a form (`multipart/form-data`), the part `body`, which may be blank when a file comes, and a part `file` for each file put in, each checked as a file handed in is (a name without a path, not empty, `MAX_FILE_BYTES`), at most `MAX_FILES_PER_COMMENT` of them and together at most `MAX_FILE_BYTES` (`request.too_large`); the whole form is read and found good before any byte is kept. A picture among the files is placed in the text as `![words](its name)`, and the pages show it there; the rest of the files follow the text, pictures in place. Answers `201` with the comment and writes `task.commented` with the task's `number` and `title`, the first words as `excerpt` and how many `files` came. At most `MAX_COMMENTS_PER_TASK` on one task (`comment.too_many`).

### `GET /api/v1/projects/<key>/decisions?open=&task=&limit=&offset=`

`{ "items": [decision, ...], "more": boolean }`: the project's, the ones that wait first, newest first within each, a page at a time as the tasks are (`limit`, `offset`, `more`); `open=true` keeps only those that wait, `task=<id>` only those about one task. A decision carries its `question`, `body` (Markdown: the context it rests on), `options` (each an `id` and a `label`, and the `key` the raiser gave it, if any, for a program to read the answer by; the last carries `own: true` when it is the person's own answer, written instead of choosing, and the options given carry no `own`), `taskId` and `taskNumber` (or `null`), `raisedBy`, `decider` (whom it is for, [ADR-0042](../adr/0042-a-decision-is-addressed-to-a-person-its-raiser-unless-another-is-named.md): the raiser, unless another person of the project was named; the first of them where several were) and `deciders` (everyone it is addressed to, in the order named, [ADR-0057](../adr/0057-a-decision-may-be-addressed-to-several-people-and-the-first-answer-ends-it.md): each finds it among their decisions, any of them may answer, and the first answer ends it; `[decider]` where one was named; answered from 0.4.4 and read as optional), `run` (the `id` and `agent` of the run that raised it, when an agent asked, or `null`), `files` (the files put on it when it was raised, [ADR-0055](../adr/0055-a-decision-carries-the-files-put-on-it-when-it-is-raised.md): each an `id` and the `file` as a comment's is, `name`, `size`, `contentType`, `sha256`; answered from 0.4.3 and read as optional), `answer`: `null` while it waits, else the chosen `option`, a `note` or `null` (the rationale given with it), `by`, `at` and `agent` (the agent the answer came through, when the person's agent wrote it in their name, or `null` when they answered themselves; [ADR-0056](../adr/0056-a-record-that-names-the-person-who-did-a-thing-names-the-agent-they-did-it-through.md); answered from 0.4.4 and read as optional); and `outcome`, what followed, in Markdown, or `null` until someone writes it, with `outcomeBy`, `outcomeAgent` and `outcomeAt`, who wrote it, through which agent, and when (each `null` until then; from 0.4.4, read as optional). Context, rationale and outcome make the decision a record ([ADR-0009](../adr/0009-documents-are-pages-of-markdown-in-a-project-addressed-by-path-versioned-and-linked-both-ways.md)); a link in any of them to a document's path is kept both ways, so that the document says the decision refers to it.

### `POST /api/v1/projects/<key>/decisions`

Takes `question`, `options` (two to `MAX_OPTIONS`, each a `label` and optionally a `key`, a lowercase word spelled as a plugin's key is and given once, which the `decision.answered` event carries back as `optionKey`, so that a program reads the answer without comparing labels), and optionally `body`, and either `taskId` or `runId`; as JSON, or, with files put on the decision ([ADR-0055](../adr/0055-a-decision-carries-the-files-put-on-it-when-it-is-raised.md)), as a form (`multipart/form-data`) whose part `decision` says what the JSON would, with a part `file` for each file, each checked as a file handed in is, at most `MAX_FILES_PER_DECISION` of them and together at most `MAX_FILE_BYTES` (`request.too_large`); the whole form is read and found good before any byte is kept, and a picture among the files is shown where the body names it as `![words](its name)`, the rest after the body. `deciderId` names whom the decision is for ([ADR-0042](../adr/0042-a-decision-is-addressed-to-a-person-its-raiser-unless-another-is-named.md)): a person who may work in the project, as a worker of a task must (`decision.invalid_decider` otherwise), or, where a plugin raises it, anyone active of the workspace ([ADR-0068](../adr/0068-a-decision-reaches-whom-it-is-addressed-to-wherever-it-is-and-a-plugins-reaches-the-managers-above-them.md)); left out, the asker, which from a run is the person the agent works for. `deciderIds` names several in its place ([ADR-0057](../adr/0057-a-decision-may-be-addressed-to-several-people-and-the-first-answer-ends-it.md)), each once in the order given and each able to work in the project, up to `MAX_DECIDERS` (`decision.too_many_deciders` beyond it): every one of them finds the decision among their own, any of them may answer, and the first answer ends it. Anyone of the project may still answer. Options are numbered from `1`. From a run, which must be the asker's and open (`decision.invalid_run`), the decision is about the run's task, `taskId` is not looked at, and the run waits (`status: waiting`) until the answer. Answers `201` with the decision and writes a `decision.raised` event, with the `agent` when a run asked and, when files came, how many as `files`.

### `GET .../decisions/<id>?wait=` and `POST .../decisions/<id>/answer`

One decision. With `wait=<seconds>` (`0` to `600`) the request is held while the decision waits, up to the server's own bound (50 seconds), and answers the decision as it stands then: how an agent learns the answer at once, woken through the database's own channel, without asking again and again. A decision answered already, or a wait of `0`, answers at once.

The answer takes `option` (the id of one of its options) or `own` (the person's own answer, where none of the options is it: one line, up to `MAX_OPTION_LABEL_LENGTH`, as an option is worded; `request.invalid` with both or with neither), and optionally a `note`. An answer of the person's own becomes one more option of the decision, numbered after the ones given and marked `own: true`, and the one chosen, so that the answer names an option either way and every reader finds its label. A decision is answered once; the answer records who gave it, the agent it came through (`agent`: the token's name when an agent wrote it in the person's name, `null` when they answered themselves; [ADR-0056](../adr/0056-a-record-that-names-the-person-who-did-a-thing-names-the-agent-they-did-it-through.md)) and when, writes a `decision.answered` event with the label of the option (`option`) and, where the raiser gave one, its key (`optionKey`), and lets a run that waited go on (`status: running`), unless another decision of its still waits.

### `PUT /api/v1/projects/<key>/decisions/<id>/deciders`

A path that is not one, or has no page, or is in a project the asker may not see, is not found.

#### `PUT /api/v1/projects/<key>/docs/<path>`

Writes the page: takes `title`, `body` (Markdown, `MAX_DOCUMENT_LENGTH`) and optionally `baseVersion`, the version the writer started from. The first write at a path answers `201` with the page at version 1; the next ones answer `200` with the next version, each kept with who wrote it, through which agent, and when. A write that changes nothing is no version and no event. The write is refused when the page has moved on since `baseVersion` (`document.conflict`), when the page is archived (`document.archived`), and when it carries as many versions as one may (`document.too_many_versions`). Every link in the body whose destination is a document path (`guides/onboarding`, from the project's root, with or without a `#fragment`) is recorded, and the page it names, written or not yet, says so. Writes a `document.written` event with `path`, `title` and `version`.

#### `POST .../docs/<path>/archive` and `POST .../docs/<path>/restore`

Put the page away, and bring it back: archived, it is kept out of the folders and the search, readable at its path, and not written to; nothing is deleted. Each answers the page and writes `document.archived` or `document.restored`; what is already so writes nothing.

#### `GET .../docs/<path>/versions` and `GET .../docs/<path>/versions/<number>`

`{ "items": [version, ...] }`, newest first: each a `number`, the `title` as it was, the `author`, the `agent` or `null`, and `createdAt`. One version adds its `body` as it was. A page without that version is `document.version_not_found`.

#### `POST .../docs/<path>/files` and `GET .../docs/<path>/files/<id>`

A file attached to the page, sent and read back exactly as a run hands one in ([above](#post-runsidfiles-and-get-apiv1projectskeyfilesid)): the parts `file` and `label` of a form, kept under the SHA-256 of the bytes, at most `MAX_FILE_BYTES`, at most `MAX_FILES_PER_DOCUMENT` on one page (`document.too_many_files`), and none on an archived page. Answers `201` with the page and writes `document.file_attached` with the label or the file's name. The bytes are read back at the file's `id`, with the same headers and the same policy as a run's file. A picture attached is shown where the page's body names it as `![words](its name)`.

### `GET /api/v1/projects/<key>/events?after=&limit=&task=&run=&decision=&document=&goal=`

`{ "items": [event, ...], "more": boolean }`: what happened in the project after event number `after` (`0` for the beginning), oldest first, at most `limit` (default and maximum `EVENTS_PAGE_LIMIT`); `more` says whether there is more after the last item. With `latest=true`, the newest `limit` events instead, oldest first, and `more` says whether there are earlier ones: how a page shows the feed as it stands without reading it from the beginning; `after` is not looked at then. The workspace's own feed takes `latest` the same way. `task=<id>`, `run=<id>`, `decision=<id>`, `document=<id>` or `goal=<id>` keeps the events about one of them: how a page shows everything that happened to a task, a run, a decision, a document or a goal. An event carries its `id` (the number), `kind` (one of `EVENT_KINDS`), the `actor` (a person, or, for what an agent did, the person it acts for), `agent` (what the person acted through: the run's agent for what a run did, else the name of the token presented; `null` when a person acted themselves), `projectId`, `taskId`, `decisionId`, `runId`, `documentId` and `goalId` (or `null`), `data` (what a feed shows without asking for the subject: `number`, `title`, `fields`, `from`, `to`, `question`, `option`, `login`, `role`, `key`, `name`, `agent`, `status`, `label`, `excerpt`, `path`, `version`, each only when the kind has it), and `createdAt`.

### `GET /api/v1/projects/<key>/events/stream?after=`

The same events as they happen, as server-sent events: one message per event, with `id` the event's number, `event` its kind and `data` the event as JSON; a comment (`: ping`) every 25 seconds of silence. A browser that reconnects sends `Last-Event-ID`, which wins over `after`, so that nothing is missed. The stream ends when the server shuts down, and when the person may no longer read the project, which is asked again before every delivery and every heartbeat: a member taken off a private project, a person deactivated or a token revoked stops reading within a heartbeat. An `EventSource` reconnects on its own, and is answered as any request is. A person holds at most `MAX_STREAMS_PER_PERSON` streams at once, across their tabs, and a process of the console `MAX_STREAMS` for everyone: one more is `feed.too_many` (`429`, `retry-after`), which a browser's `EventSource` does not retry on its own; the page shows the board as it stands and loads it again on the next visit.

The feed is written in the same transaction as the change it records, so what a stream carries happened, and what happened is carried; every process of the deployment learns of a change through the database's own channel, so a board with several `api` replicas is one board.

## Agent accounts

An agent account is a member of its own ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md) to [ADR-0089](../adr/0089-a-workspace-names-the-services-its-agents-work-with.md)): a row of the directory with `kind: "agent"`, under the rules a person is under, and never an administrator. What passes between the command and the console for the whole of that plan moved once, at 0.5.0, before the plan was built ([ADR-0043](../adr/0043-the-rest-contract-is-held-to-a-snapshot-taken-at-the-floors.md)): what stands under "In the contract" is read by every command and console from 0.5.0 on, and every route of the plan is specified below, in the change that built it ([roadmap](../roadmap.md), milestones 41 to 43).

### In the contract

- **A person** carries `kind` (`person`, or `agent`), `handle` (an agent account's, what the pages and the command call it by, `@mira`; `null` for a person), `title` (every member's, a line that says what they do; `null` for none) and `avatarParts` (what an agent account's avatar is drawn from: `set`, the version of the set of shapes, and an index into it each for `background`, `head`, `ears`, `eyes`, `mouth`, `marks`, `accessory` and `palette`; `null` for a person, whose picture is `avatar`). Each is read as optional: a console that answers none has persons only.
- **`person.updated`**, an event of the workspace's feed: a member's title, or an agent account's name or avatar, changed. Its data: `login`, `fields`, and `handle` for an agent account.
- **`agent.state_changed`**, an event of the workspace's feed ([ADR-0085](../adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md)): how an agent account stands now. Its data: `login`, `handle`, `state` (`running`, `stopped`, `refused`, `failed` or `unheard`), `was` (the state before, `null` where none had been said) and `detail` (why, in a few words, where one was said). Its actor is the account itself, whose runner said so; the supervisor whose `stop` stopped it; or nobody, where the console noted an account it has not heard from.
- **A connection** ([Connecting an agent](#connecting-an-agent)) may ask to be the account itself: `as: "self"` beside `agent` on `POST /api/v1/connect`, `as` answered by `GET /api/v1/connect/<code>`, and a claim that answers `{ "status": "signed_in", "session", "secret" }`, the command's session in place of a token; `GET /api/v1/me` says `session`, and a session its `kind` and `name`.

### `GET /api/v1/agents` and `POST /api/v1/agents`

`GET` answers `{ "items": [<agent>, ...] }`, the agent accounts the asker may see, as the people are seen ([ADR-0035](../adr/0035-who-may-see-whom-is-decided-by-one-policy-and-the-workspace-keeps-its-settings.md)), and the ones they supervise, those in first, by handle. An agent is `{ "person", "manager", "supervised", "state", "runner" }`: the account as a member, a person object with `kind: "agent"`, its `handle`, its `title` and its `avatarParts`, and `invited: true` while nobody has signed in with it; whom it reports to, `null` where the asker may not see them; whether the asker supervises it: an administrator, or above it in the reporting line, its manager or the manager of one above them; and how it stands and what its runner last said of itself, `state` and `runner`, [as below](#the-runner-put-apiv1agentsmerunner-and-the-signals), each read as optional and `null` where there is nothing to say. Supervision is one function of the policy, and what a supervisor may do of an agent account, the routes below that say so, nobody else may: an owner of a project it works in reads its runs and reports as anyone's, and nothing more. An agent account is a member, so `GET /api/v1/people` lists it among the people too, and everything that names a person, a task's worker, a decision's decider, an event's actor, names it the same way.

`POST`, for an administrator, signed in or through their agent's token ([ADR-0021](../adr/0021-a-token-configures-as-its-person-does.md)), makes one and answers `201` with it. It takes the account the agent will sign in with, as a listing names one, `host` (one the deployment signs people in through; `agent.unknown_host` otherwise) and `login` (as the host spells one); its persona, `handle` (2 to 39 lowercase letters, digits and hyphens, a letter or a digit first and last, none of the words the addresses and the command use, `RESERVED_HANDLES`: `new`, `me`, `proposals`, `setup`, `invite`, `secret`, `secrets`, `signals`, `tell`, `interrupt`, `stop`, `restart`, `reset`, `set`, `wake`; one among the workspace's agent accounts, `agent.handle_taken`; it never changes), `name` (a line up to `MAX_PERSON_NAME_LENGTH`), `title` (optional, a line up to `MAX_PERSON_TITLE_LENGTH`), and its avatar, `avatarParts` with optionally the `avatarSeed` they were rolled from, or neither, and the console rolls the parts, from the seed where one is given; `managerId`, an active member of the workspace, a person or an agent account, whoever makes the account where none is named (`agent.invalid_manager` for anyone else, or for one who reports to the account); and `project`, the key of the project it starts in (`agent.invalid_project`), where it is listed as a member when the project lists its members. The member's row is written at once, so that work is assigned to it before anyone signed in with it, and the login is let in as a listing lets one in ([ADR-0022](../adr/0022-who-is-in-is-the-consoles-own-record-and-an-administrator-keeps-it.md)); the first sign-in with that login binds the provider's account to the row, and is the account's `person.joined`. Until then the console lets in whoever holds the login, as a listing does: at a git host, where a login goes to whoever registers it, the account has to be the organization's before it is added here, and the pages, the command and the guide say so; a Workspace makes its own addresses, and there the account may be made on the way. An account added and not used is deactivated, which takes its listing away. The name and the picture stay the console's: a sign-in writes the login as the provider spells it now, and neither the provider's name nor its picture. It writes `person.listed` with `login` and `handle`.

With the account the console makes its onboarding ([ADR-0088](../adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md), points 4 to 6): a task in the project it starts in, `Set up @<handle>`, `ready`, with the account as its worker and whoever made the account as its owner, through the agent they made it through; its body says what the agent does itself and what it cannot, to be asked for as decisions, in the words of the services the workspace names (`onboardingOf` in the package), and nothing is asked there of the account it signs in with, which comes before it. The board wakes the account with it, as with any ready task it is at work on ([runner.md](runner.md#the-boards-wakes)), and the wake waits on the account's record until a runner first connects. The answer carries `onboarding`, `{ "project", "number" }`, or `null` where the board took no task; an account read later says nothing of it.

A login a member already carries is refused, `409` `agent.login_is_member`, unless the input says `convert: true` ([ADR-0104](../adr/0104-a-member-is-made-an-agent-account-only-where-that-is-asked-for.md)): a persona's proposed login may spell a colleague's, and nobody is made an agent account by a name that happens to be theirs. With `convert`, the member is made the account, once: the member's own row becomes the account, with everything it did and the sessions and tokens it holds, and the board is told with `person.updated` (`login`, `handle`, `fields: ["kind"]`). An administrator is not made one (`agent.administrator`), and a login that is an agent account already is `agent.exists`, whatever `convert` says; `convert` asks nothing of a login nobody carries. `kind` never goes back.

What `PATCH /api/v1/people/<id>` says of a member it says of an agent account, with two refusals: `role: "admin"` is `person.agent_admin`, the one thing kept from an agent account, and `managerId: null` is `person.manager_required`, since its manager is replaced and never taken away.

### `GET /api/v1/agents/proposals?count=&lang=`

A few personas to choose from, for whoever makes an account: `{ "items": [{ "seed", "name", "handle", "avatarParts" }, ...] }`, `count` of them, 4 where none is said and 12 at most (`request.invalid` otherwise). The seed is the console's own, rolled again at each asking; the name is one of those the package ships, in the language `lang` names (a language tag), else the asker's own, else the workspace's, else English, no name twice in one answer; the handle is the name's, or the first of `mira-2`, `mira-3` and on that no agent account of the workspace has; the parts are the seed's, as the package rolls them (`rollAvatar`), so that the same seed draws the same avatar wherever the package is. For an administrator. A suggestion, edited freely: what is sent to make the account is whatever its maker settled on.

### `GET /api/v1/agents/<handle>` and `PATCH /api/v1/agents/<handle>`

`GET` answers one agent account by its handle, as `GET /api/v1/agents` answers one, with `accounts` beside: the accounts it holds elsewhere ([ADR-0089](../adr/0089-a-workspace-names-the-services-its-agents-work-with.md)), an object of what it is called at each service by the service's short name (`{ "github": "acme-mira" }`), and no secret, for whoever sees the account, so that taking it out knows what to close. `agent.not_found` for a handle that is none, or the handle of an account the asker may neither see nor supervise.

`PATCH` keeps the account's persona, for a supervisor, signed in or through their agent's token: `name`, `title` (`null` for none) and `avatarParts`, with `avatarSeed` beside the parts where they were rolled from one (`null` for parts chosen by hand); one or more, `request.invalid` with none. It answers the agent, and writes `person.updated` with `login`, `handle` and the `fields` that changed, among `name`, `title` and `avatar`; what is already so writes nothing. Whoever sees the account and does not supervise it is `auth.forbidden`. The handle never changes, and neither does what the account signs in with: its login is the provider's, as a person's is.

`PATCH` also records the accounts it holds elsewhere, `accounts`, for a supervisor and for the account itself, which keeps nothing else of itself here: a service named with a name is kept, one named with `null` is taken away, one left out stays as it is. A service is spelled as a kind is, lowercase letters, digits and hyphens; a name is a line up to `MAX_ELSEWHERE_NAME_LENGTH`; an account records up to `MAX_AGENT_ELSEWHERE` (`agent.too_many_accounts`, 409). It answers the agent with its `accounts` as they are from then on, and writes `person.updated` with `fields: ["accounts"]`, once for a request that changed any; what is already so writes nothing.

And it keeps the hours of the account's day ([ADR-0085](../adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md), point 11), for a supervisor and for the account itself: `dayStart` and `dayEnd`, each an hour and a minute as `09:00` in the workspace's time zone, or `null`, which is the usual start, `DEFAULT_DAY_START`, and a day with no end. The console sends the account its briefings by them ([runner.md](runner.md#the-boards-wakes)). An agent read by a supervisor or by itself carries `hours`, `{ "dayStart", "dayEnd" }`, the start as it is acted on; a change writes `person.updated` with the `fields` that changed, `dayStart` and `dayEnd`.

An avatar is nothing but its parts ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md), point 8; [ADR-0097](../adr/0097-an-avatar-is-a-planet-of-flat-shapes-in-two-tones-filled-as-pixels.md)): a person object carries `avatarParts`, `{ "set", "palette", "ground", "form", "material", "accent", "vein" }`, each a whole number from 0 to 255 beside the set's version, and whoever shows the picture draws it with the package (`avatarPixels`, `avatarDataUrl`, the `Avatar` component). The console serves no picture of an agent account, and takes none: `avatar` is `null` for one. `palette`, `ground`, `form`, `material` and `accent` are each a place in the set `set` names by its version, counted round the end of what the set has, so that parts a reader's set does not have still draw: `palette` among its ramps of colours, `ground` among its grounds, `form` among its bodies, `material` among what lies on a body's surface, and `accent` among what stands beside a body, `0` being nothing. The names are older than the set and say only which list each is a place in. `vein` is the seed the faint squares on the ground are strewn by. A released set never changes.

### `GET /api/v1/agents/<handle>/sign-ins` and `DELETE .../sign-ins/<id>`

Where an agent account is signed in, for its supervisors ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md), point 5): `GET` answers what [`GET /api/v1/sessions`](#get-apiv1sessions-delete-apiv1sessionsid-and-delete-apiv1sessionsothers) answers the account itself, its browsers and its commands, none of them `current`; `DELETE` ends one, which is good for nothing from the next request, and answers `204` (`session.not_found` for one that is not the account's, or ended already). On the console's own pages, by a person signed in, never with a token or a command's session (`auth.session_required`), as a member's own sessions are; `auth.forbidden` for whoever sees the account and does not supervise it. How a lost machine is dealt with: a supervisor ends the session there, and the account signs in again elsewhere.

### `GET /api/v1/me/manager`

`{ "manager": person | null, "administrators": [person, ...] }`: whom whoever asks reports to, a person or an agent account, whatever they are and whether they are still in, or `null` for nobody; and the administrators of the workspace who are in, by login, who stand in where there is nobody or the manager is out. For every member, with a session or a token. A manager is whom a member turns to first, and who is answerable for an agent account; it is no rule of the board, where a decision is addressed to whomever the asker names.

### The secret store: `/api/v1/agents/me/secrets` and `/api/v1/agents/<handle>/secrets`

An agent account keeps named secrets in the console ([ADR-0087](../adr/0087-an-agent-account-keeps-its-secrets-in-a-store-of-its-own-that-only-it-reads.md)): values sealed with the deployment's key, each for its account and its name, which the account alone reads back. A name is lowercase letters, digits, dots, hyphens and underscores, a letter or a digit first and last, up to `MAX_AGENT_SECRET_NAME_LENGTH` (`git.token`, `mail.password`); a value up to `MAX_AGENT_SECRET_BYTES` of UTF-8 (`secret.too_large`); an account keeps up to `MAX_AGENT_SECRETS` (`secret.too_many`). A secret in a listing is `{ "name", "setAt", "seeded", "expiresOn" }`: when it was set, whether a supervisor set it, and the day its value ends on, where one was said. Nothing here is an event of the board's feed, and no value is ever in a log.

**The account's own**, under `/api/v1/agents/me/secrets`. For an agent account (`agent.not_found` for a person, who has no store), on a session of its own, a browser's or its command's ([`console login --self`](#connecting-an-agent)), never with a token it made for an agent of its own (`secret.own_session`): what such an agent holds reads none of the account's secrets. `GET` answers `{ "items": [secret, ...] }`, the names, by name. `GET .../<name>` answers the secret with its `value`, and notes the reading; a value this deployment's key does not open, or one sealed for another account or name, is `secret.unreadable`, to be set again. `PUT .../<name>` takes `{ "value", "expiresOn" }`, the day optional and `null` for none, sets the secret, a new one or over the one there was, and answers it, without its value. `DELETE .../<name>` removes it and answers `204`. A change on a browser's session comes from the console's own pages.

**A supervisor's part**, under `/api/v1/agents/<handle>/secrets`, with a session or a token ([ADR-0021](../adr/0021-a-token-configures-as-its-person-does.md)); `auth.forbidden` for whoever sees the account and does not supervise it. `GET` answers the names as above. `PUT .../<name>` seeds a secret, write-only: the same body, answered without the value, the secret marked `seeded`. `DELETE .../<name>` removes one. No route of a supervisor's answers a value: `GET .../<name>` is nothing.

`GET /api/v1/agents/<handle>/secret-accesses?before=&limit=` is the account's record of its store, for its supervisors: `{ "items": [{ "id", "name", "action", "by", "agent", "seeded", "at" }, ...], "more" }`, the newest first, `limit` of them (50 where none is said, 200 at most), from before the line `before` on. A line says what was done to which secret (`set`, `read` or `removed`), by whom, through which agent where they acted with a token, and whether it was a supervisor's doing; never a value.

### The runner: `PUT /api/v1/agents/me/runner` and the signals

What passes between the console and an agent account's runner ([ADR-0085](../adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md)) is specified in [runner.md](runner.md), the bodies with it; the routes, who asks them and what they refuse are here.

**How an agent stands.** An agent object carries `state`, `{ "state", "reason", "since", "heardAt" }`: one of `running`, `stopped`, `refused`, `failed` and `unheard`; why, one of a short list of words (`started`, `resumed`, `reset`, `completed`, `stop`, `model_refused`, `sign_in`, `start`, `crashed`, `no_heartbeat`); since when; and when its runner was last heard from. It is `null` until a runner has said anything of the account, and answered to whoever sees the account. `runner` is what its runner last said of itself and what was chosen for it, `{ "delivered", "latest", "session", "machine", "runner", "product", "offers", "running", "settings" }`, answered to the account's supervisors and to the account, `null` to anyone else. The console says when it last heard and claims nothing more ([ADR-0020](../adr/0020-the-console-does-not-claim-an-agent-is-at-work-a-run-says-when-it-was-last-heard-from-and-a-new-run-takes-over.md)): a runner not heard from for five minutes is noted `unheard` by the worker, and its next heartbeat says how the agent stands again.

**The runner's own**, for an agent account (`agent.not_found` for a person) on the session of its command signed in as itself ([`console login --self`](#connecting-an-agent)); its browser, or a token it made, is `agent.own_command`, since the command's session is the runner's one credential.

- `PUT /api/v1/agents/me/runner` is the heartbeat: how the agent stands and why, the last signal delivered, the open session, the machine, the runner's version, the product and what it offers to choose from, and what the session runs with; every line bounded and read by schema (`request.invalid`), the body up to 64 KiB (`request.too_large`). It answers `{ "latest", "delivered", "settings", "state" }`: the number of the account's newest signal; the most the console was ever told was delivered, where a runner that lost its own count goes on from; the model and the effort chosen for it, `null` each for the product's own, and a choice this heartbeat's `offers` do not list, where they list any, is `null` from then on, since what is chosen is kept among what the product offers; and how the console has the agent, which is `stopped` whatever the runner says while a supervisor's `stop` stands. A state that changed is `agent.state_changed`, by the account.
- `GET /api/v1/agents/me/signals/stream?after=<number>` is a stream of server-sent events, each `signal` with a signal as its data and its number as its id, from the number after `after` on, in order, with a comment in the silences. `Last-Event-ID` is read in place of `after` where it is further on. The stream ends when the command's session does, and when the process closes. It counts among the streams the account holds (`feed.too_many`).

**The record.** `GET /api/v1/agents/<handle>/signals?before=&limit=` answers `{ "items": [signal, ...], "more" }`, the newest first, `limit` of them (50 where none is said, 200 at most), from before the number `before` on, to the account's supervisors (`auth.forbidden` for whoever sees the account and does not supervise it). `GET /api/v1/agents/me/signals` answers the same to the account itself, on a session of its own, a browser's or its command's. A signal is no event of the board's feed.

**A wake the runner raises itself.** `POST /api/v1/agents/me/signals`, for an agent account on its command's session, as the heartbeat is (`agent.own_command`, `agent.not_found`): `{ "kind": "wake", "source": "messenger", "key", "text" }`, what one of its wake sources heard on the machine ([runner.md](runner.md#wake-sources)). `key` is a line up to `MAX_SIGNAL_KEY_LENGTH` saying what it is about, a thread say; `text`, optional, is someone else's words, bounded as a signal's are. It answers `201` with the signal, recorded under the next number of the account's record, by nobody, and sent on the account's stream in its order. Nothing else is raised this way, any other `kind` or `source` being `request.invalid`: a runner tells its own agent nothing in a supervisor's name, the board's or the console's.

**Sending one.** `POST /api/v1/agents/<handle>/signals`, for a supervisor, signed in on the console's own pages or through their agent's token ([ADR-0021](../adr/0021-a-token-configures-as-its-person-does.md)), takes `{ "kind", "text", "set" }` and answers `201` with the signal, numbered next on the account's record and naming who sent it and the agent they sent it through. A `tell` or an `interrupt` carries files as a form in place of the JSON ([ADR-0095](../adr/0095-a-tell-carries-files-of-any-kind-handed-to-the-agent-in-its-desk.md)): the part `signal` with what the JSON would say, and a part `file` for each, up to `MAX_SIGNAL_ATTACHMENTS`, of any kind, each with a name that is one line and no path and not empty, within `MAX_FILE_BYTES` together (`request.too_large`); the signal's `attachments` name them, `{ "id", "name", "size", "contentType" }` each. A picture is one by its bytes, a PNG, a JPEG, a GIF or a WebP, whatever the form calls it; any other file is kept as the media type its part names, and one whose part calls it a picture while its bytes are none is kept as `application/octet-stream`. `GET /api/v1/agents/<handle>/signals/<number>/files/<id>` answers the bytes of one to the account's supervisors, and `GET /api/v1/agents/me/signals/<number>/files/<id>` to the account, whose runner hands them to the agent: a picture shown in place under its kind, any other file as `application/octet-stream` with `content-disposition: attachment` and its name, both with `nosniff` and a policy that runs nothing; `file.not_found` for an id that is not that signal's. `kind` is one of `wake`, `tell`, `interrupt`, `stop`, `restart`, `reset` and `set`; `text` is up to `MAX_SIGNAL_LENGTH` characters, which a `tell` needs and an `interrupt` takes: with none, an `interrupt` stops the turn under way so that what the agent was sent and has not taken is read now ([ADR-0098](../adr/0098-a-message-is-on-the-record-where-the-agent-took-it-and-an-interrupt-may-carry-no-words.md)); `set` is `{ "model", "effort" }` for the kind `set`, one or both, a field left out staying as it is and `null` meaning the product's own again, each one of those the runner last offered where it offered any (`signal.not_offered`). A `stop` makes the agent `stopped` at once, by whoever sent it, and it stays so until a `restart` or a `reset` is sent; a `set` is kept with the account, and its runner applies it. The account's stream is woken in every process, on a channel of the accounts' own, which wakes no reader of the board's feed.

### The sessions and the transcript

A session is the lifetime of one process of an agent account's product, and leaves a transcript that the console keeps for good ([ADR-0086](../adr/0086-a-session-leaves-a-transcript-that-is-kept-for-good.md)). The bodies and their bounds are in [runner.md](runner.md#the-transcript); the routes, who asks them and what they refuse are here. Nothing of it is an event of the board's feed.

A session is `{ "id", "month", "startedAt", "endedAt", "ended", "product", "model", "effort", "resumed", "machine", "events", "lastEventAt", "away" }`: the month it began in (`2026-11`), under which everything of it is kept; when and how it ended (`stopped`, `restarted`, `reset`, `crashed`, `exited`, or `taken_over` by a session begun after it), `null` each while it is open; what it ran, with which model and effort, whether it went on with the conversation before, and where; the number of its last event and when that came; and `away`, whether its month is not with the database now, put away by whoever keeps it.

**The runner's own**, under `/api/v1/agents/me/sessions`, for an agent account on its command's session, as the heartbeat is (`agent.own_command`, `agent.not_found`).

- `POST` begins a session and answers `201` with it. One session of an account is open at a time: the one that was open ends as `taken_over`.
- `POST .../<id>/events` takes `{ "events": [...] }`, a batch in order, and answers `{ "last" }`, the number of the session's last event now. A number the session has already changes nothing; `transcript.out_of_order` (`400`) for a batch not in order, `transcript.gap` (`409`) for one that would leave a gap, `transcript.unknown_file` (`400`) for a picture that is not the session's, `transcript.session_over` (`409`) for a session that ended, `transcript.away` (`409`) for one whose month is put away, `request.too_large` beyond 2 MiB, and `transcript.session_not_found` for a session that is not the account's.
- `POST .../<id>/files` takes a form with one part `file`, a picture (`image/png`, `image/jpeg`, `image/gif`, `image/webp`) up to `MAX_FILE_BYTES`, and answers `201` with `{ "id", "name", "size", "contentType" }`, what an event names it by; `transcript.too_fast` (`429`) beyond 60 a minute for one session.
- `POST .../<id>/end` takes `{ "how" }` and answers the session; ended already, it stays as it ended.

**Reading**, under `/api/v1/agents/<handle>/sessions`, for the account's supervisors, with a session or a token, and for the account itself, as `me` or by its handle, on a session of its own (`auth.forbidden` for whoever sees the account and does not supervise it; `agent.own_command` for a token the account made).

- `GET ?before=&limit=` answers `{ "items": [session, ...], "more" }`, the newest first, `limit` of them (50 where none is said, 200 at most), from before the moment `before` on, which is a session's `startedAt`.
- `GET .../<id>` answers one; `transcript.session_not_found` for a session that is not that account's.
- `GET .../<id>/events?after=&limit=` answers `{ "items": [event, ...], "more" }`, the events after the number `after`, in order, `limit` of them (100 where none is said, 500 at most). An event is `{ "n", "kind", "at", "text", "whole", "data", "files", "sealed" }`: `text` is the whole text, or its beginning where `whole` says how many bytes the whole is; `files` its pictures; `sealed` is `null`, or `{ "by", "at", "reason" }` for an event whose content was sealed, which then has no text, no facts and no pictures.
- `GET .../<id>/events/stream?after=` is the same as server-sent events: each `event` with an event as its data and its number as its id, a comment in the silences, and an `end` with the session as its data once it is over and everything of it was sent, after which the stream ends. `Last-Event-ID` is read in place of `after` where it is further on. Whoever watches is woken on the agent accounts' own channel, by the session, and the stream counts among those the reader holds (`feed.too_many`).
- `GET .../<id>/events/<n>/text` answers `{ "n", "text" }`, the whole text of one event; `transcript.event_not_found` for a number the session has not.
- `GET .../<id>/files/<file id>` answers the bytes of a picture, shown in place under its kind, with `nosniff` and a policy that runs nothing; `file.not_found` for an id that is not that session's.

**Sealing.** `POST /api/v1/agents/<handle>/sessions/<id>/events/<n>/seal`, for an administrator, signed in on the console's own pages or through their agent's token ([ADR-0021](../adr/0021-a-token-configures-as-its-person-does.md)), takes `{ "reason" }`, a line up to `MAX_SEAL_REASON_LENGTH`, and answers the event as it is from then on: its content replaced by who sealed it, when and why. A supervisor who is no administrator is `auth.forbidden`. An event sealed already stays as it was sealed. The bytes it held go with the seal: where the store refuses to let them go, nothing is sealed and the answer is `file.store_unavailable` (`503`, with `retry-after`), for the seal to be asked again. The one way anything leaves a transcript, and on the record.

A run carries `sessionId`, the session of an agent account's runner it was begun in, or `null`: set by the console for a run the account's command begins while a session of the account is open.

### The invitation: `/api/v1/agents/<handle>/invitation` and `GET /api/v1/setup/<code>`

The invitation that leads a machine to an agent account ([ADR-0088](../adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md), point 4), and what its code opens. Both exist where the deployment signs people in, and nowhere else.

`GET`, `POST` and `DELETE /api/v1/agents/<handle>/invitation` are a supervisor's, an administrator or whoever is above the account on its reporting line, with a session or a token ([ADR-0021](../adr/0021-a-token-configures-as-its-person-does.md)): `auth.forbidden` for a member who sees the account and supervises nothing of it, `agent.not_found` for a handle that is none. `GET` answers `{ "invitation": { "createdAt", "expiresAt", "by": person | null } | null }`, the invitation as it stands, or `null` where none was made or its day has passed; never the code. `POST` makes one, in place of the one there was, and answers `201` with `{ "invitation", "code", "command" }`: the code, eight characters of the alphabet of connection codes in two groups (`ABCD-EFGH`), which is answered this once and of which the console keeps the hash alone; and the command that sets a machine up with it, `console agent setup --console <the console's origin> --code <code>`. An account has one invitation, good for `INVITATION_DAYS` (7) days or until the account's command has signed in, whichever is first: a connection approved `as: "self"` for the account ends it. `DELETE` takes it away and answers `204`, whether there was one. An invitation is on no feed; the console logs who invited which account, and never the code.

`GET /api/v1/setup/<code>` is read without a sign-in, by whoever holds the code, typed in any case and with or without its hyphen. It answers `{ "account": { "handle", "name", "title", "login", "host", "avatarParts" }, "workspace": { "name", "handle", "domain", "services" }, "console": { "url" }, "expiresAt" }`: which account the setup is for, the login it signs in with and the provider it signs in through, the names and the services of its workspace ([ADR-0089](../adr/0089-a-workspace-names-the-services-its-agents-work-with.md)), and the console to come back to. Nothing secret is among them, nothing by which the account or anyone is entered, and nobody else of the workspace. A code that opens nothing is `setup.not_found` (404), one answer whatever the reason: no invitation was made with it, its day has passed, it was taken away or made again, the account's command has signed in, or the account is out. It is answered with `cache-control: no-store`. The code is an invitation and no credential: it says which account a setup is for, and gives nobody the account.

The guide is made from that answer by the package (`setupGuideOf`, `setupGuideText`), for that account and those services, in the order a setup is done and by whom: what has to be there before the line, what the agent asks the person at the machine for and how the account signs the command in as itself, what the agent does when it starts, how it signs in elsewhere in a browser, and what it asks for where it cannot. It says what has to be there at a service and never who makes an account there ([ADR-0094](../adr/0094-the-account-an-agent-signs-in-with-is-named-and-who-makes-it-is-the-organizations-to-say.md)). `console agent setup --console <origin> --code <code>` prints it for the agent and the page `/setup/<code>` shows it to a person, who is asked for no sign-in there ([cli.md](cli.md#agent-accounts)).

## Signing in

Not part of the REST API, and described in [`deploy/README.md`](../../deploy/README.md#signing-in): `GET /auth/<provider>/login?return_to=` and `GET /auth/<provider>/callback` for each provider the deployment has (`gh`, `google`; any other is nothing), and `POST /auth/logout` from the console's own pages. A page learns why a sign-in did not complete from `?sign_in=denied|expired|failed|refused` on the page it was for.
