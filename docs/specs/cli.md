# Spec: the command line

- Status: **Draft.** Version 1 is what an agent works the board with (Claude Code, Codex, any agent with a shell), what a person's own scripts and hooks use, and what serves a console of a person's own ([ADR-0014](../adr/0014-a-persons-own-console-is-served-from-their-machine-by-the-command.md)).
- The command is `console`, the `bin` of `@skillcdn/console` (`packages/console/src/cli/`): a thin client of the [REST API](rest.md) with no logic of its own ([ADR-0006](../adr/0006-agents-work-the-board-through-the-rest-api-and-the-command-line-not-an-mcp-server.md)). `@skillcdn/console/cli` exports `runCli(argv, io)`, the command as a function; the integration tests run it against the app with no socket.

## Signing in

A person installs the package where the agent runs, or has the agent install it, and the command connects once ([ADR-0011](../adr/0011-an-agent-connects-with-a-short-code-a-person-approves-and-the-token-is-never-shown.md)): `console login --url <origin>` asks the console to connect, prints the address of the console's own page and a code of eight characters, and waits, up to the thirty minutes the code is good for; the person opens the address signed in, checks that the page shows the same code, names the agent and approves; and the command receives a token of its own, which it never prints. An agent that can run commands does this itself, in two calls ([ADR-0129](../adr/0129-a-login-under-an-agent-says-its-code-and-ends-and-the-next-call-waits.md)): where no terminal shows the command's words as they are printed, the host that runs an agent's commands shows them when the command ends, so the call that begins a connection prints the address and the code, then a line that says to tell the person both now, in a message of its own, before the command is run again, and a line that names the command to run again, how long a call of it waits (up to ninety seconds; at a terminal told `--wait 0`, while the code lasts) and, apart from that, the moment the code lasts until; it keeps the connection that waits beside the logins, and ends at once with `0`. The telling has a sentence of its own, before the one that names the command, since an agent that read the two in one ran the command first and told its person after, and the call's wait is said apart from the code's end, which an agent took for the wait. The next `console login` for that console begins no new code, claims the one kept, and waits for the approval, ninety seconds a call, ending with `3` and the words to wait on while the code lasts. `--wait <seconds>` says another wait for either call, and at a terminal too, where a wait that ran out keeps the connection the same way; with none said, a terminal's call waits where it stands and keeps nothing. What is kept of a connection that waits is its secret, its code, its page and its end, in the credentials file under its mode, for as long as the code lasts: it is never printed, `console logins` names the code and its end, `console logout` forgets it, a login kept at that console ends it, and whatever the command keeps anew carries none whose code ran out. A connection kept whose code ran out, or that the console no longer knows (`connect.not_found`: it ran out there, or a person said it was not theirs), is forgotten and said, and a new code begun in the same call. `--agent <name>` says what it calls itself; left out, the command names the agent it runs under where its environment says so (Claude Code, Codex), else `An agent`; the machine's name follows (`Claude Code on <machine>`), and the pages show the name before `on` with the whole on hover. A token made by hand on the Agents page is read from standard input with `--token-stdin` instead, for a script or a job, and checked against the console (`GET /api/v1/me` must know the person). Either way the command keeps the token as a login, with the console's address, the person's login there and the workspace's time zone as the console last said it (at `login`, `whoami` or `workspace`; the moments the command prints are in it, as ISO 8601 with its offset, and as the API gives them, in UTC, while none is known or with `--json`; [ADR-0035](../adr/0035-who-may-see-whom-is-decided-by-one-policy-and-the-workspace-keeps-its-settings.md)), in `$XDG_CONFIG_HOME/skillcdn-console/credentials.json` (`~/.config/skillcdn-console/credentials.json` when `XDG_CONFIG_HOME` is unset), readable by the person alone where the system can say so and written whole in one step ([ADR-0027](../adr/0027-the-command-keeps-a-login-per-console-and-a-token-goes-only-to-the-console-that-issued-it.md)). One machine holds a login per console and account: `login` at a second console adds one beside the first, the first is the default console, `--default` makes another the default, and `login` repeated for the same console and account replaces the token, giving the old one up at the console. `console logins` lists them, never a token. `logout [--url <origin>] [--account <login>]` gives one login's token up at its console (`DELETE /api/v1/me/token`) and forgets it; a console out of reach leaves the token to the Agents page, where its person or an administrator removes it; a console that refuses the token because its person is out (`auth.deactivated`, `auth.not_admitted`, [ADR-0044](../adr/0044-a-token-of-a-person-who-is-out-is-kept-and-refused-with-the-reason-until-they-are-back-in.md)) keeps it for when they are back in, and the command forgets it here. A token is never taken on the command line, never typed, and never printed, and a file the command cannot read as its own is never written over: the command says so and stops. Nor is the file written in a shape the command would not read back: what a console answered, the connection that waits or the login a token becomes, is held to the file's own bounds before anything is kept, and where it is beyond them the command says that the address answered what it cannot keep and stops with `1`, with nothing written and no token given up for it; what `POST /api/v1/connect` answers is read within the same bounds ([rest.md](rest.md#connecting-an-agent)).

Which console a command talks to is decided first, and the token is then the one for that console alone: the address is `--url <origin>`, else `CONSOLE_URL` in the environment, else the console `.skillcdn-console.json` binds the directory to, else the default login; the token is `CONSOLE_TOKEN` where `CONSOLE_URL` names that address (the two are a pair, for a hook or a job, and one without the other is refused), else the login kept for the address, for the account `--account <login>` or the directory names, or the one account there. A console nobody is signed in to here gets no request, whatever is kept for another; several accounts at one console with nothing to say which stop the command. An address is `https`, or `http` on this machine alone (`localhost`), and a redirect is never followed, so that a token travels to the console it was issued by and nowhere else. `whoami` and every refusal name the console and the account.

From then on the agent is that person on the board ([ADR-0004](../adr/0004-people-and-agents-reach-the-board-only-through-the-api-with-a-credential-of-their-own.md)): what it does is attributed to the person and shown as done by the agent, called what the person called the token unless `take --agent` says otherwise.

The command names its version on every request, as the product token of its `user-agent` (`skillcdn-console/<version> (cli; node <v>; <platform>)`), and the console holds it to the versions it takes ([ADR-0025](../adr/0025-the-command-names-its-version-on-every-request-and-the-console-holds-it-to-the-range-it-takes.md)): before 1.0, every command of the console's line, from the floor the console names where a release changed what passes between them ([ADR-0038](../adr/0038-the-command-and-the-console-go-together-within-a-line-and-a-release-that-changes-what-passes-between-them-raises-the-floors.md)); from 1.0, the console's major and a minor within one, either way. A command outside the range is refused with `426` (`client.outdated`, `client.too_new`), `login` included, and exits with `4` after printing the command that updates it where it is installed: `npm install -g @skillcdn/console@<version>` for one installed for the machine (`pnpm add -g`, `yarn global add`, `bun add -g` where those put it there), `pnpm add @skillcdn/console@<version>` in the project's root for one installed in the project the working directory is in (the manager its lockfile names), or `npx`, `pnpm dlx` and their kind at the version for one fetched for the run; for a checkout, pull and build. Within the range, a command older than the console is told once a day, on stderr, that a newer one exists, and one newer that what the console has not got yet is refused as not found; what it last said is kept in `notices.json` beside the credentials, and `--json` output stays the console's. `whoami` says the versions, where the command is installed and what the console takes, every time. The command holds the console to a floor of its own the same way, the oldest console it works with (`CONSOLE_AT_LEAST` in the package's `compat` module): a console below it is refused by the command itself as `console.outdated`, in the console's own form, with the command to install for that console, and exit code `4`.

## The project

The board is a project's ([ADR-0008](../adr/0008-a-workspace-holds-projects-and-what-a-person-may-see-and-change-is-decided-per-project.md)), and every command on it works in one: the one `--project <key>` names, else `CONSOLE_PROJECT` in the environment, else the one `.skillcdn-console.json` names in the working directory or the nearest directory above it. `console use <key> [--url <origin>] [--account <login>]` writes that file, after checking that the console knows the project to the person: the project; the console the command talked to, every time, since what is the default login on one machine is another console's on the next ([ADR-0112](../adr/0112-a-binding-names-its-console-and-whoami-asks-the-console-for-the-project.md)); and the account only where `--account` says so, or where the directory named it before, so that a file to be committed carries nobody's account unasked; never a token, and a key the file does not know is dropped on reading. A file from before, with the project alone, is still read, and means the default login. It is meant to be committed in a private repository, so that everyone who works in the checkout, and every agent they run in it, is in the same project at the same console without saying so, and left out of a public one, which it may bind to the organization's console. With none of the three, a command on the board says so and exits with `1`; `skills` and `skill` read the organization's pack then ([ADR-0113](../adr/0113-the-organizations-pack-is-read-where-no-project-is-named-by-every-member.md)), since a directory that names no project, a desk or a folder a repository is about to be made in, is where the skill that sets one up is looked for. `console whoami` says which of the three named the project, and whether the console has it, before any command on the board is run. A project the console does not have, or does not show the member, is refused by every command as `project.not_found`; where the directory's file or the environment named the key, which whoever runs the command has not in front of them, the refusal says what `whoami`'s says, on every command that works in that project: the key, the console, what named it, and the two things to do. `console projects` lists the projects the person may work in, with what they are in each; a project the person may not see is not found, as if it were not there.

## The commands

A table a group, each row a command: what it asks the console, and what it says. `...` is `/api/v1/projects/<key>`, the project the command works in. Everywhere: `--json` prints the console's own answer as JSON, in the shapes of `@skillcdn/console/api`; `--url <origin>` names the console this one command talks to, which must be one signed in to here; `--account <login>` the account there, where several are; `--project <key>` the project. A Markdown body given as `-` is read from standard input. A day is given as `2026-10-24`, `today`, `tomorrow` or `+7` (days from today by this machine's clock); `--due overdue` keeps the open tasks past their day, `--due week` those due by the last day of this week, the week beginning as the workspace says (`console workspace`) or, left to the language, as the person's language has it, else this machine's ([ADR-0039](../adr/0039-this-week-is-the-plans-unit-and-the-week-begins-as-the-workspace-says.md)). Every argument is bounded and checked by the console, as the REST API's schemas say; the command sends it as it was given.

## The documents

A project's pages of Markdown ([ADR-0009](../adr/0009-documents-are-pages-of-markdown-in-a-project-addressed-by-path-versioned-and-linked-both-ways.md)), by path (`guides/onboarding`): `console docs` lists a folder, `console doc` reads a page, `console write` writes one, the first version or the next, keeping the title when none is said, `console attach` adds a file from the machine, `console archive` and `console restore` put a page away and bring it back. A link in a body whose destination is a page's path refers to that page, and `console doc` says what refers to a page in return. An agent writes down what it learned where the next agent will read it, and refers to it from its reports and in what it asks.

## Configuring, as the person

What an administrator or an owner does on the pages, their agent does with `people`, `person`, `project`, `members`, `member`, `category` and `rules write` ([ADR-0021](../adr/0021-a-token-configures-as-its-person-does.md)): the console decides on every request with the same roles, so a member's agent is refused what a member is (`auth.forbidden`), and the event names the agent beside the person. `console help` lists them under "Configuring, as the person", each with its limits and its refusals by code: `project.key_taken`, `project.invalid_address`, `project.invalid_icon`, `member.invalid_person`, `member.exists`, `member.not_found`, `category.key_taken`, `category.in_use`, `category.too_many`, `person.last_admin`, `person.of_organization`, `listing.exists`, `listing.not_found`, `listing.unknown_host`. A person is named by login, as `--worker` names one; `console people` lists the logins. The tokens themselves have no command but `logout`, which gives the command's own up: they are made and removed on the Agents page, signed in, so that a token which leaks cannot outlive its removal.

## The run a command means

`report`, `hand-in`, `ask`, `finish` and `fail` act on a run. Named with `--run <id>`, that one; else the one open run begun with this token in the project (`GET .../runs?open=true&mine=true&brief=true`: the runs without their reports, which a command on a run asks for every time and never reads). None open, or several: the command exits with `1` and says so as `run.none` or `run.ambiguous`, listing the open ones, so that an agent working two tasks at once says which. A run is its person's, and a token's own are only those begun with it: where none of the token's is open, the command looks through the project's open runs (`GET .../runs?open=true`, and `GET /api/v1/me` for whom it acts as) for those of the same person begun through another of their agents, or before the command was signed in again, and `run.none` names them, each with its id, its task, the agent it was begun through and when it was last heard from, and says to go on with one by `--run <id>`, before any word of taking a task, which would end such a run; with none of the person's open, it says to take a task, as before. `--run <id>` reaches any open run of the same person; `take` says the same when the run it begins is beside another of the token's.

`tasks`, `goals`, `decisions` and `runs` show a page at a time: `DEFAULT_PAGE_LIMIT` lines unless `--limit <n>` says otherwise (up to `LIST_LIMIT`), from `--offset <n>` on, and a last line, `... more: --offset <n>`, says how to ask for the next page when there is one; with `--json`, the console's answer as it is, `more` included. An agent reads the first page and asks for the next only when what it looks for is not on it.

## Waiting for a decision

`ask` waits 60 seconds for the answer unless `--wait` says otherwise, within what an agent's shell gives one command, and, signed in as an agent account, only where `--wait` says to: nobody attends an account, the answer wakes it ([runner.md](runner.md#the-boards-wakes)), and the command says to go on with other work and with the run when the answer comes, and ends in `3` at once, saying the same where a wait it was asked for runs out; `decision <id> --wait <seconds>` waits as long as it is told, a day at most, and where it runs out for a command signed in as the account that raised the decision (`login --self`: what the login kept says, since the decision alone does not say who asks) it ends in the account's words too, that the answer wakes it, in place of how an attended agent waits on. The command asks the console to hold each request for up to 50 seconds (`?wait=`), the server's own bound, and repeats while the time lasts, with a breath between requests; the answer arrives as soon as a person gives it, since the console is woken through the database's own channel. A decision that still waits when the time is up is exit code `3`: the run waits with it, so the agent keeps waiting with `console decision <id> --wait 100`, within what its shell gives one command, and goes on meanwhile only with work that does not depend on the answer. `ask` prints the decision's id as soon as it is raised, before any waiting, so that a wait cut short loses nothing; with `--json` it prints the decision then, and again with its answer when that comes. The answer may be the person's own words rather than one of the options: it is then one more option of the decision, marked as theirs, and the one chosen; the command prints it so, and the agent acts on it as given.

## A console of one's own

`console serve [<dir>] [--port <n>] [--records <dir>]` serves a console a person built from the package, for themselves ([ADR-0014](../adr/0014-a-persons-own-console-is-served-from-their-machine-by-the-command.md)): the build in `<dir>` (its `index.html` and files) at `http://127.0.0.1:11197/`, or the port given (`0` for one the system picks), and everything under `/api/` carried to the console the command is signed in to, with its token as `Authorization: Bearer`, so that the pages never hold the token and the organization's console allows no other origin. The command listens on the loopback only and answers no request whose host is not it; a request to the API that the browser says comes from another site's page (`Sec-Fetch-Site`) is refused, as is one from a browser that does not say and names another origin. What is the browser's does not travel: cookies, the page's `Origin`, the browser's own metadata, and the referrer but for its origin when that is a page on this machine (a loopback, on any port), which travels as `Referer: <origin>/` so that the console knows which page may embed a plugin's frame ([ADR-0083](../adr/0083-console-serve-names-the-page-on-this-machine-by-its-origin.md)); what comes back travels decoded, without a cookie. The feed's stream passes through as it streams, and a file handed in as a form. Without a directory only the API is served, for a development server to send its `/api/` requests to with the loopback's host, so that a console is built with its reloading against the real board. The command checks the token against the console first (`GET /api/v1/me`), says where it serves and as whom, and runs until stopped.

`--records <dir>` serves what a desk keeps beside them ([ADR-0117](../adr/0117-a-desk-keeps-records-of-what-its-member-made-as-files-the-desks-pages-read.md)): the directory named, a desk's `records/`, at `/records/`, for the desk's pages to show, as `console serve dist --records ../records` run in a desk's `web/`. Each file is read when it is asked for; `GET` alone; nothing outside the directory, no file whose name begins with a full stop, no listing; to the pages of this origin and to no other site's. What is answered how, and what is refused by which code, is [records.md](records.md#serving). A directory that is not there yet is no error, since a desk has its `records/` once it keeps something ([ADR-0122](../adr/0122-a-desk-is-given-its-least-and-grown-by-what-its-member-asks.md)): every path under `/records/` answers `404` until it is there, the line the command prints says that nothing is kept there yet, and what comes to be kept is served from then on, with no restart. What is there and is no directory is refused before anything listens, and without `--records` every path under `/records/` answers `404`, `records.not_served`, never the build's page. The pages learn from the same answer that they hold a token (`agent`) and offer nothing a token cannot do. How a console is built from the package is in the [package's README](../../packages/console/README.md#a-console-of-your-own).

## A desk of one's own

`console desk [<directory>] [--web]` writes a person's desk ([ADR-0115](../adr/0115-a-person-has-a-desk-too-written-by-the-command-and-set-up-by-a-skill-of-the-organizations-pack.md), [ADR-0122](../adr/0122-a-desk-is-given-its-least-and-grown-by-what-its-member-asks.md)): a folder of their own that their agent begins in, and that they make a repository of at their own git account. It asks the console who the command is signed in as and writes the package's template for them ([runner.md](runner.md#the-desk)), which is the least: `README.md`, `AGENTS.md`, `CLAUDE.md` and `.gitignore`, and nothing under `records/`, `web/` or `work/`, each of which is there once it is used. Each file is written only where no file of that name is there, into `desk` in the current directory, as an agent account's desk is called, or into the directory named, `.` for the current one. It says which files it wrote and which it left as they were.

A desk is bound to no project, so the command writes no `.skillcdn-console.json`, and it refuses to make a desk where the working directory, or one above it, works in a project and the desk is to be made under it (no directory named, or one named by a relative path): the desk, and every checkout under its `work/` without a binding of its own, would work in that project too.

`--web` also writes the shell of the desk's pages into `web/` of the desk, where that holds nothing: the files of `template/desk-web` in the package, with `__VERSION__` replaced by the package's version, so that the pages are built on the version the command is, and `__TITLE__` by the desk's title, which is the person's name in letters, digits, spaces, full stops, commas and hyphens with `’s desk` after it, `My desk` where the name leaves nothing, and so stands as it is in a page, in a JSON string and in a script. A `web/` that holds something is left as it is. Where the package carries no shell, or the command does not know its version, the command ends in 1 and writes nothing, the desk's own files neither. The desk's pages are the person's own extension of the console's pages: a console of their own ([above](#a-console-of-ones-own)), served with what the desk keeps beside it. The shell is one empty page of the person's own, and the command says so: what it shows is what they then ask to see.

The last lines the command prints are what is next, in order, numbered, to say to an agent begun in that folder, or for the agent that ran the command to go on with there:

1. `Set this desk up as a repository of mine, with the skill for it in the organization's pack where it has one: console skills --search "desk setup" --limit 5`, with `and bring its pages up` after `mine` where `--web` was given. The search names a limit, since a hit is most of a kilobyte and the first is nearly always the skill.
2. `Ask me what I want to keep and to see here, and shape the desk to it, as the skill keeping-a-desk says, shipped with the console command: <path>`, the path being where the skill's `SKILL.md` is on this machine, among the skills the package carries.

Where `--web` is asked for in a desk that was there already, with nothing of the desk's own to write, the command says nothing of what is next: its member is shaping the desk, and the two lines are for a desk just made.

The command makes no repository and no remote, keeps nothing and asks nothing: the first is a skill's, of the organization's pack, and the second the skill `keeping-a-desk`'s, one of the console's own, which `console help desk` names with its place too. `--json` answers `{ "directory", "written", "kept", "web", "next" }`, `next` being the two lines in order, and `web` being `null` without `--web` and else `{ "directory", "written", "version" }`, the version `null` where `web/` was left as it is.

An agent account's desk is settled by `console agent setup` ([below](#setting-a-machine-up)), and none of a desk's own files is written for one: without `--web` the command ends in 1 and writes nothing. With `--web` it writes the shell of the pages and nothing else, into `web/` of the directory named, which must hold an `AGENTS.md`, so `console desk . --web` in its desk ([ADR-0122](../adr/0122-a-desk-is-given-its-least-and-grown-by-what-its-member-asks.md)); the title is the account's name, and no line says what is next (`next` is empty), since an agent account that asks for the shell is shaping its desk already.

`console desk check [<directory>]` reads the collections of a desk, a person's or an agent account's, and says whether they read right ([records.md](records.md#the-check)); what else a desk keeps under `records/` is its own, and is not read. It asks nothing of the console.

## Output and exit codes

Plain text on standard output: one line per thing in a list, a few lines for one thing in full, with ids given, since the commands take them, and the vocabulary's own words (`in_progress`, `waiting`), since the options take them. A line that names a member, the owner and the workers of a task, whom a decision is for, who wrote a comment, calls a person by their login and an agent account by its handle (`workers alice, @mira`), which the commands take wherever they take a login ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md)): a line tells the two apart. What went wrong goes to standard error as the console's stable code and its words (`run.task_closed: the task is done or dropped`), with a hint when there is something to do about it.

| Exit code | Meaning |
|---|---|
| `0` | Done. |
| `1` | The console refused, or could not be reached; the reason is on standard error. A read of a pack that the pack refused ends so too ([ADR-0118](../adr/0118-the-consoles-reads-of-a-pack-keep-to-the-skillcdn-commands-read-by-read.md)). |
| `2` | The command was not understood. |
| `3` | What was waited for still waits for a person: a decision's answer, or a connection's approval (`login`). |
| `4` | The command and the console do not go together ([ADR-0025](../adr/0025-the-command-names-its-version-on-every-request-and-the-console-holds-it-to-the-range-it-takes.md), [ADR-0038](../adr/0038-the-command-and-the-console-go-together-within-a-line-and-a-release-that-changes-what-passes-between-them-raises-the-floors.md)); standard error says which to update, and how. |

## What an agent is told

The command's help has two layers. `console help` is the map, read once at the start: what the board is, that the agent acts as the person whose token it holds and that everything it sends is shown to people as text, which project the commands work in and how it is named; then every command in a line, by section (signing in, the board, working, the documents, configuring), each with what it does in a sentence, a many-formed command (`task`, `goal`, `project`) listing its forms without their flags; then what holds everywhere, the exit codes and the refusals any command may meet. `console help <command>` is the reference, read when the command is about to be used: the command in full, every form and flag, what each does, the limits the console holds it to (how long a report, a summary, a question or an option may be; how many options, reports and links) and the refusals it may meet, by code, so that an agent learns them before it runs into them. The help says what the command does; how the work goes and what the organization asks are the skill's and the rules', and are not repeated in it. The skill `working-the-board` ([skills/working-the-board/SKILL.md](../../skills/working-the-board/SKILL.md), [ADR-0015](../adr/0015-the-consoles-skills-live-in-this-repository-in-the-skillcdn-format-and-the-package-carries-them.md)) says how the work goes: reading, taking, reporting at the milestones, asking and waiting, handing in, writing down, finishing. The rules of the board say what the organization and the project ask of agents ([ADR-0023](../adr/0023-the-rules-of-a-board-are-pages-the-workspace-and-its-projects-keep-read-first-by-every-agent.md)): which tasks to take, which skills to load first, what to report, when to ask; `take` prints them with the task, so that they are read once, there, and `console rules` reads them any time, as when a task is still to be chosen. The plugins of the console, if it has any, are two commands in a section of their own, `console plugins` and `console plugin <key>`; the rules a task prints end with the plugins bound to the project, a line each, and `console plugin <key>` is then read before its first command, with the plugin's own skills ([plugins.md](plugins.md), "The command").

## Running an agent on a task

What a person does, once the command is signed in where the agent runs; tried with Claude Code on 2026-10-09, with an agent that took a task, reported at each milestone, raised a decision, acted on the answer, handed in and finished, and a person who answered on the board.

1. Write the task on the board of the project, with its body as the work order: what to make, where, the milestones, what to ask.
2. Start the agent in the directory it is to work in, where `console use <key>` has named the project (once, committed), and tell it, in its own words, what this amounts to: run `console help`; take the task with `console take <number>` and follow its body; report at the milestones with `console report`; ask with `console ask` when a person must decide, and keep waiting with `console decision <id> --wait 100` until the answer comes; hand in with `console hand-in`; finish with `console finish --summary`. Say that the command is signed in already and that it must never look for or print a token.
3. Follow the run on the board, and answer the decisions it raises. The agent's reports, what it handed in and its summary are the run's record on the task's page; what is said about the task, by the person in a comment with a picture, by the agent in answer, is the discussion on the same page, in the order it came.

Work that reaches an agent in chat, in a directory that works in a project, goes the same way: the agent writes it on the board and takes it, in one command (`console task new "<title>" ... --take`, which prints the number first), tells the person the number, and works it as above, so that the board holds the work and its record, and a person decides on the board, not in the chat. A board used only to tick off what was done elsewhere is a list of things to do; the record is in the runs, the comments and the decisions.

## Signed in as the account itself

`console login --self` signs the command in as the account ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md), point 9), which is how an agent account's own command signs in, and a person's where they work at it themselves. The connection is the one every login makes ([ADR-0011](../adr/0011-an-agent-connects-with-a-short-code-a-person-approves-and-the-token-is-never-shown.md)), asking to be the account (`as: "self"`): the command prints the address and the code, the account opens the page in a browser signed in as itself, and says "this is me". What the command is then handed and keeps is a session of its own in place of a token: kept for as long as it is used, ended when left unused for the deployment's `SESSION_TTL_DAYS`, so that an agent at work has nothing to renew and one that stopped lapses by itself. It is presented as a token is and does what a token may; what is done with it is done by the account, and names no agent beside it. `console logins` and `console whoami` say that the command is signed in as the account itself; `console logout` gives the session up; the account sees it among its sessions, and ends it there, as its supervisors do on the agent's own page.

## Agent accounts

In outline, for the plan of [ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md) to [ADR-0089](../adr/0089-a-workspace-names-the-services-its-agents-work-with.md); a command is specified here in the change that builds it, and until then it is not one. The commands stay few, in the words the command already has: a list is the plural, one of a kind is named after it, and what is taken away is removed.

A command of 0.5.0 reads what the console answers of an agent account already ([rest.md](rest.md#agent-accounts)): a person's `kind`, `handle` and `title`, which `console people` prints, and the two events; `console person title` writes a member's title, `console agents` and `console agent <handle>` read the agent accounts, `console agent new` makes one, `console manager` says whom one reports to, `console login --self` signs the command in as the account itself, `console secrets`, `console secret`, `console agent secrets` and `console agent secret` keep an account's secret store, and `console agent tell`, `interrupt`, `stop`, `restart`, `reset`, `set` and `wake` send an agent account a signal, which `console agent signals` reads back; `console agent invite` makes the invitation that leads a machine to an account, and `console agent setup` prints the guide its code opens and sets the machine up; and `console runner` is an agent account's runner.

`console runner` ([ADR-0085](../adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md), [runner.md](runner.md)) takes nothing: it is started in the agent's desk, on the command signed in as the account itself (`console login --self`), and runs until it is stopped: by a signal, or, where its environment names the process that keeps it running (`CONSOLE_RUNNER_KEEPER`, that process's number, which the service on Windows says, [runner.md](runner.md#the-service)), when that process is gone. It asks `GET /api/v1/me` who it is, and refuses anyone but an agent account on its command's session; reads `runner.json` in the desk, of which it uses nothing when the file does not read, and runs with the defaults where there is none; then says a line when it is there, when a session begins and ends, and when the console is away, with ids, numbers and codes and never what a signal or an event says. It is no command of an agent's, so it is not on the map `console help` prints; `console help runner` says it in full. An agent account is named by its handle wherever the command takes a login: `--worker @mira`, `--to @mira`, `member add @mira`.

### Setting a machine up

`console agent setup --console <origin> --code <code>` makes a machine an agent account's ([ADR-0088](../adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md), point 5), from the line of its invitation, in the agent's own OS account and with no administrator's rights. It prints the guide first, the part of whoever prepares the machine and no more: what the agent does when it starts is its first task, read in its own session, and is whole on the guide's page and in `--json`. After the guide:

1. **It looks at the machine** ([ADR-0140](../adr/0140-a-machine-is-given-its-least-and-the-agent-does-the-rest-itself.md)), before anyone is asked to sign in: git, asked for its version, on macOS only once `xcode-select -p` says the Command Line Tools are there, since without them `git` opens a window; the command of the agent's product, `claude` then `codex` each asked for its version, the first that answers being the product, or the one `--driver <name>` names alone (a driver whose product's command the desk names, `acp`, is not looked for); and for a product its driver starts with a browser, the agent's browser ([ADR-0149](../adr/0149-an-agents-browser-is-a-chrome-with-no-window-unless-its-desk-names-the-products-own.md)): Google Chrome where the program that starts it with no window looks for it (`/Applications` on macOS, the folders of programs on Windows, `/opt/google/chrome` on Linux), and that program, `chrome-devtools-mcp`, asked for its version, through `cmd /c` on Windows. `--browser chrome` looks for the product's own browser tool instead: Google Chrome wherever a person keeps it, an OS account's own Applications on macOS and a command of its name on Linux among it. `--no-browser` says the agent signs in at no page, and nothing of a browser is looked for; `--browser` with a name that is neither `headless` nor `chrome`, or beside `--no-browser`, is refused, exit 2. Whatever is missing is listed at once, each with what installs it, and the command ends there, exit 1, with nothing signed in, written or run. Where nothing is, it says what it found, and in a line each what it could not see or does not give: the browser's extension where `--browser chrome` named that tool, whether the product is signed in, and that a product its driver starts with no browser has none.
2. **It signs the command in as the account.** A connection that asks to be the account itself ([above](#signed-in-as-the-account-itself)), named `console as <OS account> on <machine>`, which is what the account's page shows beside the session. The command opens the page in the machine's browser, only where its address is the console's own, prints the address and the code, and waits for the account, signed in there, to say that the command is it. It then asks the console who it is: anyone but the invited account, a person who answered by mistake say, and the command gives that sign-in up at the console, keeps nothing and sets nothing up. A command that is the account's already signs in again nowhere. What it keeps is the account's session, as the default console of the OS account.
3. **It settles the desk**: `--desk <dir>`, else this directory where it holds a `runner.json`, else `desk` in the OS account's home. A desk that is there, with a `runner.json` or an `AGENTS.md`, is left as it is. Else, where the workspace's git host says where a desk is cloned from (`https://github.com/<account>/desk.git` for `github`) and the account keeps the secret `git.token`, which is an account that pushed a desk before, the desk is cloned: `git clone` is run with the token in its environment, answered by a credential helper named in the environment too, for the remote's own origin and no other host, so that the token is on no command line and in no file; a clone that fails stops the setup, and `--new-desk` begins a new desk instead. Otherwise the template is written ([runner.md](runner.md#the-desk)), over no file that is there, its `runner.json` naming the driver of the product found and the browser looked for and found, `"browser": "headless"` or, where `--browser chrome` said so, `"browser": "chrome"`, and `"browser": "none"` where `--no-browser` said that. A desk it wrote or cloned is then made a repository where it is none (`git init`) and given, in its own configuration and for the origin of the workspace's git host alone, an empty credential helper followed by one that asks this command for the secret `git.token` (`<runtime> <command> secret git.token --url <origin> --account <login>`): the agent's own pushes are handed the token from its store, and the machine's helpers, a keychain among them, are left out. A desk that was there is given none.
4. **It writes the service that keeps the runner running**, by the module of the platform, `launchd` on macOS, `systemd-user` on Linux and `task-scheduler` on Windows ([runner.md](runner.md#the-service)): the runner started as this command was, `runner --url <origin> --account <login>`, in the desk. It loads it and looks for half a minute whether the runner is heard from, then says the machine, the operating system and the OS account as the runner said them, or where the runner's own lines are. Where a step of the module may fail and did, lingering on Linux that a system keeps for an administrator, it says what is left to do and goes on. On a platform without a module, and with `--no-service`, it writes none and says how the runner is started by hand: a line for a shell, the desk and the login quoted in it where they hold anything a shell reads as more than a word.
5. **It hands over.** Where the runner is heard from, it looks for a minute whether a session has begun (`runner.session` of `GET /api/v1/agents/<handle>`), and says: that one has, or that one begins when something wakes the agent; the address of the account's page; the account's first task, by its number and its address, where its plate holds it (`GET /api/v1/work`); that the machine's part ends there and the rest is the agent's own; how to tell the agent what changed on the machine afterwards, `console agent wake me`; and what it knows of sleep: on macOS, where the system can be asked (`pmset -g assertions`), that the runner holds the machine awake or that it does not; elsewhere, that the runner asks the system to and where its own lines say whether that holds; with what is left to whoever keeps the machine.

`--refresh` derives a machine again: a desk that is there, with a `runner.json` or an `AGENTS.md`, is left as it is, its `AGENTS.md` too, whatever the template says by now, and one that is not is settled as above; the service's files are written again where they changed, and the services are printed as they are now, for the agent to put its own `AGENTS.md` right. It runs none of the commands that load the service and unloads nothing, since it may be running under the runner it would end: what it wrote is read when the service is next loaded. Where the system reads a file only once it is told to and telling it ends nothing, as on Linux and on Windows, a refresh that wrote one tells it ([runner.md](runner.md#the-service)).
