# Spec: the runner

- Status: **Built** on both sides but for what a section says comes later; written before the runner was, and corrected where building it showed otherwise ([ADR-0085](../adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md), [ADR-0086](../adr/0086-a-session-leaves-a-transcript-that-is-kept-for-good.md)). Milestone 42 of the [roadmap](../roadmap.md) built it. The `claude` driver was written from the product's documentation and then run against the binary, 2.1.321 first, which corrected it; a version is listed as tried once the driver was run against it.
- Where things live: the runner, its modules and their registries in `packages/console/src/runner/` (`console runner`, and `@skillcdn/console/runner` for whoever builds on them); what passes between it and the console in `@skillcdn/console/api` (the schemas) and [rest.md](rest.md#agent-accounts) (the routes); the console's side in `apps/console/src/http/` and `apps/console/src/db/queries/`.

The runner is the program on an agent account's machine that keeps its agent going with nobody at the screen. It runs in the agent's own OS account, signed in as the account ([ADR-0084](../adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md), point 9): the command's session is its only credential to the console. It starts the agent's product as a child process, the product's own unmodified binary under the agent's own subscription; feeds it what the console sends; reports what the product does; and says every thirty seconds that it is there. The console calls no model API and starts no agent, still.

## Words

| Word | Meaning |
|---|---|
| runner | `console runner`: one process per agent account on its machine, started by hand or kept running by a service |
| product | The agent product the runner starts: Claude Code first. The runner never modifies it and holds none of its credentials |
| driver | The module that speaks to one product: starts it, sends it messages, reads what it does. `claude` first, then `codex`, and `acp` for whichever product speaks the Agent Client Protocol |
| wake source | A module that raises wakes from outside the console, a messenger say. `console`, the console's own stream of signals, is built in |
| service | The module that keeps the runner running across restarts of the machine: `launchd` first |
| boundary | What keeps one agent apart from another on a machine: `os-user`, an OS account each |
| session | The lifetime of one process of the product. One main session per agent account at a time |
| conversation | What the product resumes from one session to the next: continuous unless the configuration or a supervisor says otherwise |
| signal | What the console sends the runner for its agent: a record numbered per account, with who sent it |
| event | One whole block of a session's transcript, numbered per session by the runner |
| state | How the agent stands, in one word: `running`, `stopped`, `refused`, `failed`, `unheard` |

## The heartbeat

`PUT /api/v1/agents/me/runner`, every thirty seconds, and at once when the state changes. For an agent account on the session of its command signed in as itself, which is the runner's one credential: its browser, or a token it made, is `agent.own_command`. Built on the console's side ([rest.md](rest.md#the-runner-put-apiv1agentsmerunner-and-the-signals)). The body:

```json
{
  "state": "running",
  "reason": "started",
  "delivered": 8812,
  "session": "0199c4d8-0000-7000-8000-0000000000a1",
  "machine": { "name": "mac-mini", "os": "macOS 15.1", "user": "mira" },
  "runner": "0.5.0",
  "product": { "driver": "claude", "name": "Claude Code", "version": "2.1.0", "tried": true },
  "offers": { "models": ["opus", "sonnet"], "efforts": ["low", "medium", "high"], "steer": true, "images": true, "resume": true },
  "running": { "model": "opus", "effort": "high" }
}
```

- `state` is what the runner says of its agent: `running`, the session open or ready to open; `stopped`, by a supervisor's `stop`; `refused`, the model refused and the agent waits; `failed`, the product could not start or sign in. `unheard` is the console's word, never the runner's.
- `reason` is one of a short list, never what was said: `started`, `resumed`, `reset`, `completed` (a turn completed after a wait) for `running`; `stop` for `stopped`; `model_refused` for `refused`; `sign_in`, `start`, `crashed` for `failed`.
- `delivered` is the number of the last signal the runner handed to the product, `0` for none.
- `session` is the open session's id, or `null`.
- `machine`, `runner`, `product`, `offers` and `running` say where it runs, with what, what the product offers to choose from, and what the open session runs with; each a line, bounded. `tried` says whether the driver was tried with that version of the product.

The console answers what the account's settings are and where the record stands:

```json
{ "latest": 8815, "delivered": 8812, "settings": { "model": "opus", "effort": "high" }, "state": "running" }
```

`latest` is the number of the newest signal of the account; `delivered` the most the console was ever told was delivered, which is where a runner that lost its own count goes on from; `settings` is what a supervisor chose, `null` each where nothing was, and where the product does not offer it any more: a choice is kept among what the product offers, so one that this heartbeat's `offers` do not list, where they list any, is the product's own again from then on, since a product refuses at every turn a model it does not have, another product's once the desk's driver changed say; `state` is how the console has the agent, which is `stopped` whatever the runner says while a supervisor's `stop` stands. The console keeps when it last heard from the runner and claims nothing more ([ADR-0020](../adr/0020-the-console-does-not-claim-an-agent-is-at-work-a-run-says-when-it-was-last-heard-from-and-a-new-run-takes-over.md)).

A change of state is `agent.state_changed` in the workspace's feed, with `login`, `handle`, `state`, `was` and `detail`, the reason: by the supervisor whose `stop` stopped it, by the account for what its runner reported, by nobody for an account the worker found unheard, which it does for one whose runner was last heard from more than five minutes ago.

## Signals

A signal is a record of the console's, numbered per agent account from 1, whoever raised it:

```json
{
  "number": 8812,
  "kind": "tell",
  "by": { "id": "...", "login": "jane", "name": "Jane" },
  "agent": "Claude Code",
  "plugin": null,
  "source": "person",
  "key": null,
  "text": "Hold the release until the migration is checked.",
  "set": null,
  "attachments": [],
  "at": "2026-11-10T14:02:11.000Z"
}
```

- `kind`: `wake` (there is something to do), `tell` (a supervisor's words), `interrupt` (stop the current turn, then take these words, or with none what it was sent and has not taken), `stop`, `restart`, `reset`, `set` (the model and the level of effort, in `set`: `{ "model", "effort" }`, the whole choice from then on, either `null` for the product's own).
- `by` is the member who sent it, with the `agent` and the `plugin` they acted through, or `null` for the console itself.
- `source`: `person` (a supervisor's own signal), `board`, `schedule`, `messenger`, or `console` (the console's own housekeeping), with a reference in `key` (`#412`, `day`, a thread, `services`).
- `text` is a paragraph of up to `MAX_SIGNAL_LENGTH` characters; `attachments` the files sent with a `tell` or an `interrupt`, each `{ "id", "name", "size", "contentType" }`: up to 8, of any kind, within the bound on a file together; a picture is one by its bytes whatever it was called, and a file called a picture that is none is `application/octet-stream` ([ADR-0095](../adr/0095-a-tell-carries-files-of-any-kind-handed-to-the-agent-in-its-desk.md)).

`POST /api/v1/agents/<handle>/signals`, for a supervisor, with a session or a token, takes `{ "kind", "text", "set" }` and answers `201` with the signal; with files it is a form, the part `signal` with what the JSON would say and a part `file` for each. A `tell` needs words; an `interrupt`, a `stop`, a `restart` and a `reset` take them for the agent; `set` takes `{ "model", "effort" }`, one or both, a field left out staying as it is and `null` meaning the product's own again, each among those the runner last offered, where it offered any (`signal.not_offered`). A `stop` sets the agent's state to `stopped` at once, by whoever sent it, and it stays so until a `restart` or a `reset` is sent, whatever the runner says meanwhile.

`GET /api/v1/agents/<handle>/signals?before=&limit=` reads the record, the newest first, for the account's supervisors, and `GET /api/v1/agents/me/signals` for the account itself. A signal is not an event of the board's feed. Sending, the record and the stream are built on the console's side.

`GET /api/v1/agents/me/signals/stream?after=<number>` is the runner's: a stream of server-sent events, each `signal` with a signal as its data and its number as its id, from the number after `after` on, in order; a comment every fifteen seconds keeps the connection known to be alive. For the account on its command's session, and ended when that session is. The runner connects again from the last number it delivered, in `after` or as `Last-Event-ID`, so that nothing is lost and nothing delivered twice; a signal it raised itself, from a wake source on the machine, it reports with `POST /api/v1/agents/me/signals` (`wake` alone, from the `messenger`, with its `key`), and receives back in order like any other ([Wake sources](#wake-sources)).

`interrupt` and `stop` are for the session open when they are sent. An interrupt that finds a turn of that session under way stops it and gives its words at once; one that finds none, the turn done already or the session another, stops nothing, and its words are read as a tell's are. An interrupt with no words gives none ([ADR-0098](../adr/0098-a-message-is-on-the-record-where-the-agent-took-it-and-an-interrupt-may-carry-no-words.md)): it stops the turn so that what the agent was sent and has not taken is read now. The runner hands over at once what it still held, stops the turn by what the product has for that, and writes who interrupted on the session's record, a `person` event of the kind `interrupt` with no text; with no turn under way it stops nothing and writes nothing. A stop that stands at the console and that a runner never received, sent before it started, is said by the heartbeat's answer, and held all the same.

## How a signal reaches the product

A signal is fed into the open session as a message with a header, never by restarting the product:

```
[console k3f9a2 #8812 · tell · Jane (through Claude Code) · 14:02]
Hold the release until the migration is checked.
```

- The header is one line: `console`, the session's mark, the signal's number, its kind, who sent it or its source and reference (`board: #412 ready, by Tom`), and the time in the workspace's zone.
- The mark is six characters the runner makes for each session and tells the agent in the session's first message, with what a header is. Nothing outside the session knows it, so nothing the agent reads elsewhere can pass for a header.
- What came from outside the console, a messenger's message say, is carried in a block fenced longer than any run of fence characters it holds, after a header that names where it came from.
- `tell`, `wake` and the words of a `restart` or a `reset` are sent at the product's priority for "after the current tool call" where the driver can steer, after the turn otherwise; `interrupt` stops the turn first.
- The files of a signal are read by the runner at `GET /api/v1/agents/me/signals/<number>/files/<id>` and written in the desk, at `work/inbox/<number>/<name>`, for the account alone, before the message is handed over ([ADR-0095](../adr/0095-a-tell-carries-files-of-any-kind-handed-to-the-agent-in-its-desk.md)). The name is made one segment: what a file system reads as a path, a drive or a pattern becomes `_`, a bracket a parenthesis, and a second file of a name is numbered. The message says each on a line of its own after the signal's words, with the session's mark, since it is the runner that says where a file is: `[console k3f9a2 · attached file: work/inbox/8812/export.csv · text/csv · 2.0 KB]`, `[console k3f9a2 · attached picture, shown to you: work/inbox/8812/screen.png]`, or that it could not be handed over, with whom to ask. A picture is handed to the product as a picture too where the product takes one, as its bytes or by its path in the desk as the driver says (`can.imageFiles`); where it takes none the line says so and tells the agent to open the file. The pictures are kept with what the agent was sent in the session's transcript; the event names the other files as `files` and the pictures the product was not handed as pictures as `unseen`, which the agent's page says to whoever sent them. The files stay in the desk, the agent's to remove.
- What the agent was sent is written on the session's record when the product takes it ([ADR-0098](../adr/0098-a-message-is-on-the-record-where-the-agent-took-it-and-an-interrupt-may-carry-no-words.md)): at once where the product was waiting for a message; where a turn was under way, when the driver says `taken`, after the tool call under way or with the turn after, so that the record reads in the order the agent read, and a supervisor's words wait in sight on the agent's page until then; and at the latest when the turn completes. What a session ends on before the product took it is written then with `unread: true`; a product that did not start, or was not signed in, took nothing, and what it was sent is sent again.
- Signals are grouped, never capped: the runner holds what arrives within 1.5 seconds and delivers one message, the signals in order under a header each, the same `source` and `key` merged with a count; beyond 20 signals or 16,000 characters a message, the rest is said as "N more" with the command that reads them (`console agent signals`).

What the agent itself does on the board raises no wake to it.

## The board's wakes

The board wakes an agent account by rules ([ADR-0085](../adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md), point 10), which the worker role applies from where it read the feed to, as the plugins' hooks are dispatched, keeping its place a batch of events at a time, and at the event before one whose wakes could not be sent; an `api` role that carries the worker's work applies them itself. Each wake is a signal on the account's record, a `wake` from the `board` whose `by` is whoever did what woke it and whose `key` says what it is about, so that the runner says several wakes of one thing once:

| What happened | Who is woken | `key` |
|---|---|---|
| A task is written ready, or made ready, and its due day is unset, today or past | The agent accounts at work on it | `<project>#<number>` |
| An agent account is made a worker of such a task | That account, and nobody who was at work on it already | `<project>#<number>` |
| The due day of such a task is moved to today or before, or taken away | The agent accounts at work on it | `<project>#<number>` |
| A comment on a task | The agent accounts that own it or are at work on it, whatever its state and its day | `<project>#<number>` |
| A decision is raised | The agent accounts it is addressed to | `decision:<id>` |
| A decision is answered | The agent account that raised it | `decision:<id>` |
| The workspace's `handle`, `domain` or `services` change | Every agent account that was there, from the `console` and by nobody | `services` |

"Today" is the day in the workspace's time zone, UTC where it has none: a task planned for a later day wakes nobody, and appears in that day's briefing. A task is read as it stands when the worker reads the event, which is what the agent will find. What an account did itself wakes it for nothing; an account that is out is woken for nothing; a task that is put away wakes nobody. An account is woken only for what it may still read: for a task while it may work in the task's project, and for a decision while the decision reaches it, so that an account taken off a private project, and still named on a task or a decision there, is told neither a title nor an answer of it. A wake says what it is about in the console's own words, with the command that reads it (`console task 412 --project ops`, `console decision <id>`): a task's title and a decision's question on one line, and never what a comment says, which the agent reads on the board as a comment.

The first wake of an account is its onboarding task ([ADR-0088](../adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)), by the first rule: the console writes the task ready, with the account at work on it, when the account is made ([rest.md](rest.md#get-apiv1agents-and-post-apiv1agents)), and the wake waits on the record until a runner first connects.

**The briefings** are wakes from the `schedule` ([ADR-0085](../adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md), point 11), which the same pass sends each agent account whose runner was ever heard from, at the hours the account keeps, in the workspace's time zone, UTC where it has none: `dayStart`, 09:00 where the account says no other hour, and `dayEnd`, none unless it says one ([rest.md](rest.md#get-apiv1agentshandle-and-patch-apiv1agentshandle)). At the day's start, a wake with the key `day`, kept short, since the agent reads one every day: the open tasks the account is at work on that are planned for today, five of them by number, title and project and the rest counted; those carried over from before, three of them by name; how many are open with no day; how many decisions wait for it; and the command that reads its whole plate, `console work`. A line for what there is and none for what there is not, a title cut at sixty characters, and 2000 characters at the most, whatever the plate holds. On the week's first day, Sunday where the workspace says so and Monday otherwise, the key is `week`, in the day's place, and it adds the tasks planned for the six days after, three of them by name. At the day's end, where it has one, the key is `wrap`: to report on its open runs, write down what should be kept, and commit and push its desk. Each is sent once a day, and an account first heard from after its hour is told at once. `runner.json` begins a new conversation with `day` or `week` where its `conversation` says so.

**A secret's day.** 30 days before the day a secret of an account ends on ([ADR-0087](../adr/0087-an-agent-account-keeps-its-secrets-in-a-store-of-its-own-that-only-it-reads.md)), the same pass sends the account a wake from the `console` with the key `secret:<name>`: the name and the day, never the value, and the command that sets it again. Once for a value: a value set anew has a day of its own to be told of.

The worker reads the feed every five seconds, a hundred events at a time, one pass at a time whatever the number of processes: the place it read to is a row a pass locks. An event's wakes are sent before the place moves past it, so a pass that ends halfway sends an event's wakes again and never loses one. A workspace that had a history when the rules came begins at the feed's end, and a new one at its beginning.

## A session's life

- There is one main session per account. The runner begins one when there is something to deliver and none is open: `POST /api/v1/agents/me/sessions` with what it runs (`product`, `model`, `effort`, `resumed`, `machine`, as the heartbeat spells them), answered `201` with the session, its id in it. A session begun while another of the account is open takes that one over: the console ends the older as taken over, as a run takes over a run.
- The conversation is the product's, resumed from the session before where the driver can (`resume`) and `conversation` in `runner.json` is `continuous`.
- A session ends when a supervisor stops or restarts the agent, when the process dies, or when the machine restarts: `POST /api/v1/agents/me/sessions/<id>/end` with `{ "how" }` (`stopped`, `restarted`, `reset`, `crashed`, `exited`), answered with the session; one that ended already stays as it ended, `taken_over` among it, which is the console's word. The next signal begins the next.
- **An agent that cannot go on waits.** The driver says that the model refused or that the product failed, and why. The runner reports the state and restarts nothing. A supervisor's signal (`source: "person"`) is tried at once, in the same conversation. What arrives by itself waits out a cool-down, fifteen minutes at first and twice as long after each try that ends the same way, four hours at most, and then goes together as one message. A turn that completes ends the waiting.
- A supervisor's `stop` ends the session, and nothing is delivered until a `restart` or a `reset`: what arrives meanwhile is kept and delivered then, grouped. `restart` begins the next session with the same conversation; `reset` with a new one, the agent told in its first message that it was reset, by whom, and that what it was doing is on the board and in its desk.
- `set` is applied through the driver at once where the product takes it in a running session. Where the product takes its model and its effort when it starts, the open session ends as `restarted` as soon as no turn is under way, and the next, which the next signal begins, goes on with the conversation and runs with them; the heartbeat's `running` says what the session runs with.
- A `set` is a supervisor's. The account itself is given none: what an agent changes of its own model or effort is what its product lets a session change, in the product's own way, and the console adds nothing to it and takes nothing from it. Where the product says what the session runs with afterwards, the driver says so and the page shows it (`running`).
- The runner keeps a few things between its own restarts, in `work/runner-state.json` under the desk: the number of the last signal it handed over, the conversation to go on with, and the driver that conversation was begun under. A conversation is a product's own: where `runner.json` names another driver since, the conversation kept is let go and a new one begins, which the runner says in a line, since a product asked to go on with another's conversation fails at every turn. Without the file it goes on from what the console answers its first heartbeat.
- **The runner takes an update of its command by itself** ([ADR-0101](../adr/0101-a-runner-ends-for-an-update-of-its-command-and-its-service-starts-it-again.md)). At every heartbeat it reads the version of the package it runs from, as the package's manifest on the machine says it now. Another version than its own, seen twice running, is an update; a manifest that does not read says nothing. From then on nothing more is handed to the product, the turn under way ends in its own time, the open session ends as `restarted`, with a status that says why, and the runner ends with exit code `0`. The service starts it again, as after any end, on the new command; the next signal begins a session that goes on with the conversation, and what was sent meanwhile is sent again from the console's record. A runner started by hand ends the same way, says so, and is started again by hand. The runner starts no process in its own place and installs nothing itself.
- A runner the console refuses as too old (`client.outdated`) says so on its own output, with the command that installs the console's version the way this command was installed, and, once, to its agent in the open session, with that command: the agent installs it, and the runner takes the update as above. Where the agent cannot, it tells whom it reports to. The runner keeps trying meanwhile.
- Nobody is at the terminal: what the product's policy does not allow is denied and recorded, and the tool by which the product would ask a person at its terminal is taken away.

## The transcript

Built on the console's side ([rest.md](rest.md#the-sessions-and-the-transcript)). The runner reports every event of the driver, in order, as whole blocks ([ADR-0086](../adr/0086-a-session-leaves-a-transcript-that-is-kept-for-good.md)): `POST /api/v1/agents/me/sessions/<id>/events` with a batch, about once a second while there is something to send:

```json
{ "events": [
  { "n": 41, "kind": "tool_call", "at": "2026-11-10T14:02:15.120Z", "text": "git status", "data": { "tool": "Bash", "id": "toolu_01" } }
] }
```

- `n` numbers the events of the session from 1, one after another. The console answers `{ "last": 41 }`, the number of the session's last event now. An event whose number the session has already is left as it is, whatever is sent, so a batch may be sent twice; a batch out of order is `transcript.out_of_order`, and one that would leave a gap is `transcript.gap`, with the number expected in its words, so that whoever reads from a number on misses nothing: the runner asks the session where it stands and sends from there. A batch is at most 100 events and 2 MiB; nothing is added to a session that is over (`transcript.session_over`).
- `kind`: `wake` and `person` (what the agent was sent, a signal's number in `data.signal`), `assistant`, `thinking`, `tool_call`, `tool_result`, `permission` (asked and how it was answered), `status` (the product compacted, the model changed, the session began or ended, a turn completed, which is `turn: "completed"` in its `data` and what tells whoever reads the session as it happens that the agent is done) and `error`. A `person` or a `wake` the session ended on before the product took it carries `unread: true`.
- `text` is what a person reads, up to 256 KiB of UTF-8, and whatever the product said: markup, escapes and control characters are kept as they are and shown as text. The console keeps the beginning in the row, up to 16 KiB cut between characters, and the whole on the month's shelf of the blob store where it is longer; an event read back says `whole`, the size of the whole, and `.../events/<n>/text` reads it.
- `data` is a small object of facts about the block: up to 32 of them, each a word, a number, a yes or no, or nothing, under a name of up to 64 characters, a word up to 1,000. Never nested, shown as text and never run.
- `files` names the pictures of the block, up to 8, by the ids their upload answered: `POST /api/v1/agents/me/sessions/<id>/files`, a form with one part `file`, a PNG, a JPEG, a GIF or a WebP up to the bound on a file, answered `{ "id", "name", "size", "contentType" }`. An event names its own session's pictures and nothing else (`transcript.unknown_file`); a session hands in at most 60 a minute (`transcript.too_fast`).
- Before an event leaves the machine the runner takes out of it every value of the account's secret store, as it is and in the encodings a value is commonly carried in.

The console deletes none of it. `GET /api/v1/agents/<handle>/sessions` lists the sessions, the newest first, and `.../sessions/<id>/events?after=` reads the events, a page at a time, for the account's supervisors and for the account; `.../sessions/<id>/events/stream?after=` is the same as it happens, each `event` under its number, and an `end` with the session once it is over and everything of it was sent. A run the account's command begins while a session is open names it (`sessionId`), so that what the agent did for a task is found in its transcript.

Everything of a session is kept under the month it began in, by the clock everyone shares: its events and its pictures in tables of that month, and the bytes on the month's shelf of the blob store, a table of the month where the database keeps the bytes and the prefix `transcript/<month>/` in a bucket. The session's own row stays, and says `away: true` while its month is not with the database; its events then read as none, and an open session of that month takes nothing more (`transcript.away`). [deploy/README.md](../../deploy/README.md#the-transcript-of-a-month-that-is-past) says how a month is put away and brought back.

An administrator seals an event that must not be kept, `POST /api/v1/agents/<handle>/sessions/<id>/events/<n>/seal` with `{ "reason" }`: its text, its facts and its pictures are replaced by who sealed it, when and why, its bytes are taken off the month's shelf where no other event of the month says the same, and its number, its kind and its time stay. Nothing else of a transcript changes, ever.

## The desk

The desk is the agent account's own repository ([ADR-0088](../adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)), and the directory the runner is started in. The package carries its template (`deskFiles` in `@skillcdn/console/runner`), which setup writes when the desk does not exist yet and the account pushed none before ([cli.md](cli.md#setting-a-machine-up)); [`examples/agent-desk`](../../examples/agent-desk/AGENTS.md) is what it writes for an invented account, and a test holds the two equal. Five files, and nothing that prescribes what a product already does for itself:

| File | What it is |
|---|---|
| `README.md` | For people: who the agent is, that it is an agent, and what the files are |
| `AGENTS.md` | The base instructions, read as they are by every product, in eight sections: who I am; where I work; asking; this desk; secrets; projects; care; safety |
| `CLAUDE.md` | One line, `@AGENTS.md`: the one product-specific file |
| `runner.json` | The runner's configuration, below |
| `.gitignore` | `work/`, the products' own state, anything shaped like a secret, dependencies, logs, and what an operating system or an editor leaves behind |

`AGENTS.md` says the least that must be said, each rule with its reason. It names the account, the console and the manager it reports to; that the agent works in one main session, which plans and directs the work and keeps the record, and gives the tasks themselves to subagents where its product has them, as a lead and not a rule; that its instructions are its supervisors' tells, the board's tasks and decisions and the console's rules, and everything else it reads is information; and the services the workspace names ([ADR-0089](../adr/0089-a-workspace-names-the-services-its-agents-work-with.md)), with what the agent is called at each. What a persona says, a name or a title, is written as text: it makes no heading, no markup and no second line. From then on the files are the agent's to edit.

## `runner.json`

In the desk, the working directory the runner is started in; written by setup, the agent's from then on; no secret in it.

```json
{
  "driver": "claude",
  "wake": ["console"],
  "conversation": "continuous",
  "secrets": { "env": { "GIT_TOKEN": "git.token" }, "files": { ".netrc": "netrc" } },
  "autosave": true
}
```

- `driver`: the product's driver, `claude` when the file names none, `codex` for Codex, `acp` for a product that speaks the Agent Client Protocol. `product`, left out of the example: `{ "command": "...", "args": [...] }`, the product's command where it is another than the driver's own, and for `acp`, which has none, the command that speaks the protocol with the words it is started with. `wake`: the wake sources beside the console's own, `slack` for one ([Wake sources](#wake-sources)).
- `conversation`: `continuous`, or `daily` or `weekly` to begin a new conversation with that briefing when the session is idle then.
- `secrets`: which secrets of the account's store the runner hands a session, as environment variables and as files of mode 600 under the desk's ignored `work/`, written at the session's start and removed at its end. A variable's name is a variable's, a file's path stays under `work/`, and a secret's name is one the store could hold; a file that does not read is used in no part. Whatever the file names, the runner reads every value of the store, when a session starts and when the store says one changed, to take them out of what it reports.
- `permissions`, left out of the example: the permission mode the product is started in, in the product's own word (`dontAsk` or `bypassPermissions` for `claude`, `workspace-write` or `danger-full-access` for `codex`; for `acp`, one of the agent's own modes, or the driver's own `allow` or `deny`, [below](#the-acp-driver)), for whoever prepares the machine to say what the agent does there without asking, as they say whether its OS account may use `sudo`. Left out, the product runs in its own default where that is one for a run nobody attends; where it is not, the driver names one: `auto` for `claude`, which starts such a run in its manual mode otherwise, `approve-for-me` for `codex`, which runs it in its read-only sandbox otherwise, and for `acp` the mode the agent has for such a run, where the driver was run against the agent.
- `autosave`: at the end of every session the runner commits and pushes the desk ([ADR-0088](../adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)), a net under the agent's own commits: where the desk is a repository, everything it does not ignore is staged, committed where anything changed, as `Autosave at the end of a session`, and pushed. Git asks nobody at a terminal, what it prints is not kept, and a step that does not succeed is said in the runner's line by how git ended; the runner goes on. `false` turns it off.
- A runner started where there is no `runner.json` runs with these defaults and hands the session no secret.

## Wake sources

A wake source is a module that raises wakes from outside the console: what is said to the agent at a messenger. `runner.json` names the ones a runner keeps beside the console's own stream (`"wake": ["console", "slack"]`), which the runner listens to itself:

```ts
interface WakeSource {
  readonly name: string;
  /** Listens until it ends or the signal does; the runner starts one that ended again, after a while. */
  run?(host: WakeHost, signal: AbortSignal): Promise<void>;
}

interface WakeHost {
  /** A secret of the account's store, by name. */
  secret(name: string): Promise<string | undefined>;
  /** Raises a wake: the console records it, and it reaches the agent in order, as someone else's words. */
  raise(wake: { key: string; text: string }): Promise<void>;
  log(line: string): void;
  fetch(url: string, init: { method: string; headers: Record<string, string>; signal: AbortSignal }): Promise<{ json(): Promise<unknown> }>;
  socket(url: string): { messages: AsyncIterable<string>; send(text: string): void; close(): void };
  wait(ms: number, signal: AbortSignal): Promise<void>;
}
```

The runner starts each source when it starts and keeps it for as long as it runs: a source that ends is started again after five seconds where it held for a minute, and after twice as long each time, up to five minutes, where it keeps ending at once; its line says the source's name and a short name of why, and never what was said. A source tells the agent nothing itself: what it raises goes to the console, `POST /api/v1/agents/me/signals`, which records it as a `wake` from the `messenger`, by nobody, and it comes back on the runner's stream in order, with the same key merged as any wake is. Its words reach the agent as someone else's, in a block fenced longer than any run of fence characters they hold ([How a signal reaches the product](#how-a-signal-reaches-the-product)).

### The `slack` wake source

One app for one agent account ([ADR-0085](../adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md), point 2), which receives over its Socket Mode connection the events the agent's own member of the workspace can see. Written from the messenger's own documentation of Socket Mode and of the Events API, and not run against a workspace yet; the app is made from the manifest the skill `running-an-agent` carries.

- **The token** is the app's own for the socket (`xapp-...`), kept by the account in its store as `slack.app_token`. Where there is none the source says so and looks again in five minutes.
- **The connection** is asked for with `POST https://slack.com/api/apps.connections.open`, the token in the `authorization` header, and the address answered is opened only where it is the messenger's own socket (`wss://`, a host of `slack.com`). Every envelope that arrives is acknowledged by its `envelope_id`, before it is read; a `disconnect` ends the connection, and the runner starts the source again.
- **What wakes the agent**: a message in a direct conversation, and a message that mentions the member the event was delivered for (the first of the event's `authorizations`), from anyone but that member; an app's own `app_mention` too. An edit, a join, a deletion, a reaction and what the agent said itself wake nobody.
- **The wake** has the key `slack:<channel>:<thread>`, the thread being the message's own where it begins one, so that what is said in one thread is one thing to the agent; and says where it was said and by which member, with the message's words after it, cut at 4,000 characters. The agent reads the thread with the messenger's own tool.
- **An event is data**: read by schema, with ids and moments spelled as the messenger spells them and bounded lengths; what does not read wakes nobody, and nothing of an event is run.

## The service

A service is the module that keeps the runner running across restarts of the machine, a platform each: `launchd` on macOS, `systemd-user` on Linux, `task-scheduler` on Windows. It says what to write and what to run, and `console agent setup` does it ([cli.md](cli.md#setting-a-machine-up)):

```ts
interface Service {
  readonly name: string;
  /** The platforms it keeps a runner running on, as the runtime names them. */
  readonly platforms: readonly string[];
  /**
   * Whole files with their modes; commands in order, each with what it adds to the environment,
   * whether it may fail and what is left to do where it did, and how often it is tried; the
   * commands that have the system read a file written again without ending the runner; where
   * the runner's lines are kept. Or why it cannot.
   */
  plan(input: { desk: string; home: string; uid: number | undefined; user?: string; program: string[]; path: string | undefined }): ServicePlan | { problem: string };
}
```

`launchd`, for macOS, plans a launch agent of the agent's own OS account: the unit `~/Library/LaunchAgents/ai.skillcdn.console.runner.plist`, which starts the runner in the desk when the account logs in (`RunAtLoad`) and again whenever it ends (`KeepAlive`), with the `PATH` setup ran with, so that the product is found where it was, and its lines in `~/Library/Logs/ai.skillcdn.console.runner.log`; then `launchctl bootout gui/<uid>/ai.skillcdn.console.runner`, which fails where none was loaded, and `launchctl bootstrap gui/<uid> <unit>`. Nothing of it needs an administrator's rights, and so the runner runs while the account is logged in at the machine: that the account is logged in when the machine starts is for whoever prepares it. The unit holds no secret: the runner signs in with what the command keeps. What a path or a login holds is written as text of the unit. It is written from the system's own documentation and was not run on a Mac yet.

`systemd-user`, for Linux, plans a unit of the agent's own OS account, kept by that account's own instance of systemd: the unit `~/.config/systemd/user/skillcdn-console-runner.service`, which starts the runner in the desk and starts it again ten seconds after it ends (`Restart=always`), with the `PATH` setup ran with; then `loginctl enable-linger <uid>`, and `systemctl --user daemon-reload`, `enable` and `restart` of the unit, so that a unit written again is the one that runs. Its lines are in the account's journal (`journalctl --user -u skillcdn-console-runner.service`). It needs no administrator's rights. The account's systemd is there while the account has a session, or always once lingering is on for it, which also starts it with the machine: the account asks for lingering itself, which Ubuntu allows, and where a system keeps that for an administrator the service is loaded all the same and setup says what is left to do and who does it. The system answers that request before the account's systemd is there, so the command after it is tried for ten seconds; and that systemd is reached through the folder the system keeps for the account (`XDG_RUNTIME_DIR=/run/user/<uid>`), which a shell entered from another account is not told of. A refresh that wrote the unit again runs `systemctl --user daemon-reload`, which ends nothing that runs: without it the system goes on with the unit it read before. What a path or a login holds is written as words of the unit: on one line, quoted, with what the system reads as a specifier or a variable said as itself. Run on Ubuntu 24.04 with systemd 255 (2026-11-11, under WSL), from the command installed with npm and an invitation's line: the unit loaded, the runner heard from, started again ten seconds after its process was ended from outside, lingering turned on by the account itself, and a unit changed by hand written again and read. Not seen there: a restart of the machine, an OS account with no session at all, and a product, none being signed in on that system.

`task-scheduler`, for Windows, plans a scheduled task of the agent's own OS account, called by whose it is, `SkillCDN Console Runner (<account>)`, since a task is the machine's and one list holds every account's: its definition `~\AppData\Local\skillcdn-console\runner-task.xml`, then `schtasks /Create /TN <name> /XML <definition> /F`, which registers it in place of the one that was there, `schtasks /End`, which ends the one that runs, and `schtasks /Run`. The task starts when the account logs on, as the account that registered it, with none of the limits a task has by itself: it is not ended after three days, not kept from a battery, and not run below everything else. Nothing of it needs an administrator's rights, and so the runner runs while the account is logged on at the machine, as on macOS: the system refuses an account a task of its own that runs with nobody logged on, and that the account is logged on when the machine starts is for whoever prepares it. The system starts a task once and in a window, gives it the account's environment, keeps nothing it writes, and ends it by ending the one process it started. So what the task starts is one line of the system's own shell, in no window, which starts the runner in the desk with the `PATH` setup ran with, adds what it writes to `~\AppData\Local\skillcdn-console\runner.log`, starts it again ten seconds after it ends, and tells it which process keeps it (`CONSOLE_RUNNER_KEEPER`, that process's number): a runner told so looks for that process every two seconds and stops when it is gone, so that ending the task ends the runner. A runner that was left all the same, the same program started with the same words to their end, is ended with what it started before another begins: one runner for the account. A desk that is gone is a line of the log, and nothing is started. A refresh that wrote the definition again registers it, which ends nothing that runs: the next start is with what was written. What a path or a login holds is written as words of that shell, each whole, with a percent sign said by its number, since the system fills a variable in where it reads a name between two; and as text of the definition in the letters every encoding shares, a letter beyond them by its number, since the system reads a definition that names no encoding in the machine's own. A quote, which a task's command line does not carry, and a line longer than one carries are why no task is written. Run on Windows 11 (2026-11-12), from an invitation's line against a console on the same machine, in an account of the administrators' group from a shell without their rights: the task was registered and started and the runner heard from, and a turn of Claude Code ran under it; the runner's process ended from outside, it ran again ten seconds later; the task ended, the runner was gone within five seconds and nothing started it again until the task was run; a definition changed by hand and registered so was written and registered again by `--refresh`, with the runner left running; and a task that would run with nobody logged on was refused. Not seen there: the account logging on, which is what starts the task from then on, a restart of the machine, an account with no administrator's rights at all, and an account of a domain.

## The driver

The runner knows its modules by name, from four registries (`createRunnerModules`): drivers, wake sources, services and boundaries. The package registers `claude`, `codex` and `acp`, `console`, which is the console's own stream of signals, and `os-user`; what `runner.json` names is looked up there and is never a path to load. A driver is a module of the first, a product each:

```ts
interface Driver {
  readonly name: string;
  /** What the product is called, and the versions of it the driver was tried with. */
  readonly product: { readonly name: string; readonly tried: readonly string[] };
  /** What the installed product is and offers, asked without starting a session. */
  probe(): Promise<{ version: string | undefined; models: string[]; efforts: string[] }>;
  /** Starts the product: resuming the conversation before where `resume` is given, with a model and an effort where they are. */
  start(options: StartOptions): DriverSession;
  readonly can: { readonly steer: boolean; readonly images: boolean; readonly resume: boolean; readonly set: boolean };
  /** The product's permission modes, the one for a run nobody attends, and the one that allows the least. */
  readonly permissions: { readonly modes: readonly string[]; readonly unattended: string; readonly least: string };
}

interface DriverSession {
  /** A message for the agent, with pictures; `now` stops the turn first, `next` goes after the current tool call. */
  send(message: { text: string; images: Picture[]; priority: "now" | "next" }): Promise<void>;
  interrupt(): Promise<void>;
  /** The model and the effort, where the product takes them in a running session; false where it does not. */
  set(choice: { model?: string; effort?: string }): Promise<boolean>;
  stop(): Promise<void>;
  /** What the product does, as whole blocks, until it ends. */
  readonly events: AsyncIterable<DriverEvent>;
}
```

A `DriverEvent` is a transcript event before its number (`kind`, `text`, `data`, attachments), or one of the driver's own words to the runner: `taken`, once for every message it was sent, when the product reads it, said back by the product, started in a turn or prompted with; `turn_completed`; `cannot_go_on` with `refused` or `failed` and a reason of the heartbeat's list; `conversation`, the id the product resumes from next time; `ended`, with how.

### The `claude` driver

The Claude Code binary, unmodified, over its streaming JSON input and output, as its own documentation and its own help have them. What they state is relied on; what they leave unsaid was seen by running the driver against the binary, 2.1.321 first, and is held by fixtures written down from what it printed, in tests that call nobody. What was not seen there, a refusal and a sign-in that ran out, is read as the documentation gives it. A version the driver was not tried with is started all the same and said on the Live page.

- **Started** as `claude -p --input-format stream-json --output-format stream-json --verbose --replay-user-messages`, in the desk, with `--model` and `--effort` where the account's settings name them, `--resume <id>` where a conversation is resumed, `--permission-mode` and `--permission-prompts none`: nobody is at the terminal. The mode says what runs without asking. A product is started in its own default wherever that default is one for a run nobody attends, and its driver then names nothing; this product's is not: with nobody at its terminal it starts in its manual mode, in which whatever needs approval, a file written among it, is denied. So the mode is `auto` where `runner.json` names none (`permissions`), in which the product's own classifier reviews each action; a build that starts such a run in `auto` by itself needs nothing named. Where the product starts in another mode than the one asked for, as where the account or the model has no `auto`, the session's first event says so. What would still prompt is denied, the agent is told not to try it again, and the tool that asks a person at the terminal is taken away. A mode named that is none of the product's is a mistake in the desk's file and never leave to do more: the session starts in `dontAsk`, which allows the least, and its denials say so in the transcript. No file of settings is written for the product: its own settings in the agent's OS account stay its operator's and the agent's. The process stays open, reading one message a line from its standard input.
- **A message** is one line: `{"type":"user","uuid":"...","message":{"role":"user","content":[...]},"parent_tool_use_id":null,"priority":"next"}`, the content a text block and an image block for each picture (`base64`, of the kinds the product takes), under an id of the driver's, which the product says back when it takes the message off its input. `priority` is the product's own: `next` is read when the tool calls under way finish, in the same turn, or starts a turn where none is under way; `now` is read in a turn of its own, and the product stops the turn under way for it only once its tool calls finish, however long they run. An `interrupt` with its words is therefore two lines: the request that stops the turn and the tool call in it at once, `{"type":"control_request","request_id":"...","request":{"subtype":"interrupt"}}`, which is what the product's own client library sends and does nothing where no turn is under way; and then the message, with `now`.
- **What it reads**, a line each: `system` with `init`, which the product writes when it starts and again at every turn (the conversation's id as `session_id`, the model, the product's version, its permission mode), becomes a `status` event and the driver's `conversation` the first time, and again only where what it says is something else; `assistant` becomes `assistant`, `thinking` and `tool_call` events, a block each; `user` carrying tool results becomes `tool_result` events, a picture among them an attachment; `system` with `compact_boundary`, `api_retry` or `permission_denied` becomes `status`, `error` and `permission`; `result` ends a turn, with the denials of `permission_denials` the product did not say before as `permission` events. Whatever else it writes, what its commands are, how much of its allowance is left, what became of a message, is left where it is.
- **When the agent is done** with what it was sent: `turn_completed` follows a result only when no message the driver wrote still waits to be taken. A message written while a tool call runs is read in the same turn, and the two have one result; a message written as a turn was ending starts a turn of its own, and so does the message a turn was stopped for, so the result before it is not the agent done. A turn that was stopped ends in a result that calls itself an error and says how it ended (`terminal_reason`, `aborted_tools` or `aborted_streaming`): a `status`, and no error. A build that says no message back is read without, every result the end of a turn.
- **An agent that cannot go on.** A result whose `stop_reason` is the model's own word for an answer it would not give, `refusal`, is `cannot_go_on` with `refused` and `model_refused`. A result or an exit that says the product is not signed in, its login expired or its key is refused is `failed` with `sign_in`: the product's words for it are its own and no contract, so they are read by pattern, which is the first thing a version's fixtures hold. A process that does not start is `start`, and one that dies mid-turn `crashed`. What was sent to a product that did not start, or is not signed in, is kept and tried again; a turn that ended with any other error is a turn that ended, and the agent takes the next message.
- **The model and the effort** are the product's aliases and levels, as its documentation lists them, `opus`, `sonnet`, `haiku` and `fable`, and `low`, `medium`, `high`, `xhigh` and `max`; the binary offers no list of its own to ask, and its version is read from `claude --version`. They are given when the process starts, so a `set` is applied at the next session: the open one ends as soon as no turn is under way, and the next goes on with the same conversation.
- **Stopping**: the standard input is closed and the process is given a moment to end; then it is ended. A turn alone is stopped with the same request an interrupt begins with, which leaves the process open for the next message.
- **Signing in** is the product's: a subscription signed in through its own flow in the agent's OS account, or the long-lived token its own command issues, which the runner provides in the environment the product reads it from when `runner.json` maps a secret to it. The driver never reads or keeps either.

### The `codex` driver

The Codex binary, unmodified, run with nobody at its terminal: `codex exec --json`, as its own help has it. A process a turn, since that is how the product runs without a terminal, and the conversation gone on with by the id its first turn names. Written from what the binary printed when the driver was run against it, 0.164.0-alpha.11.1 first, and held by fixtures written down from that, in tests that call nobody.

- **A turn** is started as `codex exec --json --skip-git-repo-check`, in the desk, with `-m` and `-c model_reasoning_effort` where the account's settings name them, and the message on its standard input; a turn of a conversation gone on with as `codex exec resume ... <id>`. The desk is the agent's own, a repository or not one yet. A model, an effort or an id that is no plain word is left out, so that nothing the driver is handed becomes an option of the product's.
- **The mode** is said at every turn, since a turn keeps nothing of the mode the turn before ran in, in the product's own words: its three sandboxes, `read-only`, `workspace-write` and `danger-full-access`, in which whatever the sandbox does not allow is asked of nobody and refused; and `approve-for-me`, in which the desk may be written and the product's own reviewer answers what would otherwise be asked of a person. With nobody at its terminal the product runs in `read-only`, where a file written is refused, so the driver names `approve-for-me` where `runner.json` names none. A mode named that is none of these starts the turn in `read-only`.
- **No message is taken in a turn** (`steer: false`). One that arrives while a turn runs waits for the turn to end and is the next turn's, read with whatever else waited; one that is to be read now, an `interrupt` with its words, ends the turn's process first, and the product goes on from there knowing that what it was doing was cut. `turn_completed` is said when a turn ended and nothing waits.
- **What it reads**, a line each: `thread.started`, written at every turn, names the conversation and becomes a `status` event the first time; an `item` that is an `agent_message` becomes `assistant`; a `command_execution` or a `file_change` becomes `tool_call` when it starts and `tool_result` when it completes, a command with its output and what it ended in; `turn.failed` and `error` become an `error`, said once though the product writes it twice. Its reasoning, a tool of a server and a search are read as its documentation gives them, and were not seen.
- **An agent that cannot go on.** A product that is not there to start is `failed` with `start`. An error that says it is not signed in is `failed` with `sign_in`, read by pattern: its words for it were not seen, since that takes signing it out. A turn's process that ends with no word of how the turn ended fell over, and the agent cannot go on by itself: before a turn started it is `start`, as when the product does not find the conversation again (`thread/resume failed: no rollout found`, seen run), and what was sent is kept and tried again, which a `reset` cures; after one started it is `crashed`, and nothing is sent again, since what the turn was at is not known. A turn the product itself says failed, `turn.failed`, is a turn that ended, and the agent takes the next message. The product has no word of its own for an answer the model would not give.
- **The model and the effort** are each turn's, so a `set` is taken from the next turn on, with no session ended for it. What the product offers is asked of the product: `codex debug models`, the models it lists for a person to choose from and their levels of effort; its version is read from `codex --version`.
- **Pictures** are handed to it as files (`images: true`, `imageFiles: true`): each as `-i <path>`, the path the runner wrote it at from the desk, after `exec` or `exec resume` and before `--json`, since the product's option takes several values and would take what follows it for one. Only a path under `work/inbox/<number>/` goes on the command line. Seen with the binary (0.167.0), on a first turn and on one gone on with.
- **Stopping** ends the turn under way, if there is one: the process is asked to end, and then ended.
- **Signing in** is the product's own, in the agent's OS account, as with `claude`.

The product also has an app server, which takes a message in a turn and is what its own editor extension speaks; the product calls it experimental, and a driver over it is a later one.

### The `acp` driver

Any product that speaks the Agent Client Protocol, version 1: the command `runner.json` names as `product`, started once for a session and spoken to over its standard input and output, a JSON-RPC message a line, with the runner as the protocol's client. Written from the protocol's documentation and held by fixtures in its shapes, in tests that call nobody; read since against the types the protocol publishes and against the source of one agent that speaks it, an adapter that puts Codex behind the protocol, which is where the points below say what an agent does beside the protocol. Run since (2026-11-12) against that adapter, its 2.6.0 over Codex 0.167 on Windows 11 with a signed-in account and a lower model, by the driver alone with no runner around it: what it is and offers asked, eight models and six levels; turns with a shell command and with a change to a file, each with its result; a message read now, which stopped the turn and was the next; an interrupt; the model and the level set in a running session; a conversation gone on with in a new process, and one that was not there begun anew with the agent's reason; a model it does not offer left to the product's own; a picture handed over and read; and leave asked where the product's mode keeps writing back, allowed once, and refused where the desk says so, on which that agent ends its turn. Run the same day against the adapter that puts Claude Code behind the protocol, its 0.106.0 over Claude Code 2.1.322 with a lower model: turns with a command and with an edit, a message read now, an interrupt, the level set, a conversation gone on with, a picture, and its manual mode named, in which it asked leave to write, was refused and went on with its turn. The runner whole, with this driver, was run against a scripted agent only, which is where a model chosen in a running session was seen to stay the old one on the agent's page, and the calls of a second turn, numbered as the first's, to be missing from the transcript; both are corrected.

- **Started** as the command and the words `runner.json` names, in the desk. The runner says `initialize` with version 1, what it is with the command's own version (`clientInfo`), and offers no file and no terminal of its own (`fs` and `terminal` both off), so that the agent works with its own tools in the desk, and a request for one is answered as a method that is not offered. A product that answers with another version is `failed` with `start`.
- **The session** is opened with `session/new`, the desk as its directory and no MCP server of the runner's. A conversation is gone on with where the agent can: `session/resume` where it resumes, `session/load` where it only loads, with what it replays then left unread; an agent that does neither begins a new one, and the transcript says so. A conversation the agent cannot go on with, one it has no more or never kept, is said in the transcript with the agent's reason, and a new one begins, as one begins where the conversation kept was another driver's; an agent that says it is not signed in is said as that. The id of the session is the conversation's.
- **A turn** is `session/prompt`: what arrived together as one prompt, each message a block of text, with its pictures as `image` blocks where the agent takes them (`promptCapabilities.image`). The session says whether it does once the agent has said so, and the runner then hands a picture over as a file alone, saying so; for a message sent before that, the driver adds a line saying how many were not shown and where they are in the desk. How the turn ended is the answer's `stopReason`: `end_turn` is a turn completed; `cancelled` one that was stopped; `max_tokens` and `max_turn_requests` are said as a `status` and are a turn that ended; `refusal` is the model's, `refused`; an error on the request is said, and is a turn that ended. A turn the agent itself ends as cancelled where it was refused leave, which nobody stopped, is said as that.
- **No message is taken in a turn** (`steer: false`). One that arrives while a turn runs is the next turn's; one that is to be read now, and an `interrupt`, say `session/cancel` first, and the agent answers the turn as cancelled. A method of an agent's own for a message in a turn, beside the protocol, is not spoken.
- **What it reads** are the `session/update` notifications. The agent's message and its thought arrive in pieces and are kept until whole: an `assistant` and a `thinking` block each, ended by whatever comes that is something else. A `tool_call` is a `tool_call` event, its title with its input, said once the input is known: an agent may open a call before what it is called with is whole and say that in an update, so a call is said at the update that brings its input, at the next thing said of it where it has none, and before whatever else is said; a call opened under an id whose call is done is another call, so that an agent that numbers its calls anew at every turn has each of them on the record; the update that completes it or fails it a `tool_result`, with what the call held last: an update names what changed and leaves the rest as it was, so what was said when the call began is its result where its end says the status alone. The result is the text of its content, a file by its path with what became of it (written, changed, removed), and its pictures handed in; where the content holds no text, what the call's command printed, which an agent may send beside the protocol while the command runs (`_meta.terminal_output`, whole, or `_meta.terminal_output_delta`, a piece at a time, kept to 200,000 characters); and its output as data where there is neither. A `plan` is a `status`. A choice the agent changed is kept, and said to the runner where it is the model or the effort. The rest, the commands it offers, its mode, what it used and what a person typed said back, is none of the transcript's. What the agent tells beside its work, a warning or an error of its own, is taken as a `notice` (the client says that it takes them, `session.notices`, or an agent says such a thing as its own words in the middle of an answer): a `status`, or an `error` where the agent says it is one. A block is its words, without the empty lines an agent may begin or end it with.
- **What the agent asks leave for** (`session/request_permission`) is answered at once, since nobody is at a terminal, and recorded as a `permission` event. `permissions` in `runner.json` says how, in the driver's own two words, there being no one product to take a word from: `allow`, the one where it names none, takes the option that allows the call once, since an agent refused everything does no work; `deny` takes the one that refuses it once, for an agent that is to do only what its own mode lets it without asking. An agent that offers neither is answered that the request was cancelled. What an agent does without asking is its own mode's, and the protocol has a session say its modes and set one: a choice of the category `mode`, or `session/set_mode` ([ADR-0091](../adr/0091-an-agent-over-the-protocol-runs-in-a-mode-of-its-own-which-the-desk-or-the-driver-names.md)). The mode the other two drivers name, in which the product works without asking and a review of its own holds back what looks unsafe, is the agent's to have under whatever name it gives it; the protocol has no word for it. So `permissions` may also name one of the agent's own modes: the session is set to it, and what the agent still asks is refused, since the mode is what it may do with nobody there. Where `permissions` names none, an agent the driver was run against is set to the mode it has for a run nobody attends, and what it still asks is refused: `agent`, its automatic review, for the adapter that puts Codex behind the protocol, which in that mode asked nothing in the runs seen, a file written beside the desk included, and in `read-only` asked leave to write; `auto` for the adapter that puts Claude Code behind it, which starts in it where the model has one, and in its manual mode, `default`, asked leave to write. Any other agent runs in its own mode and is allowed each call once, as above: the driver cannot tell an agent that asks only for what its review held back from one that asks for everything, so whoever prepares its desk names its mode. A mode named that the agent does not offer is a mistake in the desk's file: the transcript says so with the modes the agent offers, the agent runs in its own, and what it asks is refused. When an agent gains such a mode, naming it in `runner.json` is all its desk needs; the driver's list of what each agent calls it (`UNATTENDED_MODES` in `acp.ts`, beside the versions tried) is where it becomes the default, once it was run.
- **The model and the effort** are the session's choices of the categories `model` and `thought_level` (`configOptions`): what the agent offers is what the account's settings choose from, each set with `session/set_config_option` when the session opens and when a `set` arrives, in a running session (`set: true`). What the session runs with is said when it opens and again whenever that changed, by a `set` taken or by the agent itself, so that the heartbeat's `running` is what the agent runs with now and not what its session began with. What it offers is asked without a session to run: the product is started, asked what it is (`agentInfo`, whose name is what the runner calls it and whose version is its version), a session is opened for its choices and closed again where the agent closes one (`sessionCapabilities.close`), and it is left.
- **An agent that cannot go on.** A product that is not there to start, or that opens no session in two minutes, is `failed` with `start`. The protocol's own code for a request it takes only when signed in (`-32000`), and an error that says so, is `failed` with `sign_in`; what an error says is its message with what it carries beside it (`data`), since an agent may say no more than that something failed and put why there. A process that ends by itself is `crashed`, or `start` where it never answered. What the driver cannot tell is a turn the agent ended as completed while saying, in its own words, that it failed, as the adapter read does with an error of its model: that is a turn completed, with the agent's words in the transcript.
- **Stopping** closes the product's input, then asks it to end, then ends it.
- **Signing in** is the product's own, in the agent's OS account, as with `claude`: the protocol's `authenticate` is not spoken, since it asks a person.
