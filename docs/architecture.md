## Overview

```
person (browser)  ------------------------>  console, role api  -------->  PostgreSQL
                                             |  the REST API, for the UI     the projects, each with its board: tasks, runs,
agent (Claude Code, Codex, any with a shell) |  and for agents' commands,     decisions, goals, documents, events, members;
                                             |  sign-in through a provider    people, categories, sessions, tokens; the job queue
  ---- the `console` command, over REST ---> |  sign-in through a provider
      |                                      |
      |  its own SkillCDN connection          v  a project's skills, by address, for the board
      +---------------------------------->  a SkillCDN deployment (skillcdn.ai or self-hosted)
                                             read through @skillcdn/client; or a pack in a directory of the
                                             console's own, for a local address, read with @skillcdn/reader

console, role worker      schedules, reminders, clean-up; the plugins' hooks and jobs; the wakes of the agent accounts' runners
console runner            on an agent account's own machine: signed in as the account, keeps its agent's session, feeds it the signals, reports the transcript
blob store                the files runs hand in, people and agents put in comments, and people attach to documents, keyed by content hash: rows of PostgreSQL, or a bucket through the S3 API
```

Five properties shape everything else:

- **People decide, agents work.** Every change of state is attributed: to a person, or to an agent acting for a person, named beside them, and every record that names the person who did a thing names that agent too ([ADR-0056](adr/0056-a-record-that-names-the-person-who-did-a-thing-names-the-agent-they-did-it-through.md)). A decision is a record of its own, with the question, the options, who answered and when. The aim is that people make the decisions that matter and nothing else.
- **The board is the record.** What is to be done, what is being done, what was decided and what the work rests on live in the database, never in a conversation, an agent's memory or a machine: the tasks, the runs, the decisions as records of their context, their rationale and what followed, and the documents, pages of Markdown by path with every version kept ([ADR-0009](adr/0009-documents-are-pages-of-markdown-in-a-project-addressed-by-path-versioned-and-linked-both-ways.md)). Several people, each with their own agent, see one board per project, and what a person may see and change is decided per project ([ADR-0008](adr/0008-a-workspace-holds-projects-and-what-a-person-may-see-and-change-is-decided-per-project.md)).
- **Built on SkillCDN, not inside it.** The organization's playbooks and skills are git repositories served by SkillCDN, or, where no deployment is reachable, directories on the console's own machine in the same format. The console refers to them by address and reads them through the published packages and the REST API; it stores nothing of their content.
- **One image, one database.** Local development and a cloud deployment run the same image against PostgreSQL and S3-compatible storage ([ADR-0002](adr/0002-one-image-one-database-and-the-main-repositorys-toolchain.md)). Nothing in the code names a cloud.
- **What an agent sends is data.** A report, a file, a proposed decision: parsed at the edge, bounded, stored, shown as text; never executed, never rendered as HTML.

## The operating model

Whoever runs the console for an organization deploys the image once, configures how people sign in and who is a member, and keeps the organization's playbooks and skills in git repositories in the SkillCDN format. The people of the organization then work with the agents of their own choice: each runs their agent in their own app or CLI, on their own machine and under their own subscription, and connects it to the console. The board is where their work is written down, moved along, decided on and shared. Every organization has skills and a console of its own; the console in this repository is the reference, and what an organization builds from the package is theirs.

Three consequences shape the design:

- **The console calls no model API and starts no agent.** An agent is a person's own process, working the board through the `console` command with a token that person made ([ADR-0004](adr/0004-people-and-agents-reach-the-board-only-through-the-api-with-a-credential-of-their-own.md), [ADR-0006](adr/0006-agents-work-the-board-through-the-rest-api-and-the-command-line-not-an-mcp-server.md)). The console sees what the agent reports and hands in. An agent account's runner, on the agent's own machine, signed in as the account and under the agent's own subscription, starts its agent when the board has work for it and feeds it what its supervisors say ([ADR-0085](adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md)); the console still starts none and holds no credential of a model's.
- **Nobody touches the database.** People hold sessions, agents hold tokens, both reach the board through the REST API, and every request is decided at the edge. The one database credential is the server's.
- **Identity comes from a provider; membership and roles are the console's** ([ADR-0005](adr/0005-people-sign-in-through-an-identity-provider-and-membership-and-roles-are-the-consoles-own.md)): GitHub today, Google Workspace next, more as adapters. What a person may do, and what their agents may do, is kept here.

## Vocabulary

These are the concepts the schema, the API and the UI are named after. The vocabulary in code is `@skillcdn/console/api`; the schema is in [`apps/console/README.md`](../apps/console/README.md#data-model).

| Concept | What it is |
|---|---|
| **Workspace** | An organization: its people, their sessions and tokens, and its projects. A deployment holds one until a need for more appears (`WORKSPACE_NAME`). |
| **Project** | The unit of work and of permission: a key (what paths and the command say), a name, a description, a visibility (`workspace`: everyone of the workspace is a member; `private`: only those listed), a skills address or none, a mark (an image of its own, or a symbol on a colour, or the ones the pages choose from its key and its name), and its board. Every task, run and decision belongs to one; tasks are numbered per project. |
| **Member** | A person listed in a project, with a role in it: an `owner` configures the project (its settings, its members), a `member` works on it. A workspace administrator is an owner of every project. |
| **Person** | Someone who signed in through an identity provider (GitHub, Google) and was let in: by the git host's organization, by the Workspace domain, or by an administrator's listing of their login ([ADR-0022](adr/0022-who-is-in-is-the-consoles-own-record-and-an-administrator-keeps-it.md)). Active, or deactivated: kept with everything they did, and refused. |
| **Team** | A key, a name and its members ([ADR-0073](adr/0073-a-team-is-a-name-and-its-members-a-unit-to-call-people-by-and-to-grant-a-plugins-role-to.md)): the key is what it is called by, a project key's shape, one among the projects' keys of the workspace, and never changes ([ADR-0074](adr/0074-a-team-is-called-by-a-key-that-never-changes-one-name-among-the-projects-keys.md)); a person is in any number of teams; a unit to call people by (the people listing names each person's teams, a plugin reads them) and to grant a plugin's role to, following the membership. No head and no team above a team: the reporting line says who is above whom. Kept by an administrator; not a member of a project and not an owner of work, which are later decisions if asked for. |
| **Agent** | An agent connected by a person: its kind (Claude Code, Codex, any agent with a shell), the token it holds, the person it acts for. An agent is that person for the board's purposes, and is shown as "agent for *person*". |
| **Agent account** | A member of its own kind, `agent` ([ADR-0084](adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md); built, milestone 41): under the same rules as a person and never an administrator, the one rule that reads the kind; made by an administrator, signed in through the identity provider with an account of its own, its command holding a session kept while it is used; a name, a handle that never changes (`@mira`), a title, as every member has one, and an avatar kept as a seed and its parts, drawn where it is shown and written out as a picture file where one is needed; always with a manager, a person or another agent account, whom it reports to and does not belong to. Its **supervisors**, the administrators and the line above it, watch it, tell it, interrupt it, stop it, start it again, set the model and the effort it runs with, and keep its persona. |
| **Runner** | The program on an agent account's machine, `console runner`, in the agent's own OS account, signed in as the account ([ADR-0085](adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md)): it starts the agent's product through a **driver** (`claude`, `codex`, and `acp` for whichever product speaks the Agent Client Protocol), raises wakes from a **wake source**, is kept running by a **service** module (`launchd` on macOS, `systemd-user` on Linux, `task-scheduler` on Windows), and separates agents by a **boundary**, an OS account each on a shared machine. |
| **Session** | Two things, told apart by what they are of. A member's session is where they are signed in: a browser, or, for an agent account, its command; it lasts while it is used. A runner's session is one run of the agent's product from its start to its end, one process or a process a turn as the product runs: one main session per agent account, with no idle timeout, a new one taking over an open one; ended by a stop, a crash or a restart, and resumed by the next, the conversation continuous unless the agent's configuration says daily or weekly. An agent's **state** is `running`, `stopped`, `refused`, `failed` or `unheard`: one the model refused or whose product failed waits, a supervisor's signal tried at once and what arrives by itself after a cool-down; one a supervisor stopped stays stopped until a supervisor restarts it or resets its conversation; nothing begins a new conversation for an agent that could not go on, and every change of state is an event a plugin may carry to its manager. A run names the session it began in. |
| **Signal** | What the console sends a runner ([ADR-0085](adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md)): `wake` (something to do: a task, an answer, a message elsewhere, a briefing), `tell` (a supervisor's words), `interrupt`, `stop`, `restart` and `reset`, by which a supervisor starts an agent again, with its conversation or with a new one, and `set`, the model and the level of effort it runs with; each names who sent it and where it came from, is kept with the account, apart from the board's feed, and reaches the agent as a message under a header that says so. |
| **Transcript** | What a runner's session leaves ([ADR-0086](adr/0086-a-session-leaves-a-transcript-that-is-kept-for-good.md)): every event of the driver, what the agent was sent, said, thought and did, numbered and append-only, never deleted by the console, laid out by the month so that whoever keeps the database moves what is past; read by the agent's supervisors and by the account. |
| **Desk** | An agent account's own repository at the organization's git host ([ADR-0088](adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)): its identity and its base instructions, across products, and whatever it chooses to keep; the working directory its product runs in, with the projects it works on under `work/`. |
| **Services** | The workspace's handle, its domain and the services its agents' accounts are made at, a map by role (`identity`, `git`, `messenger`) of `{ kind, ...parameters }` an administrator keeps ([ADR-0089](adr/0089-a-workspace-names-the-services-its-agents-work-with.md)); a name elsewhere is put together from the workspace's handle and the agent's, and an agent's setup is derived from the map. |
| **Task** | A unit of work in a project: number, title, body in Markdown, state, owner (one person, whoever wrote it), workers (any number of people who may work in the project, in the order they came to it; a run taking the task puts its person among them, [ADR-0037](adr/0037-a-task-has-one-owner-and-any-number-of-workers-and-a-parent-or-a-goal-is-found-by-search.md)), priority, links (repositories, pull requests, documents), parent task for a breakdown; a category or none, and a goal of the project or none; its plan, the day it is meant to start and the day it is due, set by people; and its moments, when it was first moved past ready and when it was moved to done, which the board keeps itself ([ADR-0019](adr/0019-a-task-is-planned-in-days-the-board-keeps-its-moments-and-goals-and-categories-give-the-work-its-shape.md)); it may be put away from any state, a moment the board keeps too, out of the board and the listings and open by its number ([ADR-0029](adr/0029-a-task-done-or-dropped-is-put-away-out-of-the-board-and-open-by-its-number.md), [ADR-0030](adr/0030-a-task-is-put-away-from-any-state.md)). States: `idea`, `ready`, `in_progress`, `in_review`, `done`, `dropped`. |
| **Category** | A kind of work tasks are sorted into, the workspace's own vocabulary: a key (what the command and the filters say; immutable), a name, and a colour from a fixed list. Every workspace starts with engineering, product, design, marketing and operations; an administrator renames, recolours, adds and removes them, and one tasks are sorted into stays until they are moved. |
| **Goal** | What a project works towards, on its roadmap: a title, a body in Markdown, a state (`planned`, `active`, `done`, `dropped`) and the day it is meant to be reached by. Set by an owner; its progress is its tasks counted by state, never written down. |
| **Run** | One agent's work on one task: who started it, which agent, when, and when it was last heard from; its status (`running`, that is open, `waiting` for a decision, `finished`, `failed`, `abandoned`, which a run taken over by another is too); its reports; what it handed in. The console does not claim an agent is at work ([ADR-0020](adr/0020-the-console-does-not-claim-an-agent-is-at-work-a-run-says-when-it-was-last-heard-from-and-a-new-run-takes-over.md)). |
| **Comment** | A word in the discussion on a task ([ADR-0024](adr/0024-a-task-carries-a-discussion-of-comments-with-their-files-read-as-one-thread-with-the-runs-and-the-decisions.md)): Markdown by a person, or by their agent, with the files put in it kept in the blob store, pictures shown in place where the text names them; never rewritten or deleted. The task's page reads the comments, the runs and the decisions as one thread, in the order they came. |
| **Decision** | A question that needs a person, raised from a run or by a person: the question, the context it rests on, the files put on it when it was raised (a picture of what is to be chosen between, shown where the context names it; [ADR-0055](adr/0055-a-decision-carries-the-files-put-on-it-when-it-is-raised.md)), the options, the answer (one of them, or the person's own words, kept as one more option marked as theirs) with its rationale, who gave it and when, and what followed, written afterwards: a record, not only a vote. A run that raised one waits for it. While it waits, anyone who may answer it may say anew whom it is for, and the board is told ([ADR-0096](adr/0096-a-decision-that-waits-may-be-addressed-anew-by-whoever-may-answer-it.md)). |
| **Document** | A page of Markdown in a project, under a path of lowercase segments (`guides/onboarding`) that is its address and does not change; the folders are what the paths say. Every write is a version, with who wrote it, through which agent, and when. Links to documents by path, from documents, tasks and decisions, are kept both ways. Archived rather than deleted. Files attach to it from the blob store, a picture among them shown where the body names it. |
| **Rules** | What the board asks of its agents ([ADR-0023](adr/0023-the-rules-of-a-board-are-pages-the-workspace-and-its-projects-keep-read-first-by-every-agent.md)): a page at `rules` of the workspace's own, the console's own until an administrator writes the organization's; and a page `rules` a project adds or not, written by an owner. Kept as documents are, read first by every agent, shown on the settings. |
| **Event** | An append-only record of everything that happened: in a project, or to the workspace itself. Each names who did it and, when they did it through an agent, the agent. The live feed of the UI and the audit trail; narrowed to one task, run, decision or document, its history. |
| **Artifact** | What a run hands in: a link (a branch, a pull request, a page) or a file kept in the blob store by its hash. |

## How agents take part

- **The console is a command to agents** ([specs/cli.md](specs/cli.md), [ADR-0006](adr/0006-agents-work-the-board-through-the-rest-api-and-the-command-line-not-an-mcp-server.md)). The package ships `console`, a thin client of the REST API with no logic of its own, which a person signs in once with a token they made. An agent takes a task (`console take`: a run begins; the task is the person's and in progress), reports (`console report`), hands in a link or a file (`console hand-in`), asks for a decision (`console ask`: the run waits, and the command waits a while for the answer; the decision is addressed to the person the agent works for unless another of the project is named, and a person finds the decisions addressed to them on one page, [ADR-0042](adr/0042-a-decision-is-addressed-to-a-person-its-raiser-unless-another-is-named.md)) and ends the run (`console finish`, `fail` or `abandon`). Each is one or two requests of the REST API ([specs/rest.md](specs/rest.md)), the one surface of the console; the command costs an agent nothing until it is used, and an agent learns it from its help; what an administrator or an owner does on the pages, the agent does with `console project`, `member`, `category` and `person role` ([ADR-0021](adr/0021-a-token-configures-as-its-person-does.md)). The console is not an MCP server.
- **The project's documents are the agent's to read and write** ([ADR-0009](adr/0009-documents-are-pages-of-markdown-in-a-project-addressed-by-path-versioned-and-linked-both-ways.md)): `console docs`, `console doc`, `console write`, `console attach`, `console archive` and `console restore`, each one request of the REST API under the project. An agent writes down what it learned at a path where the next one reads it, links to it from its reports and from what it asks, and the page says what refers to it.
- **A project's pack is read by address** ([ADR-0028](adr/0028-the-console-reads-a-projects-pack-through-the-deployments-rest-api-with-a-pack-token-for-a-private-one.md), [ADR-0031](adr/0031-the-console-reads-a-pack-as-the-skillcdn-command-does-and-a-local-one-from-a-directory.md)): the project's own, or the organization's (`SKILLS_ADDRESS`) when it names none. The console reads a pack as the `skillcdn` command reads one, through a port shaped like the command's own: the address of a git host at the SkillCDN deployment, through `@skillcdn/client`, with the SkillCDN token (a pack token, in the API) a private pack is read with: the project's own, set by an owner, or, for a project that reads the organization's pack and holds none, the workspace's, set by an administrator; either a token a person made at the deployment or one connected with a code they approved there, kept sealed with the console's secret and shown to nobody; and a `local` address (`/local/<owner>/<name>`) from the directory the console was given (`SKILLS_DIR`, laid out as `<owner>/<name>`), read on its own machine as the indexer reads a commit and read with `@skillcdn/reader`, so that what it answers from a directory is what a deployment would answer from the same commit; the image carries the console's own skills as such a pack. The project's Skills page and `console skills` list what the address serves, each skill with where a person reads it and the URI an agent loads it by through a connection of its own; the console's API answers every read as the pack answered it, in the shapes of `@skillcdn/core`, and the command renders it as a deployment's own tools render for a model, with the reads named as the console's commands: `console skill` reads one whole, its rules first, `console skill --file` a file of the pack, or one section of it by its offset and limit, `console skills <folder>` what a folder holds, `console skills <file>` a document's outline and `console skills --search` what words find, with the sections of a document that matched (SkillCDN 0.4), so that an agent needs nothing but the console's token and reads what it would read over MCP. The console holds a public listing per address for a minute, holds nothing read with a token, and keeps nothing of the skills ([specs/rest.md](specs/rest.md#get-apiv1projectskeyskills)).
- **Attended, or on a runner of its own.** A person runs their agent in their own app or CLI, on their own machine, under their own subscription, and connects it; the console calls no model API and sees what the agent reports. An agent account runs the same way without a person at the screen: its runner, on a machine of the organization's and in an OS account of the agent's own, signed in as the account, starts the product under the agent's own subscription, keeps its one main session going and feeds it the board's wakes and its supervisors' words ([ADR-0085](adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md)); the console never starts an agent or holds a model's credential.
- **An agent account works as a member of its own** ([ADR-0084](adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md) to [ADR-0089](adr/0089-a-workspace-names-the-services-its-agents-work-with.md), the plan for 0.5.0: the account, its persona, its command's sign-in and its secret store are built, milestone 41; the runner, the transcript and the setup are milestones 42 to 44 of the [roadmap](roadmap.md)). It is an autonomous colleague: whatever a member may be given it may be given, by the same rules, an administrator's role alone excepted. It is assigned tasks, asked and answers, owns projects and may manage people or agents, under a manager it reports to and does not belong to. An administrator makes it; it signs in through the identity provider with an account of its own, and comes onto a machine from one line pasted in its own OS account: an invitation that leads to the guide and gives nobody the account, then `console agent setup`, in which the account says "this is me" to its own command, writes its desk and starts its runner; its onboarding is a task on the board, and what the agent cannot do itself is a decision to whoever can do it; the console names the account it signs in with and says nothing of who makes it at the provider ([ADR-0094](adr/0094-the-account-an-agent-signs-in-with-is-named-and-who-makes-it-is-the-organizations-to-say.md)). Its supervisors read its transcript live and after, tell it, interrupt it and stop it; every signal names who sent it, and the board's rules say that instructions are a supervisor's `tell`, the board's tasks and decisions and the rules, and everything else information. It keeps its secrets in the console, read by itself alone and seeded write-only by a supervisor ([ADR-0087](adr/0087-an-agent-account-keeps-its-secrets-in-a-store-of-its-own-that-only-it-reads.md)), and what should outlive its machine in its desk. What the organization's services are, where its agents' accounts are made, is named once on the workspace and derived from ([ADR-0089](adr/0089-a-workspace-names-the-services-its-agents-work-with.md)); a product is a driver, a messenger a wake source, a platform a service module, so that none of them is written into the console.
- **An agent is its person, and no more.** Its token is made by one person, scoped to that person, revocable, and expiring unless the person chose otherwise; what the person may do in a project is what the agent may do there, and what the agent does names it beside the person. The command works in one project at a time: the one `--project` names, or `CONSOLE_PROJECT`, or `.skillcdn-console.json` in the working directory, which `console use` writes and a private checkout commits; and it talks to one console at a time, the one `--url`, `CONSOLE_URL` or that file names, else the default login, with the token kept for that console alone, so that a token never travels to a console it was not made at ([ADR-0027](adr/0027-the-command-keeps-a-login-per-console-and-a-token-goes-only-to-the-console-that-issued-it.md)). Finer rules, what an agent may decide alone and what must wait for a person, come after the first agents are connected.
- **The command and the console go together by version** ([ADR-0025](adr/0025-the-command-names-its-version-on-every-request-and-the-console-holds-it-to-the-range-it-takes.md)): the command names its version in its `user-agent` on every request, every answer of the API says the console's version and the range of command versions it takes, and a command outside the range is refused with `426` and told the command that updates it where it is installed. Before 1.0 the range is the console's line, from the floor a release raised where it changed what passes between them ([ADR-0038](adr/0038-the-command-and-the-console-go-together-within-a-line-and-a-release-that-changes-what-passes-between-them-raises-the-floors.md)); from 1.0, the console's major and a minor within one. The command holds the console to a floor of its own the same way. The rule lives in the package's `compat` module, which both sides read; the package may narrow it, never widen it. The Settings page names the console's version and the range first among the workspace's rows, from `me.console`, so that whoever keeps the agents' commands current reads there what they must match. The REST schemas are snapshotted at the floors, and `pnpm check` fails on a change that breaks an older command without a floor moved ([ADR-0043](adr/0043-the-rest-contract-is-held-to-a-snapshot-taken-at-the-floors.md)).
- **A run is the record of the agent's work:** who started it, as which agent, on which task; its reports and what it handed in, a picture among the files shown as a comment's is; the decision it waits for; how it ended. A run that asked waits until a person answers on the board, and is woken through the database's own channel, the same nudge the live feed runs on. A person may give up on a run that will not come back, and the console does so itself after twelve hours without a word from the run, unless it waits for an answer ([ADR-0041](adr/0041-a-run-not-heard-from-for-twelve-hours-is-ended-by-the-console.md)).
- **A task carries a discussion** ([ADR-0024](adr/0024-a-task-carries-a-discussion-of-comments-with-their-files-read-as-one-thread-with-the-runs-and-the-decisions.md)): comments by people and by their agents, each with the files put in it, pictures shown in place, small, and large over the page when pressed; the task's page reads them with the runs and the decisions as one thread. A report is the run's record; a comment is a word to the task's people: an answer to what they asked, a question that is not a decision, a remark. A comment with its files is one request, so that the board is told once and sees it whole. What a person put in reaches the agent through the command (`console file`), so that a picture on the board is looked at with the agent's own tools.
- **The console's skills say how the work goes** ([ADR-0015](adr/0015-the-consoles-skills-live-in-this-repository-in-the-skillcdn-format-and-the-package-carries-them.md)): `skills/working-the-board` for an agent working a task, `skills/planning-the-board` for one putting work on the board and setting a project up as a person asks, `skills/building-a-console` for one building a console or a script from the package, and `skills/deploying-a-console` for one deploying the console for an organization ([ADR-0017](adr/0017-the-reference-deployment-is-the-image-on-aws-behind-cloudflare-written-as-a-skill.md)), in the SkillCDN Format with `SKILLCDN.md` at the root as their manifest and the rules they share, served by SkillCDN at `skillcdn.ai/gh/skillcdn/console` with this documentation, and shipped in the package with the specifications and the sources. They are maps: the command's own help, the package's README and types, and the specifications carry what they name.
- **The rules of the board say what the organization and each project ask of agents** ([ADR-0023](adr/0023-the-rules-of-a-board-are-pages-the-workspace-and-its-projects-keep-read-first-by-every-agent.md)): which skills to load first, where the work lives, how the pages are laid out, what may be decided alone, how to report. Pages at `rules`, the workspace's own and a project's, kept as documents are; the console's own hold until an administrator writes the organization's, and change with the console's version. `console rules` reads them before a task is taken, `console take` prints them again with the task, and the settings show them. The organization's skills say how the work itself is done.
- **Hooks later.** Where an agent can run a command on its own events, a small hook can report automatically what the agent would otherwise be asked to report. Optional, additive.

## Sign-in and permissions

- People sign in through an identity provider the organization already uses, GitHub or Google (Workspace), one or both ([ADR-0005](adr/0005-people-sign-in-through-an-identity-provider-and-membership-and-roles-are-the-consoles-own.md)): the console keeps a session and never a password of its own. The provider's token is used once, server-side, to ask who the person is, and then dropped: nothing of it is kept, since membership is decided here and not at the provider. A provider is an adapter of one port, `IdentityProvider`; a person is known by the provider and its immutable id of the account, and called by their login there (an address, at Google).
- Membership is the console's own record, kept by an administrator ([ADR-0022](adr/0022-who-is-in-is-the-consoles-own-record-and-an-administrator-keeps-it.md)): a person is in or deactivated, and what let them in is written on them. The configuration names what vouches, never who: the git host's organization (`GITHUB_ORG`, read through a GitHub App at sign-in and by the worker on a schedule, which takes out those who left and back in those who returned), the Google Workspace domain (`GOOGLE_WORKSPACE_DOMAIN`), which Google vouches for at sign-in, and the first administrators (`ADMINS`), let in by that alone. Everyone else is let in by an administrator on the People page, by login: whoever signs in with that account is the person, and the listing is bound to the account from then on. An administrator takes a person out, which refuses them on every request from the next one, their agents with them, and keeps them with everything they did, their agents' tokens included: a token of a person who is out is refused with the reason, and is theirs again when they are back in ([ADR-0044](adr/0044-a-token-of-a-person-who-is-out-is-kept-and-refused-with-the-reason-until-they-are-back-in.md)); the organization's own come and go with it. A domain or an organization taken out of the configuration takes its people with it. Reading the Workspace's own directory stays open. The directory keeps a work email per person, the address Google vouched for at sign-in or one an administrator wrote, read by an administrator, the person and a plugin consented to read it, and by nobody from the feed ([ADR-0069](adr/0069-the-directory-keeps-a-work-email-read-by-an-administrator-the-person-and-a-plugin-allowed-to.md)).
- A token is what an agent, a script or a console of a person's own acts as that person with: scoped to that person, revocable, expiring unless the person chose otherwise and the organization allows it (`TOKEN_DAYS_AT_MOST`), stored as a hash, and presented as `Authorization: Bearer` to the REST API and the feed, where it is the credential and needs no origin ([ADR-0004](adr/0004-people-and-agents-reach-the-board-only-through-the-api-with-a-credential-of-their-own.md)). A token can do what its person can do and nothing on anyone else's behalf; it cannot make, list or remove tokens, which only a person signed in does, on the console's own pages, except to give itself up (`console logout`). An agent gets its token without anyone copying one ([ADR-0011](adr/0011-an-agent-connects-with-a-short-code-a-person-approves-and-the-token-is-never-shown.md)): the command asks to connect and shows a short code and an address, the person approves on the console's own pages, signed in, and the command claims the token, made then and handed over once; the console holds a bounded number of such requests at once, and a bounded number from one address as the trusted proxies resolve it, where the oldest not yet approved makes way for the next ([ADR-0047](adr/0047-a-connection-request-is-bounded-per-address-and-the-oldest-not-yet-approved-makes-way.md)); a token made by hand on the Agents page remains for scripts. An administrator sees and disconnects anyone's agents.
- An agent account ([ADR-0084](adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md)) is who the identity provider says it is, as a person is: an administrator makes it, which lets its login in as a listing does ([ADR-0022](adr/0022-who-is-in-is-the-consoles-own-record-and-an-administrator-keeps-it.md)), and it signs in with an account of its own there. In a browser it holds what a person holds. On its machine its command signs in as the account itself ([ADR-0088](adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)): the connection an agent asks for, in which the command asks to be the account (`console login --self`) and the account says "this is me" in its own browser, yields a session of the command's in place of a token, which lasts while it is used and lapses when left unused, and is held to what a token may ask: it makes no token and approves no connection. An invitation code leads a machine to the guide and gives nobody the account. The one rule of the policy that reads a member's kind keeps an agent account from administering the workspace; who supervises it, the administrators and whoever manages it directly or up the reporting line, is one function of the policy, `supervises`, as every such rule is.
- Roles in the workspace: an administrator, who configures it, and a member, who works in the projects they are in; the console's own record on the person ([ADR-0005](adr/0005-people-sign-in-through-an-identity-provider-and-membership-and-roles-are-the-consoles-own.md)). `ADMINS` makes those logins administrators when they sign in; an administrator makes or unmakes others on the People page, and the board keeps at least one.
- Roles in a project ([ADR-0008](adr/0008-a-workspace-holds-projects-and-what-a-person-may-see-and-change-is-decided-per-project.md)): an owner configures it, a member works on it; a workspace administrator is an owner of every project. A project open to the workspace has everyone of it as a member, and a listing there makes an owner; a private one has only those listed ([ADR-0035](adr/0035-who-may-see-whom-is-decided-by-one-policy-and-the-workspace-keeps-its-settings.md)). Whether a person, or the agent acting for them, may see or change anything in a project is decided on every request from these records, before any work is done, and a project that cannot be confirmed theirs is not found. Configuring, which is roles, projects and their members, is done by a person on the console's own pages or by their agent with their token, within the same roles ([ADR-0021](adr/0021-a-token-configures-as-its-person-does.md)); only the tokens themselves are a person's own doing, signed in. A project is made by an administrator, who owns it and lists its owner ([ADR-0045](adr/0045-a-project-is-made-by-an-administrator.md)). A person's agents have their person's role in a project.
- Who may see whom and what is one policy ([ADR-0035](adr/0035-who-may-see-whom-is-decided-by-one-policy-and-the-workspace-keeps-its-settings.md)): `apps/console/src/auth/policy.ts` holds every such rule as a condition the queries apply in SQL, so that a listing, a lookup and a reference agree and nothing is filtered after the fact; a route names its guard and asks nothing of its own; what cannot be decided is denied. The settings a rule depends on are the workspace's, kept by an administrator on the Settings page and read on every request: today, who sees whom on the People page, everyone or only the people one shares a project with; beside it the workspace keeps the day its calendars begin a week on and its time zone, in which the command prints moments while the pages keep the browser's, the organization's short name, its domain and the services its agents work with, by what each is to them ([ADR-0089](adr/0089-a-workspace-names-the-services-its-agents-work-with.md)), which name nothing the console already knows from its deployment, and its language, for whoever has none of their own: the pages after the browser's languages, and every plugin call for such a person or for none ([ADR-0081](adr/0081-a-workspace-has-a-language-for-whoever-has-none-of-their-own.md)). The rule of where a setting lives: what the operator decides when the deployment is made is in the environment (`deploy/README.md`); what the organization decides as it runs is on the Settings page, in the workspace's row; what a person decides for themselves, their language, is on the person. A new rule is a function there with its row in the table test, never a check in a route.
- The rules are configuration ([ADR-0023](adr/0023-the-rules-of-a-board-are-pages-the-workspace-and-its-projects-keep-read-first-by-every-agent.md)): an administrator writes the workspace's and an owner a project's, each through their agent as well, and every version names who wrote it and through which agent; everyone of the workspace reads the workspace's, and whoever may see a project reads its rules.
- Requests that change something for a person come from the console's own pages: the session cookie does not travel with other sites' requests, and the origin is checked as well.
- A person sees the browsers they are signed in on, each with what it is, where it last came from and when it was last used, and signs any of them out, or every other at once, on the settings' view of their own (`/settings/sessions`) and never through a token; a session not used for `SESSION_TTL_DAYS` ends on its own.
- Permissions fail closed: no confirmed answer, no access.

## Runtime: one image, several roles

`apps/console` builds into a single container image. The container command selects the role:

| Role | What it does | Scaling |
|---|---|---|
| `api` | Serves HTTP: the REST API for the UI and for agents' commands ([specs/rest.md](specs/rest.md)) with its live feed, sign-in, the default UI's files. Holds no state another replica needs: a change any replica makes reaches every replica's feed subscribers through the database's own notification channel. | Any number of replicas. |
| `worker` | Runs schedules, and consumes the job queue once there are jobs: today the clean-up of expired sessions, and the reading of the organization at the git host where one is named ([ADR-0022](adr/0022-who-is-in-is-the-consoles-own-record-and-an-administrator-keeps-it.md)); the plugins' jobs and hooks, which carry what waits on the board to people away from it ([ADR-0071](adr/0071-the-console-sends-no-notification-of-its-own-a-plugin-carries-them-out-of-the-board-and-back.md)); and, with agent accounts, the note of a runner not heard from for five minutes and the wakes of their runners, read from a cursor over the feed by the board's rules, and their briefings on the schedule, which are built ([ADR-0085](adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md)), and the transcript's partitions made ahead of their month ([ADR-0086](adr/0086-a-session-leaves-a-transcript-that-is-kept-for-good.md)). | Any number; interruptible. |
| `migrate` | Applies pending migrations, then exits. | Once, before a new version rolls out. |
| `verify` | Checks the months of the transcript against the chains their sessions keep ([ADR-0090](adr/0090-a-sessions-events-are-held-by-a-chain-whose-head-stays-with-the-session.md)), says what does not hold, then exits. Reads, and changes nothing. | By hand, by whoever keeps the database: after a month that was put away is back. |

A flag (`WORKER_IN_PROCESS`) lets `api` run the worker loop in-process for a single-container install. `GET /healthz` reports liveness and `GET /readyz` readiness (database reachable, schema at the expected version, workspace found). On `SIGTERM` the process stops accepting work, drains what is in flight and exits within the grace period. The exit codes and the probes are the process contract in [`deploy/README.md`](../deploy/README.md#process-contract).

## The package and custom consoles

`@skillcdn/console` (`packages/console`) is what a custom console is built from, planned in three layers:

1. **The schemas and the client** of the console's REST API, so that a custom UI talks to any console with types, and so that the API's contract has one source.
2. **The components:** the board, a task, a run, a decision, the live feed, each taking its data as props and nothing from the network.
3. **The composition:** `createConsole(config)`, the default console assembled from the components, with the places a team may replace named.

The pages speak the person's language ([ADR-0012](adr/0012-the-pages-speak-the-persons-language-from-packs-that-ship-with-the-package.md)): every word the console shows is in a pack, English and Korean ship with the package, a person's language is kept on them (`PATCH /api/v1/me`), the browser's when the pages first see them and theirs to change after that, and a plugin or an agent reads it to write for them ([ADR-0065](adr/0065-a-plugin-writes-one-text-and-a-persons-language-is-kept-from-the-first-time-the-pages-see-them.md)); a custom console passes its own packs. The command stays English. The default UI the image serves is exactly that composition with the default configuration: `apps/console/web` is one page that calls `createConsole().mount(...)`, built with Vite into static files the `api` role serves from `WEB_ROOT`, with the package's own serving of a build (`@skillcdn/console/web`: the files, the page for every other path, the policy). A custom console is a small repository that depends on the package, holds a configuration and a CI job, and builds to static files: the organization's takes the default UI's place in the image ([deploy/README.md](../deploy/README.md#a-custom-console-in-the-image)); a person's own is served from their machine. Nothing of the server is in the package but that serving, which the image and the command share. The package also carries the console's skills with their manifest, the specifications they point to, and its sources without the tests, so that an agent that installed it reads how a console is built, and from what, in `node_modules` ([ADR-0015](adr/0015-the-consoles-skills-live-in-this-repository-in-the-skillcdn-format-and-the-package-carries-them.md)).

The package is meant for two kinds of custom console: the organization's, which replaces the default UI the image serves, and a person's own, which a member builds from the package and runs for themselves, against the organization's console, with pages and components of their choosing. The second is served from the person's machine by the command ([ADR-0014](adr/0014-a-persons-own-console-is-served-from-their-machine-by-the-command.md)): `console serve <dir>` serves the build on the loopback and carries everything under `/api/` to the organization's console with the token `console login` kept, so that the page and the API share one origin, the token never reaches the page, and the organization's console allows no other origin; it refuses a request whose host is not the loopback, or that the browser says comes from another site's page. The API says with what a request acts (`GET /api/v1/me` answers `agent`, the token's name), and a console that holds a token offers nothing a token cannot do: the tokens themselves stay on the console's own pages, and everything else it does on the token as the person ([ADR-0021](adr/0021-a-token-configures-as-its-person-does.md)).

The pages route in the browser, and the addresses name what they show ([ADR-0010](adr/0010-the-default-uis-addresses-name-what-they-show-and-every-page-and-form-has-one.md)): the projects at `/`, a project's pages under `/projects/<key>` (`/tasks/<number>`, `/roadmap` and `/roadmap/<id>` (with `?view=` for the board, the list or the calendar of the goal's tasks, and `?month=` for the calendar), `/calendar`, `/docs` and `/docs/<path>`, `/decisions` and `/decisions/<id>`, `/feed`, `/skills`, `/members`, `/settings`), the person's own work across their projects at `/work`, the people at `/people` (and one person's agents at `/people/<id>/agents`, for an administrator, and their work at `/people/<id>/work`, for an administrator or an owner of a project they are in), the agent accounts that report to whoever is signed in at `/agents` (with `?view=all` for every agent account, for an administrator, and `?view=connected` for the agents that act as the person with a token of theirs), with the form that adds an account at `/agents/new/account`, an agent account's own page at `/agents/<handle>` (what it is doing as it happens, with the way to say something to it, then `/sessions` and one of them at `/sessions/<id>`, `/work` and `/settings`), the categories at `/categories`, the approval of an agent's connection at `/connect/<code>`, and the guide of an agent account's setup at `/setup/<code>`, by the code of its invitation, the one page read without a sign-in. Every form has an address (`/projects/new`, `.../tasks/new`, `.../decisions/new`, `.../roadmap/new`, `/agents/new`, and `?edit`, `?ask`, `?new`, `?version=`, `?q=`, `?month=`, `?week=` and `?page=` on what they are about; the board's filters, `?category=`, `?goal=`, `?person=`, `?mine` and `?q=`, the words typed, are part of its address), the navigation has two levels (the tabs of the level the person is on, and the person's menu with the workspace's pages), every link to one of the console's addresses is followed in place, the history is one entry per step, and the addresses of before (`/p/<key>`, `/tokens`) lead to the new ones. Every path that is not a file of the build is answered with the page, under a content security policy that runs nothing inline and loads nothing from elsewhere: a picture from elsewhere is read through the console, which fetches it from a public address and keeps it a while ([ADR-0048](adr/0048-a-picture-from-elsewhere-is-read-through-the-console-from-a-public-address-and-kept-a-while.md)). The workspace is loaded once, its lists asked for along with who is signed in; the project the page is on is loaded whole, its feed as it stands, the newest page, and from then on the project's stream says when something changed: on every event the lists are loaded again. The documents are read by the page that shows them, a folder or a page at a time, since the tree may be large, and again whenever the feed grows. My work and My decisions, come back to, stand at once with what they showed last and read again behind it, until the person signs out; a plugin's frame has a spinner in its place until its page has drawn.

## Plugins

Decided on 2026-11-01 and built in milestone 34 of the [roadmap](roadmap.md); the contract is [specs/plugins.md](specs/plugins.md). A plugin is one npm package that adds a feature of an organization's work to the console (leave, customers, money) under the console's own rule, people decide and agents work: commands and queries an agent runs through `console plugin <key> …`, pages and widgets people see in tabs the console draws, records the console keeps, decisions and tasks on a project of the plugin's, hooks, jobs and skills ([ADR-0049](adr/0049-a-plugin-is-an-npm-package-installed-into-the-image-and-enabled-by-an-administrator.md)). It is installed by building it into the image from a lockfile and read from `PLUGINS_DIR` at boot; an administrator enables it, consenting to the capabilities its manifest asks, making or choosing its board project and granting its roles to people ([ADR-0052](adr/0052-a-plugins-board-is-a-project-made-or-chosen-when-it-is-enabled-and-what-it-puts-there-carries-its-name.md)).

Its server code runs in a host process the `api` and `worker` roles spawn, under Node's permission model with an empty environment, a thread per plugin, and reaches the console only through `ctx`, whose every call the parent decides by the capabilities consented to and the person's roles and policy ([ADR-0050](adr/0050-plugin-code-runs-in-a-host-process-of-its-own-and-reaches-the-console-only-through-the-capabilities-it-declared.md)). Its data is records in tables of the console's, with versions, files, links, search and aggregates, or, by consent, a PostgreSQL schema and role of its own ([ADR-0051](adr/0051-a-plugin-keeps-its-data-in-records-the-console-holds-or-in-a-schema-of-its-own-by-consent.md)). Its pages run in a frame the console serves under a policy and a sandbox of their own, with no session, speaking over an allow-listed bridge to the plugin's own routes alone ([ADR-0054](adr/0054-a-plugins-pages-run-in-a-sandboxed-frame-and-speak-only-to-their-plugin.md)); the console draws the tabs, the sub-tabs and the front-page widgets from the manifest and keeps the settings pages its own. An agent learns of a plugin from the rules printed with its task, a line per plugin, and from `console plugins` ([ADR-0053](adr/0053-agents-reach-a-plugin-through-one-command-whose-definitions-the-console-holds.md)). Every command and every change a plugin makes is an event naming the plugin beside the person. Who may do what through a plugin is one model, stated whole in [ADR-0080](adr/0080-a-plugin-reaches-the-projects-it-is-placed-on-and-whoever-may-use-it-is-a-requester-in-its-board-project.md) and in the spec's "Security model": a plugin's own permission is what an administrator consented to, on its board project and the projects it is placed on, and no other; acting for a person is the intersection of the plugin's and the person's, recorded with both; a decision reaches its parties; and whoever may use a plugin is a requester in its board project, raising a decision there and reading it back, nothing else of the project opening to them.

## Data and storage

PostgreSQL holds the workspace, the people, agent accounts among them, their sessions and the agents' tokens (hashed), an agent account's secrets (sealed) with the record of their accesses, its invitation (the hash of its code) and the accounts it holds elsewhere (their names, no secret), the categories, the projects with their members, their goals, the tasks, the runs with their reports, the comments on the tasks, the decisions with their files, the documents with their versions, the links between documents, tasks and decisions, the events, and the job queue. The search over the documents is the database's own text search, on a column it keeps itself. Identifiers are UUIDv7, except that events are numbered, since the feed is read from a point on; timestamps are `timestamptz`; events are append-only, written in the transaction of the change they record, and the commit notifies every process that listens (`pg_notify`), which is how the feed is live without any state outside the database. Files a run hands in, files put in a comment or on a decision, and files attached to a document, go to the blob store under their content hash, and are read back at the project's one address for files, a decision's also at the decision's own, for whoever the decision reaches outside the project ([ADR-0068](adr/0068-a-decision-reaches-whom-it-is-addressed-to-wherever-it-is-and-a-plugins-reaches-the-managers-above-them.md)); one implementation of that port keeps the bytes in PostgreSQL, so that the smallest install has one dependency, and the other in a bucket through the S3 API, which the console signs its own requests to, with one pair of keys from configuration or with the credentials the platform hands the container ([ADR-0018](adr/0018-the-bucket-may-be-reached-with-the-credentials-the-platform-hands-the-container.md)), and which reads from the rows what was kept there before the bucket ([ADR-0016](adr/0016-the-bucket-is-reached-through-the-s3-api-with-the-consoles-own-signing-and-reads-what-the-rows-kept-before-it.md)). With agent accounts it holds what is known of their runners and their signals, a record numbered per account whose writing notifies a channel of the accounts' own, so that one account's stream is woken and no reader of the board's feed is, their secrets, sealed with the console's key as the pack tokens are ([ADR-0087](adr/0087-an-agent-account-keeps-its-secrets-in-a-store-of-its-own-that-only-it-reads.md)), and, in a schema of its own, the runners' sessions and the transcript events, append-only and partitioned by the month their session began, without foreign keys, the large payloads and the pictures in the blob store under that month ([ADR-0086](adr/0086-a-session-leaves-a-transcript-that-is-kept-for-good.md)), so that a past month is moved with the database's own tools. The schema is documented in [`apps/console/README.md`](../apps/console/README.md#data-model).

## Deployment

- **Locally:** `deploy/compose.dev.yaml` runs PostgreSQL; the console runs from the built output (`apps/console/README.md`). The image is built from `deploy/Dockerfile`, and CI builds and exercises it on every change.
- **On a cloud:** the same image as containers, a managed PostgreSQL and a bucket with the S3 API. [`deploy/README.md`](../deploy/README.md) is the contract: the roles, the environment variables, the bucket and its keys, what a platform must provide (secrets at runtime, health probes, a stop timeout above the grace period, logs from stdout). The definitions of a particular deployment live outside this repository ([AGENTS.md](../AGENTS.md), rule 8).
- **The smallest install** is [`deploy/compose.yaml`](../deploy/compose.yaml): the image next to PostgreSQL on one machine, the worker inside the api, the files in the database and the packs in a directory, so that nothing of it needs the internet ([ADR-0031](adr/0031-the-console-reads-a-pack-as-the-skillcdn-command-does-and-a-local-one-from-a-directory.md)). `deploy/install.sh` makes it on a host with docker, on the published image of a release, with a database password of its own making and signing in turned on once a person registered a provider; and `deploy/bundle.sh` makes the one directory a closed network carries in, the images, the files, the command for the agents' machines with what it depends on and the digest of every file, from which the same script installs with nothing fetched ([ADR-0092](adr/0092-the-image-of-a-release-is-published-and-the-smallest-install-is-made-from-a-bundle.md), [`deploy/README.md`](../deploy/README.md#the-smallest-install-and-a-closed-network)).
- **The reference deployment is a skill,** `skills/deploying-a-console` ([ADR-0017](adr/0017-the-reference-deployment-is-the-image-on-aws-behind-cloudflare-written-as-a-skill.md)): the image as tasks on AWS (ECS with Fargate) next to a managed PostgreSQL (RDS) and a bucket (S3), the secrets in a parameter store, the bucket reached with the tasks' own role and no key, reached only through Cloudflare's tunnel, whose connector runs beside the `api` container; a private deployment repository of the organization's own builds the image from a pinned release and rolls it out on every push, `migrate` first. Sized by the organization, from one person to a hundred, and priced before anything is made. `DATABASE_CA` carries a managed database's authority where a container can mount no file. The first deployment on an organization's own accounts (2026-10-11) held, and what it found went back into the skill.

## Security model

- **Untrusted input:** everything an agent sends, every request, and what SkillCDN serves of a repository. Parsed with schemas, bounded in size and depth, stored as data, shown as text or as Markdown rendered to elements, never as HTML, never executed. A file handed in is kept as bytes and handed back as bytes: shown in place only for the few kinds a browser cannot run, never sniffed, under a policy that runs nothing.
- **Fail closed** on membership, on every token, and on every project: what a person may not see is not found. Unknown and forbidden answer the same.
- **Tokens:** git-host tokens used once to ask who a person is and never kept; sessions and agent tokens stored as hashes; nothing logged. A project's pack token is kept sealed with the deployment's secret, sent to the SkillCDN deployment and nowhere else, and shown to nobody ([ADR-0028](adr/0028-the-console-reads-a-projects-pack-through-the-deployments-rest-api-with-a-pack-token-for-a-private-one.md)). The command keeps a login per console in the person's own configuration directory, sends each token to the console that issued it and no other ([ADR-0027](adr/0027-the-command-keeps-a-login-per-console-and-a-token-goes-only-to-the-console-that-issued-it.md)), never takes one on the command line, and never prints one.
- **Nobody acts for someone else:** an agent is its person, and its person only.
- **Outbound requests** go only to configured base URLs: the identity providers, the SkillCDN deployment and the bucket's endpoint. Never to a URL an agent sent, with one exception under a guard of its own: a picture a page shows is fetched from the https address a person or an agent wrote, from a public address only, the host resolved first and every address of it checked against the console's own networks, the connection made to the address checked, a redirect followed under the same rule, and nothing read but a picture of a bounded size ([ADR-0048](adr/0048-a-picture-from-elsewhere-is-read-through-the-console-from-a-public-address-and-kept-a-while.md)). A pack in a directory is read from the directory the configuration names and from nowhere else, and nothing in it is executed.
- **Plugins:** third-party code runs in a child process under Node's permission model, with no secrets, no database and no files but its own, a thread per plugin within bounds, and reaches the console only through capabilities an administrator consented to and roles they granted; its pages run sandboxed with no session; everything it does is attributed to it on the board, and held to its board project and the projects it is placed on, for a person to what the person may see, a requester's own decision apart ([ADR-0050](adr/0050-plugin-code-runs-in-a-host-process-of-its-own-and-reaches-the-console-only-through-the-capabilities-it-declared.md), [ADR-0080](adr/0080-a-plugin-reaches-the-projects-it-is-placed-on-and-whoever-may-use-it-is-a-requester-in-its-board-project.md), [specs/plugins.md](specs/plugins.md)).
- **Agent accounts** (the account, its signals, its heartbeat, its transcript, its runner, its page, its invitation, the guide, its setup, its onboarding, the board's wakes, its briefings, the `slack` wake source, the autosave and the skill `running-an-agent` built; what waits for a machine and a workspace to be run on is on the roadmap): an agent account is a member under the same rules as a person, with a manager it reports to and never an administrator's role; it is entered only through its own sign-in at the identity provider, and what its command holds is a session that lapses when unused, held to what a token may ask and ended by a supervisor at once; the console holds no credential of a model's, a messenger's or a git host's for it, only the named secrets it sealed, read by the account itself and seeded write-only by a supervisor, every access on the account's record ([ADR-0087](adr/0087-an-agent-account-keeps-its-secrets-in-a-store-of-its-own-that-only-it-reads.md)); what a runner reports is untrusted text, parsed, bounded, shown as text and never rendered, and is the console's record of what the runner said, not proof against an agent that set out to deceive its recorder ([ADR-0086](adr/0086-a-session-leaves-a-transcript-that-is-kept-for-good.md)); every signal names who sent it, what comes from outside the console cannot pass for a header, and the rules say that only a supervisor's `tell`, the board and the rules instruct ([ADR-0085](adr/0085-a-runner-on-the-agents-machine-is-told-by-signals-and-runs-one-session-at-a-time.md)); an invitation code names an account and the organization's services for a week and gives nobody the account ([ADR-0088](adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)); whether an agent administers its machine is its operator's choice, and agents that do, on one shared machine, are not separated from one another.
- **Supply chain:** lockfile with integrity hashes, a minimum release age, an allow-list for install scripts, actions pinned by commit, secret scanning.

## Open questions

1. 2.
