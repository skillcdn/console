**Pre-1.0.** Published from `main` by the release workflow, from changesets, through the registry's trusted publishing ([ADR-0007](https://github.com/skillcdn/console/blob/main/docs/adr/0007-the-package-is-published-through-trusted-publishing-and-versioned-on-the-core-line.md)). The version's major and minor are SkillCDN's, the one version of the main repository's packages the console is built on, and its patch the console's own: `@skillcdn/console` 0.5.x is the console for SkillCDN 0.5, and the changelog says what each release changed, first as `Breaking:` where it changed what existed ([ADR-0034](https://github.com/skillcdn/console/blob/main/docs/adr/0034-the-package-is-versioned-on-skillcdns-line-one-line-at-a-time-with-a-patch-of-its-own.md)). All three layers are here, and the command: the contract of the REST API, the components, the composition of the default console, and `console`, what an agent works the board with.

## What it exports

| Layer | What it is for | Status |
|---|---|---|
| The schemas and the client of the console's REST API | A custom UI talks to any console with types, and the contract has one source, shared with the server in `apps/console`. Also on its own at `@skillcdn/console/api`, which brings no React with it. | exported |
| The `console` command | The agent's side of the console: a thin client of the REST API, shipped as the package's `bin`, which a person signs in once with a token. Also as a function at `@skillcdn/console/cli`. | exported |
| The components: the board, a task, a run, a decision, the live feed | Each takes its data as props and nothing from the network. | exported |
| `createConsole(config)` | The default console assembled from the components, with the places a team may replace named. The UI the image serves is this, with the default configuration. | exported |
| The serving of a build | `@skillcdn/console/web`: the files of a build, the page for every other path, under one policy. What the image serves the default UI with, and what `console serve` serves a console of your own with. Node only. | exported |
| The contract of a plugin | `@skillcdn/console/plugin`: the manifest's schema, `definePlugin` and its definers, the types of `ctx`; `@skillcdn/console/plugin/web`: the frame's side of the bridge; `@skillcdn/console/plugin/testing`: a `ctx` for a plugin's tests; and `console-plugin`, the second `bin`, which writes a plugin from a template and checks one as a console would. A console runs them, an agent works one through `console plugin <key>`, and a person sees its pages in frames the console's page embeds, `PluginFrame` here, on the front page's `HomeGrid` among the projects, with the plugins' settings on `/settings/plugins` ([docs/specs/plugins.md](https://github.com/skillcdn/console/blob/main/docs/specs/plugins.md)). | exported |

### The API layer

```ts
import { createClient, restTaskSchema, TASK_STATES } from "@skillcdn/console/api";

const client = createClient({ baseUrl: "https://console.example" }); // the page's own origin when left out
const { items } = await client.tasks({ state: "ready" });
```

- **The vocabulary:** `TASK_STATES` (and `OPEN_TASK_STATES`), `TASK_PRIORITIES`, `GOAL_STATES`, `COLOR_NAMES` (the colours the pages paint; `CATEGORY_COLORS` is the same list), `PROJECT_ICON_TYPES` (the kinds of image a project's mark may be), `RUN_STATUSES`, `EVENT_KINDS`, `LINK_SOURCES`, with their types. One source for the database's constraints, the schemas and the board. With them, the rule of a document's path and of the links a text makes: `isDocumentPath`, `documentPathsIn`, `folderOf`, `nameOf`, `foldersAbove`, which the server records links by and the pages render them by. And a project's mark where it chose none: `projectColorOf` (a colour from its key, never gray) and `projectSymbolOf` (the first letter of its name).
- **The bounds** every input is held to (`MAX_TITLE_LENGTH`, `MAX_BODY_LENGTH`, `MAX_OPTIONS`, ...), so that a page can say so before a request is made.
- **The routes:** `REST_ROUTES` (the workspace's resources), `AUTH_ROUTES`, and the helpers that build a path (`projectPath(key, collection, id)` for everything under a project, `projectIconPath(key, icon)` for a project's image, `restPath`, `loginPath`, `signInPath`). The API itself is described in [docs/specs/rest.md](https://github.com/skillcdn/console/blob/main/docs/specs/rest.md).
- **The schemas,** in the mini build of zod, which runs in a browser: what the server answers (`restProjectSchema`, `restMemberSchema`, `restTaskSchema`, `restDecisionSchema`, `restEventSchema`, `restMeSchema`, ...) and what it is sent (`restProjectInputSchema`, `restTaskInputSchema`, `restTaskPatchSchema`, `restDecisionInputSchema`, `restAnswerInputSchema`, ...). Absent values are `null` on the wire, never missing keys. The server validates with the input schemas and is tested against the others.
- **The client:** `createClient({ baseUrl, fetch })` answers typed values parsed with those schemas, and throws an `ApiError` with the server's stable `code` (or `network`, `invalid_response`) for anything else. It takes a `fetch` and reads nothing else. With `userAgent`, every request names the client: the command sends `skillcdn-console/<version>`, by which the console holds it to the versions it takes ([ADR-0025](https://github.com/skillcdn/console/blob/main/docs/adr/0025-the-command-names-its-version-on-every-request-and-the-console-holds-it-to-the-range-it-takes.md)); `me()` answers the console's version and that range as `console`, and the `compat` module (`parseVersion`, `compareVersions`, `judgeClient`, `clientRange`, `commonRange`, `judgeConsole`, `consoleRange`, `userAgentOf`, `clientVersionOf`, the headers `VERSION_HEADER` and `CLIENT_RANGE_HEADER`, `CLIENT_POLICY`, the oldest command a console answers, by which the package narrows the common rule and never widens it, and `CONSOLE_AT_LEAST`, the oldest console the command works with; within a line of SkillCDN the two go together whatever the patch, and a release that changes what passes between them raises the floors, ADR-0038) is exported for a console or a script that compares itself with it. With `token`, a token a person made on their Agents page, every request carries `Authorization: Bearer` and no cookie: how a script or a console of a person's own acts as that person, configuring included (`createProject`, `updatePerson`, a project's `update`, `setIcon`, `addMember`, `updateMember` and `removeMember`, `createCategory`, `updateCategory` and `removeCategory`), within the person's own roles; only the tokens themselves and the approval of a connection are a session's, except that a token gives itself up with `giveUpToken` ([ADR-0021](https://github.com/skillcdn/console/blob/main/docs/adr/0021-a-token-configures-as-its-person-does.md)). The board is a project's: `client.projects()` lists those the person may see, and `client.project(key)` is the client of one, with its tasks, decisions, goals, runs, files, events, skills (`skills`, the pack by name and by count with its skills and, for a program, what the address serves as `@skillcdn/core` spells it; `skill`, `skillFile`, `skillBrowse` and `skillFind`, each answering what the pack answered as `read`, a `RestSkill`, `RestFile`, `RestBrowse` or `RestFind` of `@skillcdn/core`, with the pack's own refusal beside the status, ADR-0031; `skillRows` and `skillCode`, a page of the tables or of the fenced code blocks of a document, or of every document under a folder, as data, a `RestRows` or a `RestCode`, ADR-0100), documents, settings, members and image (`setIcon`, `removeIcon`). `tasks(filter)` narrows the board (`TaskFilter`: a state, the open ones, a category's key, a goal, a worker, a day tasks are due by, and `q`, words of the title or a number, how a task is found by searching) and pages it (`Page`: `limit` and `offset`; the answer carries `more`), as `decisions(filter)`, `runs(filter)` and `goals(filter)` are paged; a task carries its `owner` and its `workers` (any number, ADR-0037), its `category`, `goalId`, its plan (`startsOn`, `dueOn`) and its moments (`startedAt`, `doneAt`). The roadmap is `goals(filter)` (`GoalFilter`: a state, the open ones, a category's key, `q` and a page), `goal(id)`, `createGoal` and `updateGoal`; the workspace's categories are `client.categories()`, `createCategory`, `updateCategory` and `removeCategory`; `client.work()` is what is on the person's plate across their projects ([ADR-0019](https://github.com/skillcdn/console/blob/main/docs/adr/0019-a-task-is-planned-in-days-the-board-keeps-its-moments-and-goals-and-categories-give-the-work-its-shape.md)). The documents go by path: `documents({ folder })` lists a folder, `documents({ q })` finds pages by their words, `document(path)` reads one with its links both ways and its files, `writeDocument(path, { title, body, baseVersion })` writes a version, `archiveDocument`, `restoreDocument`, `documentVersions`, `documentVersion(path, n)`, `attachFile(path, upload)` and `documentFileUrl(path, id)` do the rest; `updateDecision(id, { outcome })` grows a decision's record. The rules of the board ([ADR-0023](https://github.com/skillcdn/console/blob/main/docs/adr/0023-the-rules-of-a-board-are-pages-the-workspace-and-its-projects-keep-read-first-by-every-agent.md)) are `client.rules()`, `writeRules`, `archiveRules` and `rulesVersions`, for the workspace's, and a project's `rules()`, which answers the workspace's with the project's own; a project's are written as the page `rules`. `REFERENCE_RULES` is what holds where an organization wrote none, and `isReferenceRules` tells it from a text; `fillRules` fills `{language}` (`RULES_LANGUAGE_PLACEHOLDER`) with the name of a person's language, which `languageNameOf` gives from its tag. `agentLabel` is an agent's name before where it runs, what the pages show of "Claude Code on a laptop". `connect`, `connectRequest`, `approveConnection`, `denyConnection` and `claimConnection` are the two sides of an agent connecting with a code a person approves (ADR-0011), and `personTokens` and `revokePersonToken` an administrator's sight of everyone's agents. An `EventSource` cannot carry a header, so a stream read with a token is a `fetch` of `eventStreamUrl(after)`. `handInFile` sends a file as a form, and `fileUrl` says where its bytes are read back; a file put on a decision is read at the decision's own address too, `decisionFileUrl(decisionId, fileId)` (`decisionFilePath` among the routes), by whoever the decision reaches, in a project they may see or not ([ADR-0068](https://github.com/skillcdn/console/blob/main/docs/adr/0068-a-decision-reaches-whom-it-is-addressed-to-wherever-it-is-and-a-plugins-reaches-the-managers-above-them.md)). `events(after, { task })` is everything that happened to one task.

### The command line

```sh
npm install -g @skillcdn/console                 # where the agent runs
console login --url https://console.example      # shows an address and a code; a person approves, and the token arrives here
console project new web "The web app"            # a project of your own, as on the pages; member, category and person role do the rest
console use web                                  # the project this directory works in; .skillcdn-console.json, committed; prints the sentence for AGENTS.md
console take 7                                   # a run begins on task #7 of the project, for the person the token is
console report "Found the cause: the parser trusts its input."
console hand-in ./report.md --label "the report"  # a file the console keeps, or an https link
console comment 7 "Which screen did you mean?" --attach ./shot.png   # a word in the task's discussion, with a picture; console file <id> reads one back
console skills                                   # the project's skills, with the URI to load each by
console rules                                    # what the organization and the project ask of agents; take prints them with the task
console ask "Keep the old behaviour?" --option "Keep it" --option "Change it"
console write notes/parser --title "The parser" --file notes.md   # a page of the project's documents, by path
console doc guides/onboarding                     # a page in full, with what refers to it
console finish --summary "Done: the parser refuses empty input."
console serve dist                                # a console of your own, built from this package, served for you
```

- **`console`** is the agent's side of the console ([docs/specs/cli.md](https://github.com/skillcdn/console/blob/main/docs/specs/cli.md)): a thin client of the REST API with no logic of its own, no dependencies beyond the package's, and no cost to an agent until it is used. The package states Node.js 24 as its floor and is tested on it; 22 runs the command today, checked by hand on each release. `console help` says everything an agent needs and `console --version` which version this is; `--json` answers with the console's own JSON; the exit code says whether the console did it (`0`), refused or could not be reached (`1`), did not understand (`2`), or a decision still waits (`3`), or the command and the console do not go together (`4`: the console refuses a command outside the versions it takes, and the command prints the update to make where it is installed, for the machine, in the project or fetched for the run; `console whoami` says both versions and the install, and a command behind or ahead within the range is told once a day on stderr).
- **A person signs it in once per console:** `login` checks the token against the console and keeps it as a login, with the console's address and the account, in `$XDG_CONFIG_HOME/skillcdn-console/credentials.json` (`~/.config` when unset); a machine holds a login per console and account, and a token goes only to the console that issued it. `CONSOLE_URL` and `CONSOLE_TOKEN` in the environment, together, stand in for a login at that address, for a hook or a job. A token is never taken on the command line.
- **Configuring, as the person** ([ADR-0021](https://github.com/skillcdn/console/blob/main/docs/adr/0021-a-token-configures-as-its-person-does.md)): `workspace`, `workspace edit`, `people`, `person role`, `person add`, `person remove`, `person deactivate`, `person reactivate`, `project new`, `project edit`, `project icon`, `members`, `member add`, `member role`, `member remove`, `category new`, `category edit`, `category remove` and `rules write` do what an administrator or an owner does on the pages, with the same refusals (`auth.forbidden` where the person may not), and the event names the agent beside the person. The tokens themselves have no command but `logout`, which gives the command's own up: they are made and removed on the Agents page, signed in.
- **The project's pack** is read as the `skillcdn` command reads one ([ADR-0031](https://github.com/skillcdn/console/blob/main/docs/adr/0031-the-console-reads-a-pack-as-the-skillcdn-command-does-and-a-local-one-from-a-directory.md)): `console skills` prints what a client is told on connect and every skill and document, `console skills <folder>` a folder whole, `console skills --search <words>` what the words find, `console skill <path>` a skill whole with its rules first, and `console skill --file <path>` a file, each rendered with the main repository's own renderers and the reads named as the console's commands, so that an agent reads here what it would read over MCP; a pack is at a SkillCDN deployment, or in a directory on the console's machine where no deployment is reachable.
- **The project's documents** are the agent's to read and write: `docs`, `doc`, `write`, `attach`, `archive` and `restore`, by path; a link in a body to a page's path refers to the page.
- **Every command on the board works in one project:** `--project <key>`, else `CONSOLE_PROJECT`, else what `console use <key>` wrote to `.skillcdn-console.json` in the working directory or one above it, a file meant to be committed. `console projects` lists the projects the person may work in.
- **`console serve [<dir>] [--port <n>]`** is for a person: it serves [a console of your own](#a-console-of-your-own) from your machine, the build in `<dir>` at `http://127.0.0.1:11197/`, and carries everything under `/api/` to the console the command is signed in to, with your token, which the pages never see ([ADR-0014](https://github.com/skillcdn/console/blob/main/docs/adr/0014-a-persons-own-console-is-served-from-their-machine-by-the-command.md)). The loopback only; a request from another site's page is refused. Without a directory only the API is served, for a development server.
- **The guide of an agent account's setup** ([ADR-0088](https://github.com/skillcdn/console/blob/main/docs/adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)) is made by `setupGuideOf` from what an invitation's code opens (`client.agentSetup(code)`), and printed by `setupGuideText`; `SetupGuideView` shows it, `AgentInvitationPanel` is the invitation under an account, and `setupCommandOf` and `setupSentenceOf` spell the command and the one line said on the machine. The default console shows the guide at `/setup/<code>` (`setupHref`) to a browser that is signed in nowhere.
- **`@skillcdn/console/runner`** is what `console runner` is made of ([docs/specs/runner.md](https://github.com/skillcdn/console/blob/main/docs/specs/runner.md)), for a console of one's own that drives another product or a test that runs a runner against a console: `createRunner(options)`, which takes a `ConsoleClient` on the account's command, a `Driver`, its `runner.json` and what it needs of the machine; the `Driver`, `DriverSession` and `DriverEvent` types a driver is written to, `createClaudeDriver`, `createCodexDriver` and `createSpawn`; `createRunnerModules` and `ownRunnerModules`, the four registries a module is known by; `composeSignals`, `headerOf` and `introOf`, how a signal reaches the agent; `redactorOf`, which takes the values of a secret store out of a text in the encodings they are carried in; `parseRunnerConfig`; `launchd`, `systemdUser` and `taskScheduler`, the services that keep a runner running on macOS, on Linux and on Windows, each as a plan of what to write and to run; and `deskFiles`, the template of an agent account's desk, with `deskServicesOf` for what it says of the workspace's services.
- **`@skillcdn/console/cli`** exports `runCli(argv, io)`, the command as a function that takes its environment, its streams, its `fetch` and its credential store: what the integration tests run against the app with no socket, and what a console of a person's own could embed.

### Writing a plugin

```sh
npx console-plugin init leave --key leave   # a plugin from the template: manifest, server module, web bundle, skill, tests, build
cd leave && npm install && npm run build
npm test                                    # the server module against an in-memory context, and the package as a console reads it
npm run check                               # console-plugin check: what a console, or a store, would refuse
```

A plugin is one npm package a console installs into its image and an administrator turns on ([docs/specs/plugins.md](https://github.com/skillcdn/console/blob/main/docs/specs/plugins.md) is the contract, every field and bound; [ADR-0049](https://github.com/skillcdn/console/blob/main/docs/adr/0049-a-plugin-is-an-npm-package-installed-into-the-image-and-enabled-by-an-administrator.md) to [ADR-0054](https://github.com/skillcdn/console/blob/main/docs/adr/0054-a-plugins-pages-run-in-a-sandboxed-frame-and-speak-only-to-their-plugin.md) the decisions). This package is its `devDependency`, for the types and the command; nothing of it is imported at runtime.

- **`@skillcdn/console/plugin`**, for the server module: `definePlugin({ collections, commands, queries, endpoints, on, jobs, upgrades, api, onEnable, onDisable })` is the default export of `dist/server/index.js`, built with everything it imports bundled in. `defineCollection(name, { schema, indexes, ... })` declares the records the console keeps, with a zod schema (`z` is re-exported); `defineCommand({ about, args, roles, run })` and `defineQuery(...)` are what agents run through `console plugin <key> <command>`, their `args` from `arg.text`, `arg.day`, `arg.number`, `arg.boolean`, `arg.enum`, `arg.person`, `arg.project`, `arg.record`, `arg.list` and `arg.file`, typed in `run(ctx, args)`; `defineEndpoint(...)` takes a request of a person's or a webhook's. Everything plugin code does to the console is a call on `ctx` (`PluginContext`): `ctx.records(collection)`, `ctx.console.*`, `ctx.events.emit`, `ctx.fetch`, `ctx.secrets`, `ctx.plugins`, `ctx.log`; the console refuses what the manifest did not ask with a `PluginRefusal`, and a plugin refuses in its own words with `PluginError`. The manifest, `console-plugin.json`, is read with `parsePluginManifest`; `RESERVED_PLUGIN_KEYS`, `PLUGIN_CAPABILITIES` with `capabilityWords`, the bounds (`MAX_PLUGIN_RECORD_BYTES`, `PLUGIN_COMMAND_MS`, ...) and the refusals (`PLUGIN_REFUSALS`) are the same words the console goes by. `describePlugin(definition)` is the definition as data, what the host reads and what `check` holds to the manifest.
- **`@skillcdn/console/plugin/web`**, for the web bundle: `connect()` in the frame the console serves says `ready`, receives `init` (who looks, at what, the console's design tokens, applied to `:root`), and answers `{ context, command, query, records, files, navigate, download, setTitle, onEvent, onTheme, onPath }`, each performed by the console's page under the plugin's own routes and nothing else. It depends on nothing; `@skillcdn/console/plugin/web/react` adds `usePlugin()`. A bundle imports nothing from elsewhere and never reaches for `fetch`, which `check` holds it to.
- **`@skillcdn/console/plugin/testing`**: `createTestContext({ collections, plugin, caller, console, secrets, ... })` is a `ctx` for the plugin's own tests, records in memory and checked as the console checks them, the console refusing whatever the test did not provide, `emitted` and `logged` to assert on.
- **`console-plugin`**: `init <dir> --key <key> [--name <name>] [--console <dependency>]` writes a plugin from the template this package ships (`template/plugin`), what `examples/plugin-hello` in the repository is; `check [<dir>]` reads a built plugin as a console would: the manifest, `package.json` (a permissive license, no install scripts, `files` that ship what runs), the server module loaded in a hardened thread, as the host loads one, and held to the manifest, the web bundle self-contained and its classes prefixed `pl-<key>-`, the skills in the SkillCDN Format, the migrations. Node.js 24 or newer.

### The components and the composition

```tsx
import { createConsole } from "@skillcdn/console";
import "@skillcdn/console/console.css";

createConsole({
  title: "Acme", // until the server says what the board is called
  components: { SignIn: MySignIn }, // any of Shell, Board, TaskView, DecisionList, EventFeed, SignIn, TokenList, SessionList, PeopleList, SkillList, HomeGrid, MemberList, Calendar, GoalList, WorkList, CategoryList
}).mount(document.getElementById("root"));
```

- **The components** take their data as props and nothing from the network: `Board` (one column per state, the sooner due first; given `onMove`, a card is dragged to another column with a mouse, or with a finger that rests on it a moment first, and the board scrolls on while the card is held near its edge, still or moving, as `edgeScrollOf` meters it; given `editHref` and `onArchive`, each card has a menu with the way to the task's form and, once it is done or dropped, the way to put it away; the columns `folded` names, `FOLDED_STATES`, done and dropped, by default, are strips with their count and the way to open them, still taking a card dragged onto them, and `[]` folds none), `TaskCard`, `BoardFilters` with `filterTasks` and `byDue` (the board narrowed by category, goal, person and one's own), `TaskList` (tasks as rows, a page at a time), `TaskView` (one task with its plan, its moments, its workers, its decisions and its parts, the ways to its forms in its head beside the title; given `parent`, the task it is part of when the page has read it, and `findTasks` and `findGoals`, its form searches), `TaskForm` (with the `categories` to choose from, the `people` to put on the task as its workers, and `findTasks` and `findGoals`, searches a page at a time by which the task it is part of and the goal it works towards are found, never offered whole, ADR-0037), `Calendar` and `Workload` with `workloadOf` (a month with each task across its planned days, a bar in a lane of its own, or on its one day, a due day or a start, three of a day's own and the way to the rest where it has more, the person who has each before its title, with a legend of the colours of the `categories` given, and who has what; `weekSegments` lays the bars; `TaskTip` is the task under the pointer in full, with the facts its page lists, within its item and above or below it as `placeTip` says, where there is more room, its goal named from the `goals` given; the composition narrows the page with `BoardFilters` as it does the board, the address carrying the filter with the month), `GoalList`, `GoalView` and `GoalForm` (the roadmap, one goal with its tasks by state, and the way to set one, with the `categories` to sort it into and its start and target days, ADR-0026), `GoalTimeline` with `timelineBars` (the roadmap as months: six from the month given, each goal planned in days a bar from its start to its target in the colour of its category, filled as far as its tasks are done, today marked, and the goals without days named below; `Calendar` given `goalHref` marks each goal's target day on the month), `WorkList` (a person's own work across projects), `MyDecisions` (a person's decisions across their projects: those addressed to them, the waiting first, and those they asked of others, each row naming who asked and who answers, ADR-0042; the files put on a decision read at the decision's own address, since it may be of a project the person may not see, ADR-0068, unless `fileHref(projectKey, fileId, decisionId)` says where), `CategoryList` (the categories, with the ways an administrator keeps them), `DecisionList` and `DecisionCard` (the waiting ones as cards, each with the way to answer, one of the options or a line of one's own, and, given `addressing`, the way to say anew whom it is for, [ADR-0096](https://github.com/skillcdn/console/blob/main/docs/adr/0096-a-decision-that-waits-may-be-addressed-anew-by-whoever-may-answer-it.md): the people to name, given or read when the form opens, and `onAddress`; the answered ones as the record, `DecisionLog`, a row each with who asked and when, through which agent, the answer with the word given, marked when it is the person's own, and who answered and when, twenty to a page, each page at an address given `pageHref` and `page`, or turned in place), `DecisionForm` (about the task given as `taskId`, or one found by search through `findTasks`, a page at a time, ADR-0037; addressed to `me` unless one of `deciders`, the people who may be named, is chosen, ADR-0042), `EventFeed` (a sentence per event, newest first, a page at a time; `describeEvent` makes the sentence), `Shell` (the header with the workspace, the project, the tabs of the pages and the person's menu), `SignIn` (one button per provider the deployment offers), `TokenList`, `TokenForm` and `NewToken` (the agents a person connected, as the tokens they hold, the way to make one by hand, and the one just made with its secret shown once), `SessionList` (the browsers a person is signed in on, each with what it is, when it was last used, where from and the day it signed in, the current one marked, and the ways to sign any other out, or all the others at once; - **The composition:** `createConsole(config)` returns `{ App, mount }`. `App` is the whole console as one component; `mount(container)` renders it and returns the way to take it down. `config.baseUrl` is the origin of the API (the page's own when left out), `config.components` the pieces to replace (`ConsoleComponents` names them with the props each takes), `config.languages` the packs the pages speak, `config.brand` the addresses of a symbol and a wordmark to show beside the name (ADR-0013; the default console passes those of `@skillcdn/brand`, the main repository's package of its marks), `config.client` a client of your own, for tests, `config.persona` what an agent account's persona is proposed and drawn from in place of the package's (ADR-0084): `names`, a handle and its spelling per language each, which "Add an agent account" proposes from, and `avatarSets`, the sets the avatars are drawn from on this console's pages (`AvatarSet`, which is data: its grounds and its ramps as colours, its bodies, its surfaces and its accents as outlines in a square of a hundred units; ADR-0097), each under a version the package does not use. The SkillCDN name and marks are trademarks of KDX Labs under the main repository's trademark policy, not under this package's MIT license; a custom console brings its own marks through the same slot. A console that holds a token rather than a session (one of your own, served by `console serve`) is told so by the API (`me.agent`, the token's name, or `me.session` for a command signed in as the account itself) and offers nothing a token cannot do: no tokens, no sessions and no sign-out, since those are a person's own doing, and on the Agents page the agent accounts alone; everything else, configuring included, it does on the token as the person (ADR-0021), and it keeps the choice of language on the person. The pages route in the browser and every form has an address (ADR-0010): the projects at `/`, the person's own work at `/work`, the workspace's settings at `/settings` (its rules, its categories at `/categories`, where its skills come from), a project's pages under `/projects/<key>` (its roadmap, calendar and settings among them), a task by its number, a goal and a decision by their ids, a document by its path, and the query for how a page is shown, the board's filters, the calendar's month, the week of the person's work and the settings' forms among it (`matchRoute(pathname, search)`, `PATHS`, `projectHref`, `boardHref`, `taskHref`, `goalHref`, `calendarHref`, `workHref`, `personWorkHref`, `decisionHref`, `docHref`, `settingsHref`, `projectSettingsHref`, `newTaskHref`, `newGoalHref`, `newDecisionHref`, and `movedFrom` for the addresses of before); every link to one of them is followed in place, with one history entry per step; the workspace is loaded once and the project the page is on whole, kept current by the project's stream (`useConsoleData(client, projectKey)`, for a composition of your own).
- **Pages of your own:** `config.pages` adds tabs beside the console's. Each is a `CustomPage`: a `key` (what the address says: `/pages/<key>` on the workspace, `/projects/<project>/pages/<key>` on a project), a `label` (one word, or a word by language tag with `en` standing in), a `level` (`workspace`, or `project` for a tab on every project), `wide` for a page that takes the whole window, and `render(context)`, which gets what the default pages get: the `data` of `useConsoleData` with its actions, the `project` the page is on, the `client`, the `navigation`, the `words` and the `language`. `customPageHref` names the address and `customPageLabel` the tab's word. A page that is not among the pages given shows nothing there.
- **The languages:** every word the pages show is in a pack (`Messages`, keyed as `en` is), English and Korean ship (`ENGLISH`, `KOREAN`, `DEFAULT_LANGUAGES`), and a component takes its words from the language above it (`useWords`, `useLanguage`, `LanguageContext`), English where there is none. A person's language is kept on them (`client.updateMe({ language })`): the browser's languages decide it the first time the pages see them (`chooseLanguage`, `packFor`), and the person after that; where neither names a language the pages speak, the workspace's does, as its administrator set it ([ADR-0081](https://github.com/skillcdn/console/blob/main/docs/adr/0081-a-workspace-has-a-language-for-whoever-has-none-of-their-own.md)), else the first pack. `createConsole({ languages })` replaces the packs the default console speaks, so that a custom console adds a language of its own; a pack is complete by type. A failure is read the same way: the server's code in the pack's `errors`, the server's own message being English and for programs (`errorWords(error, fallback, pack)`, `wordsForFailure(error, pack)`).
- **The styles** are one file, `@skillcdn/console/console.css`: the tokens (`--sc-*`, 87 of them, every one read by a rule), a small reset, and one class per block, all prefixed `sc-`. The look is SkillCDN's own, on a light ground ([ADR-0040](https://github.com/skillcdn/console/blob/main/docs/adr/0040-the-pages-are-light-by-default.md)): one accent, the page a pale field (the shell, `sc-shell`, paints it), the surfaces panes of frosted glass over it, and white sheets inside the panes. A custom console is a small repository that depends on this package, holds a configuration and a CI job, and builds to static files: the organization's, served by the image from `WEB_ROOT` in place of the default UI, or your own, served by `console serve` on your machine. Nothing of the server is in the package but the serving of a build, `@skillcdn/console/web`, which the image and the command share.

### A console of your own

A console you build from this package and run for yourself, against your organization's console, with the pages and components of your choosing ([ADR-0014](https://github.com/skillcdn/console/blob/main/docs/adr/0014-a-persons-own-console-is-served-from-their-machine-by-the-command.md)). It is a small repository of your own, in the shape of the default console (`apps/console/web` in the console's repository: one page, one script, one build):

```sh
npm install @skillcdn/console react react-dom
npm install --save-dev vite @vitejs/plugin-react typescript
```

```tsx
// src/main.tsx: the composition, with a configuration of your own
import { createConsole } from "@skillcdn/console";
import "@skillcdn/console/console.css";

const container = document.getElementById("root");
if (container === null) {
  throw new Error("the page has no #root element");
}
createConsole({ title: "Mine" }).mount(container);
```

```ts
// vite.config.ts: while building, the development server sends the API to console serve
import react from "@vitejs/plugin-react";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [react()],
  server: { proxy: { "/api": { target: "http://127.0.0.1:11197", changeOrigin: true } } },
});
```

```sh
console login --url https://console.example      # once: the token an agent of yours would hold serves your console too
console serve                                    # the API alone, at http://127.0.0.1:11197/api/, for the development server
npx vite                                         # your pages, reloading as you build them
npx vite build && console serve dist             # the build served whole, at http://127.0.0.1:11197/
```

The pages run on your token: what you may do on the board, they may do, and no more. The token never reaches the browser; the command adds it on the way, on the loopback only, and refuses a request from another site's page. The tokens themselves are made and removed on the organization's console, signed in, and the pages say so there; everything else, configuring included, the pages do on your token as the organization's console does on your session. Replace a component, pass your own language pack or your own marks, or compose pages of your own from the components and `useConsoleData`: the sections above say what each piece takes.

### The skills, for an agent

What an agent reads to work the board, to plan and set it up, to build a console, to write a plugin, to deploy a console or to run an agent account is in the console's repository as skills in the SkillCDN Format ([ADR-0015](https://github.com/skillcdn/console/blob/main/docs/adr/0015-the-consoles-skills-live-in-this-repository-in-the-skillcdn-format-and-the-package-carries-them.md)), served by SkillCDN at `skillcdn.ai/gh/skillcdn/console` with the architecture, the decisions and the specifications, and shipped in this package: `skills/working-the-board/SKILL.md`, `skills/planning-the-board/SKILL.md`, `skills/building-a-console/SKILL.md`, `skills/building-a-plugin/SKILL.md`, `skills/deploying-a-console/SKILL.md` and `skills/running-an-agent/SKILL.md`, each with its references, the deploying skill with its scripts, their manifest `SKILLCDN.md` with the rules they share, the specifications they point to under `docs/specs/` (`rest.md`, `cli.md`), and the sources under `src/` without the tests, so that `npm install` brings what an agent needs to read, at the version installed. Point an agent at them in `node_modules/@skillcdn/console/`, or copy a skill's folder into the agent's own skills. A project of a console may name that address as its skills address, and an organization's own skill for its console adds its rules and links these. The skills are maps: what they name, this README, the types and the specifications say in full.

## Rules

Read the root [`AGENTS.md`](../../AGENTS.md) first. This package is what other people install; it is their contract.

- **Pure where it can be.** The schemas and the components do no I/O; the client takes a `fetch` and a base URL; the command takes everything it needs through `runCli`. Nothing here reads the environment but the command's entry point, `src/cli/main.ts`, the one place the process is read (lint enforces it).
- **The main repository's packages come from npm,** by version: `@skillcdn/core` here, for addresses, the REST shapes of a pack and the renderers of what a model is given; the client, the indexer and the reader in the app. Never a path into the main repository, never a copy of its code ([ADR-0001](../../docs/adr/0001-the-console-is-the-reference-console-built-on-the-published-packages.md), [ADR-0031](../../docs/adr/0031-the-console-reads-a-pack-as-the-skillcdn-command-does-and-a-local-one-from-a-directory.md)).
- **Exported types are public contract.** A change to what `src/index.ts` exports carries a changeset written for whoever installs the package, and the README changes with the usage.
- **Runtime dependencies need a reason.** This package ships to browsers; a dependency here needs a stronger case than anywhere else in the repository.
- **A page is built from the console's parts.** Before writing a class, look in `src/styles/console.css` and `src/components/ui.tsx` for the one that is there: a row of things added to and taken from (`sc-chips` of `Chip`s), a person (`PersonChip`), a state or a kind (`Badge`, `CategoryBadge`; nothing stands before a badge's words but the dot of one that is `live`, what it names being at work this moment), facts (`sc-facts`, `sc-facts-plain`, `sc-facts-row`, `sc-person-facts`), a label (`sc-eyebrow`), a note (`Callout`), files to choose and the ones chosen (`sc-file-choice`, `sc-chosen-files`), the views of a page (`sc-subtabs`), a pane (`sc-panel`), a head (`sc-page-head`), a form in parts under headings (`sc-form-part`), steps done in order (`sc-steps`), buttons, avatars, progress bars and empty states. A part is used as it is, and never drawn again under a name of the page's own. A class of the page's beside a part places it, its grid area, its margin, its width, and leaves its colours, borders, radius and type alone; a part that should look different is changed in its own rule, for every page at once. A rule reads its colours and its sizes from the tokens; a new one is a new token, listed above. A class the pages no longer name leaves the stylesheet in the same change. A design pass changes how a page looks and not what it does: what is fetched, sent, allowed or tested changes in a change of its own. A changed page is looked at on this machine (`pnpm dev:plugins`) before its commit, at a phone's width and on a wide screen, in English and in Korean; what was not looked at is said in the commit.
