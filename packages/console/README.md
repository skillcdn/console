**Pre-1.0.** Published from `main` by the release workflow, from changesets, through the registry's trusted publishing ([ADR-0007](https://github.com/skillcdn/console/blob/main/docs/adr/0007-the-package-is-published-through-trusted-publishing-and-versioned-on-the-core-line.md)). The version's major and minor are SkillCDN's, the one version of the main repository's packages the console is built on, and its patch the console's own: `@skillcdn/console` 0.6.x is the console for SkillCDN 0.6, and the changelog says what each release changed, first as `Breaking:` where it changed what existed ([ADR-0034](https://github.com/skillcdn/console/blob/main/docs/adr/0034-the-package-is-versioned-on-skillcdns-line-one-line-at-a-time-with-a-patch-of-its-own.md)). All three layers are here, and the command: the contract of the REST API, the components, the composition of the default console, and `console`, what an agent works the board with.

## What it exports

| Entry point | What it is for |
|---|---|
| `@skillcdn/console` | What a page is built from. The components, the board, a task, a run, a decision, the live feed and the rest: each takes its data as props and nothing from the network. `createConsole(config)`: the default console assembled from the components, with the places a team may replace named. The UI the image serves is this, with the default configuration. With them the charts' and the icon pack's components, and everything of `/api` and `/charts` again, so that a page imports from one place. |
| `@skillcdn/console/api` | The schemas and the client of the console's REST API. A custom UI talks to any console with types, and the contract has one source, shared with the server in `apps/console`. It brings no React with it, and carries the format of a desk's records ([docs/specs/records.md](https://github.com/skillcdn/console/blob/main/docs/specs/records.md)): `recordsItemsSchema` and the rest, with `readRecords` and `checkRecords`. |
| `@skillcdn/console/charts` | A figure, a list of bars, a chart over time, a sparkline, a share and a table of figures, parts of the console's look for a page of your own and a plugin's: the components are in `@skillcdn/console`, and the measures they are placed by are here on their own, depending on nothing. |
| `@skillcdn/console/icons` | Some eighty glyphs drawn on one grid, for the console's pages, a page of your own, a plugin's and a prototype: `Icon` draws one by its name and `IconPicker` chooses one, both in `@skillcdn/console`, and the glyphs as data with `iconElement`, for a bundle without React, are here on their own, depending on nothing. |
| `@skillcdn/console/cli`, and the `console` bin | The agent's side of the console: a thin client of the REST API, shipped as the package's `bin`, which a person signs in once with a token. The entry point is the command as a function, `runCli(argv, io)`. |
| `@skillcdn/console/runner` | The runner of an agent account ([docs/specs/runner.md](https://github.com/skillcdn/console/blob/main/docs/specs/runner.md)), which `console runner` is made of: the drivers of the agent products, the wake sources, the service modules and their registries, for whoever builds on them, a console of one's own that registers a driver for another product or a test that runs one against a console. Node only. |
| `@skillcdn/console/web` | The serving of a build: the files of a build, the page for every other path, under one policy. What the image serves the default UI with, and what `console serve` serves a console of your own with. Node only. |
| `@skillcdn/console/plugin`, `/plugin/web`, `/plugin/web/react`, `/plugin/testing`, and the `console-plugin` bin | The contract of a plugin. `@skillcdn/console/plugin`: the manifest's schema, `definePlugin` and its definers, the types of `ctx`; `@skillcdn/console/plugin/web`: the frame's side of the bridge, and `/plugin/web/react` the same as a hook, `usePlugin()`; `@skillcdn/console/plugin/testing`: a `ctx` for a plugin's tests; and `console-plugin`, the second `bin`, which writes a plugin from a template and checks one as a console would. A console runs them, an agent works one through `console plugin <key>`, and a person sees its pages in frames the console's page embeds, `PluginFrame` of `@skillcdn/console`, on the front page's `HomeGrid` among the projects, with the plugins' settings on `/settings/plugins` ([docs/specs/plugins.md](https://github.com/skillcdn/console/blob/main/docs/specs/plugins.md)). |
| `@skillcdn/console/console.css` | The stylesheet of the pages: the tokens, a small reset and one class per block, which a console of your own imports once and a plugin's frame is handed. |

The table names the entry points, which is where to start, and not every export: a constant, a helper or a type beside them is described where it is declared, in its doc comment, and the sections below name the ones a console of your own begins with.

### The API layer

```ts
import { createClient, restTaskSchema, TASK_STATES } from "@skillcdn/console/api";

const client = createClient({ baseUrl: "https://console.example" }); // the page's own origin when left out
const { items } = await client.tasks({ state: "ready" });
```

- **The vocabulary:** `TASK_STATES` (and `OPEN_TASK_STATES`), `TASK_PRIORITIES`, `GOAL_STATES`, `COLOR_NAMES` (the colours the pages paint; `CATEGORY_COLORS` is the same list), `PROJECT_ICON_TYPES` (the kinds of image a project's mark may be), `RUN_STATUSES`, `EVENT_KINDS`, `LINK_SOURCES`, with their types. One source for the database's constraints, the schemas and the board. With them, the rule of a document's path and of the links a text makes: `isDocumentPath`, `documentPathsIn`, `folderOf`, `nameOf`, `foldersAbove`, which the server records links by and the pages render them by. And a project's mark where it chose none: `projectColorOf` (a colour from its key, never gray) and `projectSymbolOf` (the first letter of its name).
- **The bounds** every input is held to (`MAX_TITLE_LENGTH`, `MAX_BODY_LENGTH`, `MAX_OPTIONS`, ...), so that a page can say so before a request is made.
- **The routes:** `REST_ROUTES` (the workspace's resources), `AUTH_ROUTES`, and the helpers that build a path (`projectPath(key, collection, id)` for everything under a project, `projectIconPath(key, icon)` for a project's image, `restPath`, `loginPath`, `signInPath`). The API itself is described in [docs/specs/rest.md](https://github.com/skillcdn/console/blob/main/docs/specs/rest.md).
- **The schemas,** in the mini build of zod, which runs in a browser: what the server answers (`restProjectSchema`, `restMemberSchema`, `restTaskSchema`, `restDecisionSchema`, `restEventSchema`, `restMeSchema`, ...) and what it is sent (`restProjectInputSchema`, `restTaskInputSchema`, `restTaskPatchSchema`, `restDecisionInputSchema`, `restAnswerInputSchema`, ...). Absent values are `null` on the wire, never missing keys. The server validates with the input schemas and is tested against the others.
- **The client:** `createClient({ baseUrl, fetch })` answers typed values parsed with those schemas, and throws an `ApiError` with the server's stable `code` (or `network`, `invalid_response`) for anything else. It takes a `fetch` and reads nothing else. With `userAgent`, every request names the client: the command sends `skillcdn-console/<version>`, by which the console holds it to the versions it takes ([ADR-0025](https://github.com/skillcdn/console/blob/main/docs/adr/0025-the-command-names-its-version-on-every-request-and-the-console-holds-it-to-the-range-it-takes.md)); `me()` answers the console's version and that range as `console`, and the `compat` module (`parseVersion`, `compareVersions`, `judgeClient`, `clientRange`, `commonRange`, `judgeConsole`, `consoleRange`, `userAgentOf`, `clientVersionOf`, the headers `VERSION_HEADER` and `CLIENT_RANGE_HEADER`, `CLIENT_POLICY`, the oldest command a console answers, by which the package narrows the common rule and never widens it, and `CONSOLE_AT_LEAST`, the oldest console the command works with; within a line of SkillCDN the two go together whatever the patch, and a release that changes what passes between them raises the floors, ADR-0038) is exported for a console or a script that compares itself with it. With `token`, a token a person made on their Agents page, every request carries `Authorization: Bearer` and no cookie: how a script or a console of a person's own acts as that person, configuring included (`createProject`, `updatePerson`, a project's `update`, `setIcon`, `addMember`, `updateMember` and `removeMember`, `createCategory`, `updateCategory` and `removeCategory`), within the person's own roles; only the tokens themselves and the approval of a connection are a session's, except that a token gives itself up with `giveUpToken` ([ADR-0021](https://github.com/skillcdn/console/blob/main/docs/adr/0021-a-token-configures-as-its-person-does.md)). The board is a project's: `client.projects()` lists those the person may see, and `client.project(key)` is the client of one, with its tasks, decisions, goals, runs, files, events, skills (`skills`, the pack by name and by count with its skills and, for a program, what the address serves as `@skillcdn/core` spells it; `skill`, `skillFile`, `skillBrowse` and `skillFind`, each answering what the pack answered as `read`, a `RestSkill`, `RestFile`, `RestBrowse` or `RestFind` of `@skillcdn/core`, with the pack's own refusal beside the status, ADR-0031; `skillRows` and `skillCode`, a page of the tables or of the fenced code blocks of a document, or of every document under a folder, as data, a `RestRows` or a `RestCode`, ADR-0100), documents, settings, members and image (`setIcon`, `removeIcon`). `glance()` is what the project's tile at a glance shows on the front page, in one answer read at one moment (`RestProjectGlance`, ADR-0107): its tasks counted by state, the decisions waiting, and its tasks in progress, its tasks in review and its goals ahead, ordered and cut by the console, `GLANCE_ROWS` at most, each with how many there are in all. `tasks(filter)` narrows the board (`TaskFilter`: a state, the open ones, a category's key, a goal, a worker, a day tasks are due by, and `q`, words of the title or a number, how a task is found by searching) and pages it (`Page`: `limit` and `offset`; the answer carries `more`), as `decisions(filter)`, `runs(filter)` and `goals(filter)` are paged; a task carries its `owner` and its `workers` (any number, ADR-0037), its `category`, `goalId`, its plan (`startsOn`, `dueOn`) and its moments (`startedAt`, `doneAt`). The roadmap is `goals(filter)` (`GoalFilter`: a state, the open ones, a category's key, `q` and a page), `goal(id)`, `createGoal` and `updateGoal`; the workspace's categories are `client.categories()`, `createCategory`, `updateCategory` and `removeCategory`; `client.work()` is what is on the person's plate across their projects ([ADR-0019](https://github.com/skillcdn/console/blob/main/docs/adr/0019-a-task-is-planned-in-days-the-board-keeps-its-moments-and-goals-and-categories-give-the-work-its-shape.md)). What a member is told of ([ADR-0157](https://github.com/skillcdn/console/blob/main/docs/adr/0157-the-console-decides-who-is-told-of-what-and-keeps-the-record-and-a-plugin-carries-it-out.md)) is `client.notifications(filter)`, a page of them, the newest first; `readNotifications({ ids })`, or `({ all: true })`, marks them read and answers the moment it read them at (`at`); `notificationSettings()` and `updateNotificationSettings(input)` read and change the kinds, the projects turned off and whether one's own agents count, which are of everything a member is told: what a plugin that carries notifications elsewhere sends of it is that plugin's own setting, and none here. A task's bell is the project's `taskFollow(ref)`, which answers `{ on, usual, all }`, and `followTask(ref, on)`; `taskToldByDefault`, `taskTold` and `taskFollowToKeep` are the rule the console holds it by, with `TASK_KINDS_OF`, the kinds a task goes on telling its owner and its workers under. The documents go by path: `documents({ folder })` lists a folder, `documents({ q })` finds pages by their words, `document(path)` reads one with its links both ways and its files, `writeDocument(path, { title, body, baseVersion })` writes a version, `archiveDocument`, `restoreDocument`, `documentVersions`, `documentVersion(path, n)`, `attachFile(path, upload)` and `documentFileUrl(path, id)` do the rest; `updateDecision(id, { outcome })` grows a decision's record. The rules of the board ([ADR-0023](https://github.com/skillcdn/console/blob/main/docs/adr/0023-the-rules-of-a-board-are-pages-the-workspace-and-its-projects-keep-read-first-by-every-agent.md)) are `client.rules()`, `writeRules`, `archiveRules` and `rulesVersions`, for the workspace's, and a project's `rules()`, which answers the workspace's with the project's own; a project's are written as the page `rules`. `CONSOLE_RULES` is what always holds, `rulesWith` reads it whole with what an organization adds, and `addedRulesOf` takes from a text what it adds; `fillRules` fills `{language}` (`RULES_LANGUAGE_PLACEHOLDER`) with the name of a person's language, which `languageNameOf` gives from its tag. `agentLabel` is an agent's name before where it runs, what the pages show of "Claude Code on a laptop". `connect`, `connectRequest`, `approveConnection`, `denyConnection` and `claimConnection` are the two sides of an agent connecting with a code a person approves (ADR-0011), and `personTokens` and `revokePersonToken` an administrator's sight of everyone's agents. An `EventSource` cannot carry a header, so a stream read with a token is a `fetch` of `eventStreamUrl(after)`. `handInFile` sends a file as a form, and `fileUrl` says where its bytes are read back; a file put on a decision is read at the decision's own address too, `decisionFileUrl(decisionId, fileId)` (`decisionFilePath` among the routes), by whoever the decision reaches, in a project they may see or not ([ADR-0068](https://github.com/skillcdn/console/blob/main/docs/adr/0068-a-decision-reaches-whom-it-is-addressed-to-wherever-it-is-and-a-plugins-reaches-the-managers-above-them.md)). `events(after, { task })` is everything that happened to one task.

### The command line

```sh
npm install -g @skillcdn/console                 # where the agent runs
console login --url https://console.example      # shows an address and a code; a person approves, and the token arrives here
console project new web "The web app"            # a project of your own, as on the pages; member, category and person role do the rest
console use web                                  # the project this directory works in; .skillcdn-console.json, committed; prints the sentence for AGENTS.md
console take 7                                   # a run begins on task #7 of the project, for the person the token is
console report "Found the cause: the parser trusts its input."
console hand-in ./report.md --label "the report"  # a file the console keeps, or an https link
console comment 7 "Which screen did you mean?" --attach ./shot.png   # a word in the task's discussion, with a picture; console file <id> reads one back
console skills                                   # the project's skills, with the URI to load each by
console rules                                    # what the organization and the project ask of agents; take prints them with the task
console ask "Keep the old behaviour?" --option "Keep it" --option "Change it"
console doc write notes/parser --title "The parser" --file notes.md   # a page of the project's documents, by path
console doc guides/onboarding                     # a page in full, with what refers to it
console finish --summary "Done: the parser refuses empty input."
console serve dist                                # a console of your own, built from this package, served for you
```

- **`console`** is the agent's side of the console ([docs/specs/cli.md](https://github.com/skillcdn/console/blob/main/docs/specs/cli.md)): a thin client of the REST API with no logic of its own, no dependencies beyond the package's, and no cost to an agent until it is used. The package states Node.js 24 as its floor and is tested on it; 22 runs the command today, checked by hand on each release. `console help` lists the commands in one table, by who runs them, `console help <command>` says one in full, a form of it with `console help <command> <form>`, each within a bound a test holds since an agent pays for every byte it reads ([ADR-0167](https://github.com/skillcdn/console/blob/main/docs/adr/0167-the-commands-of-the-console-command-are-one-table-by-who-runs-them-its-help-is-in-layers-within-bounds-and-a-mistake-is-answered-with-a-sentence.md)), and `console --version` says which version this is; `--json` answers with the console's own JSON; the exit code says whether the console did it (`0`), refused or could not be reached (`1`), did not understand (`2`), or a decision still waits (`3`), or the command and the console do not go together (`4`: the console refuses a command outside the versions it takes, and the command prints the update to make where it is installed, for the machine, in the project or fetched for the run; `console whoami` says both versions and the install, and a command behind or ahead within the range is told once a day on stderr).
- **A person signs it in once per console:** `login` checks the token against the console and keeps it as a login, with the console's address and the account, in `$XDG_CONFIG_HOME/skillcdn-console/credentials.json` (`~/.config` when unset); a machine holds a login per console and account, and a token goes only to the console that issued it. `CONSOLE_URL` and `CONSOLE_TOKEN` in the environment, together, stand in for a login at that address, for a hook or a job. A token is never taken on the command line.
- **Configuring, as the person** ([ADR-0021](https://github.com/skillcdn/console/blob/main/docs/adr/0021-a-token-configures-as-its-person-does.md)): `workspace`, `workspace edit`, `people`, `person role`, `person add`, `person remove`, `person deactivate`, `person reactivate`, `project new`, `project edit`, `project icon`, `members`, `member add`, `member role`, `member remove`, `category new`, `category edit`, `category remove` and `rules write` do what an administrator or an owner does on the pages, with the same refusals (`auth.forbidden` where the person may not), and the event names the agent beside the person. The tokens themselves have no command but `logout`, which gives the command's own up: they are made and removed on the Agents page, signed in.
- **The project's pack** is read as the `skillcdn` command reads one ([ADR-0031](https://github.com/skillcdn/console/blob/main/docs/adr/0031-the-console-reads-a-pack-as-the-skillcdn-command-does-and-a-local-one-from-a-directory.md)): `console skills` prints what a client is told on connect and every skill, the documents outside the skills counted with what reads them, `console skills <folder>` a page of a folder, `console skills --search <words>` what the words find, `console skill <path>` a skill with its rules first, a long one in parts that each end with the command that prints the next, and `console skill --file <path>` a page of a file, each printed by the reads the `skillcdn` command itself prints with (`readPack` of `@skillcdn/cli`, [ADR-0124](https://github.com/skillcdn/console/blob/main/docs/adr/0124-the-commands-reads-of-a-pack-are-the-skillcdn-commands-own.md)) and the reads named as the console's commands, so that an agent reads here what it would read over MCP; a pack is at a SkillCDN deployment, or in a directory on the console's machine where no deployment is reachable.
- **The project's documents** are the agent's to read and write: `docs` and `doc`, with `doc write`, `doc attach`, `doc archive` and `doc restore`, by path; a link in a body to a page's path refers to the page.
- **Every command on the board works in one project:** `--project <key>`, else `CONSOLE_PROJECT`, else what `console use <key>` wrote to `.skillcdn-console.json` in the working directory or one above it: the project and the console's address, never a token, a file meant to be committed in a private repository. `console whoami` asks the console for that project and says what named it. `console projects` lists the projects the person may work in.
- **`console serve [<dir>] [--port <n>] [--records <dir>]`** is for a person: it serves [a console of your own](#a-console-of-your-own) from your machine, the build in `<dir>` at `http://127.0.0.1:11197/`, and carries everything under `/api/` to the console the command is signed in to, with your token, which the pages never see ([ADR-0014](https://github.com/skillcdn/console/blob/main/docs/adr/0014-a-persons-own-console-is-served-from-their-machine-by-the-command.md)). With `--records`, what a desk keeps under that directory is served at `/records/` beside the build, read at each request, for the desk's pages ([ADR-0117](https://github.com/skillcdn/console/blob/main/docs/adr/0117-a-desk-keeps-records-of-what-its-member-made-as-files-the-desks-pages-read.md)). The loopback only; a request from another site's page is refused, but for the files of a plugin's frame, the plugin's bundle and the console's stylesheet and faces for frames: a frame is sandboxed, its origin no page's, and the console answers those files to anyone, so the command carries a `GET` of one whatever page asks and with no token, and a plugin's pages and widgets are drawn as on the console. Without a directory only the API is served, for a development server.
- **Agent accounts** ([ADR-0084](https://github.com/skillcdn/console/blob/main/docs/adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md)) are made, set up and supervised with the same command ([its commands](https://github.com/skillcdn/console/blob/main/docs/specs/cli.md#commands-for-agent-accounts)): `agents`, `agent new` and `agent invite` for an administrator; on the agent's own machine `agent setup`, the one line an invitation carries, and then `console runner`, which a service of the machine keeps running; `agent tell`, `interrupt`, `stop`, `restart`, `reset`, `wake` and `set` for its supervisors, with `agent signals` for the record of what it was sent; and for the account itself `secrets` and `secret <name>`, its own store, `agent wake me`, a wake now or at a moment to come, and `agent reset me`, a new conversation where its work has a break, begun when its turn is over.
- **The guide of an agent account's setup** ([ADR-0088](https://github.com/skillcdn/console/blob/main/docs/adr/0088-an-agent-account-has-a-desk-and-is-set-up-from-an-invitation-by-signing-in-as-itself.md)) is made by `setupGuideOf` from what an invitation's code opens (`client.agentSetup(code)`), and printed by `setupGuideText`; `SetupGuideView` shows it, `AgentInvitationPanel` is the invitation under an account, and `setupCommandOf` and `setupSentenceOf` spell the command and the one line said on the machine. The default console shows the guide at `/setup/<code>` (`setupHref`) to a browser that is signed in nowhere.
- **`console desk [<directory>] [--web]`** is for a person: it writes a desk of your own, the folder `desk` your agent begins in, and with `--web` the shell of [your desk's pages](#a-desks-pages); `console desk check` says whether the records a desk keeps read right.
- **`@skillcdn/console/runner`** is what `console runner` is made of ([docs/specs/runner.md](https://github.com/skillcdn/console/blob/main/docs/specs/runner.md)), for a console of one's own that drives another product or a test that runs a runner against a console: `createRunner(options)`, which takes a `ConsoleClient` on the account's command, a `Driver`, its `runner.json` and what it needs of the machine; the `Driver`, `DriverSession` and `DriverEvent` types a driver is written to, `createClaudeDriver`, `createCodexDriver` and `createSpawn`; `createRunnerModules` and `ownRunnerModules`, the four registries a module is known by; `composeSignals`, `headerOf` and `introOf`, how a signal reaches the agent, with `wakeTextOf` and `wakePartsOf`, how the parts a wake source raised, its own lines and what someone wrote (`WakePart`), are written as the text of a signal and read back; `redactorOf`, which takes the values of a secret store out of a text in the encodings they are carried in, and `cutShown`, which cuts a text to a length once they are out, what a session hands its driver as `cut` so that no part of a secret stands where a driver cut a text, with `cutShownEnd`, which keeps the end of one the same way, handed as `cutEnd`, and `errorsShown`, which shows the end of what a product wrote on its standard error through it (`plainCut` and `plainCutEnd` where a driver is handed neither); `parseRunnerConfig`; `launchd`, `systemdUser` and `taskScheduler`, the services that keep a runner running on macOS, on Linux and on Windows, each as a plan of what to write and to run; and `deskFiles`, the template of an agent account's desk, with `deskServicesOf` for what it says of the workspace's services, `personDeskFiles`, the template of a person's, and `DESK_FOLDER`, what a desk's folder is called. Both templates are the least: the instructions and a structure, and no form of a thing to keep.
- **`@skillcdn/console/cli`** exports `runCli(argv, io)`, the command as a function that takes its environment, its streams, its `fetch` and its credential store: what the integration tests run against the app with no socket, and what a console of a person's own could embed.

### Writing a plugin

```sh
npx console-plugin init leave --key leave   # a plugin from the template: manifest, server module, web bundle, skill, tests, build
cd leave && npm install && npm run build
npm test                                    # the server module against an in-memory context, and the package as a console reads it
npm run check                               # console-plugin check: what a console, or a store, would refuse
```

A plugin is one npm package a console installs into its image and an administrator turns on ([docs/specs/plugins.md](https://github.com/skillcdn/console/blob/main/docs/specs/plugins.md) is the contract, every field and bound; [ADR-0049](https://github.com/skillcdn/console/blob/main/docs/adr/0049-a-plugin-is-an-npm-package-installed-into-the-image-and-enabled-by-an-administrator.md) to [ADR-0054](https://github.com/skillcdn/console/blob/main/docs/adr/0054-a-plugins-pages-run-in-a-sandboxed-frame-and-speak-only-to-their-plugin.md) the decisions). This package is its `devDependency`, for the types and the command; nothing of it is imported at runtime.

- **`@skillcdn/console/plugin`**, for the server module: `definePlugin({ collections, commands, queries, endpoints, on, jobs, upgrades, api, onEnable, onDisable })` is the default export of `dist/server/index.js`, built with everything it imports bundled in. `defineCollection(name, { schema, indexes, ... })` declares the records the console keeps, with a zod schema (`z` is re-exported); `defineCommand({ about, args, roles, run })` and `defineQuery(...)` are what agents run through `console plugin <key> <command>`, their `args` from `arg.text`, `arg.day`, `arg.number`, `arg.boolean`, `arg.enum`, `arg.person`, `arg.project`, `arg.record`, `arg.list` and `arg.file`, typed in `run(ctx, args)`; `defineEndpoint(...)` takes a request of a person's or a webhook's. Everything plugin code does to the console is a call on `ctx` (`PluginContext`): `ctx.records(collection)`, `ctx.console.*`, `ctx.events.emit`, `ctx.fetch`, `ctx.secrets`, `ctx.plugins`, `ctx.log`; the console refuses what the manifest did not ask with a `PluginRefusal`, and a plugin refuses in its own words with `PluginError`. The manifest, `console-plugin.json`, is read with `parsePluginManifest`; `RESERVED_PLUGIN_KEYS`, `PLUGIN_CAPABILITIES` with `capabilityWords`, the bounds (`MAX_PLUGIN_RECORD_BYTES`, `PLUGIN_COMMAND_MS`, ...) and the refusals (`PLUGIN_REFUSALS`) are the same words the console goes by. `describePlugin(definition)` is the definition as data, what the host reads and what `check` holds to the manifest.
- **`@skillcdn/console/plugin/web`**, for the web bundle: `connect()` in the frame the console serves says `ready`, receives `init` (who looks, at what, the console's design tokens, applied to `:root`), and answers `{ context, command, query, records, files, navigate, download, setTitle, onEvent, onTheme, onPath }`, each performed by the console's page under the plugin's own routes and nothing else. It depends on nothing; `@skillcdn/console/plugin/web/react` adds `usePlugin()`. `asObject`, `asSubject` and `asWay`, exported here and from `@skillcdn/console/plugin`, write a Korean word with the particle its ending takes, as the console's own Korean does, in place of both forms. A bundle imports nothing from elsewhere and never reaches for `fetch`, which `check` holds it to.
- **`@skillcdn/console/plugin/testing`**: `createTestContext({ collections, plugin, caller, console, secrets, ... })` is a `ctx` for the plugin's own tests, records in memory and checked as the console checks them, the console refusing whatever the test did not provide, `emitted` and `logged` to assert on.
- **`console-plugin`**: `init <dir> --key <key> [--name <name>] [--console <dependency>]` writes a plugin from the template this package ships (`template/plugin`), what `examples/plugin-hello` in the repository is; `check [<dir>]` reads a built plugin as a console would: the manifest, `package.json` (a permissive license, no install scripts, `files` that ship what runs), the server module loaded in a hardened thread, as the host loads one, and held to the manifest, the web bundle self-contained, its own classes prefixed `pl-<key>-` and the console's it uses the parts of the catalogue (`src/styles/README.md` here, which the command reads: a class of one of the console's own pages is refused, in the entry, a chunk or the stylesheet), the skills in the SkillCDN Format, the migrations. Node.js 24 or newer.

- **The composition:** `createConsole(config)` returns `{ App, mount }`. `App` is the whole console as one component; `mount(container)` renders it and returns the way to take it down. `config.baseUrl` is the origin of the API (the page's own when left out), `config.components` the pieces to replace (`ConsoleComponents` names them with the props each takes), `config.languages` the packs the pages speak, `config.brand` the addresses of a symbol and a wordmark to show beside the name (ADR-0013; the default console passes those of `@skillcdn/brand`, the main repository's package of its marks), `config.client` a client of your own, for tests, `config.persona` what an agent account's persona is proposed and drawn from in place of the package's (ADR-0084): `names`, a handle and its spelling per language each, which "Add an agent account" proposes from, and `avatarSets`, the sets the avatars are drawn from on this console's pages (`AvatarSet`, which is data: its grounds and its ramps as colours, its bodies, its surfaces and its accents as outlines in a square of a hundred units; ADR-0097), each under a version the package does not use. The SkillCDN name and marks are trademarks of KDX Labs under the main repository's trademark policy, not under this package's MIT license; a custom console brings its own marks through the same slot. The pages route in the browser and every form has an address (ADR-0010): the projects at `/`, the person's own work at `/work`, the workspace's settings at `/settings` (its rules, its categories at `/categories`, where its skills come from), what the person is told of at `/settings/notifications` (`PATHS.notificationSettings`), a project's pages under `/projects/<key>` (its roadmap, calendar and settings among them), a task by its number, a goal and a decision by their ids, a document by its path, and the query for how a page is shown, the board's filters, the calendar's month, the week of the person's work and the settings' forms among it (`matchRoute(pathname, search)`, `PATHS`, `projectHref`, `boardHref`, `taskHref`, `goalHref`, `calendarHref`, `workHref`, `personWorkHref`, `decisionHref`, `docHref`, `settingsHref`, `projectSettingsHref`, `newTaskHref`, `newGoalHref`, `newDecisionHref`, and `movedFrom` for the addresses of before); every link to one of them is followed in place, with one history entry per step; the workspace is loaded once and the project the page is on whole, kept current by the project's stream (`useConsoleData(client, projectKey)`, for a composition of your own).
- **Pages of your own:** `config.pages` adds tabs beside the console's, each a `CustomPage`. "Pages of your own" below says what a page is given, may read and is built from, "Charts" what figures are drawn with, and "A desk's pages" what a desk's pages begin as and what is ready for them.
- **The languages:** every word the pages show is in a pack (`Messages`, keyed as `en` is), English and Korean ship (`ENGLISH`, `KOREAN`, `DEFAULT_LANGUAGES`), and a component takes its words from the language above it (`useWords`, `useLanguage`, `LanguageContext`), English where there is none. A person's language is kept on them (`client.updateMe({ language })`): the browser's languages decide it the first time the pages see them (`chooseLanguage`, `packFor`), and the person after that; where neither names a language the pages speak, the workspace's does, as its administrator set it ([ADR-0081](https://github.com/skillcdn/console/blob/main/docs/adr/0081-a-workspace-has-a-language-for-whoever-has-none-of-their-own.md)), else the first pack. `createConsole({ languages })` replaces the packs the default console speaks, so that a custom console adds a language of its own; a pack is complete by type. A failure is read the same way: the server's code in the pack's `errors`, the server's own message being English and for programs (`errorWords(error, fallback, pack)`, `wordsForFailure(error, pack)`).
- **The styles** are one file, `@skillcdn/console/console.css`: the tokens (`--sc-*`, 101 of them, every one read by a rule), a small reset, and one class per block, all prefixed `sc-`. A custom console is a small repository that depends on this package, holds a configuration and a CI job, and builds to static files: the organization's, served by the image from `WEB_ROOT` in place of the default UI, or your own, served by `console serve` on your machine. Nothing of the server is in the package but the serving of a build, `@skillcdn/console/web`, which the image and the command share.

### A console of your own

A console you build from this package and run for yourself, against your organization's console, with the pages and components of your choosing ([ADR-0014](https://github.com/skillcdn/console/blob/main/docs/adr/0014-a-persons-own-console-is-served-from-their-machine-by-the-command.md)). It is a small repository of your own, in the shape of the default console (`apps/console/web` in the console's repository: one page, one script, one build):

```sh
npm install @skillcdn/console react react-dom
npm install --save-dev vite @vitejs/plugin-react typescript
```

```tsx
// src/main.tsx: the composition, with a configuration of your own
import { createConsole } from "@skillcdn/console";
import "@skillcdn/console/console.css";

const container = document.getElementById("root");
if (container === null) {
  throw new Error("the page has no #root element");
}
createConsole({ title: "Mine" }).mount(container);
```

```ts
// vite.config.ts: while building, the development server sends the API to console serve
import react from "@vitejs/plugin-react";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [react()],
  server: { proxy: { "/api": { target: "http://127.0.0.1:11197", changeOrigin: true } } },
});
```

```sh
console login --url https://console.example      # once: the token an agent of yours would hold serves your console too
console serve                                    # the API alone, at http://127.0.0.1:11197/api/, for the development server
npx vite                                         # your pages, reloading as you build them
npx vite build && console serve dist             # the build served whole, at http://127.0.0.1:11197/
```

The pages run on your token: what you may do on the board, they may do, and no more. The token never reaches the browser; the command adds it on the way, on the loopback only, and refuses a request from another site's page. The tokens themselves are made and removed on the organization's console, signed in, and the pages say so there; everything else, configuring included, the pages do on your token as the organization's console does on your session. Replace a component, pass your own language pack or your own marks, or compose pages of your own from the components and `useConsoleData`: the sections above say what each piece takes.

### Pages of your own

`createConsole({ pages })` adds pages of your own beside the console's, a tab each. Each is a `CustomPage`: a `key` (what the address says: `/pages/<key>` on the workspace, `/projects/<project>/pages/<key>` on a project), a `label` (one word, or a word by language tag with `en` standing in), a `level` (`workspace`, or `project` for a tab on every project), `wide` for a page that takes the whole window, and `render(context)`. `customPageHref` names the address and `customPageLabel` the tab's word. A page that is not among the pages given shows nothing there.

- **What a page is given** is what the default pages get, as `context`: the `data` of `useConsoleData` (the workspace, its projects and its people as the board has them, kept current, with the board's actions), the `project` the page is on, the `client` for everything else the API answers, the `navigation`, the `search` of its address (the query, `?view=...`, by which a page of several views says which is shown, as every page's address does), the `words` of the language the pages speak, and that `language`'s tag. A page acts as whoever the console acts as. On a console of your own that is you: `console serve` adds your token on the way and the page never holds it, so a page may do on the board what you may do, and no more.
- **What a page may read beside the board,** on a console served by `console serve --records <dir>`, is that directory at `/records/`, a file at a time (`fetch("/records/<file>")`): what a desk keeps. What a file says is data, whoever wrote it: bound it, parse it, and show it as text.
- **What a page is built from** is the console's parts. `src/styles/README.md` in this package is their catalogue, each part with the component that renders it and what it is for, and "Charts" below has the ones for figures. A page places parts and writes no colour, no border and no type of its own, so that it looks as the console does and takes a console's tokens.

### Charts

Figures on a page of your own, or of a plugin, are drawn with the charts: parts of the console's look like any other ([ADR-0123](https://github.com/skillcdn/console/blob/main/docs/adr/0123-charts-are-parts-placed-by-measures-and-drawn-by-the-stylesheet.md)), each a component here, a class of `console.css` and a row of the catalogue (`src/styles/README.md`). A chart takes its figures as props and nothing from the network, writes what it is given as text, and says what it shows to a reader who cannot see it: the figures stand beside the drawing as words, or under it as a table.

```tsx
import { BarList, Chart, Stat, Stats } from "@skillcdn/console";

<Stats label="Invoices this month">
  <Stat label="Sent" value="473" change={{ words: "+12%", against: "than last month", tone: "good" }} trend={[42, 51, 38, 64]} />
  <Stat label="Disputed" value="27" />
</Stats>
<Chart title="Invoices sent by week" points={["Jan 19", "Jan 26", "Feb 2"]} series={[{ name: "Sent", values: [42, 51, 38] }]} />
<BarList label="Paid to each supplier" ranked rows={[{ label: "Northwind Freight", value: 48200 }]} />
```

Choose by what the figures are, before anything else: one number that matters is a `Stat`; amounts over time are a `Chart`; a ranking or a comparison is a `BarList`; one whole in its parts is a `ShareBar`; what must be read exactly is a `FigureTable`. One chart has one scale: two measures of different size are two charts, never two axes.

- **`Stats`** (`label`) holds **`Stat`**s, as many across as there is room for. A `Stat` is a `label`, a `value` as the page writes it (`"12,480"`, `"3.2%"`), and where given a `change` (`words`, the amount with its sign; `against`, what it is measured against; `tone`, `"good"` or `"bad"` where the page knows which a rise is) and a `trend`, the run it came by, drawn as a sparkline.
- **`Chart`** is amounts over time: `title` (said to a reader who cannot see it; the page's heading says it to the others), `points` (the points' names in order, the latest last), `series` (one to a few, each a `name` and its `values`, one a point, nothing where a point has none), `kind` (`"columns"`, for amounts counted in each point, or `"line"`, for an amount followed from point to point), `size` (`"short"` in a tile), `format` (an amount as words, where the page writes it its own way), `language`, `empty` (what stands in its place where no point has an amount) and `figures` (`"beside"` where the page shows the chart's figures itself, in a `FigureTable`; left out, they stand under the chart as a table only a screen reader is told). Every series is measured by the one scale, from zero, in round steps, its marks written short where it reaches ten thousand (`1.5M`); a legend stands over the chart where there are two series or more; the points' names are thinned to as many as fit, fewer in a narrow box, the last always; a point says its figures to the pointer over it.
- **`BarList`** is a ranking or a comparison: `label`, `rows` (each a `label`, text or what the page shows for a name, a mark or a badge; a `value`; and, where given, `href`, where the label leads, `note`, what stands after it, `words`, the amount the page's way, `series`, another of the six colours, and `id`, which tells the row apart where its label is not text or two rows have one), `whole` (what a full bar stands for; the largest amount where left out), `ranked` (numbered for a reader, where the order says something) and `language`.
- **`ShareBar`** is one whole in its parts: `label`, `parts` (each a `name`, a `value` and, where given, `words`) and `language`. Each part's amount and share stand under the bar. Six parts are told apart: fold the rest into one before passing them.
- **`Sparkline`** is the run of a figure with no axis: `values`, `label` (what it shows; left out, it is an ornament beside words that say it) and `series`.
- **`Legend`** is the key by itself, where a page composes a chart of its own: `items` (each a `name` and, where given, `words` and `series`), `mark` (`"box"` or `"line"`) and `label`.
- **`FigureTable`** is rows by columns: `caption` (shown with `captionShown`), `columns` (the heads, the first the head of the rows' names), `rows` (each a `label`, text or what the page shows for a name, its `values`, a number written as the language writes it and words as they are, and an `id` as a bar's row has), `foot` (what the rows come to) and `language`.
- **The colours** are six, `--sc-series-1` to `--sc-series-6`, which the classes `sc-series-1` to `sc-series-6` draw in (`seriesClass(index)` names one, from nought): blue, coral, raspberry, teal, violet, green, the coral second so that a chart of two series shows the two that stand furthest apart. Any two of them are told apart, also by a reader who does not tell red from green, and each stands out on a light ground and on a dark one, so a console re-skinned by its tokens keeps them or sets six of its own that pass the same checks. What is past the sixth wears the neutral, `sc-series-rest`. A series is its colour wherever it is shown; words never wear one.
- **The measures** are `@skillcdn/console/charts`, with no dependency, for a bundle that draws the parts itself, a plugin's plain one say: `chartLayout(points, series)` (the scale, where each mark of it and zero stand, and where each amount stands, each a share of a hundred), `chartScale`, `columnOf`, `barLengths`, `shareParts`, `sparkPoints`, `labelStep` and `labelledPoints`, `seriesClass`, and `chartMeasure`, a share as an attribute says it (`"62.5%"`). A measure is an attribute of an SVG and never a style, so a chart is as wide as the box the stylesheet gives it, and is drawn the same in a plugin's frame, whose policy lets no style be set on an element. The components lean on React and these alone: a bundle that takes `Chart` from this package takes a few kilobytes and not the console.

### Icons

One pack for every page ([ADR-0142](https://github.com/skillcdn/console/blob/main/docs/adr/0142-the-console-has-one-icon-pack-drawn-on-one-grid-and-used-by-name.md)): glyphs drawn on a grid of twenty with one stroke, in the colour of the text they stand in. `/parts#icon` of `pnpm dev` shows them all under their names.

```tsx
import { Icon, IconPicker } from "@skillcdn/console";

<Icon name="calendar" />                       // beside words: hidden from a screen reader
<Icon name="lock" size="sm" label="Private" /> // alone: a picture with a name
<IconPicker value={glyph} label="Icon" onChange={setGlyph} />
```

- **`Icon`** takes a `name` of the pack (`IconName`; `ICON_NAMES` lists them, `isIconName` checks one that came from elsewhere) and a `size`: `xs` a caret beside a word, `sm` in a line of text, `md` by itself, `lg` in an empty state or on a card. It is drawn as elements from the pack's data, and a name the pack lacks draws an empty box. An icon stands beside the words of a button, and seldom for them. A glyph may have one part tinted in the accent under its lines; the tint goes away at `xs`, on a filled button, on a project's mark and in a place of a tone of its own (a danger button, a callout or a badge of a tone), and `className="sc-icon-plain"` takes it away anywhere else, in a line of text say.
- **`IconPicker`** is the field that chooses one, or none: the pack under it in its groups (`ICON_GROUP_LIST`), found by a glyph's name or by the words the reader's language pack gives it (`findIcons`), worked whole with the keys. A project's settings choose the mark's icon with it.
- **Without React**, `@skillcdn/console/icons` has the same pack with no dependency: `iconElement("calendar", { size: "sm" })` makes the element for a plugin's plain bundle or a prototype, and `GLYPHS` is the data, each glyph its shapes as an element's name with its measures, and `"tint"` in a third place where the shape is the tinted part, filled and never stroked. The classes (`sc-icon`, `sc-icon-sm`) are in `console.css`, which a plugin's frame already has; without it the element still draws at twenty pixels in the text's colour.
- **A glyph is added or redrawn** as a file under `icons/` in the console's repository, which `pnpm icons` writes into the package; its README there has the grid's rules. A name stays what it shows once it is published.

### A desk's pages

A desk's pages are a console of your own with pages of its member's own ([ADR-0116](https://github.com/skillcdn/console/blob/main/docs/adr/0116-a-desks-dashboard-is-a-page-of-a-console-of-ones-own-read-as-it-is-looked-at.md), [ADR-0122](https://github.com/skillcdn/console/blob/main/docs/adr/0122-a-desk-is-given-its-least-and-grown-by-what-its-member-asks.md)). The package ships their shell, `template/desk-web`, which `console desk --web` writes into a desk's `web/`: the files of a console of your own with one page of the member's own and nothing on it yet (`src/page.tsx`, at `/pages/mine`, which `/` opens on), `src/main.tsx`, which lists the pages, a `package.json` and five lines on how it is run. The page's comments say what a page is given, may read and is built from; what it comes to show is whatever its member asks for. Two words in the shell are filled by whatever writes it: `__VERSION__` in `package.json`, the package's version, for the dependency; and `__TITLE__` in `index.html` and in the README's heading, what the page is called until the server answers, as text.

```sh
npm install && npm run build                      # in the desk's web/; quiet where it went well, the pages in dist/
console serve dist --records ../records           # the pages at http://127.0.0.1:11197/, the desk's records at /records/
```

What follows is ready, for a member who wants exactly that. Nothing of it is mounted by the shell; each is added by a line.

- **`deskPage()`** is a page of its own: `pages: [page, deskPage()]` adds it at `/pages/desk` (`DESK_PAGE_KEY`; `deskPage({ key })` names another address, and `deskPage({ records })` another reader of the records). It has four views, with `DeskViews` their tabs: the desk's collections, and the member's work on the board as it stands, in figures and in its archive. `DeskPage` is its component, and `deskViewOf` and `deskHref` the address of a view.
- **The collections** are one shape a desk may keep ([ADR-0117](https://github.com/skillcdn/console/blob/main/docs/adr/0117-a-desk-keeps-records-of-what-its-member-made-as-files-the-desks-pages-read.md), [docs/specs/records.md](https://github.com/skillcdn/console/blob/main/docs/specs/records.md)): sets of things made, with where each was used and how it did by day, as files under `records/`, read again each time a view is come to. `DeskRecords` reads them and composes `DeskCollections` (the collections, each with its items counted by status and the day the last was made), `DeskCollectionView` (a collection's items narrowed by status, as cards where any has a preview and as rows where none has), `DeskItemView` (an item with its preview and its note, how it did as figures with the run each metric came by, where it was used, its files each shown in place by the kind the server says it is, a picture, a film and a sound with the browser's own controls and a PDF in a frame where its answer lets it be framed, or handed over as a download, and last its figures by day in a table; beside them its fields and its links, and the task it names where it names one) and `DeskCollectionResults` (each metric and each ratio in all, as figures with the run each metric came by; then one metric, the one the person picks: by week as one chart, columns for what is counted and a line for a share, and the items that did best by it, as bars; where the collection has no figure yet, what would fill the view), with `DeskRecordProblems` for a file that is wrong, `DeskNoRecords` where none are served, and `DeskRecordCrumbs` for the way down. What reads them is `readDeskRecords`, `readCollection` and `probeFile` over a `RecordsReader` (the page's own `fetch` at `RECORDS_BASE` where none is given); `previewSrc`, `fileSrc` and `httpsLink` are what a page may take from a record, `fieldsOf` an item's fields by their kinds, `resultsOf`, `bestItems` and `itemResults` the figures, and `recordsAddressOf` and `recordsQuery` the address of a place in the view. What a record says was written by an agent: every file is bounded and parsed with the format's schemas, what does not parse is named in a line, as a `RecordProblem`, and the rest is shown, every word is text, a link is followed only as https and opens apart, a file is read only from under its collection's `files/`, and nothing an agent wrote is ever shown as a page.
- **The board's views** are components that take their data as props: `DeskStanding` (the decisions that wait, the open runs, then the open tasks by state), `DeskFiguresView` (how many tasks were done and how the runs ended, as figures; what was done by week, as columns; and what was done by project and by category, as bars; where nothing was closed in the weeks, what would be counted) and `DeskArchive` (the closed tasks and the ended runs, found by words, a page at a time). `DeskPage` reads for them through the client, as the member, a page of each project at a time, in the brief form of the lists (`taskBriefs` and `runBriefs` of a project's client: the tasks without their bodies, the runs without their reports, which no view shows): `readOpenRuns` and `readHistory` (bounded by `DESK_PROJECTS`, `DESK_TASKS` and `DESK_RUNS`; `withHistory` joins the next page), `standingOf` and `figuresOf` (`DESK_WEEKS` weeks, as the workspace begins a week). The page says where there was more than it read.
- **The ready views are an example** of a page of figures built from the parts, laid out as [Charts](#charts) are meant: the few numbers that matter first (`Stats`), then one chart, then what breaks them down (`BarList`). No figure stands twice at one level: a chart's own figures are its table for a reader who cannot see it, and a `FigureTable` is for figures no chart beside it shows, an item's days say. Where there is nothing yet a view says what would fill it (`EmptyState`) and draws no empty axis.

A page of the member's own over the collections needs the readers and no more. `readDeskRecords({ fetch })` answers `{ kind: "none" }` where no records are served, and otherwise `{ kind: "read", collections, problems }`, a collection each with its key, its own file and its items counted by status. `readCollection({ fetch }, key)` answers a `CollectionRecords`, `{ key, found, collection, items, uses, metrics, problems }`: the collection's own file (`RecordsCollection`), or nothing where it is missing; the items (`RecordsItem`), the last made first; the uses (`RecordsUse`), the last first; the rows of figures (`RecordsMetricRow`); each with the fields [the form](https://github.com/skillcdn/console/blob/main/docs/specs/records.md) writes, and no others; and `found`, whether anything was there. `CollectionRecords` and `RecordProblem` are types of `@skillcdn/console`, the four of the form of `@skillcdn/console/api`, and the function of a page is given a `CustomPageContext` ("Pages of your own"): with those names a page is typed without a look into the package's declarations. With `{ items: true }` as its fourth argument it reads the items alone. `problems` is what `DeskRecordProblems` takes (`problems`); `DeskNoRecords` takes nothing, `EmptyState` a `title` and a `body`, `Spinner` a `label`. `DeskRecords`, the ready view of the collections, takes what a page is given and no more: `search` (the query of the page's address), `href` (the page's own address, `customPageHref(key)`), `navigation`, and `taskHref` (where a task of the board is: the package's `taskHref`); `reader` and `weekStart` where the page has its own.

Every one of them is built from the parts of `console.css` and nothing else. On the organization's console, `DeskWords` is the block of the Agents page that says what to tell an agent for a desk; it takes the console's origin.

### The skills, for an agent

What an agent reads to work the board, to plan and set it up, to build a console, to write a plugin, to deploy a console, to run an agent account or to keep a desk is in the console's repository as skills in the SkillCDN Format ([ADR-0015](https://github.com/skillcdn/console/blob/main/docs/adr/0015-the-consoles-skills-live-in-this-repository-in-the-skillcdn-format-and-the-package-carries-them.md)), served by SkillCDN at `skillcdn.ai/gh/skillcdn/console` with the architecture, the decisions and the specifications, and shipped in this package: `skills/working-the-board/SKILL.md`, `skills/planning-the-board/SKILL.md`, `skills/building-a-console/SKILL.md`, `skills/building-a-plugin/SKILL.md`, `skills/deploying-a-console/SKILL.md`, `skills/running-an-agent/SKILL.md` and `skills/keeping-a-desk/SKILL.md`, each with its references, the deploying skill with its scripts, their manifest `SKILLCDN.md` with the rules they share, the specifications they point to under `docs/specs/` (`rest.md`, `cli.md`, `plugins.md`, `runner.md`, `records.md`), and the sources under `src/` without the tests, so that `npm install` brings what an agent needs to read, at the version installed. Point an agent at them in `node_modules/@skillcdn/console/`, or copy a skill's folder into the agent's own skills. A project of a console may name that address as its skills address, and an organization's own skill for its console adds its rules and links these. The skills are maps: what they name, this README, the types and the specifications say in full.

## Rules

Read the root [`AGENTS.md`](../../AGENTS.md) first. This package is what other people install; it is their contract.

- **Pure where it can be.** The schemas and the components do no I/O; the client takes a `fetch` and a base URL; the command takes everything it needs through `runCli`. Nothing here reads the environment but the command's entry point, `src/cli/main.ts`, the one place the process is read (lint enforces it).
- **The main repository's packages come from npm,** by version: `@skillcdn/core` here, for addresses, the REST shapes of a pack and the renderers of what a model is given, and `@skillcdn/cli`, for the reads of a pack as the `skillcdn` command prints them, imported by `src/cli/` alone and never by what a page imports ([ADR-0124](../../docs/adr/0124-the-commands-reads-of-a-pack-are-the-skillcdn-commands-own.md)); the client, the indexer and the reader in the app. Never a path into the main repository, never a copy of its code ([ADR-0001](../../docs/adr/0001-the-console-is-the-reference-console-built-on-the-published-packages.md), [ADR-0031](../../docs/adr/0031-the-console-reads-a-pack-as-the-skillcdn-command-does-and-a-local-one-from-a-directory.md)).
- **Exported types are public contract.** A change to what `src/index.ts` exports carries a changeset written for whoever installs the package, and the README changes with the usage.
- **A command is added by the command's shape** ([ADR-0167](../../docs/adr/0167-the-commands-of-the-console-command-are-one-table-by-who-runs-them-its-help-is-in-layers-within-bounds-and-a-mistake-is-answered-with-a-sentence.md)), whose readers are mostly agents that pay for every byte printed:
  - **Where it goes.** What does something to a thing, or makes one, is a form of that thing (`task new`, `doc write`, `agent tell`): a word after the singular, which reads one, beside the plural, which lists. A new thing brings its two words. A word at the top that names no thing is a decision of its own, and the list of them is closed.
  - **What is added with it.** A case of the dispatch in `src/cli/cli.ts`; its page in `src/cli/help.ts`, in `forms` where it is a form; for a new command, its row in `COMMAND_GROUPS`, in the group of whoever runs it; its row in [docs/specs/cli.md](../../docs/specs/cli.md). `help.test.ts` holds the table to the pages, and `pnpm check:skills` the skills to the commands.
  - **The help's bounds.** `console help` within 3,000 bytes, a page within 2,600 (`HELP_BOUNDS`). A page past its bound is cut or its form given a page of its own; the bound is not raised. A page says what running the command does not show: what a flag means, what is refused and what to do then. It does not describe the output.
  - **What it prints.** One line a thing in a list, a page at a time with a last line that says when there is more; an id wherever a command takes one; what to run next as a whole line, with `--project`, `--url` and `--account` as they were given. What went wrong goes to standard error as a sentence: a refusal as the console's code and words, a misuse with the form to type. Nothing printed is ever both an answer and a refusal.
  - **What it reads.** A secret is never an argument: typed unseen, or from standard input or a file. An option the command does not take is refused, never dropped.
- **Runtime dependencies need a reason.** This package ships to browsers; a dependency here needs a stronger case than anywhere else in the repository.
- **A page is built from the console's parts.** A look is written once, as a part, in `src/styles/parts/`; a page's file under `src/styles/pages/` lays its own elements out and says where a part is, and gives nothing a look; a colour is written in `src/styles/tokens.css` alone. [`src/styles/README.md`](src/styles/README.md) is the catalogue of the parts, with the rules in full and how a part is added: read it before writing a class. `pnpm check:styles` holds it ([ADR-0106](../../docs/adr/0106-a-look-is-a-part-with-a-file-and-a-row-and-a-page-places-its-parts.md)). A design pass changes how a page looks and not what it does: what is fetched, sent, allowed or tested changes in a change of its own. A changed page is looked at on this machine (`pnpm dev`) before its commit, at a phone's width and on a wide screen, in English and in Korean; what was not looked at is said in the commit.
