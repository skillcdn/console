# AGENTS.md

The working agreement for this repository. It applies to AI agents and humans alike, whichever agent you are: Codex reads this file directly, Claude Code reads it through `CLAUDE.md`.

A workspace with rules of its own keeps them in its `README.md`, under "Rules" (`apps/console`, `packages/console`); `deploy/README.md` is the contract for whoever operates the image, and holds what there is to know of `.github/` too; the pages have theirs in `packages/console/src/styles/README.md`. Read them before editing there. Keep this file and those sections short and true: when a rule turns out to be wrong or stale, fix it in the same change.

## Project

The SkillCDN Console is where a team of people and AI agents works: agent accounts that are members of their own, the people who decide, and one board that holds the work to do, the runs on it, what was handed in and the decisions that wait for a person. People decide; agents work. [README.md](README.md) says what it is, [docs/architecture.md](docs/architecture.md) how it is built and what is still open, [docs/roadmap.md](docs/roadmap.md) what exists and what is next.

- **Status:** pre-alpha, on SkillCDN 0.6; `@skillcdn/console` is on npm, and the image of a release in the repository's container registry. [docs/roadmap.md](docs/roadmap.md) says what exists by area, what is in progress and what is next: start there. In short:
  - **Agent accounts** ([ADR-0084](docs/adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md) and the decisions after it): an agent that is a member of its own, signed in as itself, with a manager, a persona, a secret store, signals and a transcript, set up on a machine from an invitation and kept at work there by `console runner` under a service of the machine, through the `claude`, `codex` and `acp` drivers, each run against a product; woken by the board, by its briefings, by itself and by the `slack` wake source, its desk committed and pushed at the end of every session; the skill `running-an-agent` says how. The runner was run whole under the `systemd-user` service on Ubuntu, the `task-scheduler` service on Windows and the `launchd` service on a Mac, where an account set up from the line worked a day against a live console; what that day asked for is built and not run on a machine yet (the roadmap's "Agent accounts on real machines").
  - **The board**, per project: tasks planned in days and sorted into the workspace's categories, the runs on them, decisions, a discussion, documents, rules for agents, a roadmap of goals and a calendar. A member is told of what happens on their work by notifications of kinds they choose, read in the console, a person and an agent account by the same rules ([ADR-0157](docs/adr/0157-the-console-decides-who-is-told-of-what-and-keeps-the-record-and-a-plugin-carries-it-out.md)). A person's own agent works it connected with a code that person approves, and is held to the right console and project by the binding and `console whoami` ([ADR-0112](docs/adr/0112-a-binding-names-its-console-and-whoami-asks-the-console-for-the-project.md)). The pages speak English and Korean.
  - **Desks:** a member has a desk, a repository of their own at their own git account (`<account>/desk`), a person's written by `console desk` as an agent account's is by its setup: the folder their agent begins in, given its least and grown by what its member asks to keep and to see, as the skill `keeping-a-desk` says, with pages that are their own extension of the console's, served from their machine ([ADR-0115](docs/adr/0115-a-person-has-a-desk-too-written-by-the-command-and-set-up-by-a-skill-of-the-organizations-pack.md) to [ADR-0117](docs/adr/0117-a-desk-keeps-records-of-what-its-member-made-as-files-the-desks-pages-read.md), [ADR-0122](docs/adr/0122-a-desk-is-given-its-least-and-grown-by-what-its-member-asks.md)).
  - **Consoles and plugins of one's own:** a console is built from the package and served from the image or from a member's machine. A plugin is a feature of an organization's work as one npm package, installed by building it into the image, enabled by an administrator, run in a host of its own under capabilities and roles, worked through `console plugin <key>` and shown in sandboxed frames ([ADR-0049](docs/adr/0049-a-plugin-is-an-npm-package-installed-into-the-image-and-enabled-by-an-administrator.md) to [ADR-0054](docs/adr/0054-a-plugins-pages-run-in-a-sandboxed-frame-and-speak-only-to-their-plugin.md)); the plugins themselves, the messenger among them, live in repositories of their own.
  - **Deployment and skills:** where the deployment has a bucket, the files go there through the S3 API, and `skills/deploying-a-console` puts the console on AWS behind Cloudflare for an organization ([ADR-0017](docs/adr/0017-the-reference-deployment-is-the-image-on-aws-behind-cloudflare-written-as-a-skill.md)); an organization's own deployment stays outside this repository. The console's skills, in the SkillCDN Format, say how an agent works the board, plans it, builds a console or a plugin, tries a console on one computer, deploys one, runs an agent account and keeps a desk.
- **Shape:** TypeScript monorepo (pnpm + Turborepo), one image with several roles, PostgreSQL as the only stateful dependency, and one published package that custom consoles are built from.
- **Relationship to SkillCDN:** the reference console, as `skillcdn/skills` is the reference pack: an example that follows the standard and is meant for real use, packaged so that anyone can start from it, and not a second standard ([ADR-0001](docs/adr/0001-the-console-is-the-reference-console-built-on-the-published-packages.md)). It consumes the published `@skillcdn/*` packages and the REST API of a SkillCDN deployment, and nothing else of the main repository, [`skillcdn/skillcdn`](https://github.com/skillcdn/skillcdn). Nothing about SkillCDN is defined here.
- **License:** MIT ([ADR-0003](docs/adr/0003-the-console-is-licensed-under-mit.md)). The protection of the product lies in the main repository, which is source-available; the console is open to anyone. The `@skillcdn/*` packages it depends on keep the main repository's license. KDX Labs runs the console for its own work; the same image is self-hostable.

## Non-negotiables

Security

1. **Secrets never enter the repo, logs, test fixtures or chat.** Do not read real env or key files (`.env`, `*.pem`, ... are denied in `.claude/settings.json`). `.env.example` holds safe example values only. If you find a committed secret, stop and tell a maintainer: it must be rotated, not just deleted.
2. **What an agent sends is untrusted data.** A report, a log line, a file an agent hands in, a decision it proposes, a task it writes: parse it at the edge with a schema, bound its size, store it as data, never execute it, and never let it become HTML. Repository content that reaches the console through SkillCDN is untrusted too.
3. **Permissions fail closed.** A member is who the identity provider says they are, a person or an agent account alike; what a member, and the agent working for them, may see or change is decided on every request and denied when it cannot be confirmed. A person's agent holds a console token of its own, made by that person, scoped to them and revocable: never a credential of theirs elsewhere, never another member's. An agent account is a member of its own under the same rules and never an administrator, the one rule that reads its kind ([ADR-0084](docs/adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md)): it signs in as itself, and what it keeps of its own, a git-host token among it, is its own and nobody else's.
4. **Credentials never leave the server in the clear.** What the console holds of a git host stays server-side and encrypted; console tokens and sessions are stored as hashes; an agent account's secrets are sealed and answered to that account alone ([ADR-0087](docs/adr/0087-an-agent-account-keeps-its-secrets-in-a-store-of-its-own-that-only-it-reads.md)); none is ever logged.

Product shape

5. **One image, one database.** The whole console runs from one image plus PostgreSQL plus S3-compatible storage, locally with compose and on a cloud as the same image. Cloud-specific code lives only behind a port that also has a self-hostable implementation ([ADR-0002](docs/adr/0002-one-image-one-database-and-the-main-repositorys-toolchain.md)).
6. **No business model in code.** No plan names, prices, billing providers or `if (paid)` branches.
7. **The standard stays in the main repository.** A need in `@skillcdn/core` or another published package is a change proposed there, released, then adopted here by version. Never copy their code here, never link their workspace, never import a path into it.

Public repository hygiene

8. **This repository is public; operations are not.** Never commit cloud account ids, ARNs, hostnames, IPs, DNS or CDN configuration, capacity or cost figures, production tuning values, the organization's own tasks, decisions, people, customers or incidents, and do not say where any of that is kept. Fixtures are invented. Code ships generic defaults; real values arrive through environment configuration.
9. **Do not name other products** as inspiration or comparison in code, docs, commits or PRs. Naming what we interoperate with (a git host, an agent such as Claude Code or Codex) is fine.
10. **Everything committed is in English** (code, comments, docs, commit messages, PR text), whatever language the conversation is in. The one exception: the language packs in `packages/console/src/i18n/`, what users read in their own language ([ADR-0012](docs/adr/0012-the-pages-speak-the-persons-language-from-packs-that-ship-with-the-package.md)); a word added to the English pack is added to every other pack in the same change.

Dependencies point inward only: `apps/console → packages/console`. Both import `@skillcdn/core` and the other published packages from npm, by version, and nothing from the main repository's workspace. A workspace can only import what its own `package.json` declares, and only from another package's entry point. Changing these edges needs an ADR. Each workspace's `README.md` carries the rules for that subtree; read it before editing there.

Run everything from the repository root through pnpm. Do not use `npm`, `npx` or `yarn`; use `pnpm exec <bin>` and `pnpm dlx <pkg>`. pnpm pins its own version and downloads the pinned Node.js runtime, so project scripts behave the same on every machine.

## Workflow

**Bound to a console?** Before the first step, run `console whoami`: when it names a project, or `.skillcdn-console.json` is in this checkout, work the task through that SkillCDN console (its answer says how).

**The binding file is never committed, and no file here names a project's key.** This repository is public, and both name an organization's own console project: `.gitignore` lists `.skillcdn-console.json`, and `<key>` is a placeholder on purpose. In a fresh checkout `console whoami` names no project: ask the person for the key (`console projects` lists the projects they may work in), run `console use <key>` once, and write the key into no file of this repository.

**Before you start.** Read this file and the workspace's `README.md`, its Rules first. Check [docs/roadmap.md](docs/roadmap.md) for what is in progress and what is next, [docs/architecture.md](docs/architecture.md) for the design and its open questions, and [docs/adr/](docs/adr/) before questioning a past decision. If a product decision is missing, do not guess: add it to the open questions or ask.

**While working.** Stay inside the task's scope: no drive-by reformatting, renames or dependency bumps. Prefer the boring solution; add an abstraction when the second use appears, not before. Build what the roadmap has in progress, then what it has next, so that every push leaves something that runs.

**Definition of done.**

- `pnpm check` passes.
- New behavior has tests; a bug fix starts with a failing regression test.
- A change to `packages/console` carries a changeset, written for whoever installs it: `patch` within a line of SkillCDN, its entry starting with `Breaking:` where it changes what exists; `minor` only to adopt the next line of SkillCDN; never `major` while the major is 0 ([ADR-0034](docs/adr/0034-the-package-is-versioned-on-skillcdns-line-one-line-at-a-time-with-a-patch-of-its-own.md)).
- Docs are updated per the table below, in the same change.
- No secrets, no operations details, no business logic (rules 1, 6, 8).
- The change is safe to deploy on its own: `main` is always releasable and every push may ship.

**Commits and pushes.**

- [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): summary`, imperative, 72 characters or fewer. Types: `feat fix docs refactor test perf build ci chore revert`. Scopes: `app pkg deploy docs repo`. The body says why. Breaking changes use `!` and a `BREAKING CHANGE:` footer.
- One logical change per commit, and every commit passes `pnpm check`.
- **For now, maintainers commit and push directly to `main`.** There is no pull-request gate and no branch protection yet. Do not create branches or open pull requests unless asked. Run `pnpm check` first, `git pull --rebase` before pushing, keep commits small, and treat a red CI run on `main` as the first thing to fix.
- Never force-push or rewrite `main`, skip hooks with `--no-verify`, or commit build output.
- Keep the `Co-Authored-By` trailer your agent's own product adds, so AI-authored changes stay traceable; where it adds none, write none: a trailer is never made up.
- **Releases.** `@skillcdn/console` is versioned from changesets and published by the release workflow through the registry's trusted publishing ([ADR-0007](docs/adr/0007-the-package-is-published-through-trusted-publishing-and-versioned-on-the-core-line.md)): pending changesets become one version pull request, and merging it publishes. The version's major and minor are SkillCDN's, the one version of the main repository's packages the console is built on, declared in every manifest and resolved by the lockfile, and its patch the console's own; the lines are adopted in order, one `minor` each, and `pnpm check` holds the rule ([ADR-0034](docs/adr/0034-the-package-is-versioned-on-skillcdns-line-one-line-at-a-time-with-a-patch-of-its-own.md)). The first version is published by a maintainer by hand ([deploy/README.md](deploy/README.md#repository-settings-checklist)). The image of a release follows its package: the same workflow builds it from the same commit and pushes it to the repository's own container registry, at the package's version, with the token of its job ([ADR-0092](docs/adr/0092-the-image-of-a-release-is-published-and-the-smallest-install-is-made-from-a-bundle.md)). A deployment's own images are built and pushed outside this repository.

## Documentation protocol

Documentation is part of the change, not a follow-up. A future session starts with no memory of this one; the repository must be enough to continue.

| When you change... | Update in the same change |
|---|---|
| What the console does for people or agents: the board, the REST API, the command line | `docs/architecture.md`; the spec under `docs/specs/`; the root `README.md` if the overview changes; and the skills under `skills/` that name what changed, read again by hand: `pnpm check:skills` catches a command, a route or a file that is gone, never a meaning that changed |
| What the published package does or exports | a changeset in `.changeset/`, which becomes the package's changelog; `packages/console/README.md` when its usage changes; `skills/building-a-console/SKILL.md` where it says how a console is built |
| A skill or the manifest (`skills/`, `SKILLCDN.md`) | `pnpm check:skills` passes; a word for people in `skillcdn.translations` in every language the manifest has; where a skill is added, renamed or its description's first sentence changes, the README's table of skills, written again by `pnpm exec skillcdn catalog --write README.md`, and its row in `docs/start.md`, the page the manifest names as the first an agent reads; the package carries them as they are ([ADR-0015](docs/adr/0015-the-consoles-skills-live-in-this-repository-in-the-skillcdn-format-and-the-package-carries-them.md)) |
| A glyph of the icon pack, added or redrawn | its file under `packages/console/icons`, its line in `groups.json`, `pnpm icons`, and its search words in every language pack; `packages/console/icons/README.md` says the grid |
| A part of the pages' look: one added, changed in what it is for, or taken out; a token | the catalogue, `packages/console/src/styles/README.md`, and the part's place on `/parts` of `pnpm dev`; for a token, `packages/console/README.md` and `packages/console/src/tokens.ts` too |
| Workspaces, boundaries, runtime components, data flow, security model | `docs/architecture.md`; the repository map above; an ADR |
| A decision future contributors might reasonably undo | new ADR in `docs/adr/` (never edit an accepted ADR; supersede it) |
| Environment variables or configuration | the config module, `.env.example`, the table in `deploy/README.md` |
| Database schema | migration, the data model in the workspace's `README.md` |
| Build, image or CI | `deploy/README.md` |
| A workspace's entry points or how it is used | that workspace's `README.md`, which names the entry points and what each is for, never every export: a constant, a helper or a type beside them is described where it is declared, in its doc comment |
| An item of the roadmap is started, finished or dropped | `docs/roadmap.md`, kept as its "How this page is kept" says: a few sentences an entry, no history |
| A document is added or retired (a spec, a workspace's README) | its row in `docs/README.md`, the map of the documents |
| You learned a durable gotcha the hard way | "Gotchas" in the nearest `AGENTS.md` or workspace `README.md` |

One topic, one file. Link to where something is documented instead of restating it. Keep docs lean: current facts and decisions, not history or essays. Git history is the changelog. Anything the team needs must live in the repo, not in chat or an agent's private memory; business reasoning, comparisons with other products and operations details belong in private notes, never here (rules 8 and 9).

## Conventions

- **TypeScript:** strict, ESM, `.js` extensions in relative imports, erasable syntax only (no `enum`, `namespace` or parameter properties). Named exports only. No `any`; take `unknown` and narrow.
- **Boundaries validate, interiors trust.** Parse every external input once at the edge (HTTP, the command line's arguments, env, what an agent sends, JSON columns) with a schema; pass typed values inward.
- **Configuration:** `process.env` is read only in `apps/console/src/config/`, and by the command line only in `packages/console/src/cli/main.ts` (lint enforces both). Everything else receives typed config as an argument. Every tunable has a safe default.
- **Ports and adapters:** the domain defines interfaces (git host, blob store, clock, ids); adapters implement them; `apps/console` wires them together. Do not import an SDK outside its adapter.
- **Errors:** throw `Error` subclasses with a stable `code`. Translate to HTTP errors, or to the command line's words and exit codes, only at the edge, and never leak internals or the existence of what a caller may not see.
- **Logging:** structured logger only, no `console` (lint enforces it). Never log tokens, authorization headers or what an agent handed in.
- **Attribution:** a record that names the person who did something names the agent they did it through (`agent`: the token's name, or `null` when they did it themselves) and the plugin where one acted, as every event does ([ADR-0056](docs/adr/0056-a-record-that-names-the-person-who-did-a-thing-names-the-agent-they-did-it-through.md)). A record of what an act was about, a member or a worker, names no agent; the feed names who added them.
- **Relations between members:** code that checks how one member stands to another checks three things, every time: the direct link (the manager, the report), every level of the reporting line above or below it, and administrators, who stand outside the line and may stand in it too. A supervisor is all of them ([ADR-0084](docs/adr/0084-an-agent-account-is-a-member-of-its-own-with-a-manager-above-it.md), point 5), and a check of the manager alone is a bug. Read it through the policy (`supervises`, `aboveInLine` in `apps/console/src/auth/policy.ts`) where it fits, and give each case a test of its own: the manager, the manager's manager, an administrator out of the line and one in it, a report and a report's report.
- **Determinism:** inject time, randomness and ids so the domain stays pure and tests stay stable.
- **Naming:** kebab-case file names; tests next to the code as `*.test.ts`; integration tests as `*.int.test.ts`.
- **Pages:** a look is written once, as a part, and a page is built from the parts. Before writing a class, read the catalogue, [packages/console/src/styles/README.md](packages/console/src/styles/README.md): the part is there, with the component that renders it. A page's own class, in its file under `styles/pages/`, lays its element out and says where a part is; it writes no colour, border, radius, shadow or type, and pads no part. A colour is written in `styles/tokens.css` alone. `pnpm check:styles` refuses the rest and says what to do instead ([ADR-0106](docs/adr/0106-a-look-is-a-part-with-a-file-and-a-row-and-a-page-places-its-parts.md)). The way past a refusal is the part, never the check: nothing is added to `drawn-by-pages.json` or to the lists in `scripts/check-styles.mjs` to make a look pass, and a new part is a decision of design, asked for before it is written. A design pass leaves what a page does as it is. A changed page is looked at before its commit (`pnpm dev`), at a phone's width and on a wide screen, in both languages.
- **The command:** a command is added by the command's shape ([ADR-0167](docs/adr/0167-the-commands-of-the-console-command-are-one-table-by-who-runs-them-its-help-is-in-layers-within-bounds-and-a-mistake-is-answered-with-a-sentence.md); the rule in full under Rules in [packages/console/README.md](packages/console/README.md#rules)): what does something to a thing is a form under it (`task new`, `doc write`), never a new word at the top; its page of help says what running it does not show and stays within the bound a test holds, the bound never raised to fit; a mistake is answered with a sentence that says what to type; what is printed to be run next is a whole line.
- **What an agent account reads in every session**, its session's first words and its desk's `AGENTS.md`, is held within a bound by a test ([ADR-0174](docs/adr/0174-what-an-agent-account-reads-in-every-session-is-held-within-a-bound.md); the rule under Rules in [packages/console/README.md](packages/console/README.md#rules)): a sentence goes there only where every session does otherwise without it, what concerns one event is said by that event's wake, and the bound is never raised to fit.
- **Comments** explain why, not what.

## Testing

- Vitest. Unit tests use no network and no database, and must be fast.
- Integration tests run against real PostgreSQL (`deploy/compose.dev.yaml`, or wherever `TEST_DATABASE_URL` points) and, for the blob store, against a real store with the S3 API (the same compose file, or wherever `TEST_S3_URL` points). Never mock the database and never swap in another engine. Without a server these tests fail; they do not skip.
- Browser tests (`*.browser.test.ts`) drive a real Chromium with Playwright against the app listening on this machine, for what only a browser enforces: the policy and the sandbox of a plugin's frame. They are `pnpm test:browser`, apart from `pnpm check` and from `vitest run`, and CI runs them as a job of its own; what they see enforced, an integration test proves of the headers first.
- Agents and git hosts are tested against recorded or invented fixtures. CI makes no live calls to third parties.
- Every parser needs hostile-input cases: oversized input, deep nesting, malformed encodings, and what an agent could send on purpose.

## Dependencies

- Add with `pnpm add --filter <package> <dep>`. Versions shared across workspaces go in the `catalog` in `pnpm-workspace.yaml`.
- Justify every new runtime dependency in the commit message: why it is needed, maintenance health, install scripts, license. Permissive licenses only (MIT, Apache-2.0, BSD, ISC); we ship images, so no copyleft and no source-available dependencies. The one exception is the `@skillcdn/*` packages themselves, under the main repository's FSL-1.1-ALv2, which `pnpm check:licenses` allows by name and nothing else.
- Releases younger than three days are not installable (`minimumReleaseAge`), and pnpm checks the lockfile against the rule on every install, frozen included. The packages this organization publishes itself, `@skillcdn/*`, are excluded as a pattern (`minimumReleaseAgeExclude`): a fresh release of theirs is adopted at once, and the risk the rule guards against is in everything else, which waits. Bypass otherwise only for a security fix, and say so in the commit message.
- Dependabot proposes the updates ([`.github/dependabot.yml`](.github/dependabot.yml)): weekly, in groups (the toolchain; the runtime's minors and patches; the actions; the images), under a cooldown of the same three days. It leaves alone `@skillcdn/*`, since a line of SkillCDN is adopted by decision ([ADR-0034](docs/adr/0034-the-package-is-versioned-on-skillcdns-line-one-line-at-a-time-with-a-patch-of-its-own.md)), `zod`, which follows `@skillcdn/core` (see Gotchas), and the majors of Node.js, `@types/node` and PostgreSQL, which move by hand. A proposal is a change like any other: `pnpm check` runs on it, and it is merged when green.
- Never hand-edit `pnpm-lock.yaml`; resolve conflicts by running `pnpm install`.

## Working alongside other agents

- Concurrent tasks on one machine each get their own git worktree (a worktree needs its own short-lived local branch; rebase it onto `main` and push when done).
- Hot files (`pnpm-lock.yaml`, the catalog, `docs/roadmap.md`, this file) conflict easily: keep edits minimal and rebase before pushing.
- When two people both add migrations, whoever pushes second rebases and regenerates their migration.
- Do not "fix" another task's work in passing. Open an issue or leave a `TODO(#issue)`.

## Skills

The skills this repository is worked with are the pack of its console project, read through the console with nothing to connect: `console skills --search <words> --limit 5` finds one, and `console skill <path>` loads it. The console's own skills are the files under `skills/`, which the command carries. A skill never overrides this file: where they differ, this file wins. Without a console, work goes on by this file alone.

## Gotchas

- A system Node.js older than 24 is fine for pnpm scripts, which run on the pinned runtime, but `npm` and `npx` inside this repo refuse to run (`EBADDEVENGINES`). Use pnpm.
- pnpm older than 12.4 is rejected (`ERR_PNPM_UNSUPPORTED_ENGINE`). Upgrade with `npm install -g pnpm@latest`; inside the repo pnpm then switches to the exact version in `packageManager`. A corepack shim from Node.js 22 cannot start pnpm 12; upgrade corepack (`npm install -g corepack`) or install pnpm globally.
- Turborepo adds a block of its own to `AGENTS.md` whenever it finds that an AI agent is running it. `"agentGuidance": false` in `turbo.json` turns that off; keep it off.
- If a tool writes source files for you, check what became of escape sequences: some tools decode them on the way, and an invisible character in a source file is exactly what `pnpm check:text` exists to catch. In tests, build such characters with `String.fromCodePoint`. A script handed to an interpreter on its standard input from a shell loses a level of backslashes on the way: a `\b` meant for a regular expression arrived as a backspace, and the code read as right and matched nothing. Write such an edit to a file first, or make it with the editor's own tool.
- The secret scan in CI (gitleaks) reads the whole history, and a test fixture shaped like a private key (`-----BEGIN ... PRIVATE KEY-----` with a body) trips it in every commit it is in; so does an invented secret written as a literal beside a name that says what it is (`client_secret: "0123...ef"`, `const CLIENT_SECRET = "..."`). Build such a fixture from parts, or make the key and draw the secret when the test runs; a finding that slipped into the history is named by its fingerprint in `.gitleaksignore`, since `main` is never rewritten. `pnpm check` does not run the scan: before pushing a test that holds anything shaped like a credential, run it as CI does, with the version `ci.yml` names (`docker run --rm -v "<the checkout>:/repo:ro" ghcr.io/gitleaks/gitleaks:v<version> git /repo --redact --no-banner -v`), which prints each finding's fingerprint and never its text.
- The front-matter of a `SKILL.md` or of `SKILLCDN.md` is YAML: a plain value with `: ` in it, or one that starts with `[`, `{`, `&`, `*`, `!`, `%`, `@` or a backtick, reads as something else, and the skill is skipped or served with half its description. Quote such a value. `skillcdn check` says so before a push.
- `zod` must resolve to one copy across the workspace and `@skillcdn/core`, or the package's build fails with TS2883 on every schema composed from core's (`restSkillsSchema` and its kind): the declarations cannot name the other copy's types. After raising `zod`, or when a `@skillcdn` release moves it, run `pnpm dedupe` and commit the lockfile, then `pnpm clean` before the next build: the incremental build state in `dist/` still names the old copy, and the error outlives the fix.
- An integration test run that is killed (a crash, a Ctrl-C) leaves its `console_test_<hex>` database in the local PostgreSQL, and a role a plugin test made keeps objects there, so that `sql.int.test.ts` then fails to drop the role. Drop every `console_test_%` database (`with (force)`) and the role `plugin_tallytest`; nothing else uses them.
- The browser the tests drive blocks no window a page opens on its own, in the headless shell and in the full build alike, and whatever a test asks of a page (`evaluate`, the checks a click makes) hands a user activation to every frame of it, the sandboxed ones included. A test of what a press allows can hold only what a frame notes on its own, left alone past the five seconds a press lasts, as the `call` fixture's page does; what a browser does with a press elsewhere is not seen there.
- `apps/console` compiles without the DOM lib, so a browser test (`*.browser.test.ts`) that names `document` or `window` in a `page.evaluate` callback fails `pnpm typecheck` while passing under vitest, which does not typecheck. Hand `page.evaluate` the expression as a string, as the existing tests do, and keep `fetch` callbacks, which Node types. The console's own policy refuses a string evaluated in the page itself (`script-src 'self'`, no `unsafe-eval`), so `page.waitForFunction` given a string fails there: wait from the test, with `expect.poll(() => page.evaluate(...))`.
- `pnpm check` runs no browser test and CI's browser job does: a change to the shell, to a plugin's frame or to what the frame is told (`init`) has turned `main` red with `pnpm check` green. Run `pnpm test:browser` before pushing one.
- Between the change that raises the oldest command a console takes (`CLIENT_POLICY` in `packages/console/src/compat.ts`) and the release that carries it, the checkout refuses its own command: a console built from it takes the coming version and up, and the command built from it is still the last one (`client.outdated`, under `pnpm dev:plugins` too). To try the two together, set the package's version to the coming one in the working tree and put it back before committing. A deployment follows the release for the same reason: a console built before the version was raised refuses every command there is.
- The pull request that versions a new line is the first place where the console is that line's first version: what is written for the line before passes every check on `main` and fails there. A fixture plugin that named the consoles it runs on as `>=0.4.3 <0.6` did, when the package became 0.6.0. `apps/console/src/testing/fixture-plugins.test.ts` holds the fixtures to the next line too; whatever else reads the package's version is tried with the coming one set in the working tree, and a version pull request is merged only once its own check passed.
- A scheduled task of Windows is ended by ending the one process it started, and what that process started goes on: a service module there has the runner end with what keeps it, as `task-scheduler` does through `CONSOLE_RUNNER_KEEPER`. The scheduler reads a definition that names no encoding in the machine's own code page, and fills a variable in wherever its arguments hold a name between two percent signs: the definition is written in ASCII, a letter beyond it by its number, and no percent sign is written in it.
- The development servers are one origin, `http://127.0.0.1:<port>`, as a console is: signing in, a cookie and a plugin's frame (`frame-ancestors`) hold there and nowhere else, so opened as `localhost` the sign-in ends on a refusal and every frame stays empty. Both servers send a browser that came as `localhost` on to that address, and `.claude/launch.json` names it for Claude Code's preview, which opens `localhost` unless told.
- Several `pnpm check` runs at once, in worktrees side by side, share the local PostgreSQL, and `plugin-sql.int.test.ts` fails where two of them make and drop the plugin's role in the same moment. Run that file alone to tell it from a real failure, and run the check before a push when nothing else runs.
- `error-words.test.ts` reads every quoted dotted word in `apps/console/src` as an error's code, which must have its words in the language packs: a file's name or a secret's written so (`"index.ts"`, `"git.token"`) fails it. Keep such a word out of a quoted literal, or in `src/testing/preview-*.ts`, which the test leaves out.
- A row the database dates (`defaultNow()`) carries the day the test runs on, and whatever the injected clock dates carries the day the test says. A test that compares the two, an account made before an event say, passes until the real day goes past the test's and fails from then on, on every machine at once. Date such a row in the test, by the test's own clock. The same two clocks meet in the product: a database on another machine, or in a container, runs a part of a second ahead of the console or behind it, so a row whose date the console compares with an event's or a project's is dated by the console's clock when it is written, as a member's is, and never left to the database's default.
- `git stash` is one list for every worktree of a repository: a fork working beside others popped another's entry. Where several worktrees are at work, keep what is not ready in a commit on the worktree's own branch or in a patch file, never in the stash.
- A test that leaves a transaction open after it wrote an event holds the feed's order in its database ([ADR-0125](docs/adr/0125-a-feed-is-read-no-further-than-its-settled-end-which-its-writers-hold-a-lock-for.md)): the wake job, the dispatcher and every read of the feed by number go no further until it ends, and a test that fails before it commits leaves the rest of the file reading nothing new. Let it commit in a `finally`. `pg_locks` lists the advisory locks of every database on the server, other test files' among them: narrow it to `current_database()`.
- The pages' policy lets an image come from the console or from a `data:` address alone. A preview of a file a person chose is read into a `data:` address with a `FileReader`; an address made with `URL.createObjectURL` is refused without a word, and under `pnpm dev` nothing shows it, since the pages are served there with no policy: a browser test does.
- A heading of a spec that an accepted ADR links to by its fragment cannot change: `pnpm check:skills` reports the ADR (`fragment_not_found`), and an accepted ADR is never edited. Say what is new under the heading.
- A database's container without an init process restarts itself under load: Docker ends a health check that passed its timeout, the `pg_isready` it leaves behind is reparented to PostgreSQL as process 1, and its "no response" reads there as a crashed child, so every backend is ended and the server recovers for minutes (`untracked child process ... exited with exit code 2` in its log). Both compose files give it `init: true`; a container made before that is recreated with `docker compose -f deploy/compose.dev.yaml up -d`.
